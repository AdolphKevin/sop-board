# sop-board

在开发者本机运行的 SOP 场景验证协作看板。一个工作区可以包含多个 Git 仓库；测试同事上传用例、查看结果与证据并复核，开发者通过本机页面发起执行和处理修复。项目怎样准备依赖、启动整套服务，由数据目录中的适配定义。

状态：开发中。已接入工作区、适配、自检、执行及跨仓修复；真实模型修复与独立复测的验收记录单独保留。

## 给代理

在开发者打开的工作区会话中，先安装当前交付版本并读取随包指引：

```sh
uv tool install <本地看板检出路径>
sop-board guide
```

按指引调查实际服务与依赖、确认工作区范围，并与开发者确认正确的工作树建立/删除方法：已有仓库脚本、团队工具、个人习惯，以及被忽略配置和生成代码怎样带过去。确认后把配置与适配写入看板数据目录，再运行 `sop-board check`。向开发者报告已验证的事实、推断及依据、待回答的问题，并列出适配依赖的外部工具及其来源（仓库内、团队共用或仅本机）；团队成员共用适配前须各自具备。开发者确认后启动。Codex 与 Claude Code 使用同一份指引，不向产品仓库写搭建文件，不记录凭证值，不生成测试。

## 安装和启动

需要 Python 3.10 以上、uv、Git，以及支持 POSIX 进程组的本机环境。定位占用端口的进程使用 `lsof`。仓库内开发可运行：

```sh
uv sync
uv run sop-board guide
uv run sop-board check /absolute/workspace --data /absolute/board-data
uv run sop-board /absolute/workspace --data /absolute/board-data --port 8787
```

已安装命令的使用方式：

```sh
sop-board [工作区目录]
sop-board [工作区目录] --lan --port 8787
sop-board check [工作区目录]
sop-board guide
```

工作区缺省为当前目录；默认仅监听 `127.0.0.1`，`--lan` 开放内网并打印实际 IPv4 地址。数据默认放在 `~/.sop-board/<工作区名>/`；同名目录已登记为另一工作区时追加规范化路径摘要的前 8 位。`--data` 可指定独立数据目录，不能位于仓库内。

工作区名称就是页面与接口中的键，名称和路径在数据目录的 `workspace.json` 登记。数据库为 `workspace.sqlite3`；旧版数据目录不读取，也不迁移。配置缺失或不合格时看板仍可启动，显示“尚未搭建”与搭建做法，执行和修复停用。

停止看板会终止其环境进程组。命令行自检在看板停止后运行；看板已运行时使用本机页面的“自检”按钮。

## 配置与环境

数据目录的 `config.yaml` 是唯一配置入口：

- `repos`：仓库别名到相对工作区的仓库根路径；身份从各仓库 origin 规范化得到，并在页面显示。
- `scenarios`：相对工作区的场景目录，位于一个已声明仓库内。每个批次保存为 `<批次>.yaml`。
- `entries`：验收入口，包含 `surface`、`operate`、`observe`、`evidence`、`isolation`，可选 `address_env`、`driver`。
- `adapter.worktree`：可选命令数组，按开发者确认的方式建立工作树；最后一个非空输出行返回 `{"repos": {别名: 路径}, "env": {...}}`。
- `adapter.cleanup`：可选命令数组，删除这些工作树；缺省分别使用 Git 建立和删除命令。
- `adapter.env`：启动整套服务并保持前台的命令数组；就绪时输出并刷新 `sop-board: ready`。
- `adapter.ports`、`adapter.ready_timeout`：环境端口与就绪时限，时限缺省 180 秒。

命令工作目录和相对参数均相对数据目录。建立命令接收 `SOP_TASK_DIR`、`SOP_FIX_BRANCH`、逗号分隔的 `SOP_REPOS` 与 `SOP_BASE_<别名>`；清理另接收 JSON 格式的 `SOP_WORKTREES`。环境启动使用 `SOP_REPO_<别名>` 和 `SOP_ENV_LOG_DIR`，变量后缀将别名转大写、连字符改下划线。返回路径须为对应仓库的工作树根目录、共用同一 git common dir 并检出指定分支。返回的 env 只在内存中传递，不写入日志或报告。

同一用户本机只有一套适配环境，基线与修复目录轮流使用相同端口。停止先发 SIGTERM，十秒后仍未退出则发 SIGKILL；适配前台进程必须管理并等待自己的服务进程。标准输出和错误输出写入 `env/<序号>.log`。

自检依次核对配置与仓库、端口占用、基线环境、临时工作树环境和入口驱动技能。临时工作树也走同一建立、核对和清理入口；第 4 步列出建立、环境及清理日志。结果保存到 `checks/<时间>.json`，全部通过退出 0，否则退出 1。配置或数据目录中的适配脚本变化后须重新自检。自检通过且配置未变，启动看板即运行基线环境。

页面环境栏显示最近自检与环境状态；本机页面还显示最近 50 行日志、目录与提交号，并提供自检和重启按钮。内网页面与公开环境状态接口不返回日志或完整搭建报告。完整契约见 `sop-board guide`。

## 访问范围

无需看板令牌。页面只填写标记人，保存在浏览器的 `sop-board.marker`。内网同事可查看、上传和复核；开发者操作只接受实际连接来自回环地址，支持 IPv4、IPv6 及映射地址，其他来源返回 403 `local-only`。内网页面不生成开发者按钮。

POST、PUT 带 Origin 时必须与请求 Host 的 HTTP 来源一致，否则返回 403 `cross-origin`；不带 Origin 的命令行请求正常处理。JSON 接口必须声明 `Content-Type: application/json`，否则返回 415 `json-required`。仅 `POST /api/v1/evidence` 的二进制上传豁免 JSON 类型要求。

转发头不参与来源判断；开发者自己建立的本机反向代理或端口转发视为开发者操作。服务使用 HTTP，供可信本机和内网使用。

## 用例、合并与执行

首页填写标记人和批次名称，上传用例 YAML。用例格式保留 `metadata` 与 `test_cases`；合并会调用启动者本机已登录的 Codex，依据用例与既有场景生成新版本，核对磁盘文件未变化后写入配置的场景目录。执行者不可把 Codex 启动失败或空输出当作场景通过。

合并为每条用例给出 `kind`（flow/detail）、`kind_reason`；detail 的 `merged_into` 必须指向本次生成的流程场景。只有 flow 生成同编号场景；detail 的全部预期以 `[用例 编号]` 标注后加入目标 expected，refs 和配对文件保留来源。执行会话同时读取来源用例的前置条件、步骤和预期，在所属流程内核对细节。

合并页按流程场景列出细节归属与理由。本机开发者可点“改为单独成场景”，选择持久保存在数据目录，并进入之后每次合并的 `case_choices.json`。若模型仍把该用例作为 detail，核对拒绝写入；内网不能执行此操作。用例、场景或选择在合并期间变化时，旧输出转“待同步”。

覆盖率、用例页和报告共用按场景版本及用例内容保存的配对，不按编号相同推断覆盖。没有配对的外部场景文件须先完成合并。报告逐条列出细节用例的目标场景，并逐执行轮次列出沿用数量和理由；当前沿用总数与历史各轮明细分别展示。

场景 `metadata.repos` 列出本批次涉及的仓库，缺省全部仓库。产品指纹覆盖这些仓库的已跟踪、未跟踪且未忽略文件，排除配置的场景目录。有未提交产品改动时执行为“待提交”，列出仓库与路径；每五秒复核。开始执行前，若仓库提交号与运行环境记录不同，先重启环境。

执行会话经运行中的实际环境操作。场景、用例、配置或仓库快照变化时本轮作废，不登记结果。产品变化后，执行会话根据改动范围判断哪些场景受影响并重跑；只有同一内容此前通过且有具体理由时才能沿用，`status` 保持 `pass`，`note` 为“沿用：<理由>”，页面、任务与报告单独计数。沿用保留原通过证据。

执行、合并与修复受全局暂停控制，Codex 会话最多三个；浏览器入口共用一个浏览器名额。配置或自检不合格时执行和修复停用，返回 409 `workspace-not-ready`。Codex 不可用或会话失败保留原因及输出，由开发者处理后重试。

## 跨仓修复

一个修复任务覆盖工作区内全部待处理问题。根据各批次 metadata.repos 的并集，调用 adapter.worktree 建立 `sop-board/fix/<编号>` 分支的工作树并核对；缺省位置为数据目录 `tasks/<任务编号>/repos/<别名>`。适配可按确认的方式返回其他路径。修复会话以任务目录为工作目录，获得各实际工作树的写入范围与返回的额外环境；环境启动使用工作树加其他仓库基线的完整映射。复测前重新核对这些路径，正常重试不重新覆盖工作树；恢复任务或扩大范围时，建立命令应能复用已有工作树。

会话对每个问题给出根因仓库 `root_repo`；产品问题必须指向本任务仓库，无法定位的非产品问题填 null。只改产品代码、不写测试；被 Git 忽略的本机配置或环境问题判为 environment，写明配置项与位置后转开发者，不抄录凭据值或产生代码修补。

看板先核对所有仓库都没有改动 docs/sop/ 或配置的场景文件，再对有改动的工作树分别提交，提交信息相同。基线目录不会被暂存、保存到 stash 或还原。失败的工作树与修复分支保留，证据交回同一会话；连续三次未通过转“待开发者处理”。放弃也保留未合入的现场，不强制删除分支。

复测停止基线，使用各仓修复目录运行同一个 adapter.env，由独立新会话通过真实入口执行。范围保守覆盖问题场景，以及所有批次中声明涉及改动仓库的场景；不能沿用结果。无论通过或未通过，结束后都尝试恢复基线环境。

通过后先整组核对各仓基线分支、未提交产品改动及提交号。任一仓不满足时，所有仓库都不开始合入，逐仓说明原因，转“待开发者合入”。基线前进时只在修复工作树中合入新基线并重新复测；冲突保留现场，不自动还原。全部满足后停止环境，逐仓快进，再重启基线环境、登记独立复测结果，让场景回到人工复测队列，先调用 adapter.cleanup（缺省 Git 删除）并核对工作树已消失，再删除已合入的修复分支。Git 的逐仓操作不是跨仓事务：落地过程中若出现新的外部改动或 Git 故障，停止余下操作并保留逐仓记录，不强制回退已完成的操作。

修复页和报告按仓库列出身份、改动、提交、合入状态及原因，并显示每个问题的根因仓库。修复工作树和适配生成的本机文件不进入任务下载接口。新库使用当前用例分层数据格式（版本 4），不读取或迁移旧库；请使用新的数据目录。

## 接口与页面

工作区接口前缀为 `/api/v1/workspaces/<工作区名>`；批次前缀为其下 `/batches/<批次>`。页面前缀为 `/w/<工作区名>/b/<批次>`。

| 入口 | 用途 |
| --- | --- |
| `GET /api/v1/workspaces` | 工作区、仓库身份和批次 |
| `GET …/entries` | 当前配置的入口与问题 |
| `POST …/batches/<批次>/cases` | 上传用例，正文为 filename、content、uploaded_by |
| `POST …/batches/<批次>/cases/<用例编号>/flow` | 本机指定该细节用例单独成场景，保存选择并重新合并 |
| `PUT …/batches/<批次>/scenario-file` | 推送场景；workspace 对象只含 name，另有 path、content、commit、dirty、product_digest、fingerprints、pushed_by |
| `POST …/batches/<批次>/executions` | 本机发起待执行范围 |
| `POST …/batches/<批次>/merges` | 本机重新合并 |
| `POST …/batches/<批次>/marks` | 标记，正文为 scenario、fingerprint、status、marker；不通过另有 defect_url |
| `POST …/batches/<批次>/rounds` | 登记有证据的实际验收轮次 |
| `GET /api/v1/environment` | 环境状态；仅本机含日志和自检详情 |
| `POST /api/v1/environment/check`、`…/restart` | 本机自检与重启 |
| `GET /api/v1/guide` | 当前发行的搭建指引 |
| `GET /api/v1/tasks`、`…/<编号>` | 任务状态、范围、快照和输出 |
| `POST /api/v1/tasks/<编号>/retry`、`cancel`、`approve` | 本机任务操作 |
| `POST /api/v1/automation/pause`、`resume` | 本机暂停和恢复 |
| `POST /api/v1/evidence`、`GET …/<摘要>` | 上传和读取原始证据 |

场景、用例、轮次、证据、SOP 原文、进度与报告页保留。人工标记不改写 Agent 结果；比率与队列由服务端统一计算。批次可导出 Markdown 报告、用例/结果 YAML 和按轮次的证据 ZIP。配置 Jira 读取时仍使用 `JIRA_URL`、`JIRA_EMAIL`、`JIRA_API_TOKEN` 环境变量，认证值不进入页面或报告。

SOP 图示使用随包发行的 Mermaid 12.2.0，来自 `mermaid@12.2.0` 的 `dist/mermaid.min.js`。MIT 许可在 `src/sop_board/assets/vendor/mermaid/`，页面不依赖外部 CDN。

## 场景验收

验收以 `docs/sop/` 的场景经最终交付产物的真实入口执行为准，不写单元、接口或集成测试。工作区、适配、跨仓修复和用例分层对应 SOP-71、SOP-72、SOP-74、SOP-75；命令、数据核对与留证方式见 [验收操作手册](docs/verification.md)。实现者自检与独立业务验收分别报告；未执行的真实浏览器、模型会话与跨仓流程不能写成通过。
