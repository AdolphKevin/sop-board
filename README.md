# sop-board

SOP 验证协作看板。开发岗的代理用 [praxis-skills](https://github.com/AdolphKevin/praxis-skills) 的 `sop-verify` 技能，把业务 SOP 的验收场景与每轮验收结果推送到看板；测试岗在同一个网页上传测试用例、查看进度、复核 Agent 判为通过的场景，并按场景提交缺陷。看板展示 Agent 验收通过率、人工复测通过率与测试进度。

状态：开发中。

## 使用方式

任何成员 clone 本仓后用 uv 在本机启动看板；团队共用一份数据时，由启动者开启内网访问，其他成员用浏览器打开。分析测试用例时，看板调用启动者本机已登录的 Codex。暂不提供服务器部署。

## 相关仓库

- [praxis-skills](https://github.com/AdolphKevin/praxis-skills)：`sop-verify` 技能，从业务 SOP 写场景、派独立会话执行、登记结果。
- [team-workflow](https://github.com/AdolphKevin/team-workflow)：团队流程；看板按轮次导出的结果可直接用 `tw team scenarios submit` 登记。

## 启动与内网访问

需要 Python 3.10 或以上版本与 uv。在仓库目录安装依赖：

```sh
uv sync
```

直接启动服务，无需设置看板令牌：

```sh
uv run sop-board --data ./board-data --port 8787
```

`--data <目录>` 指定数据目录，不存在时自动创建。看到 `看板地址：http://127.0.0.1:8787/` 后即可访问首页，选择项目与批次，查看队列、指标、场景历史及证据，并按轮次导出 ZIP。

需要授权本机项目时，加上可重复的参数：

```sh
uv run sop-board --data /tmp/sop-board-data --port 8787 \
  --writable-repo github.com/example/project=/absolute/path/to/project
```

授权参数须包含非空的身份、等号和路径，路径必须是 Git 工作区根目录，数据目录须放在授权仓库之外。参数不合格时，启动以退出码 1 结束且不新建数据文件；已有空数据目录仍为空。已登记项目的名称在授权及发现新版本时保持不变。成功时输出“可写授权：项目身份（路径）”；首页和批次页显示“可写”或“只读”。去掉参数重启即可撤销授权。

看板启动时及每五秒读取授权仓库 `docs/sop/` 下除 `entries.yaml` 外的 `*.yaml`，合格内容按 `metadata.batch` 登记版本，推送人为“工作区”；同一内容在该批次中只登记一次，看板自己写入的版本也不会再次登记或触发合并。版本记录提交号和工作区是否有未提交改动，产品指纹排除 SOP 场景与入口文件。文件不合格时，批次页显示问题和行号，保留已有版本。

页面身份栏只填写标记人，保存在当前浏览器的 `sop-board.marker`。查看、上传用例、上传证据、复核与标记无需令牌。开发者操作（执行、回归检查、重新合并、批准、重试、放弃、暂停与恢复）只接受回环地址的连接，包括 `127.0.0.1`、`::1` 与 IPv4 映射形式 `::ffff:127.0.0.1`；其他来源返回 403 `local-only`，内网页面不生成这些按钮。判定使用实际连接地址，不使用转发头；开发者自己建立的本机反向代理或端口转发视为本机操作。

所有 POST、PUT 请求带 `Origin` 时，必须与请求 `Host` 的 HTTP 来源一致（主机和有效端口相同），否则返回 403 `cross-origin`；命令行请求不带 `Origin` 时正常处理。除 `POST /api/v1/evidence` 二进制上传外，必须发送 `Content-Type: application/json`（可带 `charset=utf-8`），否则返回 415 `json-required`。开发者操作即使正文为空，也须声明 JSON 类型。

授权项目的 `GET /api/v1/projects/<项目键>/entries` 无需令牌，返回 `{ok, source, entries, checks, problems}`。有 `.tw/config.json` 时，只取其中的 `acceptance_entries` 与 `checks`；否则取 `docs/sop/entries.yaml` 的 `entries` 与顶层 `checks`。入口包含 `surface`、`operate`、`observe`、`evidence`、`isolation`，可选 `address_env`、`candidate`、`start`、`reload`；`candidate` 缺省为 `in-place`，另可取 `checkout` 或 `start`，取 `start` 时须声明启动命令数组。声明错误或场景引用不存在的入口、检查时，批次页显示“入口声明不合格”与具体问题，检查任务等待声明恢复；此时新发起检查返回 409 `entries-invalid`。读取不存在的项目返回 404 `project-not-found`，未授权项目返回 409 `repo-not-writable`。

检查声明示例（命令以数组传递，不经过命令行解释器）：

```yaml
checks:
  unit:
    argv: [python3, scripts/check.py, "{output}"]
    format: junit
    report: "{output}/report.xml"
    cwd: .
    timeout: 900
    required_env: []
```

`cwd` 是检出目录内的相对路径，缺省 `.`；`timeout` 缺省 900 秒；`required_env` 缺省空数组。`format` 支持 `junit` 与 `go-json`，前者必须声明 `report`；其他检查字段忽略。场景以 `regression: {check: unit, cases: ['pkg.Order::test_create']}` 引用检查与用例。JUnit 用例名为 `<classname>::<name>`；Go JSON 用例名为 `<Package>::<Test>`，包级事件不算用例。

开发者向 `POST /api/v1/projects/<项目键>/batches/<批次>/checks` 提交空正文或 `{}`，从本机单独发起回归检查，返回 `{ok, task}`。范围为全部声明检查的场景；没有这类场景返回 409 `nothing-to-check`。每项检查在一次任务中只运行一次，不占 Codex 的三个运行名额。检查任务的读取接口另含 `scope`、`snapshot`、`void_reason`、`rounds`。

检查只运行已提交的产品代码。看板比较工作区与 HEAD 的产品指纹，包含未跟踪且未忽略的文件；有差异时任务为“待提交”，列出前十个变化路径，每五秒复核。`docs/sop/` 与当前入口声明文件不计入产品指纹。满足条件后，在数据目录 `worktrees/<任务编号>/` 检出快照提交运行检查，结束后移除。任务目录的 `snapshot.json` 固定场景版本、所选场景内容、入口与检查声明、用例并集、提交号与产品指纹；结束与登记前复核，变化时任务为“已作废”，不登记轮次。工作区场景文件的变化也会核对，不必等下一次扫描。

`{output}` 替换为任务目录的 `checks/<检查编号>/`，标准输出与错误输出存为 `output.txt`；Go JSON 的标准输出另存为 `report.jsonl`。检查继承与 Codex 相同的环境白名单，额外传入 `required_env` 声明的变量；缺变量时不启动命令，场景登记为受阻。超时终止整个进程组。报告缺失、无法解析，或声明用例缺失、失败、出错、跳过时，场景为失败；声明用例全部通过时为通过，命令退出码非零仍通过并注明退出码。

每项检查登记一个 Agent 轮次，执行者与提交人为“回归检查 <检查编号>”，会话为任务编号，证据为输出和可用报告，产品取快照提交号与指纹。检查任务的“已完成”表示运行与登记结束，各检查及场景的通过、失败、受阻另列在结果中。已作废的检查可以重试，待提交的检查可以放弃；重试重新固定快照，旧文件连同报告目录归档，避免误用旧报告。重启后待提交、排队与运行中的任务为“已中断”，清理残留检出目录。

场景列表接口的 `regression_status` 为 `passed`、`failed`、`pending` 或 null，分别表示当前产品指纹上的最新真实回归检查通过、失败或受阻、尚未运行，以及没有声明检查。普通 Agent 或人工轮次不冒充回归检查。页面对应显示“检查通过”“检查失败”“检查待运行”；产品变化后重新等待检查。

开发者向 `POST /api/v1/projects/<项目键>/batches/<批次>/executions` 提交空正文或 `{}`，发起“执行待执行场景”，返回 `{ok, task}`。范围包含没有结果、内容变化、最新结果为失败、Agent 通过后产品变化且没有检查声明的场景；最新结果为受阻或跳过的场景不自动重跑。没有范围返回 409 `nothing-to-execute`，未授权返回 409 `repo-not-writable`，入口声明不合格返回 409 `entries-invalid`。没有用例的批次在发现或推送新版本后，有用例的批次在合并写入后，自动执行新增与内容变化的场景；草稿与待同步的合并不触发。同批次尚未开始的执行任务会并入新范围，运行中的范围保持不变，后续任务等待它结束。

执行任务同样只使用已提交产品，并遵守上述待提交复核、快照核对与作废规则。任务接口的 `scope` 是场景编号与原因数组（`new`、`changed`、`failed`、`source-changed`），另返回 `snapshot`、`void_reason` 与登记的 `rounds`。批次总览列出执行和检查任务、等待原因、范围条数及轮次。执行开始时，范围内及因产品变化待确认的回归场景运行声明的检查，每项检查一次；这些场景不交给 Codex。只有检查时不启动 Codex 会话，也不占其运行名额。

需要浏览器的执行任务先取得看板进程内唯一的浏览器锁，再等待 Codex 名额：无法取得锁时为“等待浏览器”，已取得锁但三个名额已满时为“排队中”。等待浏览器不占名额，命令行任务可以同时运行；任务结束、失败或放弃后释放浏览器与名额。

开发者可用 `POST /api/v1/automation/pause` 与 `POST /api/v1/automation/resume` 暂停和恢复全部自动任务，返回 `{ok: true, paused: true}` 或 `{ok: true, paused: false}`。这两个接口只接受本机连接，正文为空或 `{}`，均须声明 JSON 类型。暂停状态保存在数据目录的数据库中，重启后保持；暂停时合并、执行和检查中尚未开始的任务（含手工发起、待提交与等待浏览器）继续等待，运行中的任务正常结束。首页顶部显示“自动任务已暂停”；本机页面同时提供“恢复自动任务”按钮，点击即可操作。

首页与批次总览的执行状态优先显示“执行中（<会话数> 个会话，开始于 <本地时间>，任务 #<编号>）”，其次为“待提交：工作区有未提交的产品改动”，再沿用原有场景状态；暂停时附“已暂停”。总览的“执行任务”列表包含执行与单独发起的检查，列出编号、种类、触发原因、范围条数、状态、开始与结束时间、作废或失败原因及登记轮次。授权批次的本机页面提供“执行待执行场景”和“运行回归检查”按钮。

候选版本由场景入口的 `candidate` 决定：

- `checkout`：在数据目录 `worktrees/<任务编号>/` 分离检出快照提交，供执行会话操作；不建立分支。
- `start`：使用同一检出目录运行入口的 `start` 命令，传入空闲端口 `SOP_PORT`；若声明 `address_env`，同时给启动命令和执行会话传入 `http://127.0.0.1:<端口>`。120 秒内收到任意 HTTP 响应即就绪，错误响应也算。提前退出或就绪超时使该入口的场景记为失败，证据为 `start.log`，与其他入口结果同轮登记。
- `in-place`（缺省）：使用开发者已运行的环境，只额外传入 `address_env` 指定的变量；缺变量时相关场景记为受阻。看板不启停该环境，结果附“运行环境按 HEAD 记录，未经核实”。这类执行需要回归检查时，在 `worktrees/<任务编号>-check/` 检出提交运行检查。

任务无论完成、失败、作废或放弃，均移除检出目录；任务结束与看板退出时终止候选服务的整个进程组，重启会清理残留目录。执行任务可重试失败、已作废、已中断与 Codex 不可用的状态，保留原范围，重新核对待提交并固定快照；待提交与等待浏览器的任务也可以放弃。重试把前次证据和报告一起归档。

每个执行任务使用一个新的 Codex 会话，工作目录为数据目录的 `tasks/<任务编号>/`，显式使用 `workspace-write` 沙箱并开启联网。目录包含筛选后的 `scenarios.yaml`、`entries.json`、`pending.json`、`snapshot.json`、`evidence/` 与发行模板生成的 `prompt.md`。驱动技能目录取 `SOP_BOARD_SKILLS_DIR`，缺省 `~/.agents/skills`；网页、接口或数据库、智能体入口分别使用 `playwright-acceptance`、`verify-backend-sop-db`、`build-scenario-validation-loop`，命令行入口使用临时 HOME，其余入口按操作说明执行。提示词要求保留产品文件，在任务目录写 `results.jsonl` 与 `evidence/` 下的证据。看板核对场景恰好一行、范围、结果字段及证据路径后才登记；不合格时在 `check.json` 写明问题，不登记部分结果。轮次执行者取 Codex 会话编号，会话取任务编号，实现者取仓库的 `git config user.name`（无值时省略），产品与内容指纹取快照，`dirty` 为 false。

### 自动修复（提交、复测与合入）

看板每 5 秒扫描授权仓库全部批次，以当前场景内容的最新结果识别问题：带缺陷链接的人工失败或受阻、Agent 失败，以及看板实际登记的回归检查失败。仅修改执行者名称不会变成检查来源。Agent 受阻和跳过留在问题队列。每个仓库只有一个进行中的修复任务，首次尝试开始时固定范围，之后的新问题在下一次尝试纳入。已转开发者或已放弃的问题，在出现新结果或场景内容变化前不重复纳入。

产品改动未提交时等待提交；只有 `docs/sop/` 的改动不会阻止开始。看板以主工作区当前分支和提交建立 `worktrees/fix-<任务编号>/` 与 `sop-board/fix/<任务编号>` 修复分支；主工作区处于分离头指针时转开发者，切回分支后可重试。修复与同仓库的执行任务互斥，已开始的执行先结束，随后修复优先。暂停自动任务同样阻止开始修复和新的尝试，运行中的会话继续结束。

任务目录保存 `problems.json`、`entries.json`、`snapshot.json`、`cases.json`、`feedback.json`、`prompt.md` 与输出模式。问题输入包含批次、场景、实际结果、证据路径、缺陷链接、此前 Agent 结果，以及已配置 Jira 的标题、描述、状态、评论和附件名；Jira 读取失败时保留原因并继续。修复会话以 worktree 为工作目录，使用可联网的 `workspace-write` 沙箱和环境白名单。后续尝试续接同一会话。提示词要求统一分析根因，只修产品缺陷，遵守仓库的开发与测试规则，不改场景和入口声明，不自行提交。

执行问题、环境问题、场景问题、需求问题和暂无法修复的产品缺陷转开发者，并保留理由与方案；同一任务中的产品缺陷继续提交。不合模式、遗漏问题、无产品改动或修改了受保护文件时，本次尝试未通过；受保护改动在独立工作目录恢复。核对通过后，看板以授权仓库配置的作者提交，首行为 `sop-board 修复 #<任务编号> 第 <n> 次尝试`，正文逐行列出批次、场景和 Jira 单号、缺陷链接或失败来源。提交不签名，照常执行仓库提交钩子；钩子拒绝时，本次尝试未通过，原因与输出保存并交回修复会话。每次输入、输出与错误按尝试归档。连续三次未通过转开发者；修复会话非零退出、超时或未写出最终输出时自动重试一次，两次中断均不计尝试次数。

对于 `checkout` 与 `start` 入口，提交后由新的 Codex 会话复测本次判为产品缺陷的全部问题，转开发者的问题与其余场景不自动重跑。每次复测使用 `tasks/<任务编号>/validations/<尝试编号>/<验证编号>/` 作为工作目录，使用可联网的 `workspace-write` 沙箱；候选代码从修复 worktree 只读访问，结果写到本次任务目录的 `results.jsonl`，证据写到 `evidence/`。`start` 入口先启动候选并确认 HTTP 就绪，启动失败时保存退出码与日志，不启动该入口的复测。

每次验证还在同一候选提交上运行全部批次中声明的回归检查，同一检查只运行一次，覆盖所有引用它的场景。问题复测全部通过、检查报告合格且声明用例全部通过后，才进入“待合入”；沿用检查运行器的口径，声明用例全通过时，命令退出码非零只作记录。网页复测与执行任务共用测试浏览器，等待时原因显示“等待测试浏览器”。复测失败、候选启动失败或检查失败的结果只保存为候选记录，不改变基线或批次统计；证据交回原修复会话开始下一次尝试。

合入前重新核对基线的提交和检出目录。基线前进时，先在修复 worktree 合入最新提交，再对合并后的候选追加复测与检查，仍计为同一次尝试；冲突时中止该合并，转“待开发者合入”。基线在主工作区或其他 linked worktree 检出时，只在该目录执行 `git merge --ff-only sop-board/fix/<任务编号>`。Git 因未提交修改拒绝时保留工作区；能够合入而另有未提交修改时，记录“工作区含未经验收的修改”。基线未在任何目录检出时转开发者合入，并说明主工作区当前分支。看板不替开发者暂存、还原、强制移动分支或推送。

合入后，每个涉及批次新增一个 Agent 轮次，采用最后一次通过的候选结果，保留执行时间；执行者为复测会话，实现者为修复会话，产品提交与指纹取合入后的基线提交。提升按任务、尝试和批次保持幂等；重启发现通过的候选已在基线中时补做提升。任务读取接口包含各次候选提交、结果、证据与提升轮次。报告显示自动修复统计，未通过的候选只计入修复尝试。

对于 `in-place` 入口，先在修复工作目录运行全部回归检查；检查通过后，按上述保护规则快进合入基线，再在授权仓库目录执行所用入口的 `reload` 命令，最后由新会话在开发者已运行的环境中复测。未声明 `reload` 时直接复测，看板不启停开发者的服务。重载命令使用环境白名单，并额外取得该入口 `address_env` 指定的变量；输出保存在任务目录，退出码非零、无法启动或超时均记本次未通过，不进行复测。基线前进时，合入最新基线后只追加回归检查，再替换与复测。任务混用原地替换与其他候选方式时，全部问题都在替换后复测，不另外启动候选服务。

运行环境复测的通过与未通过结果都直接登记为对应批次的 Agent 轮次，附“运行环境按 HEAD 记录，未经核实”；执行者为复测会话，实现者为修复会话，重启不会重复登记。重载或复测失败时，已经替换的代码保留；下一次尝试沿用同名修复分支，从基线最新提交重新建立工作目录，并续接原修复会话。连续三次未通过时转开发者处理，不自动回退；任务接口的 `merged_commits` 与各次尝试的 `merged_commit`、修复页列出实际合入的提交和证据。

项目修复页为 `/p/<项目键>/fixes`，读取接口为 `GET /api/v1/projects/<项目键>/fixes` 和 `GET /api/v1/tasks/<任务编号>`，均不需令牌；未授权项目的修复列表为空。开发者可向任务的 `/approve` 提交 `{note}` 批准方案并续接同一会话，向 `/retry` 重试中断、Codex 不可用、分离头指针或连续会话中断，向 `/cancel` 放弃任务。以上操作仅接受本机连接。`GET /api/v1/projects/<项目键>/attention` 列出需要开发者处理的任务与续接命令。

合入后看板删除修复工作目录与已合入的修复分支，保留修复记录与证据；问题场景回到复测队列，等待测试岗复核。配置了 `JIRA_URL`、`JIRA_EMAIL` 与 `JIRA_API_TOKEN` 时，每张 Jira 单收到一条文档格式评论，包含根因、改动、提交、本机基线分支及复测结果，并注明“尚未部署到测试环境”。设置 `JIRA_FIXED_STATUS` 后，看板读取可用流转并按目标状态名选择；未设置或不可达时记“Jira 状态待人工更新”。评论失败仍尝试流转，回写失败不自动重试，也不改变“已合入”状态；配置不全时记“Jira 未配置，未回写”。认证信息仅用于请求，不保存到任务文件、页面或日志；进程中断后无法确认的回写交给开发者核对。

修复页显示问题判定、根因、各次尝试与证据、合入提交、转开发者事项和 Jira 结果。SOP 场景页与详情页标出进行中的修复及待开发者处理的问题；任务结束后清除标记，详情历史保留所属修复任务。批次总览和报告按本批次的问题计数，尝试次数取整个任务，展示任务数、问题数、已合入数、转开发者数、首次尝试即通过的任务数与总尝试次数；无修复任务的报告写“暂无记录”。

`attention` 读取接口返回 `{ok, items}`，每项包含 `kind`、`task`、`batch`、`reason`、`url`、`resume`，涵盖合并、执行与修复任务。事项类型分别为 `developer-action`（待开发者处理）、`developer-merge`（待开发者合入）、`commit-needed`（待提交）、`cases-needed`（待补充用例）、`sync-needed`（待同步）、`jira-manual`（Jira 待人工处理）、`interrupted`（已中断）。页面完整地址取请求的 `Host`；有会话时给出 `codex resume <会话编号>`，否则为空字符串。

修复、复测、合入及 Jira 回写按 `docs/sop/` 中对应场景，经实际启动的看板、业务接口和页面执行，记录数据变化与证据。真实 Jira 站点的验证仍留待外部接入阶段。

批次导航中的“合并”页提供任务列表、错误原因、原始文件下载与开发者操作。有用例的批次在上传用例或场景文件变化时自动建立任务，触发原因分别为“上传用例”和“场景文件变化”。`POST /api/v1/projects/<项目键>/batches/<批次>/merges` 发起“重新合并”：相同输入已有排队或运行任务时返回该任务，否则建立新任务，即使此前相同输入已经完成。没有用例时返回 409 `cases-missing`。任务带 `scenario_file_sha256` 表示依据的场景原文摘要，无场景版本时为空字符串。

合并时，每条用例生成一条同编号场景，标题、优先级、标签、前置条件、步骤和预期按解析后的文字原样复制，只有标签含 `negative` 才作为反向场景。按用例编号排序后，分组首次出现时分配 S01、S02 等节点编号；以后新分组追加编号，合入其他节点的分组也保留原编号。重新合并时按场景编号保留回归声明；已经并入且仍在当前场景中的禁止副作用，经历史合并记录确认来源后也继续保留。

Codex 只判断角色、入口、反向类型、节点分组及原有场景的去向：保留、重复或冲突。重复场景的禁止副作用并入目标用例场景，目标没有回归声明时转移原声明；保留场景的编号和内容不变，原节点没有保留正向场景时按判断移入用例节点。任务目录保存用例、场景、入口、节点编号及可用 SOP 原文的输入快照，提示词与输出模式随包提供。入口优先取授权仓库的 `.tw/config.json`，否则取 `docs/sop/entries.yaml`；未授权项目使用最近一次推送附带的入口声明，缺少时任务失败。推送附带 `sop_sources` 时，合并快照同时保存其中的 SOP 原文；每项含 `ref`、`path`（仓库内相对路径）、`commit`、`sha256`、`confirmed_by` 和 `content`，内容上限为 2 MiB，摘要必须与原文一致。

看板独立核对输出模式、全部用例与原场景的去向、编号引用、确定字段和场景格式，失败原因逐项写入 `check.json`。业务依据有缺口时停在“待补充”，不生成草稿。未授权项目只保存草稿，不改变批次场景版本。授权项目仅在磁盘场景文件与合并依据的原文摘要相同或文件不存在时写入 `docs/sop/<批次>.yaml`，登记为“看板合并 #<任务编号>”，不创建 Git 提交。磁盘内容不同则保留原文件，任务为“待同步”；新内容由扫描另行登记并触发新任务。推断的前置状态、豁免理由在对应位置写“待确认”注释；缺少入口文件时，授权项目可以同时写出带待确认文件头的推断入口。

合并页可选任务，查看用例对应关系、原场景去向与理由、待确认的推断、缺口和原始输出。下载 `GET …/merges/<任务编号>/scenario-file` 取得合并原文，`GET …/merges/<任务编号>/pairs.json` 取得可直接用于 `sop-verify coverage --pairs` 的配对文件，全部用例归入 `covered`。没有合并结果的任务，两种下载均返回 404 `merge-result-not-found`；“待同步”任务可以下载以供核对。这两类等待人工的任务均不占运行名额。

Codex 使用启动者本机已登录的命令行工具。启动及每次取任务前核对 `codex --version`；不可用时任务停在“Codex 不可用”，恢复后须由开发者重试。同时运行最多三项，其他任务按创建顺序排队。合并任务显式使用 `read-only` 沙箱，标准输入接空设备；子进程只继承 `PATH`、`HOME`、`USER`、`LANG`、`LC_*`、`TMPDIR`、`CODEX_HOME`、`SHELL`，不继承 Jira 环境变量。`SOP_BOARD_CODEX_TIMEOUT` 设定单项时限秒数，默认 1800；设置时必须是正整数，无论是否授权仓库，不合规值都会以退出码 1 启动失败且不留新文件。超时终止整个进程组并记为失败，重启后排队或运行中的任务记为“已中断”。

`GET /api/v1/tasks?project=<项目键>&batch=<批次>` 列出任务，`GET /api/v1/tasks/<编号>` 返回任务及文件下载地址，`GET /api/v1/tasks/<编号>/files/<相对路径>` 下载原始文件，读取均无需令牌。任务文件保存在数据目录的 `tasks/<编号>/`，含输入快照、提示词、输出模式、逐行事件、错误输出、最终消息和核对记录。会话编号取 `thread.started.thread_id`。文件相对路径可包含子目录；含 `..`、绝对路径、越出任务目录或不存在时返回 404 `task-file-not-found`，任务不存在时返回 404 `task-not-found`。非零退出的错误说明为“Codex 退出码 <码>”，退出码为零但未写最终输出时为“Codex 没有写出最终输出”。开发者可向 `POST /api/v1/tasks/<编号>/retry` 提交 `{}` 重试失败、已中断或 Codex 不可用的任务；编号和输入保持不变，前次文件归档在任务目录的 `attempt-<次数>/`，仍可下载。`POST …/cancel` 仅放弃排队中、运行中、已中断、待同步或待补充的任务，并终止运行中的进程组。失败及 Codex 不可用任务须重试，不能放弃；状态不允许时返回 409 `task-state-invalid`。开发者接口也接受声明 JSON 类型的空 POST；按钮只在本机页面显示。场景列表中最新 Agent 与最新人工结果各带其实际轮次 `round`。

默认只允许本机连接。需要内网共用时，监听本机的全部网络接口：

```sh
uv run sop-board --data ./board-data --host 0.0.0.0 --port 8787
```

启动输出中的 `看板地址：http://127.0.0.1:8787/` 供启动者在本机打开；每个可用的内网 IPv4 地址会另起一行，例如 `内网地址：http://192.168.1.20:8787/`。将对应网络的这条内网地址发给其他成员访问；`0.0.0.0` 表示监听全部网络接口，不是浏览器访问地址。所有能连接该地址的人都能读取场景、证据和导出；同事也能上传用例、证据及复核标记，开发者操作仅限本机连接。服务使用 HTTP，没有传输加密，因此只应在可信内网使用，不要把端口直接暴露到公网。

在批次导航点“SOP 场景”，可按节点浏览全部场景，并筛选全部、未人工复核、Agent 已通过、不通过或受阻。筛选地址带 `?filter=`，可复制分享。场景列表与详情页共用“通过”“失败”“受阻”三个按钮：通过立即提交；失败与受阻只需填写缺陷链接，备注选填，也可取消。保存后在原处更新结果与数量，人工结果统一显示“通过”“不通过（失败）”或“不通过（受阻）”。接口拒绝时在该场景下显示错误代码和各项问题说明，并保留已填内容。

首次复核时在页面顶部的身份栏填写标记人，保存在当前浏览器的 `sop-board.marker`，可随时更换。共享电脑使用后应清除该站点的本地存储。写入接口无需认证头，JSON 请求按上述同源与正文类型规则校验。

在批次导航点“用例”，选择 YAML 文件并点“上传用例”。上传人取身份栏中的标记人。页面会逐条显示不合规字段及文件行号；YAML 语法错误还会给出解析器原因与列号。上传失败不保存数据，也不会建立新批次。上传成功后刷新页面，显示上传记录及按 `section:` 标签分组的用例；没有该标签的归入“未分组”。每条用例标明是否已有同编号的当前场景，有对应场景时可直接打开。

用例文件的顶层仅有 `metadata` 与非空的 `test_cases`。`metadata` 必填 `module`、`feature`、`owner` 和日期 `last_reviewed`（`YYYY-MM-DD`），可选字符串数组 `tags`。每条用例必填 `id`（如 `TC_DEMO_LOGIN_001`，格式为 `^TC_[A-Z0-9_]{3,}_[0-9]{3}$`）、`title`、`priority`（`P0`、`P1`、`P2`）、`type`（`functional`、`ui`、`security`、`performance`、`accessibility`），以及非空字符串数组 `steps`、`expected_results`、`tags`；可选 `description` 字符串、`preconditions` 字符串数组和 `auto` 布尔值。不接受其他字段，同一文件的用例编号不能重复。

工具可向 `POST /api/v1/projects/<项目键>/batches/<批次>/cases` 提交 JSON 正文 `{"filename":"cases.yaml","content":"<YAML 原文>","uploaded_by":"<上传人>"}`。项目须先存在；成功上传可以建立尚无场景的新批次。历次上传取并集，同编号按最后一次上传的完整内容替换；与上一次原文完全相同的上传不会增加序号。`GET …/cases` 返回上传记录、当前并集和用例覆盖数；`GET …/cases.yaml` 下载并集，文件说明取最近一次上传的 `metadata`；`GET …/scenario-file` 下载最新场景原文，尚无场景时返回 404 `scenario-file-not-found`。已有数据目录启动时自动补建用例相关表，保留原有数据。

人工标记接口只接受 `scenario`、`fingerprint`、`status`、`marker`、`defect_url`、`note`。状态只支持 `pass`、`fail`、`blocked`；通过不带缺陷链接，失败与受阻必须带链接。实际结果、问题记录与观察证据由看板生成，不再接收人工填写的 `actual`、`environment`、`finding`、`evidence`。观察记录使用 `marker`、`status`、`recorded_at`，有值时再写入 `defect_url` 与 `note`。按轮导出的 ZIP 保留原有 tw 结果格式，观察文件位于 `evidence/<序号>-observation-<轮次>.json`。

缺陷链接去掉首尾空白后核对。启动前设置可选的 `JIRA_URL`（如 `https://example.atlassian.net`），即可填写 `ABC-1` 这样的 Jira 单号，或该站点的 `/browse/ABC-1` 完整链接；看板会去掉 Jira 链接中的查询参数与片段。也可填写符合项目缺陷链接前缀的完整链接，比较不区分大小写，内容保持原样。GitHub 项目默认前缀为该仓库的 Issues 地址；其他项目可通过项目设置接口登记 HTTPS 前缀。未配置 `JIRA_URL` 时，单号须改填完整链接；两种配置都没有时须先设置其中一种。已登记的旧链接保持原样。

如需显示 Jira 标题与状态，在启动看板前同时通过环境变量设置 `JIRA_URL`、`JIRA_EMAIL` 与 `JIRA_API_TOKEN`。看板用邮箱与令牌进行 HTTP Basic 认证，读取 `<JIRA_URL>/rest/api/3/issue/<单号>?fields=summary,status`。SOP 场景页和详情页在该站点的每个 Jira 链接旁显示“标题 · 状态”，就地提交新缺陷后也会加载；其他链接不请求摘要。读取失败时显示“Jira 读取失败”，筛选与人工复核仍可继续。邮箱、令牌和 Basic 认证值只用于看板进程向 Jira 发出的请求，不放入页面、接口响应或看板日志；上游回显的认证内容会被隐藏，重定向不会转发认证头。

`GET /api/v1/jira/ABC-1` 无需令牌，成功返回 `ok`、`key`、`summary`、`status`、`url`。成功摘要只在内存中缓存五分钟，到期重新读取，重启清空；失败不缓存。单号格式不符返回 422 `jira-key-invalid`，三个变量未配齐返回 404 `jira-not-configured`，这两种情况都不访问 Jira；上游 HTTP 错误、连接失败、超时或响应无效返回 502 `jira-unavailable`，并给出不含认证内容的原因。默认超时十秒；本机模拟测试可设置 `JIRA_TIMEOUT_SECONDS` 为大于零且不超过 10 的秒数来缩短等待，其他值沿用十秒。测试和演示使用本机模拟 Jira，真实站点接入尚待另行验证。

在批次导航点“进度”，可并排查看开发侧的待执行数、已执行进度、Agent 验收通过率和一次通过率，以及测试侧的待复核数、已复核进度、人工复测通过率与误判数，下方显示用例覆盖。比率显示为分子/分母，分母为零时显示“无数据”。首页与总览显示“尚无场景”“有待执行 N 条”或“Agent 已测完”；测完时附最近一个 Agent 轮次的本地提交时间，以及当前场景的最新 Agent 通过、失败、受阻、跳过数量。

批次总览、SOP 场景、详情、用例和进度页每三秒检查一次变化；`GET …/state` 返回状态标识 `etag` 和同值的 `ETag` 响应头，带 `If-None-Match` 且数据未变化时返回 304。标识由最新场景版本、轮次和用例上传序号组成。数据变化后页面取回当前地址并替换主体，保留身份和筛选。失败或受阻的填写栏已有内容时，顶部先显示“有新数据，提交或取消后刷新”，待提交成功或取消后再更新；空栏不阻止刷新。

总览中的“导出报告”下载 `GET /api/v1/projects/<项目键>/batches/<批次>/report.md`。Markdown 报告依次包含头部、用例覆盖、Agent 统计、人工复测、修复记录、回归覆盖、合并记录和未验证范围；与页面和摘要接口共用统计口径，缺失头部信息写“无”。合并记录列出最近一个已完成合并任务移除的场景、重复或冲突、目标与理由，以及待确认的推断；没有已完成任务时写“暂无记录”。修复记录显示自动修复统计，无修复任务时写“暂无记录”；回归覆盖仍写“暂无记录”。数据未变时，两次报告仅生成时间不同。

`GET …/results.yaml` 下载测试岗结果文件，顶层含 `run_id`、`round`、`environment`、`results`。`run_id` 的时间采用看板机器本地时区；无轮次时 `round` 为 0。只导出用例并集中有同编号当前场景且当前内容有结果的项，取最新一条结果，将状态转换为 `passed`、`failed`、`blocked`、`skipped`。每项含 `case_id`、`status`、`actual_result`、`executor`、`tested_at`；配置站点的 Jira 链接提取单号为 `jira_issue`，其他缺陷链接写入 `notes`，与备注以“；”分隔。

向 `POST …/results` 提交 JSON 正文 `{"content":"<results.yaml 原文>","uploaded_by":"<上传人>"}`，可将测试岗结果登记为一个人工轮次。顶层四项及每项的 `case_id`、`status`、`actual_result`、`executor`、`tested_at` 必填，编号必须对应当前场景；失败和受阻还须有符合缺陷链接规则的 `jira_issue`。可选 `duration_ms`（非负整数）、`evidence`（路径字符串数组）、`jira_issue`、`notes`；附带的耗时和证据路径保留在导入记录中，不读取上传者本机文件。未带时区的执行时间按看板本地时区解释。任何一项不合格均返回 422 `results-invalid`，逐项列出问题，整份不保存；合格项沿用各自的执行者、执行时间和实际结果，不以上传人替代。响应含 `ok`、`round`、`imported`、`skipped`；跳过项只列在响应中，全部跳过或空结果数组时不建轮次，`round` 为 null。每条保存结果附 `import-<看板轮次>.json` 证据，含上传人、来源运行编号/轮次/环境、当时最新用例上传序号和该项原文。

按 Ctrl+C 或发送终止信号停止服务；下次用同一数据目录启动，数据会保留。

## SOP 原文与依赖

批次导航中的“SOP”显示各路径的最新原文及历次版本，版本记录含提交号、SHA-256 前 12 位、确认人与本地登记时间。选择同一路径的两个版本可查看逐行增删与未变行。场景详情的来源引用与标题文字完全相同时，可直接跳转到对应标题；重名时取路径排序后的第一个标题。没有原文时显示“尚无 SOP 原文”。

推送正文可附带 `entries` 入口声明对象和 `sop_sources` 原文数组。入口声明沿用 sop-verify 的字段（包括可选的启动、重载与检查说明）；不合格时返回 422 `scenario-file-invalid`，问题点名字段且整份不保存。原文相同不新增版本；只修改原文时不新增场景版本。不附带这两个字段时保留已经登记的入口与原文。授权仓库每五秒按场景来源 `ref` 中以空格分隔的首个有效仓库内相对文件路径读取原文，不跟随越界符号链接，不读取网址；场景不变时也登记原文变化，提交号取当时 HEAD，确认人取对应来源声明。

Markdown 使用 Python 标准库实现约定子集：标题、段落、有序与无序列表、表格、代码块、行内代码、强调、HTTP/HTTPS 链接。原生 HTML 转义，其他协议的链接按文字显示。Mermaid 图示使用随包提供的本地脚本，页面不自动加载外网资源；格式错误的图示保留原文并提示。

第三方脚本为 **Mermaid 12.2.0**，来源为 npm 的 `mermaid@12.2.0` 发行包 `dist/mermaid.min.js`（项目：[mermaid-js/mermaid](https://github.com/mermaid-js/mermaid)）。脚本与原包 MIT 许可原文位于 `src/sop_board/assets/vendor/mermaid/`；现有 uv 构建规则会把该目录及页面脚本放入发行包，无需增加 Python 依赖。

## 场景验收

验收以 `docs/sop/` 的场景经真实入口执行为准。开发中不产出单元、接口或集成测试；仓库不保留 pytest 用例或 Node 页面模型。

验收最终交付的看板：先运行 `uv sync`，在临时数据目录和空闲端口启动，再按场景使用命令行、curl 或真实浏览器完成操作，核对响应、页面、SQLite 数据及证据文件。预期取自已确认的 SOP 与方案，执行步骤及证据要求见 [验收操作手册](docs/verification.md)。

v9 使用 [SOP-BOARD-7 场景](docs/sop/sop-board-7.yaml) 与当前已交付范围；尚待后续任务实现的工作区、适配与跨仓流程单独记录。首次业务验收由未参与实现的执行者留证；实现者经真实入口的核对记为交付准备。验收结束后停止本轮服务，保存证据，再清理本轮临时数据。
