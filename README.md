# sop-board

SOP 验证协作看板。开发岗的代理用 [praxis-skills](https://github.com/AdolphKevin/praxis-skills) 的 `sop-verify` 技能，把业务 SOP 的验收场景与每轮验收结果推送到看板；测试岗在同一个网页上传测试用例、查看进度、复核 Agent 判为通过的场景，并按场景提交缺陷。看板展示 Agent 验收通过率、人工复测通过率与测试进度。

状态：开发中。

## 使用方式

任何成员 clone 本仓后用 uv 在本机启动看板；团队共用一份数据时，由启动者开启内网访问，其他成员用浏览器打开。分析测试用例时，看板调用启动者本机已登录的 Codex。暂不提供服务器部署。

## 相关仓库

- [praxis-skills](https://github.com/AdolphKevin/praxis-skills)：`sop-verify` 技能，从业务 SOP 写场景、派独立会话执行、登记结果。
- [team-workflow](https://github.com/AdolphKevin/team-workflow)：团队流程；看板按轮次导出的结果可直接用 `tw team scenarios submit` 登记。

## 启动与内网访问

需要 Python 3.10 或以上版本与 uv。在仓库目录安装依赖：

```sh
uv sync
```

在终端将自行选择的写入令牌设置到 `SOP_BOARD_TOKEN` 环境变量，再启动服务（令牌不要写入仓库）：

```sh
uv run sop-board --data ./board-data --port 8787
```

`--data <目录>` 指定数据目录，不存在时自动创建。看到 `看板地址：http://127.0.0.1:8787/` 后即可访问首页，选择项目与批次，查看队列、指标、场景历史及证据，并按轮次导出 ZIP。

需要授权本机项目时，先通过环境变量设置另一个开发者令牌 `SOP_BOARD_ADMIN_TOKEN`，再加上可重复的参数：

```sh
uv run sop-board --data /tmp/sop-board-data --port 8787 \
  --writable-repo github.com/example/project=/absolute/path/to/project
```

两个令牌必须不同，授权参数须包含非空的身份、等号和路径，路径必须是 Git 工作区根目录，数据目录须放在授权仓库之外。参数不合格、缺开发者令牌或两个令牌相同时，启动以退出码 1 结束且不新建数据文件；已有空数据目录仍为空。已登记项目的名称在授权及发现新版本时保持不变。成功时输出“可写授权：项目身份（路径）”；首页和批次页显示“可写”或“只读”。去掉参数重启即可撤销授权。

看板启动时及每五秒读取授权仓库 `docs/sop/` 下除 `entries.yaml` 外的 `*.yaml`，合格内容按 `metadata.batch` 登记版本，推送人为“工作区”；同一内容在该批次中只登记一次，看板自己写入的版本也不会再次登记或触发合并。版本记录提交号和工作区是否有未提交改动，产品指纹排除 SOP 场景与入口文件。文件不合格时，批次页显示问题和行号，保留已有版本。

页面身份栏中的“开发者令牌”单独保存在当前浏览器的 `sop-board.admin-token`；开发者按钮需要填写该栏。写入令牌仍只用于原有写入操作。开发者接口缺少或令牌不符时返回 401 `unauthorized`；使用写入令牌时返回 403 `admin-required`。

批次导航中的“合并”页提供任务列表、错误原因、原始文件下载与开发者操作。有用例的批次在上传用例或场景文件变化时自动建立任务，触发原因分别为“上传用例”和“场景文件变化”。`POST /api/v1/projects/<项目键>/batches/<批次>/merges` 发起“重新合并”：相同输入已有排队或运行任务时返回该任务，否则建立新任务，即使此前相同输入已经完成。没有用例时返回 409 `cases-missing`。任务带 `scenario_file_sha256` 表示依据的场景原文摘要，无场景版本时为空字符串。

合并时，每条用例生成一条同编号场景，标题、优先级、标签、前置条件、步骤和预期按解析后的文字原样复制，只有标签含 `negative` 才作为反向场景。按用例编号排序后，分组首次出现时分配 S01、S02 等节点编号；以后新分组追加编号，合入其他节点的分组也保留原编号。重新合并时按场景编号保留回归声明；已经并入且仍在当前场景中的禁止副作用，经历史合并记录确认来源后也继续保留。

Codex 只判断角色、入口、反向类型、节点分组及原有场景的去向：保留、重复或冲突。重复场景的禁止副作用并入目标用例场景，目标没有回归声明时转移原声明；保留场景的编号和内容不变，原节点没有保留正向场景时按判断移入用例节点。任务目录保存用例、场景、入口、节点编号及可用 SOP 原文的输入快照，提示词与输出模式随包提供。入口优先取授权仓库的 `.tw/config.json`，否则取 `docs/sop/entries.yaml`；未授权项目使用最近一次推送附带的入口声明，缺少时任务失败。推送附带 `sop_sources` 时，合并快照同时保存其中的 SOP 原文；每项含 `ref`、`path`（仓库内相对路径）、`commit`、`sha256`、`confirmed_by` 和 `content`，内容上限为 2 MiB，摘要必须与原文一致。

看板独立核对输出模式、全部用例与原场景的去向、编号引用、确定字段和场景格式，失败原因逐项写入 `check.json`。业务依据有缺口时停在“待补充”，不生成草稿。未授权项目只保存草稿，不改变批次场景版本。授权项目仅在磁盘场景文件与合并依据的原文摘要相同或文件不存在时写入 `docs/sop/<批次>.yaml`，登记为“看板合并 #<任务编号>”，不创建 Git 提交。磁盘内容不同则保留原文件，任务为“待同步”；新内容由扫描另行登记并触发新任务。推断的前置状态、豁免理由在对应位置写“待确认”注释；缺少入口文件时，授权项目可以同时写出带待确认文件头的推断入口。

合并页可选任务，查看用例对应关系、原场景去向与理由、待确认的推断、缺口和原始输出。下载 `GET …/merges/<任务编号>/scenario-file` 取得合并原文，`GET …/merges/<任务编号>/pairs.json` 取得可直接用于 `sop-verify coverage --pairs` 的配对文件，全部用例归入 `covered`。没有合并结果的任务，两种下载均返回 404 `merge-result-not-found`；“待同步”任务可以下载以供核对。这两类等待人工的任务均不占运行名额。

Codex 使用启动者本机已登录的命令行工具。启动及每次取任务前核对 `codex --version`；不可用时任务停在“Codex 不可用”，恢复后须由开发者重试。同时运行最多三项，其他任务按创建顺序排队。合并任务显式使用 `read-only` 沙箱，标准输入接空设备；子进程只继承 `PATH`、`HOME`、`USER`、`LANG`、`LC_*`、`TMPDIR`、`CODEX_HOME`、`SHELL`，不继承看板令牌或 Jira 环境变量。`SOP_BOARD_CODEX_TIMEOUT` 设定单项时限秒数，默认 1800；设置时必须是正整数，无论是否授权仓库，不合规值都会以退出码 1 启动失败且不留新文件。超时终止整个进程组并记为失败，重启后排队或运行中的任务记为“已中断”。

`GET /api/v1/tasks?project=<项目键>&batch=<批次>` 列出任务，`GET /api/v1/tasks/<编号>` 返回任务及文件下载地址，`GET /api/v1/tasks/<编号>/files/<相对路径>` 下载原始文件，读取均无需令牌。任务文件保存在数据目录的 `tasks/<编号>/`，含输入快照、提示词、输出模式、逐行事件、错误输出、最终消息和核对记录。会话编号取 `thread.started.thread_id`。文件相对路径可包含子目录；含 `..`、绝对路径、越出任务目录或不存在时返回 404 `task-file-not-found`，任务不存在时返回 404 `task-not-found`。非零退出的错误说明为“Codex 退出码 <码>”，退出码为零但未写最终输出时为“Codex 没有写出最终输出”。开发者可向 `POST /api/v1/tasks/<编号>/retry` 提交 `{}` 重试失败、已中断或 Codex 不可用的任务；编号和输入保持不变，前次文件归档在任务目录的 `attempt-<次数>/`，仍可下载。`POST …/cancel` 仅放弃排队中、运行中、已中断、待同步或待补充的任务，并终止运行中的进程组。失败及 Codex 不可用任务须重试，不能放弃；状态不允许时返回 409 `task-state-invalid`。开发者接口也接受空 POST。开发者令牌未填时，页面提示“请先在身份栏填写开发者令牌”且不发请求。场景列表中最新 Agent 与最新人工结果各带其实际轮次 `round`。

默认只允许本机连接。需要内网共用时，监听本机的全部网络接口：

```sh
uv run sop-board --data ./board-data --host 0.0.0.0 --port 8787
```

启动输出中的 `看板地址：http://127.0.0.1:8787/` 供启动者在本机打开；每个可用的内网 IPv4 地址会另起一行，例如 `内网地址：http://192.168.1.20:8787/`。将对应网络的这条内网地址发给其他成员访问；`0.0.0.0` 表示监听全部网络接口，不是浏览器访问地址。所有能连接该地址的人都能读取场景、证据和导出；写入接口依靠 `SOP_BOARD_TOKEN` 校验权限。服务使用 HTTP，没有传输加密，因此只应在可信内网使用，不要把端口直接暴露到公网。

在批次导航点“SOP 场景”，可按节点浏览全部场景，并筛选全部、未人工复核、Agent 已通过、不通过或受阻。筛选地址带 `?filter=`，可复制分享。场景列表与详情页共用“通过”“失败”“受阻”三个按钮：通过立即提交；失败与受阻只需填写缺陷链接，备注选填，也可取消。保存后在原处更新结果与数量，人工结果统一显示“通过”“不通过（失败）”或“不通过（受阻）”。接口拒绝时在该场景下显示错误代码和各项问题说明，并保留已填内容。

首次复核时在页面顶部的身份栏填写标记人与写入令牌，二者分别保存在当前浏览器的 `sop-board.marker`、`sop-board.token` 本地存储中，可随时更换。共享电脑使用后应清除该站点的本地存储。接口写入请求使用 `Authorization: Bearer <令牌>`。

在批次导航点“用例”，选择 YAML 文件并点“上传用例”。上传人取身份栏中的标记人，写入令牌也沿用身份栏。页面会逐条显示不合规字段及文件行号；YAML 语法错误还会给出解析器原因与列号。上传失败不保存数据，也不会建立新批次。上传成功后刷新页面，显示上传记录及按 `section:` 标签分组的用例；没有该标签的归入“未分组”。每条用例标明是否已有同编号的当前场景，有对应场景时可直接打开。

用例文件的顶层仅有 `metadata` 与非空的 `test_cases`。`metadata` 必填 `module`、`feature`、`owner` 和日期 `last_reviewed`（`YYYY-MM-DD`），可选字符串数组 `tags`。每条用例必填 `id`（如 `TC_DEMO_LOGIN_001`，格式为 `^TC_[A-Z0-9_]{3,}_[0-9]{3}$`）、`title`、`priority`（`P0`、`P1`、`P2`）、`type`（`functional`、`ui`、`security`、`performance`、`accessibility`），以及非空字符串数组 `steps`、`expected_results`、`tags`；可选 `description` 字符串、`preconditions` 字符串数组和 `auto` 布尔值。不接受其他字段，同一文件的用例编号不能重复。

工具可向 `POST /api/v1/projects/<项目键>/batches/<批次>/cases` 提交 JSON 正文 `{"filename":"cases.yaml","content":"<YAML 原文>","uploaded_by":"<上传人>"}`。项目须先存在；成功上传可以建立尚无场景的新批次。历次上传取并集，同编号按最后一次上传的完整内容替换；与上一次原文完全相同的上传不会增加序号。`GET …/cases` 返回上传记录、当前并集和用例覆盖数；`GET …/cases.yaml` 下载并集，文件说明取最近一次上传的 `metadata`；`GET …/scenario-file` 下载最新场景原文，尚无场景时返回 404 `scenario-file-not-found`。已有数据目录启动时自动补建用例相关表，保留原有数据。

人工标记接口只接受 `scenario`、`fingerprint`、`status`、`marker`、`defect_url`、`note`。状态只支持 `pass`、`fail`、`blocked`；通过不带缺陷链接，失败与受阻必须带链接。实际结果、问题记录与观察证据由看板生成，不再接收人工填写的 `actual`、`environment`、`finding`、`evidence`。观察记录使用 `marker`、`status`、`recorded_at`，有值时再写入 `defect_url` 与 `note`。按轮导出的 ZIP 保留原有 tw 结果格式，观察文件位于 `evidence/<序号>-observation-<轮次>.json`。

缺陷链接去掉首尾空白后核对。启动前设置可选的 `JIRA_URL`（如 `https://example.atlassian.net`），即可填写 `ABC-1` 这样的 Jira 单号，或该站点的 `/browse/ABC-1` 完整链接；看板会去掉 Jira 链接中的查询参数与片段。也可填写符合项目缺陷链接前缀的完整链接，比较不区分大小写，内容保持原样。GitHub 项目默认前缀为该仓库的 Issues 地址；其他项目可通过项目设置接口登记 HTTPS 前缀。未配置 `JIRA_URL` 时，单号须改填完整链接；两种配置都没有时须先设置其中一种。已登记的旧链接保持原样。

如需显示 Jira 标题与状态，在启动看板前同时通过环境变量设置 `JIRA_URL`、`JIRA_EMAIL` 与 `JIRA_API_TOKEN`。看板用邮箱与令牌进行 HTTP Basic 认证，读取 `<JIRA_URL>/rest/api/3/issue/<单号>?fields=summary,status`。SOP 场景页和详情页在该站点的每个 Jira 链接旁显示“标题 · 状态”，就地提交新缺陷后也会加载；其他链接不请求摘要。读取失败时显示“Jira 读取失败”，筛选与人工复核仍可继续。邮箱、令牌和 Basic 认证值只用于看板进程向 Jira 发出的请求，不放入页面、接口响应或看板日志；上游回显的认证内容会被隐藏，重定向不会转发认证头。

`GET /api/v1/jira/ABC-1` 无需写入令牌，成功返回 `ok`、`key`、`summary`、`status`、`url`。成功摘要只在内存中缓存五分钟，到期重新读取，重启清空；失败不缓存。单号格式不符返回 422 `jira-key-invalid`，三个变量未配齐返回 404 `jira-not-configured`，这两种情况都不访问 Jira；上游 HTTP 错误、连接失败、超时或响应无效返回 502 `jira-unavailable`，并给出不含认证内容的原因。默认超时十秒；本机模拟测试可设置 `JIRA_TIMEOUT_SECONDS` 为大于零且不超过 10 的秒数来缩短等待，其他值沿用十秒。测试和演示使用本机模拟 Jira，真实站点接入尚待另行验证。

在批次导航点“进度”，可并排查看开发侧的待执行数、已执行进度、Agent 验收通过率和一次通过率，以及测试侧的待复核数、已复核进度、人工复测通过率与误判数，下方显示用例覆盖。比率显示为分子/分母，分母为零时显示“无数据”。首页与总览显示“尚无场景”“有待执行 N 条”或“Agent 已测完”；测完时附最近一个 Agent 轮次的本地提交时间，以及当前场景的最新 Agent 通过、失败、受阻、跳过数量。

批次总览、SOP 场景、详情、用例和进度页每三秒检查一次变化；`GET …/state` 返回状态标识 `etag` 和同值的 `ETag` 响应头，带 `If-None-Match` 且数据未变化时返回 304。标识由最新场景版本、轮次和用例上传序号组成。数据变化后页面取回当前地址并替换主体，保留身份和筛选。失败或受阻的填写栏已有内容时，顶部先显示“有新数据，提交或取消后刷新”，待提交成功或取消后再更新；空栏不阻止刷新。

总览中的“导出报告”下载 `GET /api/v1/projects/<项目键>/batches/<批次>/report.md`。Markdown 报告依次包含头部、用例覆盖、Agent 统计、人工复测、修复记录、回归覆盖、合并记录和未验证范围；与页面和摘要接口共用统计口径，缺失头部信息写“无”。合并记录列出最近一个已完成合并任务移除的场景、重复或冲突、目标与理由，以及待确认的推断；没有已完成任务时写“暂无记录”。修复记录与回归覆盖仍写“暂无记录”。数据未变时，两次报告仅生成时间不同。

`GET …/results.yaml` 下载测试岗结果文件，顶层含 `run_id`、`round`、`environment`、`results`。`run_id` 的时间采用看板机器本地时区；无轮次时 `round` 为 0。只导出用例并集中有同编号当前场景且当前内容有结果的项，取最新一条结果，将状态转换为 `passed`、`failed`、`blocked`、`skipped`。每项含 `case_id`、`status`、`actual_result`、`executor`、`tested_at`；配置站点的 Jira 链接提取单号为 `jira_issue`，其他缺陷链接写入 `notes`，与备注以“；”分隔。

向 `POST …/results` 提交带写入令牌的 JSON 正文 `{"content":"<results.yaml 原文>","uploaded_by":"<上传人>"}`，可将测试岗结果登记为一个人工轮次。顶层四项及每项的 `case_id`、`status`、`actual_result`、`executor`、`tested_at` 必填，编号必须对应当前场景；失败和受阻还须有符合缺陷链接规则的 `jira_issue`。可选 `duration_ms`（非负整数）、`evidence`（路径字符串数组）、`jira_issue`、`notes`；附带的耗时和证据路径保留在导入记录中，不读取上传者本机文件。未带时区的执行时间按看板本地时区解释。任何一项不合格均返回 422 `results-invalid`，逐项列出问题，整份不保存；合格项沿用各自的执行者、执行时间和实际结果，不以上传人替代。响应含 `ok`、`round`、`imported`、`skipped`；跳过项只列在响应中，全部跳过或空结果数组时不建轮次，`round` 为 null。每条保存结果附 `import-<看板轮次>.json` 证据，含上传人、来源运行编号/轮次/环境、当时最新用例上传序号和该项原文。

按 Ctrl+C 或发送终止信号停止服务；下次用同一数据目录启动，数据会保留。

## 运行测试

```sh
uv run --frozen pytest -q -p no:cacheprovider tests
```

表单脚本的隔离逻辑测试还需要本机安装 Node.js 18 或以上版本，不需要安装 npm 包。其余测试通过临时目录中的真实 HTTP 服务与 SQLite 核对结果；浏览器操作和内网另一台机器的访问仍需另行验收。
