# 执行场景

场景键写作 `<文件>#<场景编号>`（编号唯一时可省文件）。范围取 `pending`（缺省：未执行、待复测、失败、受阻、跳过）、`all`，或列出场景键，三者取其一，不能混写。分几步实现后统一验收时，范围按下文「统一验收：选范围」选。

## 独立执行（首选）

1. `sop-board run launch --scope <范围> [--implementer <会话编号> | --implemented-by <操作者>]`：守护进程按项目 `agents` 配置启动一个新的无头会话。它只拿到 prompt 文件，会话编号由启动器取得，启动记录就是独立性的证据。实现者参数按下文「实现者与独立性」填。启动前按 `run prepare` 的规则核对范围，被拒绝时不启动会话，处理见「准备时的拒绝」。
2. `sop-board run wait [--timeout <秒>]` 等它结束（缺省 1800 秒；退出码 3 表示超时、启动仍在运行，可再次 wait）。`sop-board launch status` 查看启动记录与日志；使用者要求停止时 `sop-board launch stop --launch <编号>`。
3. 把 wait 输出中的提交结果（登记、作废、未执行的场景及原因，服务停启与自动恢复）如实转述。`results` 里运行的 `status` 是 `submitted` 才有登记的结果。wait 返回 `launch-no-work`（会话退出了却没有产生运行）或 `launch-failed`（会话没能启动或异常退出）时，这一轮未完成验收（已有 submitted 结果仍如实转述）：把 `problems` 与 `log_tail`（启动日志末尾）里的原因转告使用者，原因排除后重新 launch。`launch-unsubmitted` 表示会话已退出，但有关联运行或沉淀未提交或已放弃：转述工作编号、状态和日志；运行仍为 prepared 时，由使用者决定继续执行并提交，还是 `sop-board run abandon --run <编号>`，协调会话不替他处理。

协调会话只发起和转述：结果由执行会话写出并提交，协调会话保持原样转述。同一检出已有运行中的启动时返回 `launch-running`，报告该启动并等它结束。

## 当前会话执行

使用者要求当前会话执行时：

1. `sop-board run prepare --scope <范围>`。
2. 读输出的 prompt.md 与 brief.md，按其执行、留证、写结果。
3. `sop-board run submit --run <编号> [--implementer <会话编号> | --implemented-by <操作者>]`，如实转述提交输出。

`--scope pending|all` 只从合格的场景文件里选场景。`run launch` 输出的 `launch.invalid_files`、`run prepare` 输出的 `invalid_files` 非空时，这些文件里的场景没有纳入本轮：把文件与问题转告使用者，报告范围时写明。

## 实现者与独立性

实现者是改了被验收产品代码的会话或操作者，按事实填，二者只给一个：

| 被验收的代码是谁改的 | 填 | 记为 |
| --- | --- | --- |
| 本会话在这次对话里改的 | `--implementer <本会话编号>` | 由 `run launch` 的会话执行：独立验收；本会话自己执行：实现者自检 |
| 使用者说明的另一个本机会话 | `--implementer <他给的会话编号>` | 独立验收 |
| 使用者说明的别的机器上的操作者 | `--implemented-by <操作者>`（见 [shared.md](shared.md)） | 独立验收 |
| 使用者没说明，本会话也没改 | 都不填 | 独立性未声明，报告里照此说明 |

只发起、转述验收的协调会话没有改代码，它的会话编号不是实现者：使用者只说“做完了，请验收”而没说是谁改的，属于最后一行，直接不填，不追问。修复复验的实现者由系统自动取修复会话。

## 分步实现时的验收时机

一项需求分几步实现，或几项需求接连实现时，按本节定每一步什么时候验收。验收安排从每一步的事实推出，每一步都写理由；“每步都验”“全部做完再验”只是事实恰好都指向同一边时的结果。

底线：交付条件不变。分步验收只改变每条场景在哪一步执行，要经独立真实入口执行的场景一条不少；先验的通过要到交付时仍然可信（见「先验通过的场景」）。实现者自检每一步都做。

### 开工前定验收安排

在改动任何文件之前，对每一步定下“做完就验”或“并到后面一起验”，逐条对照这些事实：

| 事实 | 为什么影响时机 |
| --- | --- |
| 这一步会先单独交付，或装给别人用 | 交出去的部分要先有独立验收 |
| 后面的步骤会重做这一步验过的实现 | 现在验的结果到时还要重验 |
| 后面的步骤以这一步正确为前提 | 这一步有错，后面的步骤跟着返工 |
| 各步改动的范围重叠 | 重叠多时，晚发现的缺陷难分清出自哪一步 |
| 涉及鉴权、持久化、金额、消息、并发 | 高风险，出错的代价大 |
| 验收一轮的成本：环境、真实账号、人工复核、时间 | 成本越高，合并轮次越省 |

事实指向不同方向时，写明怎样取舍。做完就验的步骤，如果后面的步骤还会改到它依赖的实现，同时写明它的场景靠哪种做法到交付时仍然可信（见「先验通过的场景」）。把验收安排发给使用者，每一步一行：

    第 N 步 <做什么>（涉及 <场景键，还不确定时写“待定”>）：做完就验 | 并到第 M 步之后一起验 —— <依据的事实>

使用者确认或调整后再动手，按确认后的安排执行。

### 每一步做完后如实标注

每一步做完都做实现者自检（运行改动、核对输出）。报告与提交说明给每一步标三者之一：**已独立验收**（附运行编号）、**只做了实现者自检**、**未验证**。

- 做完就验：自检后按上文「独立执行」发起验收（这一步是本会话实现的，`--implementer` 填本会话编号），独立通过后才标已独立验收。
- 并到后面一起验：报告写“第 N 步只做了实现者自检，未经独立验收，并到第 M 步之后一起验”。这一步的场景在第 M 步之后那一轮执行和登记；在那之前，这一步的说法停在“已实现，实现者自检”。

### 先验通过的场景

代码改动不改变场景状态：先验通过的场景，在后面的步骤重做了它依赖的实现之后仍显示通过，`status --json` 的 `queues` 和 `--scope pending` 都不会再列出它。这样的通过要到交付时仍然可信，二选一，写进验收安排：

- 守护：先验的那一步通过后，使用者同意即按 [guard.md](guard.md) 沉淀，之后每一步做完运行 `sop-board retest`。交付时守护有效且最近一次运行通过，这条通过就仍然可信；retest 未通过的场景转待复测，进入 pending。后续步骤改了守护引用的测试文件时，守护失效（retest 把它列在 `not_guarded` 并附原因），这条场景改走下一种做法。
- 重新执行：统一验收时按场景键把它们列入范围（下一节）。

两样都没有的，这条通过不能算进交付。

### 统一验收：选范围

范围 = 全部推迟验收的步骤的场景 + 先前通过、被后续步骤重做了实现、又没有“守护有效且最近一次运行通过”的场景。

1. 逐条核对先前通过的场景：它的通过取证于哪一步之后（对照验收安排、`git log` 与 `sop-board report` 中每条结果取证时的代码版本），后面的步骤有没有改它依赖的实现。没改过的不动。改过的运行 `sop-board retest --scenario <键>…`：守护有效且这次通过的，通过仍然可信，不列入；列在 `not_guarded`（没有守护或守护已失效）或未通过的，列入范围。告诉使用者哪些场景因此重新执行、为什么。
2. 把推迟步骤的场景（新增和修改过的在 `queues.not-run` 中）与上一步列入的场景一起按键列出：`sop-board run launch --scope <键> <键> …`；范围接近全部场景时用 `all`。
3. 统一验收完成的标志：范围内每条场景都在这一轮取得独立真实入口通过；第 1 步没有列入的被重做场景，守护有效且最近一次运行通过。`queues` 为空只说明没有未执行、待复测、失败、受阻的场景，先验场景是否仍然可信要按第 1 步核对。

## 未执行与受阻

执行会话按 prompt.md 判定，你转述时用同一口径，按性质分，不看发生在开始前还是执行中：

- **未执行**：本机暂时不具备、补齐或换一台机器就能执行。用到的服务本机未搭建或被人停着、缺入口声明的凭据变量、等人处理的事（真实或未声明账号登录、人机验证、只发到使用者本人设备的验证码、身份使用次数到上限）。不登记结果，场景状态不变，仍在 pending；工作台详情显示最近一次未执行（谁、什么时候、缺什么）。转告使用者缺什么，补齐后重跑。
- **受阻**：意外故障或全队都不具备的能力。服务或浏览器异常退出、前置数据准备失败、证据丢失、运行作废、browser may not be secure、入口或观察能力还没建设、需要停外部共享中间件的故障场景。

`run prepare` 不要求每个服务都在运行，输出的 `not_running` 列出没在运行的服务，`missing_address_env` 列出缺失的入口地址；它们只影响用到它们的场景。

独立复验（`--fix`）须完整执行，不接受未执行：本机缺条件时先补齐。

## 依赖故障的场景

场景起点要求某个依赖不可用时，执行会话在运行中用 `sop-board env stop <服务>` 停、`sop-board env start <服务>` 启，停启记进本轮运行，提交或放弃时还停着的自动恢复；结果详情显示“执行时 <服务> 已停止”。只能停 `adapter.services` 中 `stoppable: true` 的服务。没有 prepared 运行时返回 `run-required`；运行之外要恢复环境，用 `sop-board env restart`。

| error_code | 处理 |
| --- | --- |
| `service-not-declared` / `service-unknown` | 项目没声明服务，或服务名不在声明里（输出列出已声明的服务）：核对名称；确实没有对应的服务时场景记受阻 |
| `service-not-stoppable` | 服务不可停：场景记受阻，写明原因 |
| `service-timeout` | adapter 没在 `adapter.service_timeout` 秒内完成停启，停止请求已撤回：如实写进 finding，场景记受阻，转告使用者检查 adapter |
| `service-unavailable` | 服务当前不是运行中（本机未搭建、异常退出）或环境没有运行：本机未搭建记未执行，异常退出记受阻 |

## 准备时的拒绝

`run prepare` 与 `run launch` 用同一套核对：

| error_code | 处理 |
| --- | --- |
| `scenario-not-found` | 范围里的场景键不存在，或省略文件后编号不唯一：对照场景文件写全 `<文件>#<场景编号>` |
| `scenario-file-invalid` | 指名的场景所在文件不合格：按列出的文件、字段与行号转告使用者，修正后再准备 |
| `nothing-to-run` | 范围里没有要执行的场景；`problems` 同时列出不合格文件时，转告使用者这些文件的场景没有纳入 |
| `run-prepared` | 本检出已有 prepared 运行：报告编号；是本会话的就完成并 submit；使用者同意放弃后 `sop-board run abandon --run <编号>` |
| `env-busy` | 端口被另一检出的环境占用，输出写明占用者与 `env down` 命令：转告使用者，由他决定 |
| `browser-busy` | 该身份正被真人占用：使用者说完成后 `sop-board browser release --identity <身份>` 交还，再准备 |
| `browser-unrecovered` | 看板重启后没认回的有界面窗口，处理见「账号与真人操作」末段 |
| `draft-not-runnable` | 范围含草稿场景：先按 [draft.md](draft.md) 确认 |

运行目录使用 `run prepare` 返回的 `directory`，重号时会顺延目录名称；不要按运行编号拼路径。

## 账号与真人操作

项目声明的测试账号（含测试邮箱）声明即授权：执行会话直接用声明的凭据变量登录、读验证码，你不向使用者要授权，也不写授权记录。

真人只做三类事：真实账号或未声明账号的登录、人机验证、只发到使用者本人设备的验证码。执行会话遇到它们时，把相关场景记未执行并登记待人处理（`sop-board attention list` 可见）；人完成并交还后，这些场景仍在 pending，直接重跑。需要人做时：

1. `sop-board browser open --identity <身份> --headed`：在该身份的 Chrome for Testing 窗口打开入口（窗口已开着时只取得真人租约，不重启），请使用者在窗口里完成。
2. 使用者说完成后，`sop-board browser release --identity <身份>` 交还。窗口保持打开，之后的运行直接沿用其中的登录与验证。

`browser close` 会结束浏览器，人做过的验证随之作废，只在使用者要关掉浏览器时用。出现 `browser may not be secure` 时停止，相关场景记受阻并照录原文。身份处于 crashed 状态时，经使用者同意后 `sop-board browser open --identity <身份> --reset-crash`。

看板停止时保留有界面的浏览器窗口，重启后认回仍在运行且调试端口有应答的窗口，之后直接沿用。无头浏览器与产品环境照旧停止；要结束窗口用 `sop-board browser close --identity <身份>`。用 `sop-board restart` 重启时，无头浏览器、租约与进行中的运行也都保留，环境几十秒后重新就绪。

窗口未认回时，`browser status` 显示进程号与原因，租约、`run prepare` 和 `browser open` 返回 `browser-unrecovered`，不会另起浏览器。把进程号与原因转告使用者；窗口恢复应答后再次请求会重新核对。只有使用者确认不要这个窗口（里面的登录与验证随之作废）时，才用 `sop-board browser close --identity <身份>` 结束。看板停止仍保留未认回窗口。

## 人工复测结论

使用者转述测试同学的复测结论时：`sop-board mark <场景键> pass|fail|blocked|changed [--defect <缺陷链接>] [--note <说明>]`（阻塞为 blocked、需求变更为 changed，缺陷链接与说明可选）；复测人是别人时加 `--as <姓名>`。

使用者问哪些场景等测试同学复核时，看 `status --json` 的 `review_queue`：状态为通过、最新结果是 Agent 独立真实入口通过、之后还没有人工标注。Agent 独立通过的人工确认率与误判明细在 `sop-board report` 中。
