# 修复失败场景

修复 → 另一会话独立复验 → 开发者提交 → 关闭。

## 修复（修复会话）

1. `sop-board fix prepare [<场景键> …]`：缺省为当前检出全部失败或受阻的场景。同一检出同时只有一个进行中的修复，返回 `fix-open` 时报告它的编号与会话。
2. 读输出的 prompt.md 并按其执行：在当前检出改产品代码，写 fix.json。
3. `sop-board fix submit --fix <编号>`。非产品问题登记到待人处理，转告使用者。
4. 产品问题进入待复验：运行 `sop-board run launch --fix <编号>`，由守护进程启动一个未参与修复的新会话复验，再 `sop-board run wait`。修复会话自己复验只记为实现者自检，修复因此不能关闭。

## 复验（另一会话）

1. `sop-board run prepare --fix <编号>`：范围由修复决定，实现者自动取修复会话。
2. 按 prompt.md 经真实入口实际执行并留证，`sop-board run submit --run <运行编号>`，如实转述结果。

## 关闭

复验通过后，开发者审核并自己提交修复改动，然后运行 `sop-board fix close`（省略 `--fix` 时取本检出最近一个待关闭的修复）。被拒时按输出处理：

- 缺少独立复验通过：安排另一会话复验。
- 列出未提交的文件：请开发者提交。
- 列出内容与复验时不一致的文件：重新独立复验。

使用者决定放弃时：`sop-board fix abandon --fix <编号>`。

提交、复验、关闭、放弃都在产出修复的机器上进行；别的机器返回 `fix-not-local` 时按 [shared.md](shared.md)「别的机器产出的修复」处理。
