# 会话修复与独立复验

先完成入口技能的 status 检查，读取 [sessions.md](sessions.md) 取得并记录本会话身份。修复在已登记的开发者当前工作区进行；保留原有未提交改动。

1. 确认使用者要处理的问题范围，运行 `sop-board fix prepare <工作区> --scenario <批次>#<场景> --session <修复会话标识>`。多个问题用空格分隔；省略 --scenario 时认领当前可处理的问题。自定义数据目录加 --data。已在其他修复任务中的场景不接管，呈报返回的任务编号；fix 不使用 --replace-queued 替换归属。
2. 读取 prepare 返回的提示词、问题与证据、仓库目录和快照。操作契约以提示词为准。分析所有认领问题，按实际根因填写分类与仓库；只在列出的当前仓库目录修产品代码，不建工作树、不改 SOP 或场景、不写测试、不提交、不推送。业务预期不足时向使用者确认，不通过改预期让场景通过。
3. 在任务目录写出根因输出，再运行 `sop-board fix submit <工作区> --task <编号>`。输出或受保护文件校验失败时，先呈报问题并修正，保留失败材料。非产品问题交使用者处理，不修改产品代码或发起复验。
4. 产品修复登记为“待验证”后，按 sessions.md 分两段创建未参与实现的新会话并取得其原生编号。运行 `sop-board execute prepare <工作区> --fix <修复任务编号> --session <复验会话标识>`，不再指定批次或 --scope；准备时就拒绝修复会话自己的标识。范围由问题场景与涉及改动仓库的场景共同确定，可能跨批次，不能缩减。
5. 按 sessions.md 写 handoff 文件后交接任务目录、项目验证技能与手册、入口环境及授权记录位置。复验者从 repos.json 读取仓库目录；snapshot.json 的 session_files 是复验准备时、修复输出已登记后的产品文件清单。按新提示词经真实入口执行全部场景，不能沿用旧结果，不参与修复。结束前按手册停止本轮自己启动的服务进程并核对已退出，保留使用者已有服务和浏览器；在结果 note 中列出已停止的名称、PID 或进程组与停止结果，没有启动则写明，停止失败列出仍运行的进程及原因。结果写回新任务目录，再 `sop-board execute submit <工作区> --task <复验任务编号>`。实现者由原修复记录绑定，提交仍核对身份。使用者要求当前实现会话自检时可报告自检事实，但不能借换标签完成这里的独立复验要求；没有独立会话时明确保留待验证。
6. 复验未通过时交回失败与证据。需要继续修复时由原修复会话重新 fix prepare，保留旧尝试，再修正、submit 并另开独立复验。输出不合格可在同一复验任务修正重交；输入变化作废时重新准备复验。
7. 复验通过后交开发者审核并自行提交。收到已提交的说明后运行 `sop-board fix land <工作区> --task <修复任务编号>`。该命令只核对提交内容、关闭记录并按配置回写缺陷单，不替开发者提交或合入。提交内容与复验快照不同则报告差异，重新独立复验，不绕过核对。

交回根因、各仓改动、实际复验范围与轮次、关闭状态，以及未完成的人工事项和 Jira 回写结果。没有真实独立执行证据时，不把命令成功或模拟输出登记写成独立验收通过。场景执行与修复均不建设测试；另行授权的测试建设使用 regression-distill。
