# 从需求资料编写业务 SOP

本阶段需要已登记且配置合格的工作区；不要求启动产品环境或运行 check。已有已确认 SOP 原文只需登记时，转 [draft.md](draft.md) 的 sop upload。

1. 取得使用者指定的资料文件、批次与本会话标识，按 [sessions.md](sessions.md) 核对身份与数据目录写权限。运行 `sop-board sop prepare <工作区> <批次> --source <资料1> <资料2> --session <标识>`；可重复 --source，指定数据目录用 --data。读取返回提示词、提示词指定的 sop-guide.md 与全部资料副本，按契约写 final.json。再次执行相同 prepare 可生成 sop.md 预览并记录问题，不代替业务确认。
2. 完整呈报 SOP 规则与问题，按提示词的业务场景格式逐项询问。资料冲突或结果未写明时在这里等待，不把技术方案、代码或自己的建议当成业务答复。
3. 收到使用者针对本批次本问题的原话与姓名后，运行 `sop-board sop answer <工作区> --task <编号> --question <Q编号> --text <原文> --author <姓名>`；也可用 `<工作区> <批次>` 定位唯一未结束任务。不能挪用其他批次或旧问题的答复。读取更新后的 answers.json，按最新答复修订正文；仍有疑问就新增具体问题，再呈报。更新 final.json 后 prepare 预览，核对答复原文与答复人已写入 sop.md。
4. 全部问题已答、正文已经更新后，按提示词核对最终标题与正文已去掉“待业务确认”“确认稿”等过程状态措辞，未覆盖范围只记业务范围，确认信息留给命令附加。把最终 SOP 呈报使用者，取得其在本次确认请求中明确指定的业务确认人。此前的自我介绍、答复人、上传人或会话编号不能代替；缺姓名时直接询问确认人的姓名，不给示例姓名。得到确认后运行 `sop-board sop submit <工作区> --task <编号> --confirmed-by <姓名>`。确认人同时作为此次原文登记人记录；若使用者要求另由他人上传，使用已有原文的 sop upload 并填写各自姓名。
5. 成功后报告 SOP 版本和 CLI 返回的原文或预览位置；有可用看板链接时一并提供。看板未运行时说明这一点，或报告 CLI 给出的位置；返回“看板地址”占位时照实说明，不为寻找链接额外运行命令或启动看板。来源清单、内容摘要、业务答复与确认人可在 SOP 页核对，随后的草稿已由原会话认领。使用者已授权生成验收场景时继续 [draft.md](draft.md)；否则询问是否继续，等待决定。

提交被拒时按返回原因修正，不删除已呈报问题、伪造答复或改写来源副本。已结束任务不复活；资料或原文变化导致作废后重新 prepare。答复补充会保留历史，原答案已被新答案替代时以最新答复修订正文。真实模型的理解与规则质量必须由未参与实现的会话核对，命令成功不能代替业务确认。

## 问题呈报模板

每个问题单独按下面六项完整呈报，不改成表格或一行摘要。保留 Q编号、来源摘录与矛盾双方的原话；一个“请确认”只问一个业务决定。本阶段尚无用例时明确写“尚未生成用例”，并列出 questions.affected 中的规则编号或资料章节，不编造用例编号。

```markdown
### 标题：<Q编号> <一句话标题>

**场景**
<谁在什么前置状态下，从哪里做什么>

**目前的写法**
<资料原文及来源；冲突时分别列双方原文>

**缺什么**
<还缺哪一项能确定业务结果的依据>

**请确认**
<直接询问所需的一个业务决定，不暗示答案或暂不纳入，等待使用者针对本问题答复>

**涉及用例**
<已有用例的编号与标题；尚无用例时写明，并列涉及规则或资料章节>
```
