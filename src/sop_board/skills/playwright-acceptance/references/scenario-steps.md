# 场景写法要求

本技能按场景文件逐步执行，不补全业务含义。场景格式（`id`、`polarity`、`initial_state`、`steps`、`expected`、`forbidden_effects` 等）由本技能 [contracts.md](contracts.md) 与 sop-board 场景文件校验器规定；下面是让步骤可以直接翻译成 Playwright 操作的补充要求。执行者可补充技术定位；业务目标、前置分支或预期缺失时，列出具体问题退回场景作者，暂停该场景。其他已明确且互不依赖的场景可继续，最终如实列出缺口。

## 四项要求

1. **步骤用页面上看得见的文字，并写明所在界面。**
   - 可执行：`在收件箱弹窗的会话列表中点击第一项`、`点击按钮 "Join conversation"`、`在输入框 "Start writing..." 中输入 123456789`
   - `点击新建宏` 若业务动作和对象已明确但缺少实际按钮文案，可经源码和只读探测补成定位映射；不需要为 DOM 技术细节重新确认业务。
   - `回复客户` 若未明确客户对象、渠道及内容，不能由执行者猜测。
2. **前置条件写到能确定分支。** 同一步骤在不同状态下会走到不同界面。例如 B 端收件箱：客户离线时发送按钮变成 "Send email"；会话由 AI 处理时才有 "Join conversation"。`initial_state` 要写明：当前店铺、当前账号与界面语言、目标对象的状态（在线/离线、AI/人工、已付款/未付款）、用什么数据。
3. **预期只写可观察的结果。** `页面提示 "退款成功"`、`订单状态显示 "部分退款"`、`消息 "123456789" 出现在会话中且输入框清空`。不要写 URL、接口返回、数据库字段；需要核对数据时，写明用哪个只读观察点（页面、API 查询脚本）。
4. **禁止的副作用要覆盖对外影响。** 发邮件、发消息给真实客户、修改真实店铺、全额退款等。

## 示例

```yaml
- id: SOP-02-P01
  polarity: positive
  title: 人工接管 AI 会话并发送消息
  actor: 测试店铺管理员
  priority: P0
  verify: shopify-admin
  initial_state:
    - 已在 Chrome 测试 profile 中登录开发店铺 lw-wzp-test-1，后台语言为英文
    - 应用首页 "Escalated Tickets" 卡片可见
    - 会话列表第一项由 AI 处理（显示 "Assistant"），客户在线
  steps:
    - 在应用首页 "Escalated Tickets" 卡片中点击按钮 "Go to inbox"
    - 在收件箱弹窗的会话列表中点击第一项
    - 在 "AI is processing" 提示下点击按钮 "Join conversation"
    - 在输入框 "Start writing..." 中输入 123456789
    - 点击按钮 "Send"
  expected:
    - "Join conversation" 按钮消失，出现输入框
    - 消息 "123456789" 出现在会话中，输入框清空
    - 列表第一项显示 "Me"
  forbidden_effects:
    - 发送按钮为 "Send email"（表示客户离线，走邮件渠道）
    - 向客户邮箱发出邮件
```

## 退回清单

执行前对照以下问题，有一条成立就退回：

- 源码及只读探测后仍无法确定动作对象，或需要猜测业务分支？
- `initial_state` 无法确定该步会走哪个分支？
- 某条 `expected` 不能在页面或声明的观察点上看到？
- 场景会对真实客户、真实店铺或外部系统产生影响，而 `forbidden_effects` 没有覆盖？
- 场景引用的 `verify` 入口在工作区 `config.yaml` 的 entries中没有声明？

代理推断出来的预期不能直接写进脚本：先记入方案问题清单，确认后由场景作者补进场景并写明 `confirmed_by`。

## 定位映射的边界

执行者记录“原场景步骤 → 实际控件/iframe/定位器 → 源码或探测依据”，保留原场景编号与业务预期。可以把同一步拆成多个技术操作，但不能新增业务预期、修改角色/订单选择规则、用其他对象替代目标、生成新编号或另建批次来绕过原场景。发现这些需求时退回上游确认。
