# 回归沉淀

守护测试替场景发现代码改动带来的回归：`sop-board retest` 运行守护命令，未通过的场景转为待复测，交真实入口复测。首次验收、场景内容变化、缺陷复验仍须真实入口。所以守护必须完整：每条 expected 与 forbidden_effects 都有测试，且证明测试能抓住对应的问题。

## 1. 准备

在产品仓库的检出目录运行：

```sh
sop-board distill prepare [<文件>#<场景编号> ...]
```

不写场景时，准备当前检出全部“待沉淀”的场景。只有同一指纹上有独立真实入口通过、且没有有效守护的场景才能沉淀，prepare 会拒绝其他场景。按输出给出的 prompt.md 工作。材料都在工作目录：scenarios.yaml（场景原文）、acceptance.json（独立通过的结果编号；Web 场景的通过 spec 在其运行目录）、repos.json（本检出的仓库目录）。

## 2. 调查并选层

先调查仓库已有的测试框架、目录、夹具与启动命令，以及 CI 实际运行哪些测试。读[分层选择](references/layers.md)，为每条预期选能观察到该结果的最低成本层；接口与数据库共同产生结果时，另读[数据库接口测试](references/backend-db.md)。

## 3. 写测试并在本机运行

沿用已有设施，断言只取自场景原文。只改测试、夹具与测试启动脚本，不改产品代码与场景文件。测试运行时的输出（报告、截图、缓存）写到仓库外或已被忽略的目录：retest 要求运行前后产品快照不变。

守护命令必须输出 junit（运行器把 `{junit}` 替换为输出路径）。实际运行，逐个核对声明的测试名都出现在执行清单中且通过；零用例、被跳过或缺环境都不算通过。测试与预期不符时停下，报告现象与依据，交调用方决定是否修改产品。

## 4. 核对检出能力（必需）

在独立临时副本里受控改错，或复现已知缺陷：确认失败的是对应的业务断言，而不是编译、依赖或环境错误。只在临时副本里改错，原检出只留沉淀改动。把被改的规则、副本差异、命令与失败输出存进一个文件，作为 detection 证据。做不到的场景不写进守护。

## 5. 写 guard.json 并登记

按[guard.json 契约](references/report.md)在工作目录写 guard.json，然后运行：

```sh
sop-board distill submit
```

看板守护进程会核对 acceptance、逐条覆盖、测试文件与检出能力证据，浏览器层还要做断言保真检查，再按 retest 的规则实际运行一次命令。全部合格后才合并进 `<场景目录>/regression.yaml`。被拒时按输出修正后再提交。

## 6. 交回改动

测试文件与 regression.yaml 留作未提交改动，由开发者审核后提交；不要自行提交或推送。交回：改动清单、每条预期的覆盖、实际运行与检出能力结果、submit 输出。
