# 回归沉淀

测试保护已确认的业务预期；场景验收结论仍由真实入口执行与人工复核产生。按以下顺序完成，报告和运行证据放在产品仓库外。

## 1. 核对发起条件

读取指定场景的完整原文、来源规则、产品真实验证手册与本任务授权记录。逐条核对：

- `metadata.sources` 有实际确认人；或看板草稿已确认，且该场景对应的问题已回答。记录确认依据。
- 实现至少经真实入口通过一次，开发者自检或独立验收均可。读取原始通过证据，核对场景内容指纹、产品提交与内容摘要、执行者；与沉淀开始前的当前场景及产品内容一致。

缺确认人、没有通过证据或证据对应内容已变化时，停止该场景，说明需要确认预期或重新经真实入口执行，暂不写测试。独立验收尚未完成可以沉淀，报告明确写“独立验收未完成”。

## 2. 调查并选层

调查仓库现有测试框架、目录、夹具、启动命令与持续集成（CI）任务，记录哪些命令实际运行哪些测试。读 [分层选择](references/layers.md)，为每条 `expected`、`forbidden_effects` 中的业务断言选择成本最低且能观察该结果的一层，同一断言只覆盖一次；列出仍需真实入口验收的部分。接口与数据库共同产生结果时，另读 [数据库接口测试](references/backend-db.md)。

## 3. 写测试与本机运行

沿用已有设施，断言取自场景原文及已确认规则。测试名或标签包含 `<批次>#<场景编号>`；框架不支持该字符时用标签，并在报告 `tag` 中保留原文。允许修改测试、夹具、测试启动脚本、最小 CI 配置及项目知识的测试引用，产品代码保持不变。

实际运行并保存原始输出及执行清单。逐个核对报告声明的测试名都出现在实际执行清单中且通过；零用例、跳过、缺环境或声明测试未被发现均记“未运行”，不能只凭退出码判通过。测试与预期不符时保留失败用例，停止扩写该场景，报告现象、预期依据与疑似原因，交调用方决定是否修改产品。

## 4. 核对检出能力

按业务风险选已知缺陷复现，或在独立临时副本中受控改错。保存被改规则、缺陷版本或副本差异、命令和输出，确认失败的是对应业务断言；编译、依赖、环境失败或任意非零退出都不算。只在临时副本改错，结束核对原工作区只含沉淀改动。尚未验证的如实记“未运行”及原因。

## 5. 报告与登记

按 [报告格式](references/report.md) 写完整 `regression.json`，覆盖每条原预期、每个声明测试、本机运行和 CI 证据。CI 缺运行编号或链接、对应提交、实际执行清单和原始输出时，只能记“已接入，未验证”或“未接入”；不得为补 CI 证据擅自提交或推送。

产品对应的看板工作区存在时运行：

```sh
sop-board distill submit <工作区> --report <仓库外目录>/regression.json
```

使用自定义数据目录时加 `--data <数据目录>`。没有看板时只留下报告。登记失败保留报告、输出与未登记原因，不能把登记失败改写成成功。登记仅记录测试关联，不提交场景执行轮次。

## 6. 交回改动

改动留在工作区，由调用方审核后提交。交回改动清单、逐项覆盖与未覆盖范围、实际运行及检出能力结果、独立验收和 CI 状态、报告及原始输出位置、关联登记结果。开发者之后提交测试时，将报告中对应测试的 `commit` 改为真实提交，再次登记；看板按提交中的文件摘要核对并更新关联。
