# 合并测试用例（工作 #$work）

要合并的收件箱条目：$inbox。原文在 $directory/inbox/，测试同学的问答在 answers.json，合并前的场景摘要在 before.json。

场景目录：$scenarios。场景文件和用例文件都在仓库里，直接编辑它们，改动留给开发者审核提交。看板不保存场景版本，也不会回写这些文件。

## 怎样合并

1. 先读现有场景文件与场景写法（https://github.com/AdolphKevin/sop-board/blob/main/docs/sop-guide.md）。
2. 判断每条用例：
   - 是一个完整的业务流程，就生成或更新场景，四要素来自用例的前置条件、步骤与预期；
   - 只是一个细节预期，就把它并进所属流程场景的 expected，带上用例编号。
   场景的 refs 写上用例编号与收件箱来源（如 `inbox:3 TC_REFUND_001`）。
   - 用例改变了其他已有场景的预期（业务交叉，例如改价用例改变了退款金额的预期），同样修改那些场景的四要素；内容一变它们就回到未执行。
3. 用例与现有场景冲突、或缺业务信息时，不要猜：
   - 能问使用者的，在对话中直接问；
   - 需要测试同学回答的，运行 `sop-board ask --about inbox:<编号>（或 <文件>#<场景编号>） --text "<问题>"`，结束本轮，等答复后再合并。
4. 场景文件的 metadata.sources 记录依据与确认人：使用者在对话中确认的写本机操作者（$operator）；测试同学答复的写答复人。不要询问确认人是谁。
5. 不删除用例原有的断言，不放宽预期，也不按代码现状改写预期。

## 提交

运行 `sop-board merge submit`。它会校验全部场景文件，有问题时列出文件、字段与行号，修正后再提交。通过后输出新增、移除、改动的场景编号，以及角色或入口的变化，并把收件箱条目标为已合并。把这份差异转述给使用者，其中因业务交叉而修改的场景单独说明理由。不要提交 git。
