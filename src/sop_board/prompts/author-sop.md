# 编写业务 SOP（工作 #$work）

资料副本在 $directory/sources/（清单与摘要见 sources.json）。把 SOP 写成场景目录 $target 下的一个 Markdown 文件，然后运行 `sop-board sop submit --file <该文件>`。

## 依据

业务 SOP 的结果只来自业务资料，以及使用者针对当前问题给出的答复。技术方案和代码只用来确定角色、入口、字段与状态名，技术实现细节不转成业务要求。资料之间、或资料与代码矛盾时，保留双方原文并提问；资料没写明的结果同样列为待确认，不按当前实现补答案。

## 结构

正文用这六个二级标题：$headings。

| 部分 | 写清什么 |
| --- | --- |
| 业务目标与范围 | 要完成的业务结果、开始与结束边界、包含与不包含的事项 |
| 角色 | 谁提出、谁处理、谁确认，分别从哪个入口参与 |
| 业务规则 | 每条规则一个 `### R<编号> <标题>` 小节，写条件、操作、结果，附来源资料编号与原文摘录 |
| 流程图 | mermaid 代码块表达主流程与条件分支 |
| 禁止的副作用 | 资料明确禁止发生的业务结果；没有依据时先提问，不自创限制 |
| 未覆盖范围 | 不属于本次需求、缺资料或仍需人工确认的业务范围及原因 |

## 提问

遇到矛盾或空缺，在对话中直接问使用者一个具体的业务决定，同时引用相关原文，不预设答案。例如 PRD 写“7 天内可申请退款”，技术方案写“15 天”，就问“签收后多长时间内可以申请退款？”。得到答复后，把确定的口径写回规则和流程图；明确暂不纳入的写进未覆盖范围并写明原因。

只问业务内容，不要问“确认人是谁”：登记时自动以本机操作者署名。只有使用者明确说是别人确认的，才加 `--as <姓名>`。

## 登记

正文用确定的业务表述，去掉“待确认”一类的过程措辞；仍有未答的问题时继续提问，先不提交。确认记录由 `sop submit` 追加在文末，正文里不要自己写。
