# 为工作区搭建 SOP 看板

这份指引随 sop-board 发行。Codex 与 Claude Code 使用相同的指引，在开发者自己打开的会话里完成搭建；不要自行登录账号或读取、记录凭证值。

## 1. 安装并确认范围

运行 `uv tool install <看板的本地检出路径或发行来源>`，然后运行 `sop-board guide`，以已安装版本输出的指引为准。
确认需求涉及哪些仓库、它们共同的工作区目录。单仓工作区可以是仓库根目录；跨仓工作区应覆盖全部依赖仓库。检查语言工作区文件、启动配置及本地依赖，不能只以当前会话目录推断范围。范围不清楚时当场询问开发者。

启动命令为 `sop-board [工作区目录]`，缺省当前目录；`--lan` 开放内网，`--port` 指定看板端口。数据默认放在 `~/.sop-board/<工作区名>/`，同名工作区已登记为另一目录时，名称追加规范化绝对路径的 SHA-256 前八位。`--data <绝对目录>` 可显式指定独立数据目录，不能放在仓库内。旧版数据目录不能读取，也不迁移。

代理只在看板数据目录写配置、适配与搭建报告，通常是 `~/.sop-board/<工作区名>/`；不向产品仓库写搭建文件。不要生成单元、接口或集成测试。使用开发者已有登录状态，不改凭证。

## 2. 查清实际环境

从仓库、启动配置、IDE 启动项、文档和开发者说明查清服务及依赖：启动顺序、语言环境、工作区设置、生成代码、数据库、缓存、消息队列、回调和固定隧道地址。用实际监听端口、进程与服务响应交叉核对，文档可能过时。
核对各服务互相引用的地址、端口和数据库名是否一致；发现矛盾向开发者说明事实与依据，不猜测后直接改产品配置。
凭证只写所在位置与所需环境变量名，不把值写入配置、日志或报告。需要用户交互式登录时请用户操作真实浏览器。

## 3. 写 config.yaml

文件位于看板数据目录；以下仅为字段形状示例，路径、端口与命令须依据实际工作区填写：

```yaml
repos:
  app: .
scenarios: docs/sop
entries:
  api:
    surface: http
    operate: "通过实际运行的接口执行场景"
    observe: ["响应", "持久化数据"]
    evidence: ["请求与响应", "数据查询结果"]
    isolation: "使用本轮隔离的数据，结束后清理"
    driver: verify-backend-sop-db
adapter:
  prepare: [python3, prepare.py]
  env: [python3, env.py]
  ports: [8000]
  ready_timeout: 180
```

- `repos`：别名到相对工作区的 Git 仓库根路径。别名以小写字母开头，只含小写字母、数字、连字符；不能越出工作区或重复指向同一仓库。每个仓库须有 origin；看板从它规范化得到展示身份，不手填仓库身份。
- `scenarios`：相对工作区的场景目录，必须位于一个已声明仓库内，不能等于仓库根目录。文件名为 `<批次>.yaml`；文件的 `metadata.batch` 与文件名一致。`metadata.repos` 可列出本需求涉及的仓库别名，省略表示全部仓库。
- `entries`：名称到真实验收入口。必填 `surface`、`operate`、`observe`（数组）、`evidence`（数组）、`isolation`；可选 `address_env` 和 `driver`。`address_env` 指明提供入口地址的环境变量；可从启动看板的环境或 prepare 的输出传入。不要把密钥放在操作说明或地址里。
- `driver`：技能目录名，不能是路径。缺省 web 使用 playwright-acceptance，http/db 使用 verify-backend-sop-db，agent 使用 build-scenario-validation-loop；cli 使用命令行入口。其他 surface 须显式声明技能。技能默认在 `~/.agents/skills/`，可用 `SOP_BOARD_SKILLS_DIR` 指定目录。
- `adapter`：仅含 `prepare`、`env`、`ports`、`ready_timeout`。`prepare` 可省略，`env` 必填，均为非空命令数组，不经 shell。命令工作目录及参数中的相对路径均相对看板数据目录；需要管道等操作时把逻辑写在适配脚本内。
- `ports`：环境使用的 TCP 端口数组，可为空，不能重复。`ready_timeout` 为正整数秒数，缺省 180。

配置不接受重复字段、YAML 锚点或格式外字段。配置或命令脚本变更后重新自检，不能继续沿用旧的通过结果。

## 4. 适配契约

| 命令 | 输入 | 要求 |
| --- | --- | --- |
| `adapter.prepare`（可选） | `SOP_REPO_<别名>` 是本次各仓库 worktree；`SOP_BASE_<别名>` 是对应基线目录 | 使 worktree 可以编译、启动，例如复制被忽略的本机配置、生成代码、写语言工作区文件。最后一个非空标准输出行必须是 JSON `{"env": {...}}`，值均为文字；看板把这些额外环境变量传给修复会话与 adapter.env，不把它们存进报告。不能覆盖看板的 SOP_REPO、SOP_BASE、SOP_ENV_LOG_DIR 输入变量。 |
| `adapter.env` | `SOP_REPO_<别名>` 是本次使用的基线或修复目录；`SOP_ENV_LOG_DIR` 是环境日志目录 | 按正确顺序启动整套服务并保持前台；所有服务就绪后，标准输出打印并立即刷新一整行 `sop-board: ready`。失败以非零退出并说明原因。 |

变量后缀把别名转为大写，连字符改成下划线，例如 `service-a` 对应 `SOP_REPO_SERVICE_A`。

看板以独立进程组运行环境，同一用户本机只保留一套。基线与修复目录轮流使用相同端口和地址，因此固定隧道地址也无需改变。不要在脚本里脱离进程组或以后台守护进程逃离管理；脚本应处理终止并等待其子进程退出。停止先发 SIGTERM，十秒后仍存活则发 SIGKILL。
环境标准输出和错误输出记录在数据目录 `env/<序号>.log`，服务自己的附加日志写入 `SOP_ENV_LOG_DIR`。适配日志、配置及搭建报告仅在本机查看，不在普通场景证据中复制凭证或私有配置。

依赖安装、各语言工作区、复制被忽略的配置、生成代码及等待数据库/队列等工作属于适配；看板不内置这些项目知识。工作区已有准备或启动工具时，适配直接调用。临时复制的配置随看板工作树清理，不在看板数据中另存副本。

## 5. 自检五步

运行 `sop-board check <工作区目录> [--data <数据目录>]`，逐项核对：

1. 配置格式、仓库路径和已提交的基线；
2. 声明端口未被其他进程占用，失败时列出端口和进程；
3. 用基线目录启动环境，在时限内就绪后停止；
4. 为每个仓库建立临时 worktree，调用 prepare，再启动这套目录的环境，等到就绪后停止并清理 worktree；
5. 入口驱动技能存在。

每步输出结果与日志位置，完整报告保存在 `checks/<时间>.json`。全部通过退出 0，否则退出 1；失败后修正事实问题并重新自检，不能伪造就绪行、删除步骤或用单元测试冒充业务验证。

## 6. 报告并启动

向开发者报告三部分：已验证的事实（附命令和日志位置）、推断及依据、待回答的问题。报告只写凭证位置，不写值。开发者确认后启动 `sop-board <工作区目录>`；需要内网同事参与时加 `--lan`。
配置有效、最近自检通过且配置未变时，看板自动启动基线环境；否则页面显示尚未搭建或未通过自检，执行与修复停用。本机页面可自检、重启环境并看最近 50 行日志；内网页面不显示日志和开发者操作。

产品或运行方式变化后按本指引更新适配。产品改动未提交时执行等待提交；涉及仓库提交号与运行环境不一致时，看板先重启环境，再由新会话经真实入口执行场景。只以实际场景结果验收，不新增测试。
