# 为工作区搭建 Flow Board

这份指引随 Flow Board 发行，命令名为 `sop-board`。Codex 与 Claude Code 使用相同的指引，在开发者自己打开的会话里完成搭建。业务验收以 [docs/standard.md](https://github.com/AdolphKevin/sop-board/blob/main/docs/standard.md) 为统一正文，场景写法与四份记录模板从该页进入；账号按其“测试账号与授权”一节处理，凭据仅经环境变量传递。

## 1. 安装、登记并进入搭建目录

安装包后运行 `sop-board skills install`，将随包的 `sop-board`、`regression-distill` 和 `playwright-acceptance` 链接到当前 HOME 下的 `~/.agents/skills/`（Codex）与 `~/.claude/skills/`（Claude Code）。命令输出实际解析路径和包版本，重复安装或升级后运行会更新本包链接；遇到其他来源的同名目录或链接时列出来源并跳过，留给使用者处理。开发会话要求把已确认场景沉淀为低成本回归测试时，使用 `regression-distill`；场景执行与修复会话仍按各自范围工作。

询问开发者工作区名称和全部 Git 仓库目录。仓库可以分散在任何位置，无需共同的外层目录；可先从语言工作区文件、启动配置和本地依赖中列出候选目录，请开发者确认完整范围。名称以字母或数字开头，只含字母、数字、点、下划线和连字符，最长 64 字符。

运行 `uv tool install <看板的本地检出路径或发行来源>`，然后完整读取 `sop-board guide`，以安装版本为准。运行 `sop-board init <名称> <仓库目录>... [--data <目录>]` 登记。init 会逐个核对工作树根目录与 origin，任一不符都不会创建数据目录；核对全部通过后输出数据目录、各仓别名与身份，以及继续搭建的命令。

数据缺省放在 `~/.sop-board/<名称>/`，`--data` 可指定其他目录，但不能位于任何已声明仓库内，且 init 不覆盖已有目录。当前会话不能写数据目录时，请开发者使用 init 打印的命令新开会话继续：

```sh
codex -C <数据目录> "按 sop-board guide 继续为工作区 <名称> 搭建"
```

安装与 init 需要目标目录写权限。先核对本次授权和目录范围；已有权限时直接完成，缺权限时请开发者在可写环境执行或按客户端方式授予目录权限。Codex 可用 `--add-dir <数据目录>`，也可用上面的命令从数据目录开始；Claude Code 使用 `/add-dir <数据目录>`。涉及 Git 工作树写入的 check 由使用者在沙箱外运行，开发会话读取最近结果。

Codex 缺省只能写启动目录；配置与适配的搭建会话以数据目录为工作目录，只读产品源码。Claude Code 在当前会话执行 `/add-dir <数据目录>` 后继续。第 2、5 步所需的真实验证手册在具备该产品仓库写权限的会话中编写或补齐；仅能写数据目录时，先把手册草稿与缺项交给产品仓库会话完成，再继续核对引用。配置、适配、技能和报告仍写数据目录。

旧版登记或数据库不读取、不迁移，使用 init 新建工作区。开发者指出旧数据目录时，可阅读其中的适配脚本；经开发者确认后，在新数据目录重写。旧库的用例与轮次不带入。

确认登记文件中的名称和仓库清单正确后继续。配置、适配、验证技能和搭建报告写入数据目录，真实验证手册写入产品仓库；产品源码与凭据保持原样，搭建按场景核对。

## 2. 查清实际环境

从仓库、启动配置、IDE 启动项、文档和开发者说明查清服务及依赖：启动顺序、语言环境、工作区设置、生成代码、数据库、缓存、消息队列、回调及固定入口地址。用实际监听端口、进程和服务响应交叉核对，文档可能过时。
核对各服务互相引用的地址、端口和数据库名是否一致；发现矛盾向开发者说明事实与依据，不猜测后直接改产品配置。
按 [docs/standard.md 第 2 节](https://github.com/AdolphKevin/sop-board/blob/main/docs/standard.md#2-为项目设计验收方式)调查项目事实、列业务保证、选择入口与观察点，把事实及来源写入产品仓库的真实验证手册。已有手册在原文补齐；多仓共用负责联合验证仓库的一份手册。手册至少覆盖标准第 3 节的环境与依赖、干净环境和连续重跑、失败证据、隔离清理、CI 留证、维护与账号类别。入口缺口记录受阻范围、建设任务和负责人，开发与测试分别确认。
凭据只写所需环境变量名和获取方式。真实账号由用户在真实浏览器登录；本地隔离测试账号按标准在任务开始时取得一次授权，将环境、账号和操作范围保存在本机任务记录中，同一任务的开发和执行会话沿用。账号声明本身不是授权。

## 3. 与开发者确认 worktree 的正确建法

写适配前，先查明并与开发者确认：仓库是否已有建立或删除工作树的脚本及说明；团队共用什么工具；开发者平时怎样建立、切换和删除工作树；被 Git 忽略的本机配置、语言工作区文件及生成代码怎样带过去。确认要使用的命令、目录安排、依赖工具及清理方式，再写适配，不能只因为 Git 提供 worktree add 就假定它能完成搭建。

有仓库脚本或团队工具时直接调用。仅安装在个人机器上的工具或个人技能也可以使用，但须在搭建报告列明；团队共用适配之前，每位成员都必须具备这些依赖。若开发者已明确确认只需普通 Git 工作树，则省略 worktree 和 cleanup 命令，由看板执行默认 Git 操作。

## 4. 写 config.yaml

配置位于看板数据目录，只保存本机绑定。入口的操作、账号、观察、证据、隔离与清理正文放在产品仓库手册，`entries` 必填说明写简短引用；引用章节的例子见 [docs/standard.md](https://github.com/AdolphKevin/sop-board/blob/main/docs/standard.md#手册配置与验证技能的分工)。以下仅示意字段形状，路径、端口和命令依据实际工作区及已确认的方法填写：

```yaml
repos:
  app: /absolute/path/to/app
  lib: /another/location/lib
scenarios: {repo: app, path: docs/sop}
skill: project-verification
entries:
  api:
    surface: http
    operate: "按 app 仓库 docs/operations/verification.md 第 2 节 api 入口操作"
    observe: ["按同手册第 3 节核对响应、数据和禁止副作用"]
    evidence: ["按同手册第 3 节保存原始输出和数据查询"]
    isolation: "按同手册第 4 节准备隔离数据、留证后清理"
    address_env: APP_URL
adapter:
  worktree: [python3, worktree.py]
  cleanup: [python3, cleanup.py]
  env: [python3, env.py]
  ports: [8000]
  ready_timeout: 180
```

- `repos`：别名到 Git 工作树根目录的绝对路径，也可用 `~/` 开头。init 根据目录名生成别名：转小写、非法字符变连字符并合并，首字符不是字母则加 `r-`，重名依次加 `-2`、`-3`。不能重复指向同一目录。仓库须有可规范化的 origin，看板据此显示身份。
- `scenarios`：仅含 repo、path。repo 是已声明别名；path 是该仓内不含 `..` 的相对目录，不能等于仓库根目录。文件为 `<批次>.yaml`，metadata.batch 与文件名一致；metadata.repos 指定涉及仓库，省略时为全部。来源 metadata.sources[].ref 中的路径相对场景所在仓库；`<别名>:<仓内路径>` 可引用其他已声明仓库。批次、版本及问题记录的路径显示为 `<别名>:<仓内路径>`。
- `snapshot_exclude`：可选的仓库别名到仓内相对路径数组，例如 `{app: [docs/test-cases/]}`。默认 `{}`，只额外排除明确声明的文件或目录；目录包含全部后代，按完整路径匹配，不支持通配符。路径不能为空、为绝对路径、含 `..`、指向仓外或等于仓库根目录，仓库别名必须已登记。与场景目录一样，同时从已提交内容和工作区内容（含未跟踪、修改、删除）中排除；相似前缀路径及其他仓库不受影响。只声明不参与产品运行的材料，运行配置、代码及影响业务行为的文档应继续计入快照。
- `skill`：必填技能目录名，指向数据目录 `skills/<skill>/SKILL.md`；写法见下一步。
- `entries`：surface、operate、isolation 必填非空文字，observe、evidence 必填非空文字数组，可选 address_env、credential_env、driver 和 web_evidence。说明字段引用手册也须填齐；账号和授权记录的位置写在手册及技能中。address_env 指明地址环境变量；看板入口从启动环境或工作树适配返回的 env 取得，会话入口从会话自身环境取得。配置只写变量名。
- `entries.<入口>.web_evidence`：仅用于 `surface: web`，可选对象，内含 `video`（录屏）与 `trace`（操作轨迹）布尔开关；每项省略时为 `true`，`false` 时模板不启动该录制，也不要求该附件。`evidence` 继续是非空文字数组，用来声明截图、只读查询等业务证据。任务的 `entries.json` 保留声明，`scope.json.web_evidence` 按场景编号固定补齐默认值后的开关；执行、会话执行及修复复验共用。转换和提交仍要求实际 pass/fail 至少一份真实证据，不按扩展名强制录屏或 trace；声明中的具体业务证据由执行者和复核者逐项核对。
- `credential_env`：可选、不重复的环境变量名数组，如 `[DEMO_BUYER_PASSWORD]`。名称以字母或下划线开头，后续只含字母、数字、下划线。看板调度的执行、修复和复测会话只从看板启动环境取得这些取值；开发会话入口从会话自身环境取得，工作树适配不能替换它们。使用按本任务授权记录；配置、脚本、任务材料、提示词、日志与报告只记变量名，内网页面与接口不显示变量名。缺变量时只把涉及该入口的场景记为受阻，finding 写缺失名称；地址变量同时被列为凭据时也只经环境传递。
- `driver`：可选辅助技能目录名。Web 入口未声明 driver 或声明 `playwright-acceptance` 时，使用随 sop-board 包发行的 Web 技能（`sop-board playwright guide` 查看），SOP_BOARD_SKILLS_DIR 中存在同名技能时可覆盖。其他声明的 driver 先找数据目录 `skills/<driver>/SKILL.md`，再找 SOP_BOARD_SKILLS_DIR（缺省 `~/.agents/skills/`）；都没有则配置不合格。除 Web 外不按 surface 自动选择技能，未声明的入口只遵循项目验证技能。skill 与 driver 名只含字母、数字、下划线、点、连字符，不能为 `.` 或 `..`。
- `adapter`：仅含 worktree、cleanup、env、ports、ready_timeout。worktree 和 cleanup 各自可省略，env 必填；声明的命令均为非空数组，不经 shell。命令的工作目录及参数中的相对路径相对数据目录；管道等逻辑写入适配脚本。
- `ports`：不重复的 TCP 端口数组，写入环境中所有服务监听的端口，包括服务之间互相调用的端口；没有监听服务时可为空。共享的外部基础设施端口（如开发库、缓存）不写入，在搭建报告“外部工具与外部依赖”一节说明。ready_timeout 是正整数秒数，缺省 180；建立和清理命令也须在此时限内结束。

例如某工作区仅保存截图和一条关键只读查询，并把用例原文排除出产品快照，可在现有配置中合并以下片段（`app` 和 `web` 替换为现有仓库别名、入口名，保留其他字段）：

```yaml
snapshot_exclude:
  app: [docs/test-cases/]
entries:
  web:
    surface: web
    evidence: ["每条场景保存截图", "每条场景保存一条关键只读查询及其结果"]
    web_evidence: {video: false, trace: false}
```

配置变更后须重新自检并重新准备任务；已准备任务保留原配置摘要，不能用新规则提交旧任务。产品快照中的提交号仍原样记录；会话执行按内容摘要判定有效性，看板运行中的提交号保护沿用原规则。场景原文、用例并集和配置仍单独核对，排除产品摘要不绕过这些校验。

配置拒绝重复字段、锚点、显式标签及格式外字段。配置或数据目录中的命令脚本变化后须重新自检。

## 5. 编写项目验证技能

先按 [docs/standard.md](https://github.com/AdolphKevin/sop-board/blob/main/docs/standard.md)第 2、3 节完成或补齐产品仓库的真实验证手册，并记录开发与测试的独立确认及未决事项；可从[项目验收方案模板](https://github.com/AdolphKevin/sop-board/blob/main/docs/templates/project-verification.md)开始。在数据目录 `skills/<skill>/SKILL.md` 编写读取该手册的项目技能；开发会话与看板执行会话共同遵循手册。以 YAML 文件头开始，name、description 均为非空文字：

```markdown
---
name: project-verification
description: 通过本项目实际入口执行场景并保存结果证据。
---

执行前先读取 app 仓库的 docs/operations/verification.md 与其中指定的本任务授权记录。

## api 入口

按手册第 2 节操作、第 3 节核对与留证、第 4 节隔离与清理。
本机地址取 APP_URL；本次仓库目录按任务提供的路径确定。
```

每个声明入口都有一个含入口名的 `## ` 二级标题，逐项指向手册对应章节，并说明本机参数的取得方法：

- 操作章节，以及工具、地址环境变量和本次仓库路径的绑定。
- 账号章节与本任务授权记录的位置，读取记录后按已确认范围操作。
- 观察与留证章节，覆盖页面、响应、数据及禁止副作用。
- 隔离、清理、前置条件与易错点所在章节。

完整操作正文保留在产品手册，技能只引用章节。技能可引用自身目录内的辅助脚本，技能目录内不允许符号链接。自检前逐入口核对手册路径、章节和本机绑定齐全；搭建报告单列手册位置、确认状态、授权记录位置与技能摘要，请开发者确认。

执行和独立复测先读取该项目技能，随后读取技能引用的产品仓库手册和本任务授权记录；入口声明辅助技能时再按任务 entries.json 的绝对路径读取。按任务提供的仓库路径找到对应版本的手册，修复复测使用修复工作树中的手册。看板执行会话只读产品仓库；看板修复会话只对已核对的修复工作树增加写入范围。开发会话必须能写其任务所在的数据目录，执行时产品代码仍只读；会话修复只写准备材料列出的当前产品仓库，并保留原有改动。

快照记录技能目录全部普通文件的相对路径与内容摘要；执行或复测期间变化则本轮作废，原因含“验证技能变化”，不登记结果。技能内容变化不使已有结果失效，也不要求重新自检；报告逐轮记录摘要前 12 位。文件头、入口标题等若不再合格，工作区仍会变为“尚未搭建”。

## 6. 适配契约

| 命令 | 输入 | 要求 |
| --- | --- | --- |
| `adapter.worktree`（可选） | SOP_TASK_DIR 为任务目录，SOP_FIX_BRANCH 为分支名，SOP_REPOS 为逗号分隔的仓库别名，SOP_BASE_<别名> 为各基线目录 | 按确认的方式建立工作树并使其可编译、启动。最后一个非空标准输出行是 `{"repos": {"别名": "路径"}, "env": {"变量名": "文字值"}}`；repos 恰好包含全部涉及仓库，env 可为空。未声明时在任务目录 repos/<别名> 用 git worktree add 建立。 |
| `adapter.cleanup`（可选） | 与 worktree 相同，另有 SOP_WORKTREES，内容为别名到已核对路径的 JSON | 删除这些工作树及其工具登记，退出 0 表示命令成功；看板还会核对目录和 Git 工作树登记是否消失。未声明时用 git worktree remove。合入后的修复分支由看板在清理成功后删除。 |
| `adapter.env` | SOP_REPO_<别名> 为本次使用的仓库目录，SOP_ENV_LOG_DIR 为日志目录 | 启动整套服务并保持前台；所有服务就绪后输出并立即刷新完整一行 `sop-board: ready`。失败以非零退出并说明原因。基线与修复目录使用相同端口及地址。 |

别名转大写、连字符改为下划线作为变量后缀，例如 service-a 对应 SOP_BASE_SERVICE_A 和 SOP_REPO_SERVICE_A。工作树命令只收到本任务涉及仓库的基线变量；env 启动时收到修复工作树及其他仓库基线组成的完整映射。

返回绝对路径最明确；相对路径按命令工作目录（数据目录）解析并规范化。工作树不必放在默认 repos/ 下，但必须是工作树根目录、与对应基线的 git common dir 相同，并检出 SOP_FIX_BRANCH。不能返回基线本身，不能覆盖任务目录、看板数据目录或任务的 evidence、sop、attempts、interruptions、validations 证据目录。任一不符即建立失败，不使用该环境。

看板沉淀使用同一适配，`SOP_FIX_BRANCH` 传入 `sop-board/distill/<编号>`，另有 `SOP_BASE_COMMITS` JSON（别名到固定提交）；建立脚本须从指定提交检出，重复调用复用原路径与分支。默认 Git 方式直接使用指定提交。清理脚本只删除传入且已核对的工作树；沉淀分支保留给开发者处理尚未合入的提交。

env 的变量名和值须合法，不得覆盖上述看板输入变量。看板把它们传给修复会话和 adapter.env，仅在进程内保留，不写入日志或报告。基线启动不调用建立命令，adapter.env 应能直接使用基线目录。

同一进程内复用已建立的工作树及返回环境；任务范围增加或看板重启后，可能重新调用 worktree 取得环境。脚本应识别并复用同任务已有工作树，返回相同路径，不覆盖未完成的修复或移动分支。cleanup 应能安全重试；不能借清理改动基线。失败输出中的未核对路径不会交给删除命令，可能保留供开发者检查。

自检使用独立任务目录和临时命名分支。依赖安装、复制被忽略配置、语言工作区、生成代码及服务顺序都由适配负责；已有工具可直接调用，看板不内置项目知识。复制的本机配置随工作树删除，不在数据目录另存凭据副本。

环境在独立进程组运行，同一用户按声明端口互斥；端口不重叠的工作区可同时运行。端口锁冲突时显示占用工作区，环境栏显示“等待端口 <端口>（工作区 <名称>）”，看板每 10 秒重试，取得锁后自动启动基线环境。共享基础设施的隔离仍由项目负责。停止先发 SIGTERM，十秒后仍存活则发 SIGKILL。脚本须管理并等待自己的子进程，不脱离进程组。环境日志为 env/<序号>.log；建立与清理日志位于 checks/ 或 worktree-logs/。适配日志、配置和搭建报告仅在本机查看，任务附件不会公开工作树或适配生成的其他本机文件。

## 7. 自检五步

由使用者在沙箱外、按已确认的环境与工作树操作范围运行 `sop-board check [名称] [--data <数据目录>]`：

1. 核对配置、仓库路径、已提交基线，以及每仓 Git 实际生效的 user.name 和 user.email（仓库级或全局均可）；缺失时指出仓库、字段和设置方法；
2. 获取与运行环境相同的端口锁，核对声明端口空闲，IPv4 与 IPv6 探测开启地址复用，忽略已关闭连接的 TIME_WAIT；绑定失败时列出监听进程；
3. 用基线目录启动环境，就绪后核对每个声明了 address_env 的入口，其变量在看板进程环境中非空，然后停止；
4. 通过 worktree 命令或默认 Git 方式建立临时工作树，核对路径、共同 Git 仓库及分支，用返回的目录和 env 启动环境；就绪后同样核对各入口地址变量，适配返回的 env 可提供变量；结束后通过 cleanup 或默认 Git 方式删除，再删除临时分支；
5. **验证技能**：核对项目技能文件、YAML 文件头、各入口二级标题、目录内没有符号链接，以及声明的辅助技能存在；消息列出项目技能绝对路径、每个入口及其辅助技能。

每步记录结果与日志位置，报告为 checks/<时间>.json。全部通过退出 0，否则退出 1。自检还逐个列出声明凭据变量“已设置／未设置”，只显示名称；缺凭据不使其他入口停用，执行时按涉及场景记受阻，变量名格式不合格则配置检查失败。不能伪造就绪行、删步骤或用测试代替业务验证；失败后先查明原因及残留工作树，再修正适配。

因权限拒绝、命令在当前环境不可用、检查器正被其他操作占用或主动中断等原因不能完成时，报告“自检未能在当前环境运行”及原因，提示在沙箱外重试，退出 1。这类尝试标为 completed=false，单独保存到 checks/unavailable/，不替换已完成的自检结论，也不因这次尝试作废进行中的任务。配置仍未变化且原有有效通过记录存在时继续适用；没有有效通过记录不会因此放行。已实际核对出端口占用、在规定时间内未就绪、配置/Git 身份/技能/地址声明或适配返回契约不合格时，仍保存未通过的正式结果。历史报告和已作废任务不自动改写或复活。

## 8. 配置 Jira 读取

先问开发者：“团队的缺陷链接是否使用 Jira Cloud（`*.atlassian.net`）？”不使用时跳过本步骤；缺陷链接仍按非空原文保存，不要求 Jira 变量才能完成搭建或通过五步自检。

使用 Jira Cloud 时，说明需要以下两个环境变量：

- `JIRA_EMAIL`：开发者的 Atlassian 账号邮箱。
- `JIRA_API_TOKEN`：该账号的 API token，由开发者自行在 [Atlassian 账号安全设置页](https://id.atlassian.com/manage-profile/security/api-tokens) 创建；创建方式见 [Atlassian 官方说明](https://support.atlassian.com/atlassian-account/docs/manage-api-tokens-for-your-atlassian-account/)。

请开发者自己在**启动 sop-board 的环境**中设置，例如自己的 shell 配置或密钥管理工具。代理不索取这两个值，不请开发者粘贴到对话，不读取、写入或回显值，也不代为操作账号。凭据值不得出现在数据目录、适配、技能、日志或搭建报告中。

代理只在准备启动看板的同一环境按变量名检查是否非空，只输出名称和状态。例如在未开启命令跟踪回显的 shell 中：

```sh
if [ -n "${JIRA_EMAIL:-}" ]; then echo 'JIRA_EMAIL：已设置'; else echo 'JIRA_EMAIL：未设置'; fi
if [ -n "${JIRA_API_TOKEN:-}" ]; then echo 'JIRA_API_TOKEN：已设置'; else echo 'JIRA_API_TOKEN：未设置'; fi
```

不要打印环境变量列表或读取开发者的 shell 配置来查找值。两个变量均非空时，本机环境栏显示“Jira 读取：已配置”，否则显示“Jira 读取：未配置”；内网页面及环境接口不显示这项配置状态。“已配置”只说明变量已设置，不能当作单据读取成功。

按下一步启动看板后，请开发者提供一张真实测试单据的**链接**，通过本机 `GET /api/v1/jira/summary?url=<编码后的链接>` 读取。只请求本机摘要接口，由看板使用启动时的变量访问链接对应的 Jira 站点。搭建报告只写返回的单据标题与状态，或失败原因；不记录认证值或打印完整进程环境。未能读取时如实报告，不妨碍缺陷原文保存。

## 9. 报告并启动

必须使用以下模板，将完整报告写入数据目录的 `setup-report.md`，并在会话最终回复中给出相同内容。七个二级标题按此顺序保留；某一节没有内容时写“无”。推断不能写成已验证事实。凭据只写位置与变量名，不写值。

```markdown
## 已验证的事实
逐条列出已验证事实，附执行命令或日志位置。

## 推断及依据
列出尚未验证的假设与依据。

## 待回答的问题
列出尚需开发者或同事确认的问题。

## 工作树建立与清理方式
记录确认采用的建立、清理方法，以及本机配置和生成文件的处理。

## 外部工具与外部依赖
逐项注明来源：仓库内、团队共用或仅本机；说明共享基础设施及隔离方式。
团队成员共用适配前须各自具备这些依赖。

## 验证技能摘要
列出产品手册路径、章节、独立确认状态及本任务授权记录位置，概述技能的本机绑定，请开发者确认。

## Jira 读取
说明是否使用 Jira、所需变量是否已设置；启动后补充单据标题与状态或失败原因。
未执行读取时如实说明，不记录凭据值。
```

开发者确认后运行 `sop-board [名称]`，需要内网同事参与时加 --lan。自检通过且配置未变时自动启动基线环境，否则执行和修复停用。本机页面可自检、重启并看最近 50 行日志，内网页面不显示日志及开发者操作。

省略名称且未给 --data 时，根据当前目录所在 Git 仓库查找 `~/.sop-board/*/config.yaml` 的 repos：唯一匹配时使用，没有则提示 init；多个则列名称请开发者指定。--data 始终读取其中 workspace.json 的登记名称。

运行方式变化后按同一指引更新适配和项目验证技能。看板执行在产品改动未提交时等待；涉及仓库提交与环境不同则先重启，再由新会话经真实入口执行。验收只看实际场景结果，场景执行与修复会话不新增测试。用户另行授权回归建设时使用 regression-distill，报告和证据保存在仓库外；有对应看板工作区时用 `sop-board distill submit <名称> --report <regression.json> [--data <目录>]` 登记，测试改动留给开发者审核提交。

开发会话入口使用已登记的工作区；编写 SOP、生成草稿、合并只需配置合格，执行与修复还须当前自检通过。先运行 `sop-board status [名称] --json [--data <目录>]`，报告待处理事项；省略名称和数据目录时按当前产品仓库查找，找不到则回到本指引登记，不隐式新建。随包 `sop-board` 技能支持草稿生成与修订、用例合并、场景执行：prepare 返回任务目录及提示词，按其契约写出结果后 submit。看板可以不运行；正在运行的同类任务不能接管，排队任务经使用者同意后可用 `--replace-queued` 取消并认领。业务答复、排除理由与确认姓名由使用者提供。

已有业务 SOP 可用 `sop-board sop upload <名称> <批次> <文件> --uploaded-by <姓名> --confirmed-by <姓名> --session <标识>` 登记，新草稿任务由会话认领。已中断、放弃或作废的任务不复活；无关的排队/等待任务不阻挡会话准备，实际环境占用仍互斥。会话失败只提示处理，不自动交给看板；需要看板修复时，由开发者在本机修复页明确选择。Codex 沙箱中只读 status 的 setup_check 与最近报告，不运行 check；未通过时请使用者在沙箱外执行。确认人须当次明确指定，草稿确认后先取得是否继续合并的决定。

会话执行从任务目录 repos.json 读取仓库路径，使用自己的入口环境，结束前停止自己按手册启动的服务并在结果 note 列出名称、PID 或进程组及停止结果；允许未提交产品改动并保存内容摘要；准备后输入变化则作废，提交代码但内容相同不使结果失效。默认交给未参与实现的新会话，交接仅含任务目录、项目技能与手册、入口环境和授权记录位置。使用者要求当前实现会话执行时，`execute prepare --session` 与 `execute submit --implementer` 填相同身份，登记为自检；省略实现者则为未声明。原生会话编号无法取得时使用明确说明的稳定替代标签。会话修复用 fix prepare/submit，在当前工作区只改产品代码，不写测试、不提交；用 execute prepare --fix 派不同会话完整复验，开发者自行提交后用 fix land 核对内容并关闭。修复复验不接受实现者自检。编写业务 SOP 用 sop prepare --source 固定需求资料，逐项呈报后由 sop answer 记录使用者原话与姓名；更新正文、全部问题已答且当次给出确认人后 sop submit 登记，来源清单、摘要、答复与确认人在 SOP 页可查，后续草稿仍由该会话处理；完整参数见各命令 `--help` 和 docs/reference.md 的“开发会话入口”。

也可在本机场景页勾选满足资格的场景，点击“沉淀为回归测试”。发起前核对确认人及当前场景的最新 Agent 通过记录和证据；缺少时显示原因并整体拒绝。产品有未提交改动时可先入队“待提交”，列出路径；提交后若通过记录不匹配新产品，则转“待验证”并列出场景。待验证不自动安排执行，不受自动执行开关影响；开发者在本机任务页或场景页点击“执行这些场景”，只执行所列范围。它们在新产品上经实际执行或有效影响判定沿用通过后，沉淀自动开始。两个等待状态重启后保持，开始时保存新通过快照并保留入队快照。入队固定原文、来源、证据、各仓提交与摘要、配置及适配脚本、验证与沉淀技能版本，开始前和登记前再核对，变化则作废。

默认使用产品已有测试设施。需要看板服务时勾选相应选项，按修复复测方式切换工作树环境，结束、失败或取消后恢复基线。修复、执行、沉淀互斥，并按此顺序优先调度；浏览器沿用既有占用规则。项目技能须说明测试设施、真实验证手册和本任务授权记录位置。

新 Codex 会话在独立工作树按随包 regression-distill 执行，报告写任务目录，由看板结束时统一登记。任务页显示路径与改动；开发者自行审核提交后填写各仓完整提交号，点击“已处理”，看板按提交核对摘要后升级关联。放弃保留关联历史；两种处理均先展示尚未提交的改动，再确认清理。失败可再次清理且保留现场。重启将运行中的沉淀标为已中断，重试复用工作树并归档上次材料到 attempts/<序号>/；登记收据防止重复关联。内网只看状态、场景和时间，操作、报告与会话材料仅限本机。完整状态和接口见 docs/reference.md 的“入口二：本机看板调度”。

缺陷链接填写非空文字即可，按提交原文保存，不需要配置前缀。Jira 站点从符合规则的 HTTPS `*.atlassian.net/browse/<单号>` 链接取得；读取配置与启动后核对见第 8 步。合入后的目标状态可通过 `JIRA_FIXED_STATUS` 指定。

修复等待整个工作区的验证任务结束。人工不通过需由测试同事在批次总览或 SOP 场景页点击“复核完成，开始修复”；内网也可操作，使用身份栏的标记人。自动任务暂停或已有修复未结束时继续等待。建任务后不扩大问题范围，新失败留给下一任务。
