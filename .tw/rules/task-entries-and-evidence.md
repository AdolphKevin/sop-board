# 任务内核、两个入口与证据有效性

各类任务通过 task_types 的 inputs、prepare、launch、consume、actions 约定接入 kernel；调度顺序、互斥、进度、恢复与归档保持单一实现，业务模块保留自己的资格与登记。任务按任务/尝试保存收据，重试归档不覆盖已有材料。数据库格式保持 5，旧表不加列，新增记录通过新表维护。

看板调度与开发会话共用输入校验和业务登记。session_tasks 保存认领，看板不调度或恢复接管这些任务；只能认领未认领的排队任务，结束任务重新准备。会话准备只受同批次同类任务及实际产品环境占用/恢复阻挡，不继承其他看板排队依赖；会话处理中的会话修复与批次执行互不阻挡，修复复验仍与执行互斥。会话失败由使用者决定继续会话修复或本机交给看板，交接绑定具体失败结果。

Web 证据正文继续由入口 evidence 声明，web_evidence 仅控制录屏与 trace，缺省均开启；scope 按场景固定声明，模板与转换共用。产品摘要按仓库排除 snapshot_exclude 的明确路径，默认没有额外排除；场景、用例并集和配置仍各自核对。具体字段与配置示例维护在 docs/reference.md。

证据是否仍对应产品以内容摘要判断，提交本身不使通过记录失效。看板执行与沉淀仍等待产品提交；沉淀开始前内容相同可更新提交号，内容不匹配才待验证，等待不自动安排执行。运行中的场景、用例、业务配置与技能仍要复核；执行开始后的产品变化不作废，按准备时快照登记并列出变化路径，这些通过一直待判定；开始时未提交的文件连同内容摘要随轮次登记，下一轮把内容已不同的列入 changes.json 的 previous_uncommitted。会话执行允许未提交内容，并记录提交、改动清单、内容摘要及 dirty。

会话修复只改当前工作区产品代码，不写测试、不自行提交；复验必须由未参与修复的新会话完整执行。执行入口、执行者、实现者与独立性按真实关系记录，不能改标签制造独立验收。任务材料按类型白名单向内网投影，轮次业务身份不与任务级会话隐私混淆。

会话命令只在确实找不到登记工作区时附初始化指引，其他拒绝保留具体原因。编写业务 SOP 的公共规则随包提供并复制到任务目录，与 docs/sop-guide.md 对应规则同步；用普通 wheel 安装核对可读。原文答复时间与页面共用显示时区，原始答复记录不改写。最终正文与过程说明分开，确认信息由登记命令附加；业务提问和确认人询问不预设答案。看板未运行时报告已有位置，不为寻找链接额外运行命令。

命令、状态和字段的具体正文维护在 docs/reference.md；统一验收方法在 docs/verification.md。上述 guards 是业务场景索引，不是新增自动测试。

D88：前置数据先用登记配方，显式允许 adhoc 后才在声明环境与 scope 内临时写入；真实流程及 real_only 对象不能写库代替。准备记录在落盘前按配方与入口凭据声明脱敏，经任务与场景关联到结果，仅留痕、不提供预期。批次准备摘要进入后续任务；数据配方页及整理操作仅本机，内网结果只投影说明、参数与时间。

D89：web_evidence、atlas、fixtures 及配方文件是运行辅助配置，格式仍须合格，但不使已准备的执行与复验作废、不使全量自检失效。已准备任务冻结完整设置，新轮次采用新值；业务配置内容与适配脚本仍参与摘要。config-digests 只保存内容摘要映射，首次遇到未改配置时保留旧摘要兼容历史自检，排版不影响后续摘要。

D90：工作区清单对已检出子模块读取其自身 HEAD，未检出时读取外层索引 mode 160000 的提交，与已提交清单使用同一哈希方式；不能把向上发现的外层 HEAD 当作子模块提交。场景依据为 docs/sop/sop-board-16.yaml 的 SOP-161～163，SOP-168 执行侧完整验收在后续阶段。

D84：声明了 atlas 的 Web 入口可梳理交互地图（任务类型 atlas，看板与会话共用提示词、严格输出结构与登记）。地图只记录页面、导航、控件、各语言文案、定位器、打开对象、请求与源码位置；可见性、校验、默认值、业务结果属于场景预期，结构拒收。地图按版本存放在数据目录 atlas/<入口>/v<版本>/，不参与执行作废；按页面源码摘要与 JSON 多语言文件逐键摘要判断过期。执行者只写 atlas-feedback.jsonl 反馈，登记结果时收下，格式不合格的行只提示不影响登记；下一次梳理处理后标为已采纳。梳理只读源码、不占产品环境；--browser 只读核对时准备阶段核对没有运行中的执行与修复。内网只读查看地图，发起梳理仅限本机。场景依据为 docs/sop/sop-board-16.yaml 的 SOP-164。

D85：有地图后按批次对照界面（atlas 任务的 bind 模式，任务批次为该批次）：步骤对应页面与控件，加引号的文字逐条判 match/translation/mismatch/absent/data，登记时核对引号全覆盖、引用存在、match 文字确实存在。mismatch 与 absent 成为界面对照条目，按场景内容指纹登记，内容改变后条目以“场景已改”关闭。条目由人（本机或内网，须填姓名）决定：按 SOP 照常执行；改 SOP 的场景退出待执行范围，单列为 waiting-change，不算受阻、跳过或暂缓；未定按 SOP 判。场景依据为 docs/sop/sop-board-16.yaml 的 SOP-165。

D86：执行与单批次复验的任务目录另有 brief.md（不超过 5KB 的速查卡）、atlas.json（地图节选：绑定页面、到达路径、所用文案与全部页面索引）、bindings.json（绑定与对照决定）和 atlas-versions.json；提示词、速查卡与 Web 技能正文合计不超过 15KB，技能细则在 references/ 按需读取。轮次登记把准备时的地图版本写入 round_atlas，轮次接口返回 atlas；地图更新不作废在途轮次。

D87：Web 模板把业务断言失败标为预期失败（附失败截图与页面结构快照，关闭本场景新开的页面），worker 不重启、调试连接保留，后续场景继续；受阻、连接断开、目标页关闭仍为意外失败，由 maxFailures: 1 停止本轮。缺省上限为单场景 4 分钟、定位或操作 15 秒、导航 30 秒，可用环境变量覆盖并记入报告。progress-reporter.mjs 逐条重写 report.partial.json，中途退出时以 --allow-partial 转换。atlas.mjs 按地图打开页面、定位控件、等待请求，地图缺口抛出 AtlasGap 并写入反馈。场景依据为 docs/sop/sop-board-16.yaml 的 SOP-166、SOP-167。

D91～D95：agents 运行配置按任务类型选择 codex 或 claude；claude 经 claude_runner 调用 claude -p stream-json，事件转换为看板活动，--json-schema 结构化结果写 final.json，临时错误续接同一会话至多 3 次；缺省权限按沙箱分只读和可写两组，配置 args 时只用配置。执行计划按身份→首个页面→前置状态分组，只读在前，模式 pending/failed/regression，会话 execute prepare --plan 取第一轮。连续运行由看板主循环每 10 秒推进，跳过有待人处理事项的场景，内存不足或锁屏等待并写明原因，任务失败重试一次后暂停，同一问题挡住 run.stop_when_blocking 个场景时暂停，暂停均登记待人处理。待人处理事项须填姓名标记已处理；身份池按 24 小时与 1 小时计数，超出上限拒绝并登记待人处理。agents、run、entries.*.identities 都是运行配置，不作废在途轮次。

D96：执行期间只有部分所选场景的内容或用例变化时，只作废这些场景：不登记它们的结果，提交输出与任务结果列出 voided_scenarios，场景回到待执行；全部所选场景变化或验证技能变化时仍整轮作废。配置分两级：业务配置（仓库、场景目录、技能、snapshot_exclude、入口说明与凭据声明、adapter 的 mode 与启停命令）改动须重新自检；运行配置（入口 web_evidence、atlas、identities，顶层 fixtures、agents、run，adapter.health、adapter.heal 及地图、绑定、配方文件）不作废在途轮次。场景依据为 docs/sop/sop-board-18.yaml 的 SOP-181。

D97：adapter.mode: external 表示服务由使用者维护，看板不启停，只接受 mode、health、heal、ready_timeout。自检、看板每轮执行、会话执行与复验准备前都探测；未通过先执行已授权的 heal 再探测一次，仍未通过则登记环境待人处理（同一说明未处理前不重复）并拒绝开始，会话已认领的任务保留，恢复后同一 prepare 继续。探测与自愈输出不保存。此模式下看板修复、修复复测与需要服务的沉淀不运行（use_repair 拒绝，fix_start_reason 说明改用会话修复）；环境栏内网只显示探测项名称与是否通过，“重新探测”仅限本机。场景依据为 SOP-182。

D98：问题台账（issues、issue_scenarios、issue_fixes）按工作区编号，人只能设为 open、deferred、closed，其余状态按最近关联修复显示；执行结果行可带已存在的 issue 编号归并场景，界面对照按 SOP 判的不符或缺失条目自动登记产品问题；stop_when_blocking 计数时，结果行明确归入问题的按问题计，其余按受阻说明计，同一说明的场景全属同一未关闭问题时以该问题标注，场景另属别的问题不拆开同一原因的受阻；暂停后继续从下一轮开始，并标记本批次的暂停事项已处理。会话修复：其他会话的修复只阻止重叠场景；两个修复不能同时处于会话处理中（共用工作区，改动会混在一起），已提交、待验证的修复不再挡住新修复；fix prepare --issues 按问题认领并关联。fix land 没有专门复验时，接受修复输出登记之后、执行者与提交者都不是修复会话、非自检、技能摘要相同、准备时修复改动文件内容与现在一致的执行轮次，且全部产品问题场景最近结果为通过；再以最近一轮的文件清单（同执行轮次的排除规则）核对修复仓库全部内容，并要求已提交。场景依据为 SOP-183。

D99：默认业务确认人存于 settings（default_confirmer:<工作区>），由使用者经 sop-board confirmer 设置；会话命令的姓名参数省略时先用同一命令给出的其他姓名，再用默认值，都没有则拒绝，会话标识与 agent 名仍拒绝；看板网页表单仍逐次填写。cases upload 记录原文件路径（case_upload_sources），cases export 按某次上传的用例与顺序输出最新内容，--write-back 只在原文件自上传或上次回写后未改动、且不计入产品快照时写回，否则拒绝并给出 snapshot_exclude 写法。decisions 表登记人的原话与姓名，decision list 汇总会话决定、台账修改、界面对照决定与合并答复；批次页显示问题台账、决定记录与环境状态。prepare、submit 成功时列出其他会话认领的处理中、待验证、待提交任务。草稿与合并提示词要求把同一对象、角色、页面、条件下互相矛盾的预期作为问题交人决定。场景依据为 SOP-184。

D100：会话修复 fix land 只核对修复输出登记时记下的 changes：内容须与独立通过快照一致（否则 fix-content-changed）、须已提交（否则 fix-commit-required），两者都只列这些文件；其他文件的变化不挡住关闭，成功输出与尝试记录列出 other_changes（超过 100 条另记总数）。顶层 local_only（写法与校验同 snapshot_exclude，运行配置，不计入业务配置摘要）声明本机专用、永不提交的文件，关闭时单独列为 local_only；changes 中的文件不受声明影响。两种依据的比较都排除场景目录与 snapshot_exclude，“已跟踪但已删除”与“不存在”视为相同。执行快照照常包含 local_only 文件。

D101：会话修复的再次准备、fix submit、复验准备与提交、fix land 只核对本修复的问题场景（复验为所选场景）：仍在当前版本、指纹与认领时（复验为准备时）相同、引用用例的前置条件、步骤与预期与修复快照相同（description、tags 等不比较）；不再比较全部批次的场景版本、用例并集、配置摘要与自检状态。受保护的 SOP 与场景文件只在再次准备与 fix submit 时核对（SOP-146-N02），复验与 land 不核对。复验准备另须 require_ready，复验快照的 config_digest 取准备时的值，复验期间业务配置或自检状态变化仍作废。看板修复的冻结规则不变。

D102：已放弃的会话修复，最后一次尝试已登记产品修复输出（不是已放弃、运行中或已中断）、产品问题没有被其他未放弃的修复认领时，fix land 可按 D98 的独立通过关闭为已处理，关闭说明写明此前放弃的时间；否则返回 fix-not-ready 或 fix-problem-reclaimed。其他操作仍不复活已放弃的修复。verified_by_rounds 同时返回逐个问题场景的原因，fix-validation-required 据此列出须补跑的场景。

D103～D105：cases put 按编号与并集当前内容比较，只登记新增与改写；片段继承最近非澄清上传的 metadata 并去掉 sop-draft，问题行号仍对应原文件。署名只用使用者姓名或默认业务确认人，依据原文与上传、编号一起登记为“按条增改”决定；全部未变化不写记录。按条上传不记录原路径，不能 write-back。export --case 按指定顺序导出并集当前内容，文件头取最近非澄清上传，只配合 --out，与 --upload、--write-back 互斥。

增量合并以最近 merge-land 收据为基线，核对场景输入为该轮落地结果（陌生手改期间按 D108 取最近落地版本），比较落地后（含 case_updates）的用例及草稿确认信息；升级前任务兼容读取 final.json 与已登记澄清改写。SOP、入口声明、独立场景选择、排除范围变化、通用答复或基线找不到所答缺口、没有变化或具体答复涉及用例、不可读基线均全量。具体缺口答复涉及用例与新增、变化用例取并集作为增量范围，delta.json 保留答复原文、缺口与关联用例。只有看板开发者重新合并与会话 prepare --full 强制全量，其他触发名称不决定模式。delta.json 与追加提示词仅用于增量；输出须覆盖全部变化用例，出现的条目完整覆盖沿用值，缺失条目才补齐，relocate 不沿用。仅沿用仍适用的节点、豁免、kept 去向及全部关联用例未变化的缺口，缺口重新编号。补齐后仍经 merge_conversation.validate 与原 judgment_problems/assemble 核对，不新增宽松核对器。完整判断与下一轮基线材料存于仅本机的 judgment.json；result_json 保存模式、原因、基线、计数与已落地场景差异，沿用数不含输出给出的用例判断。数据库格式仍为 5，不加表和列。场景依据为 SOP-201～203，真实入口与独立验收另行留证。

D106：看板启动扫描与工作区配置变化不再给批次排合并；合并输入与落地核对只看入口声明，不看工作区配置摘要，其他配置（snapshot_exclude、适配等）变化不使合并待同步或改为全量。入口声明变化时进行中的合并落地转待同步，由人重新合并。

D107：显示队列与执行范围分开。pending 只计当前内容没有结果的场景；最近 Agent 结果与最近结果都是通过、且产品内容摘要不同或执行期间有变化的场景单列 source-changed（产品变化待判定），不进复测，暂缓与等待修改场景仍优先排除。queue_counts、queues、页面和 status 共用同一统计来源；执行按钮条数、pending_scope、--scope pending、执行计划 pending 模式及影响判定、沿用规则保持不变。具体状态行、队列与指标维护在 docs/reference.md；场景依据为 docs/sop/sop-board-21.yaml 的 SOP-211。

D108～D113：已有落地合并的用例批次遇到陌生场景内容，扫描与 PUT 都登记版本、按真实配对分组提示 scenario-edited，不排合并；匹配本批任一合并写入版本才复制它自己的配对与内容依据。restore 还原最近落地版本并保留手改历史。手改期间执行与修复复验准备拒绝 scenario-file-edited；由用例、答复或决定触发的合并取最近落地场景作输入，模式按 D104/D109，落地覆盖手改并记入 scenario_diff，准备后再次变化时看板待同步，会话沿用已作废。人发起重新合并保持全量并预告重建编号。无用例批次保持原行为。
