# 真实项目主流程最小验收计划（v9）

> 状态：草案，待确认 · 日期：2026-10-20 · 对象：[v9 方案](../proposals/2026-10-20-v9-workspace.md)第 5 节的三段 · 执行与判定：AdolphKevin（未参与实现）· 环境：开发者本机的真实工作区
>
> 实施时把本计划写成场景文件 `docs/sop/sop-board-v9.yaml`，此后以场景文件为准。

## 1 目的

证明看板在一个跨多个仓库的真实项目上走通主流程：

搭建 → 上传用例 → 合并 → 执行 → 复核 → 跨仓修复 → 复测 → 合入 → 报告。

另在一个结构不同的项目上完成搭建，证明看板没有绑定某个项目。本计划只验主流程，页面文案、接口字段等细节由快速组测试覆盖。

## 2 项目、需求与用例

- **项目 A**：开发者本机的在线客服系统工作区。工作区目录本身不是仓库，里面有主服务、网关、公共库、AI 服务（Go 与 Python）、消费者、调度、Webhook 等多个仓库；本机各服务分别启动，依赖数据库、缓存、消息队列和模型服务。
- **需求**："访客发消息，AI 自动回复，访客与客服都看到回复"，涉及主服务、网关、公共库、AI 服务（Go 与 Python）共 5 个仓库。
- **用例**：测试同事已有这条流程的用例时，选 10–15 条；没有时，由未参与实现的测试代理按主流程写 10–15 条，交测试同事确认。其中放 3–5 条细节类用例，用来验证分层。用例不是看板的 YAML 格式时，由代理转换并经测试同事确认。
- **缺陷**：修复环节需要一个根因不在入口仓库的代码缺陷。优先用真实的、尚未修复的缺陷；没有时，在试跑分支的公共库或 AI 服务里放一个演练缺陷，结果中标明"演练"。
- **项目 B**：结构不同的项目，例如单仓库的 Python 服务，或另一组 Go 服务。只验证搭建和一条场景的执行。

## 3 准备

- **试跑工作区**：为涉及的 5 个仓库建试跑分支的 worktree，放在单独的试跑目录。可以用项目已有的多仓 worktree 工具，它会处理语言工作区与本机配置。看板只合入试跑分支，不推送；日常开发目录与分支保持原样。
- **端口**：停止开发者手工启动、且适配也会启动的服务，因为端口相同。数据库、缓存、消息队列等基础设施保持运行。
- **数据**：环境若连接团队共享的开发库，执行会在其中留下测试会话。只使用测试店铺。
- **业务前置条件**：测试店铺满足该流程的条件（例如已开启 AI 回复、有可用额度），模型服务的密钥可用。
- **工具**：本机 Codex 已登录（看板用它执行与修复），驱动技能已安装；搭建用 Codex 或 Claude Code 均可。要从网页验收时，准备测试专用的 Chrome 配置，商家端由开发者本人登录。
- **记录表**：每一步的开始与结束时间、人工介入的次数和原因。

## 4 场景

共 12 条，按段排列。

### 段 1：搭建、合并、执行、复核

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| E1 搭建 | 在试跑工作区打开 Codex，说"按 sop-board 的安装说明为这个工作区安装并搭建"，回答它的提问；确认后运行 `sop-board` | 代理装好看板，确认了工作区范围，`sop-board check` 全部通过；报告列出服务、依赖、入口、推断与待回答的问题，凭证只写位置；适配启动的服务、端口与依赖，与开发者平时手工启动的一致（由开发者对照核对）；开发者没有手写配置；启动后页面显示环境就绪 |
| E2 上传与合并 | 只填标记人，上传 10–15 条用例 | 合并完成；每条流程类用例生成同编号场景；细节类用例列在"交给单元测试"栏，每条附理由；全程没有令牌输入 |
| E3 执行 | 等待看板自动执行；开发者另抽 3 条场景，按相同步骤手工操作 | 每条场景有结果与证据；记录 Agent 判定与手工判定的一致数 |
| E4 复核 | 在"SOP 场景"页对一条 Agent 通过的场景点"通过"；对缺陷相关的场景标"失败"并填缺陷链接 | 页面不跳转，状态就地更新；"失败"进入问题队列 |
| N1 内网 | 加 `--lan` 重启，从另一台设备打开看板，再直接向执行接口发一次请求 | 能查看、上传与复核；看不到执行等开发者按钮和环境日志；直接请求被拒绝，环境没有变化 |

### 段 2：跨仓修复、复测、合入

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| E5 跨仓修复 | E4 标"失败"后等待修复任务 | 任务工作目录包含该需求 5 个仓库的 worktree，经适配准备后能编译并运行快速检查；根因分析指出根因所在的仓库与文件；开发者独立判断根因是否正确（演练缺陷与放入的位置对比） |
| E6 修复代码复测 | 等待复测 | 有改动的仓库快速检查通过；环境切换到修复 worktree 启动；新会话复测问题场景并通过；此时各仓库的试跑分支还没有变化 |
| E7 合入与重启 | 等待合入，然后复核 | 各改动仓库快进合入试跑分支；环境用基线目录重启；场景回到复测队列；复核通过 |
| N2 不能快进 | 修复进行中，在一个涉及的仓库留一处未提交的产品改动 | 任务停在"待开发者合入"，列出该仓库与原因；所有仓库的试跑分支都没有变化 |
| N3 根因在本机配置 | 标"失败"一条由本机配置造成的问题，例如两个服务之间的端口或数据库名不一致；试跑时已有这类问题就直接使用 | 修复会话判为环境或配置问题，指出具体的配置项，转"待开发者处理"；没有代码提交 |

### 段 3：报告与通用性

| 编号 | 操作 | 预期 |
| --- | --- | --- |
| E8 报告 | 导出本批次的 Markdown 报告 | 含用例覆盖（细节类标"交给单元测试"）、Agent 与人工结果、修复记录（根因、尝试次数、合入提交）、未验证范围 |
| E9 第二个项目 | 在项目 B 中改用 Claude Code 重复 E1，再执行一条场景 | 自检通过，场景有结果与证据；看板代码与搭建指引都没有为项目 B 修改 |

## 5 记录与判定

- 每条场景由 AdolphKevin 判定通过或不通过，证据位置写进结果。
- 另记录以下事实，不设门槛：
  - 各步耗时，人工介入次数与原因；
  - 搭建用了多久、经过几轮自检，开发者补充了哪些信息，报告是否指出了本机配置中的矛盾；
  - Agent 判定与手工判定一致的比例；
  - 根因判断是否正确，修复尝试次数。
- 交付记录写明哪些缺陷是演练。

## 6 不在范围

Jira 读写、场景沉淀、长时间运行的稳定性、多人同时使用。
