# Flow Board v10 重写方案

## Context

用户在实际使用 sop-board（cw2-live-chat 等项目）中整理出 7 个问题，要求从根因出发重新设计，直接替换，不留双轨与兼容代码。调查结论：这些问题有一个共同根因：项目靠决定条目（D1～D117）逐条打补丁扩张，而不去掉产生问题的结构。结果是：

- 两条入口（看板后台调度 + 会话认领）共用一个 25 种状态的任务内核；
- 看板在数据库里另存一份场景真相，并会回写仓库；
- “只认场景、不写测试”让确定性规则全部变成需要真实入口重跑的场景；
- 出于对 AI 的不信任，每次登记都要真人署名、只接管用户已打开的 Chrome。

本方案在 `feat/session-board-friction` 上重写（先把当前未提交改动提交留档，再切新分支），SOP-BOARD-22/23 不单独发布，由重写整体替代。

## 已定决策（2026-11-10 用户答复）

1. 单一路径：Agent 工作全部由会话经 CLI 完成；看板的“AI 重跑”只在本机可用，用同一技能在检出目录启动无头会话。删除任务内核、看板调度、认领与接管规则。
2. 保留：测试用例上传与合并、SOP 编写与草稿、交互地图与 spec 库、数据配方与身份池。
3. 场景以仓库文件为准：看板不存场景版本，也不回写场景文件；结果按内容指纹记录。
4. 不单独发布 22/23，在其分支上重写。
5. 看板采用三栏场景工作台。
6. 保留 adapter 脚本：看板守护进程用 adapter 按检出启停环境，加入端口偏移。
7. 守护测试由 `sop-board retest` 直接运行。
8. 沉淀时机：通过后进入“待沉淀”，由人在会话里或点看板按钮触发。
9. 本仓开发期间不写测试，先验收再沉淀成 pytest。
10. 内网不能发起 AI 重跑，只能人工复测标注、答复问题、批注草稿、上传用例。
11. 一并删除：问题台账与决定记录、旧方案与设计文档、执行计划与连续运行、只读巡检 patrol；Jira 联动删除。
12. 场景集确认时的补充（2026-11-10）：守护进程、服务与浏览器可以按验收需要在 agent 会话中启动；会话可用 `inbox add` 上传用例或 SOP；运行时与操作者文件始终在 `~/.sop-board`；specs 只保留 check；错误码 `run-prepared`、`launch-running`、`draft-not-runnable`、`project-format`、`browser-crashed`、`env-busy`、`browser-busy`；`fix close` 须独立复验通过且修复文件已提交并与复验时一致；漏检后重新沉淀须有新的独立通过。
13. 补回人工复核（2026-11-10）：重写时把“Agent 通过、等待人工复核”的队列和误判统计一并去掉了，与标准中“所需人工复核已完成”的交付条件不符。改为“待人工复核”徽标与筛选；统计 Agent 独立通过的人工确认率、复核覆盖与误判明细。人工标注不通过仍直接使场景显示为失败。
14. 导入的 v9 结果（2026-11-10，特例已由决策 18 取代）：cw2 从 v9 看板迁到 v10 时，旧看板的执行结果与证据由一次性脚本直接写库，`product_digest` 为空。决策 18 之后所有通过都不随代码改动失效，这类结果只是没有记录代码版本，没有单独的状态规则。本仓不提供导入命令，也不读取旧格式数据。
15. 左栏一键展开收起与隐藏（2026-11-11 使用者需求）：工作台的左栏树缺省展开（文件都展开，场景不超过 40 条的文件连节点一起展开），原来只能逐个折叠，也不能隐藏左栏。工作台与业务 SOP 的左栏各加一个“全部展开 / 全部收起”切换按钮：树中所有分组都已展开时显示“全部收起”，点击后收起全部分组；否则显示“全部展开”，点击后展开全部。两页的缺省展开状态不变（业务 SOP 页仍只展开当前打开的文档）。结果与手动展开收起一样记在浏览器 localStorage（按项目与页面分别记），刷新与 15 秒轮询后保持；有筛选或搜索时只作用于当前显示的结果，不改记住的状态，清除筛选或搜索后树按记住的状态显示。左栏另有“隐藏左栏”按钮，隐藏后右栏占满宽度，左侧留一条窄栏，其中的“显示左栏”按钮恢复左栏；隐藏状态记在浏览器 localStorage，工作台与业务 SOP 共用，内网同样可用。
16. 真人完成后交还浏览器，不关窗口（2026-11-11 使用者需求）：原流程要求真人登录后运行 `browser close`，它会结束浏览器进程，之后的运行再拉起一个无头浏览器；有界面窗口里通过的人机验证、浏览器权限与证书例外因此作废，使用者要重复登录、验证。cw2 的会话只好直接调用本机接口解除占用。改为：真人在 `browser open --headed` 的窗口里完成登录、人机验证或二次验证后，运行 `browser release` 交还，只解除真人占用，窗口与页面保持打开；之后的运行直接沿用这个浏览器进程，不重启。没有加 `--headed` 的 `browser open` 遇到正在运行的有界面窗口时直接沿用，不取得租约，也不再把它重启成无头。`browser close` 只在要结束浏览器时使用。
17. 声明的测试账号即授权（2026-11-11 使用者确认）：原标准要求“账号声明本身不是授权”，每个任务开始时另取授权并写授权记录，导致会话反复询问、拒绝登录项目给它的测试邮箱、把浏览器权限提示也交给人。改为：项目验证手册或配置里声明的测试账号（包括为验收注册的第三方账号与测试邮箱），声明即授权，AI 在声明的测试环境与用途内直接登录、申请并读取测试邮箱中的验证码，受身份使用次数限制；不再逐任务取得授权、不写授权记录。测试环境自身在看板浏览器中触发的提示（本地网络访问、localhost 自签名证书警告等）由 AI 处理。仍由人完成的只有：真实或生产账号与未声明账号的登录、人机验证、只发到使用者本人设备（手机、身份验证器）的验证码，以及遇到 `browser may not be secure` 时停止。

18. 验收范围由业务变化决定（2026-11-11 使用者决定）：原规则是产品快照一变，所有通过都转待复测，再靠守护通过或执行会话事后写 `impact.json` 保留通过。开发活跃时几乎所有场景一直是待复测，待人工复核随代码变化消失，cw2 迁移还为此开了决策 14 的特例。使用者指出：哪些场景需要验收是业务问题，业务变化体现在 SOP 和场景文件上；很多代码改动（例如某个小工具的性能优化）不改变业务，不需要场景测试。改为：
    - 代码改动不改变场景状态：场景内容没变，它验证的业务就没变，已有通过保持有效。产品快照只记录每条结果、标注和守护运行取证时的代码版本；执行期间变化的路径照常记下，不影响状态、独立性、待沉淀与待人工复核。快照变化时 `run prepare` 照旧重启环境。
    - 业务交叉在编写时识别：写或改 SOP 时核对已有 SOP，口径改变的已有规则确认后一并改正；生成场景或合并用例时核对已有场景，预期改变的已有场景直接修改，指纹一变即回到未执行。不新增影响面字段或登记文件，也不要求代码改动登记影响面。
    - 守护是回归网：`retest` 缺省运行全部有效守护，未通过的场景转待复测；通过只留作证据，不改变状态。删除“守护通过”状态。
    - 删除保留通过（`kept`、`impact.json`、`previous-results.json`、`changes.json`、待执行原因 `source-changed`）；人工复核与确认率不再要求同一快照。数据库格式不变：早先写入、带 `reused_from` 的结果仍算通过，但不算经真实入口的独立通过。

19. 左栏可调宽度（2026-11-12 使用者需求）：左栏宽度固定为 360px，较长的文件、节点与场景标题被截断，悬停也看不到全文。改为：工作台与业务 SOP 页的左栏右边缘加拖拽手柄，宽度可调范围为 240px 到窗口宽度的 60%，双击手柄恢复 360px；宽度记在浏览器 localStorage，两页共用、不分项目，刷新与 15 秒轮询后保持，隐藏再显示左栏后不变；内网同样可用。文件、节点与场景标题悬停时显示全文。点名称与点箭头仍都是展开或收起，与决策 15 一致。
20. 草稿审阅并入工作台（2026-11-12 使用者决定）：原来有两处入口：独立的“草稿批注”页只列文件、批注列表和批注表单，不显示场景四要素，和工作台的展示方式差别很大；工作台草稿场景的批注卡只有一个文本框，测试同学不知道该批注什么，也没有“同意”。`draft confirm` 只要求没有未处理的批注，没人看过也能确认，确认人记为运行命令的操作者（cw2 在 2026-11-12 有 3 份草稿共 32 条场景，批注为 0）。改为：
    - 删除“草稿批注”页与导航项，`/p/<项目>/drafts` 不再提供，不做跳转。草稿只在工作台“草稿”筛选中审阅。
    - 草稿场景详情依次为：标题上方的“文件 › 节点”路径（点哪一级打开哪一级的面板）；四要素；`refs` 指向的 SOP 规则原文（可展开）；固定的检查清单；批注表单；“同意”按钮。草稿不显示复测表单。检查清单五项：场景是否忠实于 SOP 规则；预期能否直接观察并带具体值；禁止副作用是否写全；起点数据是否具体；是否漏了反向、边界或与已有业务交叉的场景。
    - 每条草稿场景的审阅状态只有三种：**待审**（当前指纹上没有同意）、**有批注**（该场景有未处理的批注）、**已同意**（当前指纹上有同意且该场景没有未处理的批注）。有未处理批注时“同意”不可点并说明原因；同意后又有人批注，以批注为准；会话修改场景使指纹变化后，原有同意失效，回到待审；批注不采纳、场景未改时，原有同意仍有效。文件级批注不影响单条场景的同意，但会阻止确认。
    - 同意按“文件 + 场景 + 指纹”记在看板数据库，不写场景文件，不区分检出：同一看板上任何检出中内容相同的场景都显示已同意（配了共享库时，同一产品的各台机器上也一样，见已定决策 21）。内网可以同意，须署名（顶栏姓名）；本机页面缺省以操作者署名。只能撤销自己的同意。同意后自动打开同一文件中下一条待审场景，没有待审场景时停留在当前场景并提示。
    - 草稿文件与节点那一行右侧有常显的「审阅」按钮。节点面板完整列出组内每条场景的四要素，提供“同意本组 N 条待审场景”，有未处理批注的场景跳过并列出原因，同意逐条记录、可逐条撤销。文件面板显示需求说明与来源、审阅进度（待审、有批注、已同意的条数）、文件级批注列表与表单；全部已同意且没有未处理批注时显示“可以确认”，本机页面附 `sop-board draft confirm <文件>` 命令，内网不显示命令。不提供整份文件一键同意。
    - 左栏中草稿场景的状态点按审阅状态显示，草稿文件与节点行显示“已同意 x/y”；“草稿”筛选的计数不变。
    - `draft confirm` 要求文件中每条场景在当前指纹上已同意，且文件没有未处理的批注；否则以业务失败退出并列出未同意的场景与未处理的批注。`confirmed_by` 写同意人（去重，按首次同意时间排序，用“、”连接），不再写操作者；删除 `draft confirm` 的 `--as`。`draft annotations` 的输出带每条场景的审阅状态与同意人；`status --json` 的草稿计数按待审、有批注、已同意分开。不新增命令。
    - 内网写入范围增加“同意或撤销自己的同意”。
    - `docs/sop-guide.md` 中“草稿可写入代码推理预期”的说法删除，以随包 `draft.md` 为准：预期只来自 SOP 原文与使用者答复。
21. 多人共享验收记录（2026-11-12 使用者决定，同日经审查修订）：原来看板的全部状态（结果、证据、标注、批注、同意、待答复）都在运行看板的那台机器的数据目录中，一个研发验证过的场景，另一个研发用 sop-board 启动同一个产品后看不到。出发点：sop-board 围绕**产品**做场景验收，共享的单位是产品（cw2 是一个产品，不是 13 个服务），一个分支是产品的一个迭代；仓库、服务与中间件只是各人在本机拉起验收环境、修复和回归的材料，怎么搭是各人自己的事。协作只经 Agent 对话和看板完成：不往产品仓库写入任何东西，不扫描使用者的目录，“是不是同一个产品”由 Agent 问使用者。改为：
    - **共享库**：各台机器直连同一个 PostgreSQL。内网没有现成的，就在一台常驻机器上用 docker 起一个；文档给出具名卷与每日 `pg_dump` 的示例，sop-board 自己不做备份。本机 `config.yaml` 的 `shared_database` 写主机、端口、库名、用户名；密码写在同一处的 `password`（已定决策 27）或放 `~/.pgpass`。密码不出现在页面、接口、命令输出、日志、报告与证据里；主机、端口、库名只出现在本机命令输出与本机页面，不进报告、证据和内网页面。驱动 `psycopg[binary]` 作为常规依赖随包安装。
    - **没配共享库时**：业务记录存本机 SQLite。两种库使用同一套 SQL 和同一套规则，只有连接、事务和加锁按库分开写。环境、浏览器、租约等本机状态始终在本机 SQLite。
    - **连不上与版本**：连不上共享库时，凡是读写业务记录的命令和看板页面都返回 `database-unreachable`，本机输出写明连的是哪台主机；不做离线队列，也不做本地缓存。共享库记录表结构版本：`init --new` 在空库中按当前版本建表；版本不符时，新旧两个方向都返回 `database-version`，并写明需要的 sop-board 版本；不降级，不让两种格式同时可用。这次不提供升级命令，留到第一次修改表结构时再做，届时先列出正在使用的看板和未提交的运行。本机 SQLite 仍是格式一变就拒绝读取。
    - **共享的记录**：Agent 结果与人工复测标注；运行记录的业务部分（范围、执行者与独立性、未执行清单及原因、服务停启记录）；证据索引（sha256、大小、名称、产出机器）；守护运行、沉淀登记（场景、指纹、测试摘要、沉淀人、机器、时间）与漏检；修复记录（问题场景、修复会话与操作者、状态、关闭时间、产出机器与检出）；草稿批注与同意、提问与答复、收件箱；待人处理（每条附产出机器）。
    - **留在本机的**：检出路径、环境、浏览器实例、租约、启动记录、测试账号使用次数、数据配方留痕、修复的文件基线与复验摘要、运行目录。
    - **机器标识**：数据根目录下的 `machine.json` 保存生成一次的随机标识和显示名（缺省“操作者@主机名”）。“产出机器”都指它，不用主机名或地址当标识。
    - **先后顺序**：业务记录库给结果、标注、守护运行、修复关闭分配同一串递增序号，状态推导只比较序号；执行时间只用于显示。
    - **提交可重试**：`run submit` 依次做三步：证据文件存入本机证据目录；一个事务把结果、证据索引和运行记录写入业务记录库；更新本机运行状态、释放租约、恢复服务。每次运行在共享库里以“机器标识 + 本机运行编号”唯一，重复提交不重复登记。第二步失败时运行保持 prepared，结果留在运行目录，恢复后重新 `run submit`；第三步失败时，重新提交只补做第三步。
    - **证据文件**留在产出它的机器上，存放在数据根目录下按内容寻址的 `evidence/` 目录，不随项目数据目录重建而丢失。每个带 `--lan` 的看板启动时把机器标识、显示名、内网地址和对等令牌登记到共享库；别人查看时，由本机看板从产出机器的看板取回（请求须带令牌）、核对 sha256 后转给页面，不在本机保存，内网页面里不出现别的机器的地址；那台看板没开、没加 `--lan` 或登记的地址已失效，就显示“证据在 <机器显示名> 的机器上”。`report --zip` 遇到别人机器上的证据：产出机器的看板可达时取回，核对 sha256 后放入；不可达时报告逐条写“证据在 <机器显示名> 的机器上，未包含”，并在输出里写明缺少的条数。
    - **产品与加入**：共享库按产品登记，每个产品有 ID 和名称。项目的 `config.yaml` 写了 `shared_database` 而还没绑定产品时，业务命令返回 `product-unbound`；没写 `shared_database` 的项目运行 `init <项目>` 返回 `shared-database-required`。`sop-board init <项目>` 列出共享库里已有的产品（名称、创建人、有结果的场景数、最近写入时间），附一条参考“本机 N 条场景中，有 M 条在该产品里已有结果”，以 `product-choice-required` 结束，不自动绑定。Agent 先问使用者，使用者回答后用 `init <项目> --join <ID>` 或 `init <项目> --new [--product <名称>]` 完成绑定（名称缺省为本机项目名），绑定关系记在本机的 `project.json`；`--join` 的 ID 不存在时返回 `product-not-found`。绑定时另外提示两件事：本机已有的结果不带入共享库，已登记的守护会因验收结果不在共享库而失效，须重新验收后再沉淀；`regression.yaml` 引用、但本机没有登记的仓库别名。改绑时重新运行 `--join` 或 `--new`，已写入原产品的记录留在原产品。
    - **不碰仓库**：新建、加入和共享都不读取、不比对任何仓库的 origin，不扫描目录，不往产品仓库写东西。本机登记仓库时原有的 origin 身份核对不在这次范围。
    - **状态**仍按“文件 + 场景 + 内容指纹”判断，记录分两类。**结论**（Agent 的通过与失败、人工标注、修复关闭）在产品内共享，按分支归属：分支取场景文件所在仓库的当前分支，其余仓库的分支与提交记在快照里。**非结论**（受阻、跳过、守护未通过）只在产出它的机器和检出上影响状态。**本分支优先**：某场景的当前指纹在本分支上有结论时，只用本分支的结论；一条都没有时，用全部分支的结论，并在状态旁标出来源分支。某个看板上的状态，由这样选出的结论加上本检出自己的非结论，按序号用“场景状态”一节的规则推导；没配共享库的单机项目用同一规则。别人的非结论不改变本机状态，显示在场景详情里：各机器最近一次的受阻、跳过、未执行和守护未通过，写明谁、哪台机器、什么时候、原因。每条记录都记下产出时的分支，在历史里显示。
    - **守护是否有效**由每个看板按本检出的 `regression.yaml` 和测试文件现算，其中三条查业务记录库：验收结果是同指纹的独立通过、没有登记过漏检、检出能力证据在证据索引里有记录。沉淀成功时把沉淀登记写入业务记录库。共享库里有当前指纹的沉淀登记，但本检出没有这条守护或测试摘要不同时，不显示“待沉淀”，显示“已由 <沉淀人> 沉淀，本机未同步”；`retest` 不运行它，也不写记录。守护引用的仓库在本机没有登记、命令跑不了时，`retest` 把它列为“本机无法运行”，不记作未通过。
    - **独立性**：`run submit` 和 `run launch` 新增 `--implemented-by <操作者>`，与 `--implementer <会话编号>` 二选一。填操作者时，与本机操作者不同记独立验收；相同则以参数错误拒绝，要求改填会话编号。实现者由使用者在任务里说明；没说明的照旧记未声明，会话不追问。
    - **修复**：修复记录共享，修复关闭使场景转待复测的规则对所有看板生效。`fix submit`、`run prepare --fix`、`fix close`、`fix abandon` 只能在产出修复的机器和检出上执行，其他机器返回 `fix-not-local` 并写明产出机器。别人要验证时，等修复提交推送后用普通的 `run prepare --scope` 执行；结果是共享结论，但不关闭那条修复。
    - **cw2 迁移**：用一个放在仓库外的一次性脚本，把 `~/.sop-board/cw2` 里现有的记录导入共享库，建立产品 cw2，把 `blur-yin` 统一为 `blur.yin`，并保留原结果编号（已提交的 `regression.yaml` 用结果编号引用验收结果）。证据文件留在原机器上，登记为由它产出。仓库里不提供导入命令。
    - **这次不做**：多个迭代并行的完整支持（只做本分支优先，不做分支之间的合并、比较与按分支的报告）；共享搭建资料（配置、adapter、验证技能）；测试账号使用次数跨机器合并、多人共用测试账号和外部数据时的互相干扰、同一批场景被重复执行时的去重、主动通知；升级命令；跨机器复验并关闭别人的修复；把本机旧记录导入共享库。
22. 环境按产品来（2026-11-12 使用者决定，同日经审查修订）：原来 adapter 只报告整体就绪，任何一个服务没起来，`check` 和 `run prepare` 就失败，不需要这些服务的场景也跑不了；需要某个依赖故障的场景没有正规的模拟办法，cw2 只好在本机 `env.py` 里专门写了一套暂停机制。仓库、服务与中间件只是材料，不要求每次都全部活着。改为：
    - **adapter 契约**：服务声明写在本机 `config.yaml` 的 `adapter.services`，格式是 `名称 → {about: 业务说明, stoppable: 是否可停}`。adapter 把每个服务的状态写到 `SOP_ENV_LOG_DIR/services/<名称>.state`，状态变化时改写；取值为运行中、已停止、本机未搭建、异常退出，异常退出附日志路径；声明了但没有状态文件的服务显示“未上报”。守护进程在同一目录写 `<名称>.request` 表示停止，删除它表示启动；adapter 轮询并执行，完成后更新状态文件。没声明 `services` 的 adapter 照旧工作，只有整体就绪与否。
    - **部分就绪**：只要 adapter 输出就绪，环境就算可用。`env status` 和本机看板显示每个服务的状态。`run prepare` 和 `check` 不再要求所有服务都在运行，只列出哪些服务没在运行、哪些入口地址缺失。运行目录里写明各服务的状态和业务说明，供执行会话判断。
    - **故障模拟**：新增 `sop-board env stop <服务>` 和 `env start <服务>`，由守护进程按契约转交给 adapter，等状态变为目标值才返回，超过 `adapter.service_timeout`（缺省 60 秒）返回 `service-timeout`。只能停 `stoppable` 为真的服务：没声明 `services` 返回 `service-not-declared`，名称不在声明里返回 `service-unknown`，不可停返回 `service-not-stoppable`。两条命令只在本检出有 prepared 运行时可用，否则返回 `run-required`；运行之外要恢复环境，用 `env restart`。提示词改为：不得直接杀进程或改动环境；场景起点要求某个依赖故障时，用这两条命令来停、启。场景起点仍用业务语言写，不写服务名，执行会话按服务的业务说明对应。
    - **记录与恢复**：每次停、启都记进本轮运行：谁、什么时候、停了哪个服务、停着期间执行了哪些场景；结果详情里显示“执行时 <服务> 已停止”。`run submit` 或 `run abandon` 时还停着的服务，由 sop-board 自动恢复并记录。
    - **范围**：只限本机由 adapter 启动的服务。外部共享的中间件不能停，需要这类故障的场景记受阻并写明原因。延迟、错误注入等其他故障方式这次不做。
    - **未执行和受阻的分界**按性质划分，不看发生在开始前还是执行中。**未执行**是本机暂时不具备、补齐或换一台机器就能执行的情况：场景需要的服务本机未搭建或被人为停着；缺少入口声明的凭据变量；等人处理的事（真实账号登录、人机验证包括执行中途出现的、只发到本人设备的验证码、身份使用次数到上限），照旧登记到待人处理。未执行不形成结论，不改变任何人看到的状态；场景详情显示最近一次未执行的情况（谁、什么时候、缺什么）。**受阻**是意外故障，或全队都不具备的能力：服务或浏览器异常退出（附日志末尾并登记待人处理）；前置数据准备失败、证据丢失、运行作废；出现 `browser may not be secure`；入口或观察能力还没建设（标准第 7 节的入口缺口），以及需要停外部共享中间件的故障场景。对应的服务状态：本机未搭建、已停止记未执行，异常退出记受阻。独立复验仍须完整执行，不接受未执行。
    - **`retest`** 不判断失败原因。守护未通过时，场景在本检出转为待复测，原因写明当时本机没在运行的服务，以及工作区是否有未提交改动。待复测的场景由 AI 经真实入口复测，按上面的分界判断：因为服务没搭或停着跑不通，记未执行，场景保持待复测；能跑通，再判通过或失败。在本检出重新运行守护通过，也回到通过。
    - **故障场景的沉淀**：守护写在不需要真实停服的层（单元、接口或组件层，用替身模拟依赖不可用）；写不出这样的测试时不沉淀，沉淀报告里写明原因。
    - **同步修改**：`docs/standard.md` 中缺凭据变量、数据库不可用、环境缺失、缺密钥和入口缺口各处的受阻口径；`prompts/run.md` 与 `run prepare` 写进 brief 的说明；playwright-acceptance 技能的正文、参考、模板和转换脚本（要能产出未执行）；regression-distill 技能；`docs/sop-guide.md` 说明故障场景的起点怎样用业务语言写。
    - **演示项目**加第三个仓库 stock（库存服务），商城下单依赖它；库存服务不可用时，商城按演示 SOP 显示明确的降级提示。演示 adapter 按新契约声明服务、上报状态、响应停启。
    - **实施顺序**：先做决策 19、20，再做 22，最后做 21；实现与独立验收由不同的会话或代理完成。决策 19、20 做完就单独验收；决策 22 与 21 都实现后统一验收（理由见已定决策 23）。
23. 验收时机按情况决定（2026-11-12 使用者需求）：一项需求分几步实现，或几项需求接连实现时，标准和随包技能都没有说什么时候验收。会话只能照固定流程走：要么每一步都验一遍，要么全部做完才验。前者在后一步会重做同一块实现时白验一遍，后者在某一步要先单独交付时又缺了验收。本仓实现已定决策 19～22 时就遇到了：决策 19、20 不改数据库格式、可以单独装给使用者，值得单独验收；决策 22 验过的内容会被决策 21 的存储改造重做，并到最后统一验收更省。使用者要求在用 sop-board 的项目里也能这样按情况分析。改为：
    - **不变的底线**：交付条件不变（标准第 6 节）。分步验收只改变每条场景在哪一步执行，不减少要经独立真实入口执行的场景；先验的通过要到交付时仍然可信，见下文“先验的结果怎样保持有效”。实现者自检每一步都做。
    - **逐步判断**：开始实现前，会话对每一步判断“做完就验”还是“并到后面一起验”，把安排和理由告诉使用者，由使用者确认或调整，不照搬某一种固定节奏。判断看这些事实：这一步是否会先单独交付或装给别人用；后面的步骤是否会重做这一步验过的实现；后面的步骤是否以这一步正确为前提；各步改动的范围是否重叠（重叠多，晚发现的缺陷难分清出自哪一步）；这一步是否涉及鉴权、持久化、金额、消息、并发这类高风险内容；验收一轮的成本（环境、真实账号、人工复核、时间）。
    - **如实标注**：每一步的状态分三种：已独立验收、只做了实现者自检、未验证。并到后面验收的步骤，在报告和提交说明里写明“未经独立验收”，不说成可以验收或可以交付。
    - **先验的结果怎样保持有效**：代码改动不改变场景状态（已定决策 18），所以先验通过的场景在后面的步骤重做了它依赖的实现之后仍显示通过，`--scope pending` 不会再选中它。这样的通过要到交付时仍然可信，二选一：先验的那一步通过后沉淀守护，之后每一步用 `retest` 检查，交付时守护有效且最近一次运行通过（守护是回归网，已定决策 18）；或者在统一验收时用 `run prepare --scope <场景>…` 或 `run launch --scope <场景>…` 把这些场景明确列入、重新执行。两样都没有的，这条通过不能算进交付。
    - **统一验收的范围**：全部推迟验收的步骤的场景，加上先前通过、被后续步骤重做了实现、又没有“守护有效且最近一次运行通过”的场景。
    - **落在哪里**：`docs/standard.md` 第 5 节新增“分步实现时的验收时机”；随包 sop-board 技能在入口写明多步工作开始前先定验收安排，并在执行参考里列出判断依据与范围的选法。不新增命令，不新增场景状态。
24. 浏览器调试端口被占用时顺延（2026-11-12 使用者同意）：身份浏览器的调试端口按 `9400 + 槽位×20 + 身份序号` 计算，不区分项目和数据根目录，被占用时直接报错。同一台机器上开着两个项目的看板时，两边 main 检出的第一个 Web 身份抢同一个端口：使用者运行着 cw2 时，别的项目 main 检出上的 Web 场景都无法执行；本仓已定决策 19～22 的验收也只能把这些步骤挪到 worktree 检出里做替代。改为：
    - 缺省端口仍按原公式计算。缺省端口被别的进程占用时，顺延到下一个空闲端口，不报错；一直找不到空闲端口才报错。
    - 实际端口记在浏览器实例里，`browser status` 显示它；`run.env` 的 `PW_CDP_ENDPOINT` 与 `PW_IDENTITIES` 指向实际端口。执行者本来就只经这些变量连接，不需要知道公式。
    - 浏览器运行期间端口不变；下一次启动时重新从缺省端口找起。守护命令声明了 `browser:` 时同样适用。
    - 不结束、不干扰占用缺省端口的进程。
25. 待沉淀只在状态为通过时显示（2026-11-12 使用者决定）：原规则是同一指纹上已有独立真实入口通过、又没有有效守护就显示“待沉淀”，不看场景当前的状态。于是场景独立通过之后被测试同学标为不通过、阻塞或需求变更，仍然带着“待沉淀”，等于提示把一条已经被人判为不通过的通过沉淀成守护。统一验收中两个验收代理都指出了这一点。改为：
    - “待沉淀”徽标、“待沉淀”筛选及其计数、`status --json` 的 `distill` 与 `distill_queue`、报告里单列的待沉淀场景，都只包含同时满足三条的场景：状态为通过；同一指纹上已有经真实入口的 Agent 独立通过；没有有效守护。
    - 状态不是通过时（失败、受阻、待复测、需求变更、跳过）不显示“待沉淀”，也不显示“已由 <沉淀人> 沉淀，本机未同步”。场景回到通过后照常显示。
    - `distill prepare` 指名状态不是通过的场景时拒绝，返回 `distill-not-passing` 并写明该场景当前的状态；不带场景键时只取待沉淀的场景，自然不含它们。`distill submit` 登记时同样核对。
    - 已经登记的守护不受影响：守护是否有效仍按原条件判断，人工复测不通过记漏检的规则不变。
26. 看板重启后保留有界面的浏览器窗口（2026-11-13 使用者决定）：看板守护进程停止时会关闭它启动的全部浏览器，启动时还会清掉上次遗留的浏览器进程。真人在有界面窗口里完成的登录和人机验证只在这个浏览器进程里有效（已定决策 16），所以每次重启或升级看板，使用者都要在每个身份的窗口里重新登录、验证。cw2 开着 6 个 Shopify 身份的有界面窗口，试用期每修一轮就要重装、重启一次看板。改为：
    - **停止时保留有界面的窗口**：看板守护进程正常停止时，不结束有界面的浏览器进程，窗口和页面保持打开，并在输出里写明保留了哪些；无头浏览器不需要人登录，照旧随看板关闭。环境照旧随看板停止。
    - **启动时认回**：看板守护进程启动时，逐个 检出×身份 查看 profile 目录。有浏览器进程正在使用这个 profile（profile 的进程锁指向的进程还在运行，它是运行时登记的 Chrome for Testing，命令行的 `--user-data-dir` 就是这个 profile），而且它的调试端口有应答、应答来自这个进程，就认回：登记为运行中，沿用它的调试端口，有界面与否取自进程的命令行。认回之后，租约、`browser status`、`browser open`、`browser release`、`browser close` 与崩溃规则都和守护进程自己启动的浏览器一样。
    - **遗留的无头浏览器照旧清理**：看板被强杀后留下的无头浏览器，启动时结束并清理。进程已经不在的（使用者在看板停着时自己关了窗口），不认回也不报错，下一次需要时照常启动。
    - **有界面的窗口不自动结束**：有界面的窗口里是真人完成的登录和验证，所以核对不通过时也不结束它。端口核对在后台反复进行，最长 15 秒；始终不通过（调试端口没有应答，或端口被别的进程占用）就登记为“未认回”并写明原因，`browser status` 显示它，这个身份的租约、`run prepare` 与 `browser open` 返回 `browser-unrecovered`，写明进程号、原因和两条出路：窗口恢复应答后再次请求会重新核对并认回；确实不要这个窗口了，用 `sop-board browser close --identity <身份>` 结束它。看板不为这个身份另起浏览器。
    - **不依赖本机数据库里的记录**：认回只看 profile 目录和进程本身。看板被强杀、本机数据库重建之后，仍在运行的有界面窗口照样认回。环境的孤儿进程清理仍靠数据库里的记录：看板被强杀并且本机数据库又被重建时，遗留的环境进程要使用者自己结束。
    - **崩溃监视**：认回的浏览器不是守护进程的子进程，用查看进程是否还在的办法发现它退出，之后按崩溃规则处理；取不到退出信号时写明“进程已退出”，日志与崩溃报告照常引用。
    - **要关掉窗口**：`sop-board browser close --identity <身份>` 结束浏览器，认回的也一样；看板停着时，使用者直接关窗口即可。

28. 一台机器一套环境，多个 Agent 轮流和并行使用（2026-11-13 使用者决定）：同一台机器上几个 Agent 在不同 worktree 并行开发同一个产品，开发完各自验收时互相挡住。看板守护进程一停，就停掉全部环境、无头浏览器和它启动的会话；升级看板要手工结束进程、等它退出、在后台重新启动、再核对窗口是否认回，进行中的验收都被打断。`port_step: 0` 时只有一套环境，另一个检出的 `run prepare` 直接返回 `env-busy`，不排队，要有人去 `env down` 别人的环境。同一检出同时只能有一个 prepared 的运行，一次运行又会租下入口的全部身份，几个执行会话不能在同一套环境里分开身份同时跑。浏览器按 检出×身份 各一份 profile，换一个检出就要把真实账号重新人工登录一遍。结论按分支名归属，worktree 分支上验收过的场景合并回 main 后不算数。也考虑过每个检出各起一套环境（包括 Docker Compose 这类现成方案），按 cw2 的梳理（2026-11-13）：一套环境约 3.2 GB（两个前端开发服务器占 2.2 GB），另加 Kafka 1.2 GB，16 GB 的机器已经在大量使用 swap；主题名是代码常量、消费组写死，每套都要单独的 Kafka；定时任务的锁和雪花 ID 的节点号靠共享 Redis 协调，不能每套各用一个；前端访问后端和 Shopify Webhook 都经唯一的 ngrok 入口。使用者认定一台机器多开环境是伪需求：大多数电脑的内存撑不起多套环境；要更多并行就加机器、加人，多台机器共享验收记录已由已定决策 21 做到。真正要的是一套环境让多个 Agent 轮流用、并行用，互不打断。改为：
    - **停止与重启命令**：
      - `sop-board stop [项目]`：让守护进程按现有规则正常停止（停掉环境、无头浏览器和启动的会话，保留有界面的窗口，已定决策 26），等它退出后输出保留了哪些窗口。守护进程没在运行时返回 `daemon-not-running`。
      - `sop-board restart [项目]`：换一个守护进程，进行中的工作不受影响。保留全部浏览器（有界面的和无头的）、浏览器租约、启动的会话和 prepared 的运行。环境不跨重启保留：旧进程照常停掉环境，新进程启动后重新拉起原来在运行的环境（cw2 在热缓存下 8～42 秒就绪）。新进程沿用原来的端口和 `--lan`，在后台运行，输出追加到 `<数据目录>/serve.log`；命令输出列出保留与认回的浏览器和会话，以及正在重新拉起的环境。守护进程没在运行时返回 `daemon-not-running`。在 Codex 沙箱里拒绝执行并提示在终端运行：沙箱里启动的看板起不了浏览器（见“进程与入口”）。
      - **认回**：新进程按已定决策 26 的核对认回浏览器，租约照旧有效；无头浏览器只认回 `restart` 交接下来的，看板被强杀后遗留的照旧清理，强杀后的认回也照旧释放旧租约。启动的会话按进程号和命令行认回，用查看进程是否还在的办法监视；取不到退出码时按有没有产出运行判断（沿用 `no-work`）。为此会话输出不再经守护进程转写，改由随会话存活的转写进程遮蔽后写进启动日志，遮蔽范围不变（已定决策 27 保存的共享库密码）。
      - **重启窗口**：`daemon.json` 标明正在重启，这期间 CLI 等新进程就绪（最多 120 秒），不直接返回 `daemon-not-running`。环境重新就绪之前，prepared 的运行用不了环境：每个这样的运行记一条“环境随看板重启中断”（起止时间），运行摘要里列出；执行提示词写明，这段时间里失败的步骤等 `env status` 就绪后重做该场景，不记失败或受阻。
    - **一套环境在检出之间轮流用**（`port_step: 0`）：
      - 环境由当前检出的 prepared 运行占住；没有 prepared 运行时就是空闲，别的检出要用时由守护进程直接停掉它、为那个检出拉起，不用谁去 `env down`。只用 `env up` 拉起、没有运行在用的环境不算占用，随时可能被换走。
      - `run prepare` 新增 `--wait <秒>`：环境被别的检出占着、要用的身份被别的运行或真人占着，或者环境要重启而还有别的运行在用时，在本机排队，最多等这么久；轮到了就照常准备，超时返回原来的错误码（`env-busy`、`browser-busy`）。不带 `--wait` 时照旧立即返回这些错误。两种情况的输出都带队列：排第几，前面是谁（检出、运行、会话、等了多久）。看板启动的会话按提示词带 `--wait`。
      - **队列**只在守护进程内存里，按到达先后。等待者按会话编号识别：请求结束（超时或断开）后 60 秒内同一会话再来，保留原来的位置；超过就出队。不持久保存，看板重启后清空。
      - **不插队**：有别的检出在等环境时，占用环境的检出不能再开始新的运行，新运行排在等待者后面，直到环境换出去。
      - 看板概况页显示环境当前属于哪个检出、哪些运行和身份在用、谁在等。
      - `port_step` 不为 0 时各检出照旧各有一套环境，只按身份排队。
    - **同一环境里并行跑多个运行**：
      - 取消“同一检出同时只能有一个 prepared 的运行”。同一套环境上可以有多个 prepared 的运行，按身份分开：`run prepare --identity <身份>`（可重复）只为这些身份取得浏览器租约，`run.env` 与 `identities.json` 只列这些身份；不写时照旧取本轮 Web 入口的全部身份。
      - 身份租约整机独占：同一个身份同一时刻只给一个运行或一位真人（human 租约，已定决策 16）。
      - **分开场景**：`--scope pending` 展开时跳过本检出其他 prepared 运行里的场景；明确指定的场景已在别的 prepared 运行里时返回 `scenario-in-run`，写明是哪个运行。
      - **按运行定位**：`env stop|start` 等原来按“本检出的 prepared 运行”找运行的命令，改为取 `--run`，其次 `SOP_BOARD_RUN`（`run.env` 里有）；本检出有多个 prepared 运行又没有指明时返回 `run-ambiguous`，列出各运行。
      - **停服务要独占环境**：`env stop|start <服务>` 只在这套环境上只有这一个 prepared 运行时可用，否则返回 `env-shared` 并列出其他运行；有服务被停着时，别的运行要用这套环境就排队。
      - 环境因快照变化要重启时，等这套环境上没有别的 prepared 运行（排队，或返回 `env-busy`）。
      - 看板的“AI 重跑”照旧同一检出只启动一个会话。
    - **身份浏览器各检出共用**：
      - 每个身份一个浏览器，profile 放在 `<数据目录>/browsers/<身份>/profile`，不再按检出分开：真人每个身份只登录一次，哪个检出的运行拿到租约就用它。缺省调试端口改为 `9400 + 身份序号`，被占用时照旧顺延（已定决策 24）。
      - 交给与上一次不同的检出之前，经调试协议清空这个浏览器的 HTTP 缓存，cookie、本地存储和登录保留，避免上一个检出的前端资源被当成本检出的代码。
      - 升级到这一版时，原来按检出存放的 profile 不迁移，旧窗口不再认回：使用者关掉它们，在新窗口里把真实账号重新登录一次（v10 不写迁移和兼容旧数据的代码；使用者 2026-11-13 选择重新登录一次，不沿用 main 检出下的旧目录）。
    - **结论随合并带回**（补充已定决策 21 的“本分支优先”）：
      - 当前分支的结论除了记在本分支上的，还包括“已并入”的：结论所在运行准备时的快照里各仓库都没有未提交的改动，执行期间产品也没有变化（`product_changed` 为空），并且快照里每个仓库的提交都已是本检出对应仓库 HEAD 的祖先。本分支的结论（含已并入的）里有当前指纹的，就只用它们；一条都没有时照旧用全部分支的结论，并标出来源分支。
      - 已并入的结论在状态旁和历史里标“来自 <分支>（已并入）”。
      - 提交在本机找不到（例如别人还没推送）、仓库在本机没有登记、快照里有未提交改动的，都不算已并入，照旧只按分支名归属。要让验收结论随合并带回 main，验收前先提交；随包技能写明这一点。
      - 只用已有的记录：共享的运行记录里本来就存着准备时的快照（各仓库的提交、分支与未提交改动数），不改表结构。祖先关系按提交对缓存。
    - **本机库格式升到 8**（使用者 2026-11-13 选择）：“同一检出只能有一个 prepared 运行”由本机库的唯一索引强制，身份浏览器也要按身份记录，所以本机库升格式，不在打开时修改表结构。本机库与共享库的格式号分开：本机 8，共享库与没配共享库时的业务记录表仍是 7，别的机器不受影响。本机库改动：`local_work` 的唯一索引只约束 distill；`browser_instances` 以身份为主键，另记最近一次交给的检出。升级后旧的本机库按 `project-format` 拒读：把 `board.sqlite3`（连同 `-wal`、`-shm`）移走后重新启动看板即重建；共享库里的业务记录不受影响，没配共享库的项目则连同业务记录一起丢弃（v10 不写迁移）。升级前先提交或放弃本机 prepared 的运行、修复与沉淀。
    - **实施顺序**：先做停止与重启；再一起做轮流使用、并行运行和身份浏览器共用（多个运行要靠身份租约分开，换检出要靠共用的身份浏览器）；最后做结论随合并带回。各步什么时候验收，开工前按已定决策 23 定。
    - **同步修改**：`docs/reference.md`（守护进程、命令一览、运行准备、浏览器代理、错误码 `scenario-in-run`、`run-ambiguous`、`env-shared`）；`prompts/run.md` 与 sop-board 技能（`--wait`、`--identity` 的用法，环境随重启中断时重做场景，验收前先提交）；playwright-acceptance 技能（身份浏览器各检出共用）；现行场景集 `docs/sop/environment.yaml`、`browser.yaml`、`run.yaml`（`port_step: 0` 由直接返回 `env-busy` 改为排队与自动切换、同一检出多个 prepared 运行、按身份的 profile、`stop` 与 `restart`）；`.tw/` 里已定决策 24、26 和共享记录的知识。
    - **不做**：一台机器上多套环境并行（不加槽位池，不做按身份转发流量的浏览器代理）；`port_step` 保持现状，适合演示项目这类轻量产品，真实产品一般设为 0。环境跨看板重启保留。看板“AI 重跑”同一检出启动多个会话。队列持久保存或跨机器排队。多台机器共用同一批测试账号时的互相干扰（已定决策 21 推迟的，仍不做）。

## 目标架构

### 核心概念（只有这些）

| 概念 | 定义 | 存放 |
| --- | --- | --- |
| 项目 | 原“工作区”，由名称和若干仓库组成，是一台机器上对一个产品的搭建。仓库身份取规范化后的 origin | `~/.sop-board/<名称>/config.yaml`、`project.json`、`board.sqlite3`（本机库格式 8，业务记录表格式 7；旧目录直接拒读，不迁移） |
| 产品 | 共享的单位：多人协作时各机器的项目绑定到共享库里的同一个产品，有 ID 和名称；没配共享库时，项目自己就是产品（已定决策 21） | 共享库的产品登记；绑定关系在本机 `project.json` |
| 机器 | 一个数据根目录，有生成一次的随机标识和显示名（缺省“操作者@主机名”）；共享记录里的“产出机器”都指它 | `~/.sop-board/machine.json` |
| 业务记录库 | 结果、标注、守护运行、修复、批注等业务记录的存放处：配了 `shared_database` 是共享的 PostgreSQL，否则是本机 SQLite，两者同一套表与规则 | 见“数据库”一节 |
| 检出 | 项目各仓库的一套工作副本。`main` 是登记路径；worktree 检出按 git common dir 自动识别：当前仓库和同一父目录下的兄弟 worktree 组成一套，缺的仓库回落到 main。每个检出有槽位号 | 数据库 `checkouts` 表 |
| 场景文件 | 产品仓库 `scenarios.path` 下的 yaml，**唯一真相**。从检出目录现读（按 mtime 缓存），格式沿用 `scenario_file.py`，元数据增加 `status: draft\|confirmed` | 产品仓库 |
| 场景键 | `<文件名>#<场景编号>`，指纹沿用现有算法（四要素） | 计算得出 |
| 运行 | 一次执行或复验：范围、检出、产品快照、执行者、实现者、独立性、未执行清单及原因、服务停启记录。运行编号由本机分配，在业务记录库里以“机器标识 + 本机运行编号”唯一 | `work` 表（kind=run）+ 本机 `runs/<编号>/` 目录 |
| 结果 | 运行中某场景的结果与证据，绑定指纹，记录取证时的产品快照、产出机器、检出与分支。通过与失败是结论，受阻与跳过是非结论（已定决策 21） | `results` 表（kind=agent）；证据文件按 sha256 存在产出机器的 `evidence/` 目录 |
| 标注 | 测试同学对场景当前内容的复测结论（通过 / 不通过 / 阻塞 / 需求变更，可附缺陷链接、说明与姓名，均不必填），都是结论 | `results` 表（kind=manual） |
| 未执行记录 | 某次运行里某场景因本机暂时不具备条件而没有执行：谁、哪台机器、什么时候、缺什么。不是结果，不参与状态推导（已定决策 22） | 运行记录的业务部分 |
| 守护 | 场景到低成本测试的关联，绑定场景指纹与测试文件摘要 | 产品仓库 `<scenarios.path>/regression.yaml` |
| 守护运行 | 一次在某快照上运行守护命令的原始结果，记录产出机器与检出；未通过是非结论，只影响产出它的检出 | `guard_runs` 表 + 输出文件 |
| 沉淀登记 | 某场景某指纹已由谁、在哪台机器、用哪份测试（测试摘要）沉淀为守护；别的机器据此显示“已沉淀，本机未同步” | 业务记录库 |
| 修复 | 失败场景 → 会话在当前检出改产品 → 独立复验运行 → 提交后关闭 | `fixes` 表 |

### 场景状态（按检出推导，不存储）

参与推导的记录按已定决策 21 选出，都限于场景的当前指纹：

- **结论**（Agent 的通过与失败、人工标注、修复关闭）在产品内共享，按分支归属。本分支上有结论时只用本分支的；一条都没有时用全部分支的，并在状态旁标出来源分支。已并入当前分支的结论也算本分支的：取证时各仓库没有未提交改动、执行期间产品没变，且各仓库的提交都已是本检出 HEAD 的祖先；显示为“来自 <分支>（已并入）”（已定决策 28）。
- **非结论**（受阻、跳过、守护未通过）只取本机本检出产出的。
- 未执行记录不参与推导，只显示在场景详情里。

选出的记录按业务记录库分配的序号排先后，然后：

- **未执行**：没有选出任何结果。
- **通过**：最新结果为通过，且没有更晚的未通过守护运行。代码改动不改变状态（已定决策 18）。
- **待复测**：本检出最近一次守护运行未通过，且晚于最新结果；或最新为失败、受阻，之后修复已关闭；或测试同学标注不通过后修复已关闭。
- **失败 / 受阻 / 跳过**：最新结果如此（测试同学标注不通过按失败、标注阻塞按受阻显示）。Agent 的受阻与跳过只在产出它的检出上改变状态；别的机器上的受阻、跳过与守护未通过不改变本机状态，显示在场景详情的“其他机器上的情况”里。
- **需求变更**：测试同学复测时标为需求变更。场景文件按新需求修改后指纹变化，回到未执行。
- **待沉淀**（徽标，只与“通过”并存）：状态为通过，同一指纹上已有经真实入口的 Agent 独立通过，且没有有效守护（已定决策 25）。
- **待人工复核**（徽标，可与“待沉淀”并存）：状态为通过，且最新结果是 Agent 经真实入口的独立通过，之后还没有人工标注。测试同学标注任一结论后徽标消失。
- **Agent 独立通过的人工确认率**：样本是每条 Agent 独立真实入口通过，配对关联该结果的最近一条人工“通过”或“不通过”；分子为人工通过，分母为人工通过加不通过。人工阻塞与需求变更不进分母，单列计数。复核覆盖 = 有配对的样本数 / 全部样本数。人工不通过的样本列为误判明细，供每周复盘逐条归因（Agent 判错、场景缺漏、环境等）。

### 进程与入口

- `sop-board serve [项目] [--lan] [--port]`：**看板守护进程**，可以在终端或 agent 会话中启动（使用者 2026-11-10：可以根据验收需要启动服务和浏览器）。在 Codex 沙箱里（环境有 `CODEX_SANDBOX`）启动的看板及其子进程仍受沙箱限制：浏览器启动即中止，启动的会话读不到客户端的登录凭据。serve 在这种环境下启动时先打印这条提示；技能要求会话在沙箱里不自行启动看板，请使用者在终端启动（2026-11-13 真实会话验收发现）。负责：网页、按检出管理 adapter 环境、浏览器代理、本机无头会话启动器。CLI 需要环境或浏览器时，通过回环 HTTP 调用守护进程（数据目录里的本机令牌文件鉴权）；守护进程没运行时直接报错并给出启动命令。配了共享库且带 `--lan` 启动时，把机器标识、显示名和内网地址登记到共享库，供别的看板读取本机的证据（已定决策 21）。停止与重启用 `sop-board stop|restart`：`restart` 保留浏览器、浏览器租约、启动的会话与 prepared 的运行，由新进程认回，并重新拉起原来在运行的环境（已定决策 28）。
- **会话 CLI** 是 Agent 工作的唯一入口。看板上的“AI 重跑”“沉淀”按钮（仅本机）用同一份 `sop-board` 技能在检出目录启动 `codex exec` 或 `claude -p`（按 `agents` 配置），只记录进程号、日志和退出码；同一检出同时只运行一个。

### 检出与环境（问题 3）

- **识别**：`gitops` 对 cwd 运行 `git rev-parse --show-toplevel --git-common-dir`。common dir 等于某个已登记仓库时，该仓库就属于当前检出；同一父目录下的兄弟目录，如果是其他已登记仓库的 worktree，也并入同一检出；剩下的仓库回落到 main。检出第一次被看到时登记并分配槽位，main 的槽位固定为 0。`checkout create <名称> [--from ref]` 沿用 adapter.worktree 和 cleanup 契约，复用 cw2 的 `worktree.py`，并沿用 `worktrees.validate_path` 的三项核对。
- **环境**：守护进程按检出运行 `adapter.env`，传入 `SOP_CHECKOUT`、该检出各仓库的 `SOP_REPO_<别名>` 和 `SOP_PORT_OFFSET = slot × port_step`。实际端口为 `ports + offset`；入口地址变量从 adapter 的 ready 输出里读取。
  - `port_step: 0` 时各检出共用同一组端口，环境在检出之间轮流用（已定决策 28）：环境由当前检出的 prepared 运行占住，没有 prepared 运行就是空闲，别的检出要用时守护进程直接换成它的；被占着时 `run prepare` 返回 `env-busy`（写明占用的检出、运行与排队情况），带 `--wait` 时在本机排队等待；`env up` 照旧直接返回 `env-busy`。不互相覆盖。
  - 环境记录启动时的快照，快照变化后由 `run prepare` 重启；这套环境上还有别的 prepared 运行时，等它们结束（已定决策 28）。
  - 守护进程重启时，清理记录在案、但已成为孤儿的进程组；经 `restart` 重启时，新进程重新拉起原来在运行的环境（已定决策 28）。
- **服务与部分就绪**（已定决策 22）：`adapter.services` 声明服务的名称、业务说明和是否可停。adapter 把各服务的状态写到 `SOP_ENV_LOG_DIR/services/<名称>.state`（运行中、已停止、本机未搭建、异常退出），守护进程用同目录的 `<名称>.request` 文件请求停止、删除它请求启动。adapter 输出就绪即环境可用，不要求所有服务都在运行；`env status`、本机看板和运行目录列出各服务的状态。`env stop|start <服务>` 只在本检出有 prepared 运行、且这套环境上只有这一个 prepared 运行时可用（已定决策 28），停启记进运行，`run submit` 或 `run abandon` 时自动恢复还停着的服务。没声明 `services` 的 adapter 照旧工作。
- **check**：只做三件事：校验配置；在当前检出拉起环境并探测就绪；核对浏览器运行时。环境就绪以 adapter 输出就绪为准，没在运行的服务和缺失的入口地址只列出，不算失败。删除五步自检中的工作树建立与清理步骤，也不再把它当作执行门槛，因为 `run prepare` 拉起环境本身就是核对。
- **快照**：`gitops.product(checkout)` 沿用分批 git 读取，按 各仓 HEAD + `git status --porcelain` 输出缓存。快照只记录取证时的代码版本、决定环境是否重启，不参与状态判定（已定决策 18）。场景目录、`snapshot_exclude` 以及 `regression.yaml` 引用的测试文件不计入快照。

### 浏览器代理（问题 5、6）

- **运行时**：`src/sop_board/assets/runtime/` 带 `package.json`（固定 `@playwright/test` 1.64.1）和 lock 文件。`sop-board browser install` 在 `~/.sop-board/runtime/` 中 `npm ci`，再设置 `PLAYWRIGHT_BROWSERS_PATH=~/.sop-board/runtime/browsers`，执行 `playwright install --no-shell chromium ffmpeg`。可执行文件路径取自 `playwright-core` 的 `chromium.executablePath()`，与 CfT 版本一起写入 `runtime.json`。此后不再读 `~/.sop-board/node_modules` 和共享的 `~/Library/Caches/ms-playwright`。
- **启动**：只有守护进程能启动浏览器，执行者不自己启动。守护进程可以在 agent 会话中运行；浏览器缺省无头，启动即崩溃时按下面的崩溃规则记受阻并写明信号与日志。
  - 每个身份一个浏览器，各检出共用（已定决策 28）：`--user-data-dir=<数据目录>/browsers/<身份>/profile --remote-debugging-port=<端口> --no-first-run --no-default-browser-check --use-mock-keychain`。交给与上一次不同的检出之前清空 HTTP 缓存，cookie、本地存储与登录保留。
  - 不加 `--enable-automation`。默认无头运行（`--headless=new`）；`browser open --headed` 和真人登录使用同一份 profile。
  - 缺省端口 = `9400 + 身份序号`（已定决策 28 起不含槽位）；被别的进程占用时顺延到下一个空闲端口，实际端口记在浏览器实例里并经 `run.env` 交给执行者（已定决策 24）。
  - `/json/version` 15 秒内有应答才算就绪。
- **租约**：`run prepare` 为本轮 Web 场景用到的身份取得租约（带 `--identity` 时只取这些身份；身份租约整机独占，已定决策 28），确保对应浏览器已启动，并写出 `runs/<编号>/run.env`，其中有 `PW_CDP_ENDPOINT`、`PW_IDENTITIES`（每个身份带 endpoint）、`PLAYWRIGHT_BROWSERS_PATH`、`PW_NODE_ROOT`。身份被真人登录占用时，直接返回 `browser-busy`。删除 `WAIT_BROWSER`，也删除身份的 `cdp` 字段。
- **真人登录与交还**：`browser open --identity X --headed` 在有界面的 CfT 窗口打开入口地址，并持有 human 租约（窗口已开着时只取得租约，不重启）。用户自己输入密码、完成人机验证或 2FA，profile 保留登录态；之后用 `browser release` 交还：只解除 human 租约，窗口和页面保持打开，下一次取得租约的运行直接沿用这个进程（仍是有界面窗口），人在窗口里通过的验证、权限与证书例外都还在。没有 `--headed` 的 `browser open` 遇到运行中的有界面窗口时直接沿用，不取得租约，不重启成无头。`browser close` 结束浏览器并释放租约，只在要关掉它时使用。出现 `browser may not be secure` 时停止，该身份的场景记为受阻并写明原文。不回退到用户日常 Chrome，也不改 UA 或参数绕过。（已定决策 16）
- **看板停止与重启**（已定决策 26）：守护进程正常停止时关闭无头浏览器，保留有界面的窗口；启动时按 profile 目录认回仍在运行、调试端口有应答的浏览器，遗留的无头浏览器照旧清理，核对不通过的有界面窗口不结束、登记为未认回。认回的浏览器用查看进程是否还在的办法监视。经 `restart` 重启时无头浏览器和租约也保留，由新进程认回（已定决策 28）。
- **崩溃**：监视线程 `wait()` 浏览器进程。异常退出时，记录信号、`chrome.log` 末尾，以及启动之后写出的 `DiagnosticReports/Google Chrome for Testing*.ips`。持有租约的运行在提交时，相关场景记为受阻，finding 写成“浏览器进程 <时间> 因 <信号> 退出，日志 <路径>”，同时加一条待人处理。租约持有期间不自动重启，下一次取得租约时再启动。30 分钟内异常退出两次，状态记为 crashed，须由人运行 `browser open --reset-crash`。模板里补上 `page.on('crash')` 和 `/Target crashed/`，渲染进程崩溃也按受阻处理。
- **playwright-acceptance 技能改动**：
  - `templates/connection.mjs` 只读 `PW_CDP_ENDPOINT`，删掉 7-19 行（DevToolsActivePort、`PW_CHROME_USER_DATA`）和 39-114 行（`targetTransport`、`PW_CDP_MODE`），保留 `connectOverCDP :128`。
  - `identity.mjs:25-28` 改用 `spec.endpoint`。
  - `fixtures.mjs` 补上崩溃处理；`global-setup.mjs` 只检查 endpoint。
  - `SKILL.md` 和 `references/{web,workflow,shopify,commands}.md` 改成“连接看板启动的 Chrome for Testing；执行者不启动浏览器，也不运行 playwright install”。
  - 删除 `scripts/patrol.mjs`，`references/spec-library.md` 改名为 `spec-fidelity.md`。

### 守护与沉淀（问题 4）

- **`<scenarios.path>/regression.yaml`**：放在产品仓库，随检出走。

  ```yaml
  version: 1
  commands:
    unit: {repo: app, cwd: ., argv: [uv, run, --group, dev, pytest, -q, "--junitxml={junit}"], timeout: 900}
    web:  {repo: app, cwd: acceptance/specs, argv: [node, "{playwright}", test, --reporter=junit], timeout: 1800, browser: merchant}
  guards:
    "orders#SOP-12-P01":
      fingerprint: <场景指纹>
      acceptance: {result: <结果编号>, executor: <会话>, product_digest: <摘要>}
      tests: [{id: t1, repo: app, path: tests/test_orders.py, sha256: <摘要>, name: "test_orders::test_rename", layer: unit, command: unit}]
      coverage: {expected: [{index: 0, text: "…", tests: [t1]}], forbidden_effects: [{index: 0, text: "…", tests: [t1]}]}
      detection: {method: mutation, assertion: "…", evidence: <证据 sha256>}
      ledger: []   # 浏览器层测试的保真账本
  ```

- **守护有效的条件**，缺一不可：
  - 场景存在，当前指纹相同；
  - 各测试文件是仓库内的普通文件，且 sha256 一致；
  - coverage 逐条、按顺序覆盖全部 expected 和 forbidden_effects，文字与当前一致；
  - 检出能力的证据在证据索引里有记录（证据文件可以在别的机器上）；
  - `acceptance` 在业务记录库中是同指纹的独立通过；
  - 没有登记过漏检。

  只覆盖了部分预期的守护不写进索引。有效性由每个看板按本检出的文件现算，不存成共享记录（已定决策 21）：
  - 沉淀成功时把沉淀登记（场景、指纹、测试摘要、沉淀人、机器、时间）写入业务记录库。
  - 业务记录库里有当前指纹的沉淀登记，但本检出的 `regression.yaml` 没有这条守护或测试摘要不同时，不显示“待沉淀”，显示“已由 <沉淀人> 沉淀，本机未同步”；`retest` 不运行它，也不写记录。
  - 守护引用的仓库在本机没有登记、命令跑不了时，`retest` 把它列为“本机无法运行”，不记作未通过。
- **`sop-board retest`**：由守护进程执行，不需要 AI，用来发现代码改动带来的回归。
  1. 记录快照，列出守护有效的场景（缺省全部，可指定）。
  2. 运行有效守护引用的命令：只用 argv，不经 shell；工作目录是检出对应仓库下的 `cwd`；超时后结束整个进程组；环境变量是该检出的 adapter 环境加上运行时变量；声明了 `browser:` 的命令先取得租约，再注入 CDP 变量。
  3. 每条命令退出码为 0，声明的测试名都出现在 junit 里且结果为通过（跳过或缺失都不算），并且运行前后快照不变，才写入一条通过的 `guard_runs`，原始输出存为证据，场景状态不变。
  4. 其余情况写入一条未通过的 `guard_runs`，场景在本检出转为待复测并附上原因；`retest` 不判断失败原因，原因里写明当时本机没在运行的服务，以及工作区是否有未提交改动（已定决策 22）。之后经真实入口通过，或修好后在本检出重新运行守护通过，就回到通过。别的机器的状态不变，只在场景详情里看到这条记录（已定决策 21）。

  只运行一次 retest 的范围由 `--dry-run` 预览；仓库里有未提交改动也可以运行，因为快照包含工作区内容。
- **漏检**：某场景最近一次守护运行通过，之后真实入口执行或人工复测发现失败时，记一条漏检。该守护随即失效，直到重新沉淀，且测试摘要发生变化。漏检只在同一台机器的同一检出内判定（守护运行与失败的结果出自同一份工作副本）；登记后按“文件 + 场景 + 指纹 + 测试摘要”共享，各看板都按它判守护失效。
- **沉淀**：
  - 状态为通过、同一指纹上已有独立真实入口通过、但没有有效守护的场景，显示为“待沉淀”（已定决策 25）。
  - `distill prepare [F#ID…]` 在当前检出准备工作目录。会话在当前检出写测试（不提交），写出 `guard.json` 后运行 `distill submit`。
  - submit 交给守护进程处理：按上面的有效条件核对；浏览器层测试另跑保真检查（沿用 `spec_library.ast/check_one/qualified :109-122,465-565`），基线是 `git show HEAD:<path>`，首次以产生独立通过的那份 spec 为准；然后按 retest 的规则实际运行一次；全部合格后合并进 `regression.yaml`，留给开发者审核提交。
  - 首次沉淀的基线按场景认，不按文件名认：取那条独立通过所属运行目录里覆盖该场景的 spec，守护 spec 改了名字也以它为基线。运行目录在本机、却找不到或找到不止一份覆盖该场景的 spec 时，submit 拒绝并列出运行目录与找到的文件；只有独立通过出自别的机器（本机没有那份运行目录）时才不设基线。这次比较按各自 spec 所在目录认文件；spec 直接导入的 `./fixtures.mjs` 是可替换的运行适配接口（守护要在 retest 里独立运行，必须换一份），不计入断言比较，项目自写的 `library.mjs` 及其导入照常比较；替换后的夹具是否真的执行步骤、断言失败会不会传出来，由沉淀时的实际运行与检出能力证据核对。基线本身不合 spec 规则（规范脚本只经 `./fixtures.mjs`、`./library.mjs` 导入）时，submit 拒绝并写明出问题的是基线，要按规则写 spec 重新验收后再沉淀；执行会话写验收 spec 时就遵守这条规则（2026-11-13 真实会话验收发现）。
  - 看板上的“沉淀”按钮仅本机可用，作用是启动一个无头沉淀会话。
  - 需要某个依赖故障的场景，守护写在不需要真实停服的层（单元、接口或组件层，用替身模拟依赖不可用）；写不出这样的测试时不沉淀，沉淀报告里写明原因（已定决策 22）。
- **spec 库并入守护的浏览器层**：`regression.yaml` 取代 `INDEX.json`，成为唯一索引。`seed()` 改为从 `regression.yaml` 预置：守护有效就预置，过期的只作参考。删除 `index/version_digest/promote/import_cw2`、`_history` 和 `baseline` 目录。
- **regression-distill 技能改动**：
  - `SKILL.md:8` 改为“完整守护由 `retest` 运行，发现代码回归”；
  - 第 15-16 行改为只认独立通过，删除“独立验收未完成可以沉淀”；
  - 检出能力核对改为必需；
  - 产出改为 `guard.json` 加 `distill submit`，删除 CI 段落和按提交重新登记；
  - `references/report.md` 改成上面的结构。

### 看板：三栏场景工作台（问题 2）

- 路由：`/` 是项目列表（只有一个项目时直接进入）。`/p/<项目>?checkout=<名称>` 是工作台：左栏是 文件→节点→场景 树，每条带状态点，可一键全部展开或收起，左栏本身可隐藏（已定决策 15）、可拖拽调宽（已定决策 19）；顶部是检出切换、搜索和状态筛选（待复测、失败、待人工复核、待沉淀、通过、未执行、草稿），各筛选带计数；概况页另显示 Agent 独立通过的人工确认率与复核覆盖。右栏顺序固定：
  1. 标题和徽标（P 级、入口、正反向）；
  2. 当前状态和原因（例如“守护测试未通过：…”）。结论来自其他分支时标出来源分支；另显示最近一次未执行（谁、什么时候、缺什么）和“其他机器上的情况”（各机器最近一次的受阻、跳过、未执行和守护未通过，写明谁、哪台机器、什么时候、原因）；
  3. 起点、步骤、预期、禁止（预期和禁止逐条列出，附守护覆盖标记；别人已沉淀而本机未同步的，标“已由 <沉淀人> 沉淀，本机未同步”）；
  4. 最新结果和证据画廊：截图、内联视频（沿用 Range 播放）、trace、请求响应。trace 在本机页面可直接在 Trace Viewer 中打开；内网页面提供下载，并说明下载后在 Trace Viewer 中选择该文件打开（浏览器不允许 https 的 Trace Viewer 读取 http 的内网地址，直接打开的链接在内网无法使用，不提供）。结果写明产出机器与分支；执行时有服务被停着的，显示“执行时 <服务> 已停止”。证据在别的机器上时，由本机看板从那台机器的看板取回并核对后显示，读不到就显示“证据在 <机器显示名> 的机器上”；
  5. 复测标注表单：通过、不通过、阻塞、需求变更；缺陷链接、说明与姓名都可不填，每个输入框独占一行；姓名在顶栏填一次，各页面与场景共用，使用者主动修改才变；
  6. “AI 重跑此场景”“运行守护”“沉淀”三个按钮，仅本机；
  7. 历史（折叠），每条写明产出机器与分支。历史列出参与本看板推导的记录：当前内容上按“场景状态”一节选出的记录；旧内容上的记录只列本分支的结论和本检出的非结论，别的分支上内容不同的结果不列入。

  草稿场景的详情与审阅见已定决策 20：不显示复测表单，显示路径、四要素、SOP 规则原文、检查清单、批注表单与“同意”。URL 带 `#<场景键>`，可以直接分享。
- 其他页面只保留：收件箱和待答复（上传用例、回答问题）、SOP 原文、交互地图、待人处理、运行记录（本机可以看日志）、报告导出、设置（仅本机，已定决策 27）。草稿只在工作台的“草稿”筛选中审阅（已定决策 20）。本机页面另显示本检出各服务的状态（已定决策 22）。
- 内网可以：查看、复测标注、回答问题、批注草稿、同意草稿场景或撤销自己的同意、上传用例或 SOP。不显示本机路径、会话编号、命令和凭据变量名，也不显示共享库的主机、端口与库名。内网的写入只限上面几种；其他写入，以及发起运行、沉淀、守护和设置页，都只接受实际回环连接。POST 继续核对同源和 JSON 类型。
- 删除的界面术语：批次、轮次、待同步、已作废、沿用、执行入口、看板与会话之分、任务状态。独立性只在历史里显示。

### 独立性（取代交接仪式）

- 首选做法：协调会话运行 `sop-board run launch …`，由守护进程启动一个新的无头会话执行。这个会话只拿到 prompt 文件，会话编号由启动器取得（Claude 用 `--session-id`，Codex 读 `thread.started`），启动记录就是独立性的证据。原来的两段交接、handoff 文件与替代标签规则全部删除。
- 当前会话自己 `run prepare` 时，执行者取自 `CODEX_THREAD_ID` 或启动器注入的 `SOP_BOARD_SESSION`，取不到就要求 `--session`。实现者有三个来源：修复复验时自动取修复会话；否则用 `--implementer <会话编号>` 或 `--implemented-by <操作者>` 声明（二选一）；不声明记为“未声明”。仍然分三类：独立验收、实现者自检、未声明。
- 跨机器验收时执行会话拿不到实现者的会话编号，用 `--implemented-by <操作者>`：与本机操作者不同记独立验收；相同则以参数错误拒绝，要求改填会话编号。实现者由使用者在任务里说明，没说明的照旧记未声明，会话不追问（已定决策 21）。`--implementer` 只填改了被验收代码的会话：协调会话自己没改代码、使用者也没说明实现者时不填。
- **范围核对与启动结果**（2026-11-13 真实会话验收发现）：`run launch` 启动会话之前，按 `run prepare` 的同一套规则核对范围（场景是否存在、是否草稿、所在文件是否合格、同一检出是否已有 prepared 的运行），不合格就以同样的错误码直接拒绝，不启动会话。指定的场景所在文件不合格时，`run prepare` 与 `run launch` 都返回 `scenario-file-invalid`，列出文件、字段与行号，不报 `scenario-not-found`；`--scope pending|all` 不因别的文件不合格而拒绝，照常按合格文件选场景，输出与运行目录说明列出未纳入的不合格文件，执行会话在报告中转述。启动失败（`failed`）同样让 `run wait` 以业务失败返回。启动的会话准备了运行（或沉淀）却没有提交就退出时，`launch status` 写明哪项工作未提交，`run wait` 以 `launch-unsubmitted` 业务失败返回（使用者 2026-11-13 决定）。启动的会话退出时没有产生任何运行（或沉淀）工作，`launch status` 把这次启动标为“未产生运行”并附日志末尾，`run wait` 以业务失败返回。启动器交给客户端的目录一律先解析成真实路径，只把需要写入的目录作为可写目录。

## 风险与说明

- **不兼容**：v10 不读旧数据目录。cw2 需要重新 `init` 新项目，旧结果和证据只能在旧目录与 Git 历史中查阅。cw2 有轮次在运行时不升级已安装的工具，到时把升级命令交给用户执行。
- **Paseo 下的崩溃对话框**：chan-product 的 WebKit 崩溃不在本仓范围，完成后单独告知用户（例如在 agent 场景下停用它的 `iphone-webkit` project）。
- **守护进程可以在 agent 会话中启动**：浏览器缺省无头以避开窗口注册失败，启动崩溃会如实记受阻；`status` 会显示守护进程是否在运行，并给出启动命令。
- **工作量**：约 9k 行新代码、技能与文档全部重写，按阶段推进；每个阶段结束先自检，再进入下一阶段。
- **共享库是唯一一份业务记录**（已定决策 21）：连不上时不能读写业务记录，也没有本地缓存；备份由部署共享库的人按文档示例自己做。各机器的 sop-board 版本须与共享库的表结构版本一致。
- **两种库的验收**：现行场景缺省在 SQLite 上验收；已定决策 21 的场景和各能力文件的 P0 场景在 PostgreSQL 上再验收一遍；沉淀出的守护测试对两种库各跑一遍。
- **共享库密码在本机 config.yaml 里是明文**（已定决策 27）：靠文件权限 600 和各处输出不外露来保护。能读本机数据目录的会话读得到它，随包技能要求会话不读取、不输出这一项。不愿意把密码放在配置里的，照旧不写 `password`、用 `~/.pgpass`。
- **各看板显示的是本检出的场景内容**：检出落后时，别人按新内容登记的结果对不上本机的指纹，显示为未执行；拉取后即一致。
- **Codex 沙箱提示只认 `CODEX_SANDBOX`**：这个变量可能只在 macOS 的 Codex 沙箱里设置，Linux 上 serve 的提示与技能里的判断可能都不触发。未核实，先记下不处理（使用者 2026-11-13）。
- **一台机器一套环境**（已定决策 28）：并行的上限是这套环境里的身份数；检出之间切换要重新拉起环境（cw2 在热缓存下 8～42 秒），各检出交替排队时会反复切换。要更多并行就加机器。升级到这一版时，按检出存放的旧 profile 不迁移，真实账号要在新窗口里重新登录一次。
- **守护拿不到本机才有的值**：retest 只给守护注入入口地址变量，守护需要本机路径（例如演示库的 SQLite 文件）时没有可移植的来源，只能写进命令或测试。以后处理（使用者 2026-11-13）。
