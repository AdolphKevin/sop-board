## 二、问题

### 1. 手改场景文件触发全量重新合并，并静默还原手改（最重）

- 使用者说“修改 SOP”，协调会话让子代理直接改 `docs/sop/ChatWILL架构升级-20260828-组织-品牌-店铺.yaml`。看板约 1 秒后排合并（`service.py:1015`，`trigger=场景文件变化`），先后产生 #124、#125、#126、#128。四次都是全量，由看板后台的 Codex 执行，合计约 45 分钟。#125 因为编辑还没停下就转成“待同步”，结果作废，至今仍挂在 attention 里（见问题 6）。
- #124：45 个场景被并为细节，以镜像行出现（场景数 429→384）。镜像行按看板里的旧用例副本重建，手改的新术语被改回旧文字。会话误以为是子代理误删，另派一个 Opus 子代理去恢复，结论是不能恢复。
- #128：TC_OS_ORG_002 的手改被按用例原文重建。同一次合并还改写了约 50 处节点描述，改了 16 个场景的角色或验证方式（如 TC_SEC 组由 api 改为 app）。这些都没人要求，也没有提示。
- 随包技能（`SKILL.md`、`references/merge.md`）里没有一处说明场景文件是合并产物、手改会怎样。“实现与返工会话不改 docs/sop”只写在本仓的 AGENTS.md 里，产品会话看不到。

### 2. 针对缺口的答复会把下一轮变成全量

D104 第 3 条规定：有待处理的合并回复就全量。#129 只涉及 128:G1（3 条用例）和 3 条按条增改，却要求对 497 条全部给出判断。会话处理时手写脚本，从 #128 复制了其余 494 条。看板调度的 Codex 合并遇到同样情况会整批重判，耗时和漂移风险同问题 1。

### 3. 合并结果看不懂，等待只能轮询数据库

- 合并落地时，`push` 算出的新增、改动、移除场景没有写进任务结果。`task show` 的 result 约 70 KB，全是判断明细，没有“场景数前后、哪些场景并入了哪条流程、哪些角色或验证方式变了”这样的摘要。会话靠 diff 场景文件、只读打开 `workspace.sqlite3` 查 versions 和 tasks，才弄清 #124 做了什么。主会话和 6 个子代理都直接读过数据库。
- 没有等待命令。处理 #127 的子代理在等自动合并时提前结束了；其他子代理用 sqlite 轮询循环等 #128。

### 4. 仓库用例与看板副本的差异看不见，也没有作废路径

- 仓库 `docs/test-cases` 改完术语后，会话要自己写 ruby/python 比对 HEAD、工作区和 `case_versions`，才定下 put 哪 11 条。`cases put` 不带 `--case` 时，会登记仓库里所有与并集不同的条目，其中包括落后于合并澄清的条目（会把澄清改回旧版），所以会话不敢直接用。
- 使用者要“直接删除”旧用例，但没有 `cases delete`。会话翻了 sop-board 源码和数据库，才确定改用覆盖。真要作废一条用例，现在只有 `merge exclude --gap`，必须挂在某个缺口上。

### 5. 没把产品改动对已通过结果的影响告诉使用者

改版提交后，主批次 219 条通过全部进入“产品变化待判定”。整站 UI 都改了，多数场景证明不了不受影响，按标准第 5 节要重跑。这与任务最初“已通过场景不重跑，只改脚本”的设想冲突，使用者没有被告知。改版会话只在删除旧用例时加载过一次 sop-board 技能；技能里没有“提交产品改动前后报告待判定”的要求，产品仓库的约定（AGENTS.md、验证手册）里也没有。

### 6. 小问题

- `sop-board --help` 只显示启动看板的参数（`cli.py:22` 按首个参数分发），看不到 status、cases、merge、task 等子命令；也没有 `--version`。会话是靠试 `sop-board cases delete --help` 才摸清子命令的。
- 本机 attention 里，#125（待同步）的原因是空的：`fixes.py:808` 直接取 `task['error']`，默认说明只在内网投影（`task_visibility.py:89`）里才补上。而且它之后 #126～#131 都已落地，它还挂着。
- `--reason` 要求写“使用者原话”，但使用者在选择题里选中的选项是会话写的文字，技能没说这种情况怎么记。
- 没有默认确认人时，技能规定只在使用者要求时才设置（`ledger.md:21`），于是会话在同一任务里反复询问署名，也没提示有这个设置可用。
- `merge.md` 提到 `snapshot_exclude` 时只举了用例目录。cw2 的 `.tw/` 知识文档计入产品快照，team-knowledge 又要求知识与代码同一个 PR，结果改知识会让已有通过进入待判定。cw2 只好约定“轮次进行中不改 .tw”。
- cw2 的 `agents` 没有配置 `merge`，自动合并缺省用 Codex。使用者决定保持缺省 Codex，需要时由使用者在工作区 `config.yaml` 的 `agents.merge` 选用 Claude（已支持，见 reference.md「执行代理」），本方案不改。

### 7. 项目自建的验收脚本层（另立方案）

cw2 在 Core 的 `.tw/local/sop-org-settings/accept-run`（Git 忽略，31 MB）里自建了一套东西：

- 每个场景一份规范 spec，共 248 份，下一轮直接预置复用，不再重写；
- 页面对象；
- `check-specs.py`：与历史上通过的 spec 对照断言和 SQL，文字替换与结构改写分别登记在 `text-ledger.json`、`assertion-ledger.json`，并写明理由；
- 只读巡检 `patrol.mjs`；
- 轮次驱动 `drive.py` 和暂停开关 `drive.pause`。

随包的 playwright-acceptance 只有交互地图。这次改版正是靠这套东西，让 248 份脚本在不放宽断言的前提下跟上新界面，但它不受版本管理，也不随包发行。

## 三、目标

- 场景文件只由合并改写；手改既不触发合并，也不会被静默覆盖，能看到、能还原。
- 针对具体缺口的答复，和按条增改一样只判断涉及的用例。
- 合并改了什么、任务何时结束，用命令就能知道，不用读数据库。
- 会话在宣布“可以验收”前，先把产品改动对已通过结果的影响告诉使用者。

## 四、决定

### D108 场景文件手改不触发合并

本批已有落地合并时，看板发现场景文件内容与最新版本不同（工作区扫描或 PUT），按下面处理。不区分内容的来源：手改、从 Git 拉到同事已合并好的文件、切换分支，都按同一规则处理（使用者决定 2）。

1. 内容与本批任一已落地版本相同（例如 Git 切回旧提交）：登记新版本并沿用该版本的配对，不排合并。
2. 其他情况：照常登记版本，但不排合并；新增 attention 种类 `scenario-edited`。原因中列出相对最近落地版本新增、删除、改动的场景编号，分为“由用例生成”（有配对）和“非用例场景”两组，并写明：“由用例生成的场景会在下一次合并时按用例重建，手改不会保留；要改措辞或预期，请改用例后按条增改。”

处理方式有三种：

- `sop-board merge restore [工作区] 批次`（仅本机）：把最近落地版本写回工作区场景文件，输出将被覆盖的场景编号；之后按第 1 条沿用配对，`scenario-edited` 消失。手改内容已作为版本登记过，可以追溯。
- 人发起重新合并（看板“重新合并”或会话 `merge prepare --full`）：照旧全量。准备输出列出将按用例重建的手改场景。
- 会话把手改转成用例改动后 `cases put`（技能流程，见 D112）。

其他规则：

- `scenario-edited` 存在期间，执行准备与修复复验准备都会被拒，返回 `scenario-file-edited` 和上述处理方式。
- 没有用例、只有场景文件的批次不受本条影响，保持现状。
- 合并进行中场景文件被改：沿用现有的“待同步”；不再为新内容自动排合并，按第 2 条进入 `scenario-edited`。
- `scenario-edited` 存在期间，由按条增改、上传、答复或决定触发的合并，以最近落地版本作为场景输入基线，未配对的手改版本不作为输入。模式仍按 D104 判断，例如只有用例变化时为增量。落地时用合并结果写回场景文件，覆盖手改内容；D110 的 `scenario_diff` 列出被覆盖的手改场景；`scenario-edited` 随之解除。合并期间文件再次变化，仍转“待同步”。
- D104“不改的”中“场景文件变化触发的合并为全量”一句随之删除；人发起的重新合并仍为全量。

### D109 针对缺口的答复走增量

- D104 第 3 条改为：有 `--gap none` 的通用答复，或答复的缺口编号在基线中找不到时，为全量；答复都针对具体缺口（`任务:缺口`）时，为增量。`merge reply` 只接受当前暂缓清单中的缺口，所以“基线中找不到”只是防御性分支，正常入口构造不出来，不单独验收；验收改为核对过期缺口答复被拒。
- 增量时，变化集合 = 新增与变化的用例 ∪ 所答缺口涉及的用例。`delta.json` 列出答复与对应缺口；答复是否采纳，仍按全量合并提示词的规则判断。
- 本批不纳入与重新纳入（exclude/include）仍为全量，不在本方案范围内。

### D110 合并摘要与等待

- 合并落地时，把场景文件差异写进任务结果 `scenario_diff`，包括：
  - 落地前后的场景数；
  - 新增、移除、改动的场景编号；
  - 移除的场景中，由用例生成、本次改为细节的，写出它并入的流程场景；
  - 改动的场景中，角色、入口（verify）、正反向有变化的逐条列出，写明字段名和前后值。
- `task show` 在任务对象顶层给出这份摘要，判断明细仍放在 result；合并页的任务详情显示同样的摘要。
- 全量合并改动了已有场景的角色或入口时，任务说明写“全量合并改动了 N 个场景的角色或入口”，在合并页和 `task show` 中显示。这条只提示，不阻挡落地。
- 新增 `sop-board task wait [工作区] --task <编号> [--timeout 秒]`：
  - 等待期间：任务处于看板或会话仍在推进的状态时继续等待。这些状态包括排队中、运行中、会话处理中、等待合并、等待浏览器，以及分析、修复、复验、合入、沉淀等进行中状态。
  - 返回：任务进入任何其他状态时返回，即已结束或需要人处理，例如已完成、失败、待补充、待同步、已中断、已放弃、待开发者处理、等待提交。返回时输出与 `task show` 相同的 JSON。
  - 退出码：0 表示任务已到达结束或需要人处理的状态，具体状态看输出；2 表示参数错误或任务不存在；3 表示超时，此时输出当前状态，不取消、不重排任务。
  - 省略 `--timeout` 时默认 600 秒；`--timeout 0` 表示不限时。

### D111 用例差异预览与作废

- `cases put … --dry-run`：比较方式和输出与正式运行相同（新增、改写及变化字段、未变化、被替换来源、`overrides_clarification`），但不登记上传、决定或合并，也可以不带 `--by` 和 `--reason`。会话先 dry-run 并向使用者呈报，再按使用者选定的 `--case` 正式登记。
- `merge exclude` 增加 `--case <编号>`（可重复），与 `--gap` 二选一。使用者决定某条用例本批不再纳入时，不必挂在缺口上。署名和 `--reason` 规则同现有 exclude；登记为一条答复记录（gap 记 none）并写入 `merge_exclusions`，数据库格式不变；随后的合并按现有规则排除该用例。重新纳入仍用 `merge include --case`。
- 不提供物理删除，用例的上传与版本历史都保留。

### D112 随包技能与指引文本

- `SKILL.md` 表格增加一行：“改场景的措辞、预期，或去掉某些场景 → 合并（按条增改 / 本批不纳入）”。
- `merge.md` 开头增加“场景文件”一段：
  - `docs/sop` 下的场景文件由合并生成，不要手改；
  - 改措辞或预期 → 改用例后 `cases put`；
  - 不要的用例 → `merge exclude --case`；
  - 已经手改了 → 按 `scenario-edited` 的提示还原，或转成用例改动。
- `merge.md` 的“按条增改”：先 `--dry-run` 查看差异并呈报，再按使用者选定的编号 put。
- 署名与依据：
  - 使用者在选择题中选定的内容，`--reason` 写成“选择：<选项原文>（问题：<问题原文>）”，不当作原话。
  - 同一任务中第二次为署名询问使用者、且姓名相同时，提示可以用 `confirmer --set` 设为默认确认人，是否设置由使用者决定。
  - 署名范围以一次请求为限（2026-11-08 补充）：一次请求指使用者提出的一项操作，从提出到登记完成，包括差异确认往返。之前请求中的姓名不沿用到新的请求；新请求及其确认都没有给出姓名、又没有默认业务确认人时，先询问并结束本轮。起因是 SOP-225-N01 在最终快照验收失败：实现时写入入口技能的“已有姓名授权时沿用”没有限定范围，会话据此把上一次请求的姓名用于新请求的登记。
- `snapshot_exclude` 的提示改为：用例目录和知识文档目录（如 `.tw/`）不影响运行时，可由使用者决定排除。
- `SKILL.md` 增加“交付前”一步：会话改动了已登记工作区的产品仓库，准备提交或宣布可以验收时，先运行 `status`，向使用者报告各批次的待执行与产品变化待判定数量；说明待判定场景在下一轮逐条判定影响、受影响的须重跑，并估计大致范围。没有说明这些之前，不宣布“可以进入验收”。
- `sop-board guide` 输出的产品仓库约定片段增加同一条（供写入产品仓库的 AGENTS.md），因为只改产品代码的会话不一定会加载 sop-board 技能。
- `references/sessions.md` 说明 `task wait`。合并、执行、修复各参考中，查任务状态统一用 `task show` 和 `task wait`，不只读查询数据库。

### D113 命令行与待处理事项

- `sop-board --help` 列出全部子命令，每个附一句说明，按“看板 / 会话入口 / 台账 / 安装”分组。新增 `sop-board --version`，输出包版本与安装来源。
- 本机 attention：
  - 任务原因为空时，使用与内网相同的默认说明；
  - 同批次之后已有合并落地的“待同步”合并，不再列入 attention。任务页仍可查到，并说明“已被合并 #N 取代”。“落地”指之后同批次合并任务的状态为“已完成”；#N 取编号大于它的第一个这样的任务。只排队、运行、待补充、失败或取消的后续任务都不算取代。
