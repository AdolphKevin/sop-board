## 2 为什么要一起改

- **生命周期各写一套。** 现有任务调度是 `tasks.py` 中按类型分支的循环；修复在 `fixes.py` 另有状态与 worktree；B 为沉淀新写了输入快照、结束复核、已中断与重试、`attempts/` 归档、worktree 记录、放弃与清理；A 为合并加了续接与部分落地；C 要把每类任务拆成“准备 → agent → 提交”。不统一，同样的规则会写四遍，互斥与优先级也难以保持一致。
- **人的答复形式不一。** 草稿批注（SOP-BOARD-11）、合并对话（A 的 D68）、会话问答（C）本质相同：问题单 → 真人答复 → 采纳。
- **产品快照规则不一。** B 加了“待提交 → 待验证”，C 需要在未提交的改动上执行。产品内容摘要本就按文件内容计算（`repositories.py:50-80`），统一以内容为准即可。

## 3 决定

编号接 A 的 D71。A、B 已确认的决定继续有效，本节只写修订与新增。

### D72 任务内核

- 每类任务实现同一组约定：
  - `inputs`：输入快照的组成与比较，变化项给出业务语言的名称（沿用 `executions.py:197-198`、`distill_inputs.changed` 的写法）；
  - `prepare`：生成任务目录与提示词；
  - `launch`：看板入口启动 Codex 的参数（沙箱、写入目录、环境变量、输出模式、续接会话）；
  - `consume`：读取输出、按契约校验、重新核对输入快照，一致才登记；
  - `actions`：该类任务允许的操作（重试、取消、批准、标记已处理、放弃、清理）。
- **统一状态**：排队中、待提交、待验证、等待浏览器、等待合并、运行中、会话处理中、已完成、待补充、待同步、待开发者审核、已中断、已作废、失败、Codex 不可用、清理失败、已处理、已放弃。各类任务只使用其中适用的状态；页面与接口按同一套名称显示。
- **统一恢复**：看板重启时运行中的任务记为已中断；重试先把上一次的输出与会话记录归档到 `attempts/<序号>/`，重新固定输入快照；登记按“任务、尝试序号”幂等。B 的这些做法推广到所有任务类型。
- **统一调度**：互斥与优先级以表定义，取代 `tasks.py` 中按类型的分支：修复 > 执行 > 合并与草稿 > 沉淀；同一工作区的执行、修复、沉淀互斥；同一批次的合并与执行互斥；浏览器单占；同时运行上限 3。
- **进度**：A 的 D69 进度显示（开始时间、已用时长、超时上限、最近活动、仅本机的事件摘要）由内核提供给所有任务类型，合并页之外的任务页同样显示。
- 数据库格式保持 5；新增表按现有方式以 `CREATE TABLE IF NOT EXISTS` 加入 `SCHEMA`，现有表不加列。

### D73 两个入口

- 每类任务的执行方式为 `board`（看板调度 Codex，现状）或 `session`（会话认领）。会话认领的任务记在新表 `session_tasks`：任务编号、会话标识、认领时间；看板调度器跳过这些任务，页面显示“由会话 <标识> 处理”。
- 会话入口的命令，与看板入口调用同一组内核函数：

| 阶段 | 准备 | 提交 |
| --- | --- | --- |
| 1 写业务 SOP | `sop-board sop prepare <工作区> <批次> --source <文件>...` | `sop-board sop submit … --confirmed-by <确认人>` |
| 2 SOP 生成草稿 | `sop-board draft prepare <工作区> <批次>` | `sop-board draft submit`；另有 `draft annotate`、`draft confirm` |
| 3 用例合并为场景 | `sop-board cases upload …`；`sop-board merge prepare <工作区> <批次>` | `sop-board merge submit`；`sop-board merge reply` 记录答复 |
| 4 执行场景验收 | `sop-board execute prepare <工作区> <批次> [--scope …]` | `sop-board execute submit … --implementer <实现者>` |
| 5 修复与复验 | `sop-board fix prepare <工作区> [--scenario …]` | `sop-board fix submit`；复验用阶段 4 的 `--fix <编号>`；`sop-board fix land` |
| 沉淀（已有） | — | `sop-board distill submit`，改为内核登记 |

- 所有准备命令以 `--session <标识>` 记录会话：优先取工具提供的真实编号（Codex 的 `thread_id`、Claude Code 的 `session_id`、子代理编号），取不到时用“工具-日期时间-用途”的稳定标签，同一任务内复用。
- 命令直接读写本机工作区数据目录（与 `distill submit` 相同），看板运行与否都可用；只在本机可用，内网没有对应接口。
- 同一批次同一类任务同时只有一个未结束；看板任务已在运行时会话准备被拒，排队中时提示后由使用者决定是否取消。`sop-board task list|show|cancel` 管理任务；`sop-board status [<工作区>]` 按当前仓库找到工作区，列出批次概况与待开发者处理的事项。

### D74 会话入口须先登记工作区（用户 2026-10-22 决定）

所有阶段要求当前仓库属于已登记的工作区；找不到时技能停止并引导按 `sop-board guide` 运行 `sop-board init`。阶段 1～3 只需配置合格；阶段 4、5 还要求 `sop-board check` 通过。

### D75 随包入口技能 `sop-board`

- 新增 `src/sop_board/skills/sop-board/`，由 `skills install` 与 `regression-distill`、`playwright-acceptance` 一起链接到 `~/.agents/skills/` 与 `~/.claude/skills/`。描述覆盖中英文触发说法：根据 PRD 或需求写 SOP、生成验收场景、合并测试用例、执行 SOP 验收、复验或修复不通过的场景等。
- `SKILL.md` 只做路由：先运行 `sop-board status`，有待处理事项先报告；判断阶段后读取 `references/<阶段>.md`。各阶段说明只写会话侧的步骤、必停点与角色要求；操作契约以 `prepare` 输出的提示词为准，提示词只在 `src/sop_board/prompts/` 保留一份。
- Web 执行用 `playwright-acceptance`；执行通过后可按 `regression-distill` 沉淀。

### D76 答复统一

- A 的 D68 合并对话答复表增加“来源”：看板或会话。会话中由使用者给出的答复经 `merge reply` 写入，答复人为使用者本人，状态与采纳规则与看板答复相同，看板合并对话中可见。
- 草稿批注保持现有表；会话中的答复经 `draft annotate` 写入，作者为答复人。
- 阶段 1 写 SOP 时的待确认问题，以及会话呈报的合并缺口，均按 A 的 D66 业务场景格式书写（标题、场景、目前的写法、缺什么、请确认、涉及内容）。
- agent 不得代替真人答复、确认或选择“本批不纳入”；确认类命令要求 `--confirmed-by` 或 `--author` 为使用者明确给出的姓名。

### D77 产品快照与证据有效性

- 证据是否对应当前产品只比较产品内容摘要，提交本身不使证据失效。
- 看板入口的执行与沉淀仍要求产品已提交（环境由看板从提交启动）。B 的 SOP-127-N03 照旧：有未提交改动时显示“待提交”；提交后内容与通过证据的摘要不同则进入“待验证”，相同则直接开始。
- 会话入口允许在未提交的改动上执行：快照记录各仓提交、未提交文件清单与内容摘要，标记 `dirty`；提交后内容不变，结果继续有效。

### D78 阶段 1：根据需求资料写业务 SOP（用户 2026-10-22 决定纳入）

- 输入：使用者给出的 PRD、需求描述、技术方案、评审记录等，准备时复制进任务目录；可读工作区仓库源码。
- 新提示词 `prompts/author-sop.md`，产出业务 SOP Markdown：业务目标与范围、角色、按节点编号的规则（每条附来源文件与原文摘录）、主流程与分支的 mermaid 流程图、禁止的副作用、未覆盖范围、待确认问题。
- 预期只来自业务资料（PRD、需求描述、评审结论）；技术方案与代码只用于确定角色、入口、字段与状态名。资料之间或资料与代码矛盾、资料未写明的结果，一律列为待确认问题，不得编造。
- 必停点：会话呈报规则与问题，答复写回 SOP 并注明答复人；全部有答复后由使用者给出业务确认人。`sop submit` 按 `POST sop` 的同一校验登记为批次 SOP 原文，并记录来源资料清单与摘要，随后按现有规则进入阶段 2。
- `docs/sop-guide.md` 新增“业务 SOP 怎样写”一节。
- 看板页面暂不提供上传需求资料的入口；任务按两入口设计，看板入口另行提出。

### D79 阶段 2～4 的会话入口

- **草稿**：任务目录与 `generate.md` 不变；`draft submit` 走 `generation_problems` 校验，版本记录会话标识。`draft confirm` 在使用者给出确认人后执行，确认后转为 `sop-draft` 用例（与看板相同）。
- **合并**：任务目录与 `merge.md` 不变，含 A 的 `clarifications.json`；`merge submit` 走 A 的缺口、部分落地、用例更新核对，由 `assemble()` 拼装、经 `land()` 落地。会话把缺口按 D66 格式呈报使用者，答复按 D76 记录后再开一轮。
- **执行**：快照与任务目录与看板相同；`execute.md` 只按入口区分环境准备一段（看板入口由看板启动环境；会话入口由执行会话按项目验证技能与手册准备入口），其余不变（D83 修订）；`execute submit` 走 `read_results` 校验，执行中输入变化即作废。`sop-board playwright submit` 保留，改用同一登记逻辑。
- **独立性**（用户 2026-10-22 决定）：默认派一个未参与实现的新会话执行（Claude Code 子代理、`codex exec` 或使用者新开的窗口），交接只含任务目录、项目验证技能与手册、入口环境说明。`--implementer` 与执行者不同登记为独立验收，相同登记为实现者自检，缺省登记为独立性未声明。使用者要求当前会话执行时照实登记为自检。
- **入口环境**：执行会话按项目验证技能与手册准备入口；`address_env` 与 `credential_env` 从会话自身环境读取，缺少声明的凭据变量时相关场景记受阻（与 D65 相同）。账号授权沿用任务开始时的授权记录。
- **展示**：批次页、场景详情与 D27 报告显示每轮的执行入口、执行者、实现者与独立性，独立验收、自检与未声明分开统计。看板入口的执行轮次照旧为“独立性未声明”，在报告中如实显示。

### D80 阶段 5：会话中的根因分析、修复与复验

- `fix prepare` 认领问题场景，取数与看板相同（`fixes.py` 的 `discover`）：最新结果为失败的场景，以及复核完成的人工失败或受阻场景。已在看板修复任务中的场景不可认领；被会话认领的场景看板不建修复任务。任务目录与 `fix.md` 不变。
- 修复在开发者当前工作区进行（用户 2026-10-22 决定），只改产品代码，不写测试，不提交；`fix submit` 核对根因输出（同一 schema）与受保护的 SOP、场景文件未被改动，记录修复会话与改动文件清单，任务进入“待验证”。分类为环境、场景写法、需求变化或无法修复时不进入复验，交使用者处理。
- 复验：`execute prepare --fix <编号>` 选出问题场景与受影响场景，由未参与修复的新会话执行；复验会话与修复会话相同则拒收。登记时实现者为修复会话、执行者为复验会话。
- 开发者审核并提交后运行 `fix land`：核对提交后的产品内容摘要与复验快照一致，关闭修复记录，按看板现有方式回写 Jira；不一致时说明差异，须重新复验。
