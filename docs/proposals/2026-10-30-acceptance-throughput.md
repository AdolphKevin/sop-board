## 目标与非目标

**目标**：

- 执行前把 Web 入口的交互梳理成工作区资产，执行时直接使用。场景文案与界面不一致的地方在执行前暴露，由人决定。
- 无关的前置数据不再靠页面一步步建。
- 单个场景的平均执行时间从约 7 分钟降到 3 分钟以内。
- 批次可以连续无人值守运行，需要人的事集中处理，夜间不断流。
- 规则按多日大批次重新划分：少作废、修复可以并行、批次状态都在看板上，不靠协调会话手写交接。

**非目标**：

- 不改变独立性原则：执行者仍须未参与实现；预期只来自已确认的场景；结论只来自真实入口的实际观察。交互地图、绑定和配方只说明“怎么操作”，不提供预期。
- 不替人完成真实账号登录、人机验证和二次验证，不在生产环境写数据。
- 不在产品仓库新增测试；不恢复根 tests/。
- 同一浏览器入口不并行跑多个轮次。

## 第一期 SOP-BOARD-16：交互地图、数据配方与执行减负

### D84 交互地图是工作区资产

**定位**：每个 `surface: web` 的入口可以有一份交互地图，记录页面、导航、控件、弹窗、表格和各语言文案，由前端源码梳理并可经浏览器只读核对。它属于工作区，跨批次、跨轮次复用，按前端源码变化标记过期。

**配置**：在入口下声明 `atlas`。

```yaml
entries:
  merchant-app:
    surface: web
    # ……原有字段
    atlas:
      repos: [cw2-live-chat-front-b]   # 必填：前端仓库别名，须已登记
      languages: [en, zh]              # 可选：要记录的界面语言，缺省按前端多语言文件推断
```

**存储**：

- 文件放在 `<数据目录>/<工作区>/atlas/<入口>/v<版本>/`，包括 `atlas.json`（机器读）、`atlas.md`（人读）和可选的 `evidence/`（浏览器核对留下的页面结构快照）。
- 版本、源码文件摘要与执行者反馈另建侧表登记，数据库格式保持 5。

**内容**（`atlas.json`，结构严格，不接受未声明的字段）：

- `pages[]`：页面编号、各语言标题、路由、所在容器（主文档、iframe 或新标签页）、从起点到达的路径（经哪些控件）、就绪信号（可见的标题或控件）、控件、弹窗、表格、源码位置，以及核对情况（源码 / 浏览器核对日期）。
- `controls[]`：编号、角色（button、link、textbox……）、各语言可访问名称、多语言键、推荐定位器、`data-testid`、打开的页面或弹窗、发出的请求（方法与路径，作等待依据）、源码位置。
- `dialogs[]`、`tables[]`：标题、字段、列、行操作、空状态文案。
- `glossary[]`：被上述控件引用的多语言键及其各语言文案。

**禁止写入的内容**：

- 不写谁能看到或操作（角色可见性），也不写校验规则、默认值、业务结果与副作用。这些都是场景的预期，写进地图就会把当前实现当成正确答案。
- 校验时拒收未声明的字段。

**生成**：新任务类型“梳理交互”（`atlas`），看板与开发会话两个入口共用同一提示词和校验。

| 入口 | 命令或操作 |
| --- | --- |
| 开发会话 | `sop-board atlas prepare [工作区] --entry <入口> --session <标识> [--stale \| --pages <编号,…>] [--browser]`，产出后 `sop-board atlas submit [工作区] --task <编号>` |
| 看板 | 工作区「交互地图」页，本机点击“梳理交互”（全量或只更新过期页面） |

- **读取范围**：任务只读 `atlas.repos` 的源码，包括路由、导航、页面组件、弹窗、表单、表格和多语言资源。
- **浏览器核对**（`--browser`）：只做只读探测，不保存、不提交、不改数据；与执行一样占用该入口的浏览器名额；真实账号登录仍由人完成。
- **增量更新**：`--stale` 只重写过期页面并检查新增路由；`--pages` 只重写指定页面；其余页面原样沿用上一版。
- **处理反馈**：提交时可以写明已处理的执行者反馈，看板把这些反馈标为已采纳。

**过期**：

- 登记时按页面记录其源码文件的内容摘要。之后前端改动涉及的页面标为过期，在地图页、执行节选和下一次梳理中列出。
- 过期页面仍可使用，执行者以实际页面为准。

**执行者反馈**：

- 执行者发现地图缺失或有误时，在任务目录写 `atlas-feedback.jsonl`（页面、控件、问题类型、实际所见、证据）。
- 看板在登记执行结果时一并收下。反馈格式有误只提示，不影响结果登记。

**页面**：

- 工作区「交互地图」页列出各入口的版本、生成时间、页面数、过期数和待处理反馈，页面详情展示控件、弹窗、表格、各语言文案与源码位置。
- 内网可以只读查看，没有操作按钮。

### D85 场景绑定与界面对照清单

**绑定**：

- 有交互地图后，按批次把场景对应到地图：每一步在哪个页面、用哪些控件；场景里加引号的界面文案（「」“”）逐条对照前端文案。
- 绑定还记录场景的操作身份（取场景 actor）以及是否改动数据，供第二期编排使用。
- 由“梳理交互”任务的绑定模式完成：`sop-board atlas bind [工作区] <批次> --session <标识> [--stale]`，看板侧为批次页的“对照界面”按钮。`--stale` 只处理内容有变化的场景，以及绑定到过期页面的场景。

**对照结果**：

| 结果 | 含义 | 是否进清单 |
| --- | --- | --- |
| `match` | 某种声明语言里有完全相同的文案 | 否 |
| `translation` | 场景文案是前端另一种声明语言里同一个多语言键的译文，自动对齐 | 否 |
| `mismatch` | 对应的控件存在，但文案在所有声明语言里都不同 | 是 |
| `absent` | 找不到对应的控件或文案；也包括无法对应到任何控件的步骤 | 是 |

**由人逐条决定**（本次决定②）：批次页「界面对照」列出 `mismatch` 与 `absent` 两类条目，每条显示场景原文、所在位置、前端各语言文案，以及按 SOP 会怎样。本机与内网都可以决定，须填决定人姓名；也可以用 `sop-board atlas decide [工作区] <批次> --item <场景>#<条目> --decision sop|change --by <姓名> [--note <说明>]`。

| 决定 | 执行时的处理 |
| --- | --- |
| 按 SOP | 照常执行；实际文案不符时判失败，finding 写明实际文案 |
| 改 SOP | 该场景暂不进入待执行范围，显示“等待修改场景”，单独计数，不算受阻或跳过；场景内容变化后条目自动关闭，新内容需要重新绑定 |
| 未定 | 照常执行，按 SOP 判 |

### D86 执行时使用地图与绑定，执行材料瘦身

**任务目录新增的内容**：执行准备（看板、会话执行与修复复验）在场景入口有交互地图时，另外放入：

| 文件 | 内容 |
| --- | --- |
| `atlas.json` | 节选：待执行场景绑定到的页面、到达这些页面要经过的控件、用到的多语言文案，以及全部页面的索引（编号、标题、路由）作兜底；注明地图版本和过期页面 |
| `bindings.json` | 待执行场景的绑定，以及各条界面对照的决定 |
| `brief.md` | 不超过 5KB 的执行速查卡：阅读顺序、范围、证据要求、地图与反馈用法、数据配方规则、时间上限与停止条件、逐条写结果 |

**提示词与技能**：

- `prompts/execute.md` 与 Web 技能改为“速查卡加按需阅读的参考文档”。
- 开场必读的材料（提示词、速查卡、技能正文）合计不超过 15KB；参考文档只在遇到对应情况时再读。

**执行规则**：

- 执行者先用地图和绑定，只有地图缺了才只读查阅前端源码，并写进反馈。
- 预期只来自场景；通过必须以实际页面为依据，不能凭地图或源码判通过。
- 轮次记录所用的地图版本，供追溯，不参与作废判断。

### D87 Web 场景失败隔离与时间上限

**失败隔离**：

- 业务断言失败只记该场景失败：保留截图和页面结构快照，关掉该场景打开的页面，回到入口起点，继续下一个场景。
- 业务失败不得引起 worker 重启或新的调试连接，避免再次弹出授权。
- 只有连接异常、授权等待、出现未知遮挡或状态不明时，才停止本轮。
- 模板去掉 `maxFailures: 1`，具体机制在实现中确定；现有的 worker 复用测试保持通过。

**时间上限**（缺省值，可用环境变量覆盖，并记入报告）：

| 项目 | 上限 |
| --- | --- |
| 单个场景 | 4 分钟 |
| 定位或操作 | 15 秒 |
| 页面导航 | 30 秒 |

**操作库**：模板增加 `atlas.mjs`，执行者用 2～4 行代码完成一步，不再现写探查脚本。

- 按地图打开页面、取控件（各声明语言的名称都试）、取弹窗和表格、等待请求、截图、附加说明。
- 地图里找不到时抛出可识别的“地图缺口”，执行者据此写反馈。

**逐条落盘**：

- 每个场景结束就保存结果，执行会话中途退出时，已完成的场景不丢失。
- `sop-board playwright convert` 能转换部分结果，未执行的场景列入缺失清单。

**重试规则**（写进速查卡）：

- 只重跑没通过的场景。
- 业务失败最多再确认一次。
- 单个场景累计 15 分钟或 4 次仍没有结论时，记下现象和证据后转下一个：判断不了的记受阻，有证据表明产品不符的记失败。

### D88 前置数据：配方优先，声明范围内可临时写

本次决定①。标准第 5 节已允许“准备无关前置数据”，这里定义边界和留痕要求，并让 Web 技能与标准一致。

**定义**：

- 无关前置数据是场景 `initial_state` 中不由本场景步骤产生、也不是本场景要验证其产生过程的对象和状态，例如“组织已有 20 个成员”“品牌已归档 31 天”“套餐为 Pro”。
- 被验收流程应生成的对象，仍由该流程经真实入口产生。

**准备顺序**：

1. 先用工作区登记的数据配方。
2. 没有合适配方，而且工作区允许临时写入时，可以在声明的写入范围内临时写入。
3. 两者都不行，或需要的对象属于“只能经真实入口产生”的种类时，记受阻，finding 写明缺什么配方或范围。

**配置**：工作区顶层的 `fixtures`。

```yaml
fixtures:
  environment: "dev 环境 livechat-new 库"   # 必填，说明可以写入的环境
  scope:                                   # 必填，写入范围
    - "只写本轮测试组织（名称以 os-accept- 开头）及其品牌、店铺、成员、邀请、团队"
    - "不删除数据，不修改其他组织和共享配置"
  credential_env: [ACCEPT_DB_WRITE_DSN]    # 写入用凭据的变量名
  adhoc: true                              # 允许范围内临时写入；false 时只能用配方
```

**配方**：放在 `<数据目录>/<工作区>/fixtures/recipes.yaml` 及同目录的脚本里，每个配方包括：

- 名称、说明与参数；
- 产生的对象；
- 执行命令（数组，参数按名称替换）；
- 可选的写入前后只读核对命令。

`real_only` 列出只能经真实入口产生的对象种类，例如需要 Shopify 授权的店铺连接。

**命令**：

| 命令 | 说明 |
| --- | --- |
| `sop-board fixtures list [工作区]` | 列出范围、配方、`real_only` 和是否允许临时写入 |
| `sop-board fixtures run [工作区] <配方> (--task <编号> \| --batch <批次> --session <标识>) [--scenario <编号>] [--param 名=值 …]` | 运行配方 |
| `sop-board fixtures exec [工作区] (--task <编号> \| --batch <批次> --session <标识>) --reason <说明> [--scenario <编号>] -- <命令…>` | 在范围内临时写入；只在 `adhoc: true` 时可用 |
| `sop-board fixtures mark [工作区] --run <编号> (--promoted <配方> \| --dismiss) --by <姓名>` | 把临时写入标为“已整理为配方”或“无需整理” |

- `--batch` 用于协调会话在开跑前统一准备数据，记录会出现在该批次之后各轮的任务目录里。
- 临时写入在「数据配方」页单列为“待整理”。

**留痕**：

- 每次运行都写入任务目录 `evidence/fixtures/`，并在看板登记：配方名或完整命令、参数、退出码、输出、写入前后的核对结果、时间和执行者。
- 凭据取值一律打码。
- 带 `--task` 与 `--scenario` 的准备记录由看板关联到该场景的结果，测试同事复核时能看到哪些前置条件是写库准备的。

**禁止**：

- 在声明环境之外写入；
- 使用破坏性语句（DROP、TRUNCATE、无条件的 DELETE 或 UPDATE）；
- 修改范围外的数据；
- 用写库代替 `real_only` 对象或被验收的流程。

建议项目为写入凭据单独开一个只能写测试数据的数据库账号，写进项目手册。

**页面与内网**：

- 工作区「数据配方」页只在本机显示，包括配方、范围、最近运行和待整理的临时写入。
- 内网只在场景结果中看到打码后的准备记录。

### D89 运行辅助配置不使本轮作废

以下字段只影响“怎么跑”：

- `entries.<入口>.web_evidence`
- `entries.<入口>.atlas`
- 顶层 `fixtures`
- 交互地图、绑定和配方文件

改动这些字段时：

- 进行中的轮次不作废，按准备时固定的设置跑完；
- 不要求重跑全量自检，只做配置格式校验；
- 下一轮准备时采用新值。

其余配置字段仍按现行规则处理。第三期 D96 会给全部字段分级。

### D90 未检出子模块的产品指纹

- **问题**：产品快照遇到目录型条目时，会在子目录里运行 `git rev-parse HEAD`。子模块没有检出时，取到的是外层仓库的 HEAD（`src/sop_board/repositories.py:140`）。
- **改法**：子模块未检出时，改用外层仓库索引中记录的子模块提交；已检出时，取子模块自身的 HEAD。
- **效果**：工作区快照与已提交清单对同一个子模块给出相同的摘要，外层仓库提交不再改变它。

## 第二期 SOP-BOARD-17：执行计划、执行代理与连续运行

### D91 执行计划

执行准备可以按计划取场景：看板为“按计划执行”，会话为 `execute prepare --plan <模式>`。看板据此生成批次的 `plan.json`，并在批次页展示分组、轮次和进度。

**分组与排序**：

- 按身份 → 首个页面 → 前置状态分组：身份和页面取自 D85 的绑定，前置状态取 `initial_state`。
- 组内先只读核对，后改动数据。
- 场景 `initial_state` 引用其他场景时，按依赖排序。

**轮次**：每轮按组取 15 个场景，可配置，上限 25。

**模式**：

| 模式 | 范围与顺序 |
| --- | --- |
| `pending`（缺省） | 失败 → 新增或内容变化 → 受产品变化影响 → 其余；同类中 P0 在前 |
| `failed` | 只取失败和受阻的场景 |
| `regression` | 只取受改动影响的场景：前端改动经地图页面的源码文件找到绑定的场景，后端改动沿用现有的影响判定 |

### D92 执行代理可选 Claude Code

新增顶层 `agents` 配置，按任务类型选择执行代理。

```yaml
agents:
  default: {runner: codex}
  execute: {runner: claude, model: claude-sonnet-5-5, effort: medium}
```

- `claude` 代理用无交互模式运行，记录会话编号作为执行者身份，事件转成看板的“最近活动”，用 `--resume` 续接。
- 权限参数由配置声明，看板不擅自跳过权限确认。
- 遇到容量满载、限流等临时错误时，等待后续接同一会话，最多 3 次。
- 已逐条落盘的结果不会丢失（见 D87）。

### D93 连续运行

批次页的“连续执行”和 `sop-board run [工作区] <批次> [--plan <模式>]` 会按计划连续运行轮次：

**轮次之间**：

- 探测环境（第三期 D97 的健康探测）；
- 检查空闲内存（缺省低于 25% 不开新轮，轮中低于 8% 停止本轮并保留可续接的现场）；
- 清理多余的浏览器标签页（保留身份页，见 D95）；
- 发现锁屏就暂停。

**停止规则**：同一个问题挡住 5 个以上场景时暂停（阈值可配置），在批次页提示整合问题后修复。

**断流处理**：

- 执行会话异常退出，先续接同一会话，仍失败才停止本轮。
- 某组需要人处理时跳过该组，其他组照常继续。

暂停、继续和停止在批次页和命令行都可操作。

### D94 待人处理队列

**来源**：

- 执行者：人机验证、OAuth 授权、第三方后台设置、需要放行的权限、邮箱验证；
- 驱动：环境探测失败、自愈失败；
- 计划：`real_only` 前置需要人准备。

这些都登记为待人处理事项，写明影响的场景和操作说明。

**处理**：

- 看板首页和批次页显示待人处理事项；
- 本机标记“已处理”时填写姓名，受影响的场景重新排队；
- 每天收工前，按计划汇总“接下来需要你做的事”，一次问完。

### D95 身份池与验证码策略

在 Web 入口下声明 `identities`：

- 身份编号、对应场景 actor 的名称、账号与密钥的变量名；
- 独立的浏览器资料目录或调试端口；
- 验证码策略：`mailbox` 真实邮箱、`backend` 用只读配方从后端读取（须事先授权）、`manual` 人工；
- 次数上限：每天登录次数、每小时和每天的验证码数。

**操作与计数**：

- 操作库的 `as(身份)` 返回该身份已登录的页面：保持登录，不退出，不在同一个浏览器里切换账号。
- 看板记录每个身份的登录与发码次数，接近上限时提前提醒；超出上限就停止该身份，转为待人处理。

**真实邮箱至少用一次**：`real_once: true` 时，每批至少用真实邮箱完整收一次验证码，并留证。

**登录步骤**：由项目在地图目录的 `hooks/identity.mjs` 提供。梳理交互时可以根据登录页的源码起草这份钩子，凭据只经环境变量传入。

## 第三期 SOP-BOARD-18：规则细化、使用者维护的环境、问题台账与编写体验

### D96 场景级作废与配置分级

**场景级作废**：执行期间场景或用例变化时，只作废内容变了的场景（不登记它们的结果，提交输出与任务结果列出 `voided_scenarios`，场景回到待执行）；本轮其他场景照常登记。所选场景全部变化或验证技能变化时，仍按标准使整轮作废。

**配置分级**：

| 级别 | 字段 | 改动后 |
| --- | --- | --- |
| 业务配置 | `repos`、`scenarios`、`skill`、`snapshot_exclude`、入口的 `surface`、`operate`、`observe`、`evidence`、`isolation`、`credential_env`、`address_env`、`driver`、`adapter` 的 `mode` 与启停命令 | 按现行规则处理 |
| 运行配置 | `web_evidence`、`atlas`、`fixtures`、`identities`、`agents`、`run`（轮次大小、阈值）、`adapter.health/heal` | 不作废，不要求全量自检 |

`adapter.mode` 归为业务配置：切换模式必然同时增删 `env`、`ports` 等启停字段，本来就要重新自检。

### D97 使用者维护的环境

**声明方式**：

- `adapter.mode: external` 表示服务由使用者或其脚本启停，看板不启停服务。
- `adapter.health` 声明探测项（URL、端口或只读命令），自检和每轮开始前都只做探测。
- `adapter.heal` 声明已授权的自愈命令，例如重连端口转发。

**探测失败的处理**：先执行自愈，再探测一次；仍失败就转为待人处理。

缺省仍是现行的看板托管模式。

### D98 问题台账与修复波次

**问题台账**：看板原生的问题台账，替代各项目手写的 markdown 台账。

- 字段：稳定编号、标题、类型（产品、场景写法、环境、工具）、根因、影响的场景、状态、决定记录（谁、何时、原话），以及修复任务、提交、Jira 等关联。
- 状态：待处理、修复中、待验证、已关闭、暂缓。
- 来源：执行结果中的失败与受阻（结果可带 `issue` 字段归并到同一问题）、界面对照中“按 SOP”的条目、人工新建。

**修复波次**：

- 一个会话修复可以纳入多个问题（`fix prepare --issues …`；看板侧为“修复所选问题”）。
- 场景互不重叠的会话修复可以同时存在，取代“同一工作区只能有一个未结束的会话修复”。会话修复共用当前工作区，两个修复不能同时处于“会话处理中”（同时改代码会让各自的改动混在一起）；已提交修复输出、处于待验证或待提交的修复不再挡住新修复。

**关闭条件**：

- 修复涉及的问题场景，都在包含修复改动的产品快照上由独立执行者通过（任何执行轮次都算，不限专门的复验任务），而且改动已经提交，`fix land` 即可关闭。
- 专门的复验任务仍然可以用。

**和停止规则衔接**：问题台账提供 D93 停止规则所需的“一个问题挡住多少场景”。

### D99 编写与协同体验

**默认业务确认人**：

- 使用者可以为工作区设置一次默认业务确认人；
- 会话展示该姓名，并用于答复、确认和上传，人另行指定时以指定为准；
- 同一次交互里人给出一个姓名，覆盖这次所需的全部署名；
- 命令仍不替人推断姓名。

**场景一致性检查**：草稿和合并时，比对同一对象、角色、页面、条件下的预期。互相矛盾时作为缺口提问，例如“空团队不能选”与“把空团队设为默认团队”。

**用例导出与回写**：

- `sop-board cases export [工作区] <批次> [--upload <上传编号>] --out <文件>`：按原上传的格式和顺序导出答复改写后的用例。
- SOP 草稿生成的用例另行导出。
- `--write-back` 写回会话上传时记录的原文件路径。只在原文件自上传或上次回写后未改动、且不计入产品快照（已在 `snapshot_exclude` 或场景目录内、被 Git 忽略或不在任何仓库内）时写回；否则拒绝并给出 `snapshot_exclude` 的写法，不自动改动快照范围，避免回写本身改变产品摘要。

**批次运行页与决定记录**：

- 批次页的运行区集中展示计划、当前轮次、待人处理、问题台账、环境探测和决定记录。决定记录汇总合并答复、界面对照决定，以及会话用 `sop-board decision add --by <姓名>` 登记的决定。
- 同一工作区有多个会话在准备或提交任务时，提示这些会话及其任务，减少一个会话的提交打断另一个会话的轮次。

## 风险与对策

| 风险 | 对策 |
| --- | --- |
| 地图把当前实现的行为带进预期 | 地图结构严格，不收可见性、校验、默认值和业务结果；预期只来自场景；通过必须有实际页面依据 |
| 写库准备的数据与真实流程产生的数据不一致，造成假通过或假失败 | 配方优先用产品自身的接口，或从经真实流程产生的数据复制；`real_only` 对象不得写库；结果注明哪些前置是写库准备的，测试同事可复核 |
| 临时写入误伤共享数据 | 声明环境与范围；禁止破坏性语句；建议使用受限的写入账号；全量留痕；临时写入列为待整理 |
| 失败隔离改变 worker 行为，导致连续授权弹窗 | 业务失败不重启 worker；连接与授权问题仍立即停止；保留并通过现有的 worker 复用测试 |
| 新增的配置与页面增加学习成本 | 全部可选；`sop-board guide` 增加分步指引；没有声明时行为不变 |
