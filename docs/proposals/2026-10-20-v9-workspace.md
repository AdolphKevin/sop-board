## 0 摘要

- **看板只做通用流程，项目相关的部分由代理搭建**：上传用例、合并、执行、复核、修复、复测、合入是看板的通用流程。怎样启动一个项目的整套服务、怎样用修复代码启动、用什么入口验收，因项目而异，写成项目适配。
- **安装与搭建交给工作区里的代理**：开发者在工作区里打开 Codex 或 Claude Code，说"按 sop-board 的安装说明为这个工作区安装并搭建"。代理按看板自带的搭建指引安装看板、生成适配，跑到自检通过，再请开发者确认。之后在工作区运行 `sop-board` 即可启动；仓库身份从各仓库的 origin 读出。
- **页面只填标记人**：默认只监听本机。开放内网后，同事可以查看、上传用例和复核；执行、修复这类开发者操作只在本机页面可用。
- **一个需求跨多个仓库**：修复会话的工作目录包含所涉全部仓库的 worktree，一次根因分析覆盖全部仓库；各仓分别提交，一起复测，一起合入。
- **只以场景验收**：开发中不产出单元、接口与集成测试。用例中的格式、边界等细节并入所属流程场景的预期，由 Codex 经真实入口一起核对；修复以问题场景复测为准，产品变化后重跑受影响的场景。
- **暂缓**：场景沉淀、守护与趋势页（原 SOP-BOARD-6）、Jira 回写。

## 2 决定

### D30 工作区（取代 D14 的启动参数与 D20 的授权参数）
已由 [SOP-BOARD-8 的 D37](../designs/SOP-BOARD-8.md) 修订。

- 工作区是开发者本机的一个目录，包含需求可能涉及的全部 Git 仓库；单仓库项目的工作区就是仓库本身。从某个仓库里开始搭建时，代理按指引找出外层工作区（例如上级目录的 go.work 引用了这个仓库和它的兄弟仓库），请开发者确认。
- 看板用 `uv tool install` 安装为 `sop-board` 命令；启动命令为 `sop-board [工作区目录]`，缺省为当前目录，`--lan` 开放内网访问。
- 看板的数据、配置和项目适配放在同一个目录 `~/.sop-board/<工作区名>/`，不写进任何仓库。团队要共享适配时，由开发者自行导出到私有仓库。
- 配置 `config.yaml` 由代理按搭建指引生成（D33）：
  - `repos`：仓库别名到工作区内的相对路径；
  - `scenarios`：场景文件所在目录，位于某个仓库内；
  - `entries`：验收入口，字段沿用场景入口格式，可加 `driver` 指定驱动技能；
  - `adapter`：项目适配的命令（D33）。
- 看板从各仓库的 origin 读出身份，用于页面显示和报告。配置列出的仓库，就是看板可以建 worktree、提交和合入的仓库。

### D31 免令牌（取代 D14 的写入令牌与 D20 的开发者令牌）

- 页面只填标记人，保存在浏览器。复核、上传用例、标记不需要令牌。
- 开发者操作（执行、重新合并、批准修复方案、重试、放弃、暂停与恢复）只接受来自本机地址的请求；内网页面隐藏这些按钮。
- 写入请求使用 `Content-Type: application/json`，看板核对 `Origin` 与看板自身地址一致；命令行请求没有 `Origin`，照常处理。这样别的网页无法借浏览器向看板发请求。
- 开发者自己在本机架设的反向代理或端口转发，视为开发者本人的操作。

### D32 需求跨仓（修改 D13 的项目与 D24 的范围）

- 批次（一个需求）属于工作区。场景文件 `<批次>.yaml` 放在 `scenarios` 目录，`metadata.repos` 列出本需求涉及的仓库别名；省略时为全部仓库。
- 执行、修复、复测都以批次涉及的仓库为范围。修复任务按工作区计，同一时间一个（沿用 D24 的整体修复）。

### D33 项目适配由代理搭建（新增；取代 D23 的三种候选方式与 D25 的原地替换）
已由 [SOP-BOARD-8 的 D38](../designs/SOP-BOARD-8.md) 修订。

看板定义适配契约并调用它；契约之外的项目知识都写在适配里。

**适配契约**

| 命令 | 输入 | 要求 |
| --- | --- | --- |
| `adapter.worktree`（可选） | `SOP_TASK_DIR`（任务目录）、`SOP_FIX_BRANCH`（如 `sop-board/fix/12`）、`SOP_REPOS`（涉及的仓库别名，逗号分隔）、`SOP_BASE_<别名>`（各仓库的基线目录） | 按项目自己的方式为每个涉及仓库建好该分支的 worktree，并让它们可以编译、启动，例如生成语言工作区文件、复制被 Git 忽略的本机配置、生成代码。最后一行标准输出为 JSON `{"repos": {别名: 路径}, "env": {...}}`；看板核对每个路径是对应仓库在该分支上的 worktree，再把 `env` 传给修复会话和 `adapter.env`。未声明时，看板在任务目录 `repos/<别名>` 下用 `git worktree add` 建 |
| `adapter.cleanup`（可选） | 同上，另有 `SOP_WORKTREES`（JSON，别名到路径） | 按项目自己的方式删除这些 worktree。未声明时，看板用 `git worktree remove` 删除，合入后的修复分支由看板删除 |
| `adapter.env` | `SOP_REPO_<别名>`（本次使用的各仓库目录：基线检出或修复 worktree）、`SOP_ENV_LOG_DIR` | 启动入口所需的整套服务并保持在前台；全部就绪后在标准输出打印一行 `sop-board: ready`；失败时以非零退出并写明原因。基线与修复代码使用相同的端口与地址 |

- `adapter.ports` 列出环境要监听的端口，供自检核对占用、页面显示。
- 看板以独立进程组运行 `adapter.env`，在 `adapter.ready_timeout`（缺省 180 秒）内等待就绪行，停止时先发 SIGTERM，10 秒后发 SIGKILL。本机同一时间只运行一套环境。
- 基线与修复代码轮流使用同一组端口和地址，所以只能挂在固定隧道地址上的应用（例如 Shopify 内嵌应用），也能用修复代码复测。
- 依赖顺序、各语言的工作区设置、复制被 Git 忽略的本机配置、等待数据库和消息队列等项目细节，都由 `adapter.worktree` 与 `adapter.env` 负责。worktree 的建法因项目和机器而异：适配可以调用仓库里的脚本或团队共享的工具；只装在开发者个人机器上的工具（例如个人技能）也可以用，搭建报告写明这一依赖，团队成员共用这份适配前须各自具备。
- 本机配置常含凭证：看板不保存它们的副本（适配复制进 worktree 的文件随 worktree 删除）；环境日志、适配文件与搭建报告只在本机页面显示；搭建报告只写凭证所在位置，不写值。

**自检**：`sop-board check [工作区目录]`，页面上也有同名按钮。依次核对：

1. 配置格式与仓库路径；
2. 适配要用的端口没有被其他进程占用（被占用时列出进程，比如开发者手工启动的服务）；
3. 用基线目录运行 `adapter.env`，在时限内就绪，然后停止；
4. 按 `adapter.worktree`（未声明时用 `git worktree add`）为每个仓库建临时 worktree 并核对，用这些目录运行一次 `adapter.env`，在时限内就绪，然后停止，并按 `adapter.cleanup`（未声明时用 `git worktree remove`）删除；
5. 各入口的驱动技能在技能目录中存在。

每一步写明结果与日志位置。全部通过后，看板才能启用执行与修复。

**搭建指引随看板发行**

- 搭建指引是看板仓库中的一份 Markdown，随包安装，`sop-board guide` 输出当前版本的全文；README 的"给代理"一节写明安装命令，并让代理先运行 `sop-board guide`。指引、适配契约与看板代码在同一个仓库，一起发版。
- 指引写明：
  - 安装看板（`uv tool install`），确定工作区范围；
  - 从仓库、启动配置、IDE 启动项、文档和开发者说明查清服务与依赖，并以实际监听的端口和进程核对（文档常过时）；
  - 核对服务之间互相引用的地址、端口和数据库名是否一致，把矛盾告诉开发者；
  - 与开发者确认 worktree 的正确建法：仓库里有没有现成的脚本或说明、团队用什么工具、开发者平时怎么建、被忽略的配置与生成代码怎么带过去；按确认的方式写 `adapter.worktree` 与 `adapter.cleanup`，只用 `git worktree add` 就够时省略它们；
  - 编写适配，选择验收入口与驱动技能；
  - 运行 `sop-board check`，修正到全部通过；
  - 向开发者报告已验证的事实、推断及依据、待回答的问题，以及适配依赖的外部工具（哪些在仓库里、哪些只在本机），凭证只写位置；开发者确认后启动看板。
- 代理只写 `~/.sop-board/<工作区名>/`，在开发者自己打开的会话里工作，有疑问当场问开发者。Codex 与 Claude Code 使用同一份指引。
- 项目变化后，开发者让代理按同一指引更新适配。
- 工作区还没有适配时，看板页面显示这段做法，执行与修复保持停用。

项目知识留在生成的适配里，指引保持通用。

### D34 跨仓修复与复测（修改 D24、D25）

- 修复任务开始时，看板用 `adapter.worktree` 为批次涉及的每个仓库建 `sop-board/fix/<编号>` 分支的 worktree（未声明时由看板用 `git worktree add` 建，基于各仓库当前分支），核对后记下路径。修复会话以任务目录为工作目录，提示词列出各 worktree 路径，带上适配给出的环境变量，只改产品代码，不写测试（仓库自己约定 TDD 时也一样）；提示词列出仓库别名、路径与身份。
- 一次根因分析覆盖全部问题和全部仓库；会话判定每个问题的根因所在仓库，只修产品缺陷（v8 D24 的修复要求不变）。
- 有改动的仓库各提交一次，提交信息相同（任务编号、尝试次数、场景与缺陷链接）。
- 复测：停止基线环境，用修复 worktree 运行 `adapter.env`，由新会话经真实入口复测问题场景及受影响的场景。
- 合入：问题场景全部通过后，先核对每个有改动的仓库都能快进合入。条件是基线分支在工作区检出、没有未提交的产品改动、基线没有前进（前进时先在 worktree 中合入基线并再复测一次）。全部满足后逐仓 `git merge --ff-only`，再用基线目录重启环境。任一仓库不满足时都不合入，任务转"待开发者合入"，列出每个仓库的原因。
- 连续三次未通过转"待开发者处理"；基线代码保持修复前的状态，修复分支留给开发者。

### D35 用例按验证分层合并（修改 D16）

- Codex 合并时把每条用例归为两类，并写明理由：
  - **流程类**：角色经真实入口完成的业务流程，或业务上的失败；生成同编号场景。
  - **细节类**：字段格式、取值边界、校验提示、接口字段等；并入所属流程场景的 `expected`，在同一次执行中核对，对应关系记入配对。
- 合并页按流程场景列出并入的细节用例与理由。测试同事或开发者可以把某条用例改为单独成场景，看板重新合并。
- 产品变化后，执行任务由 Codex 按改动判定受影响的场景并重跑；判定为不受影响的场景写明理由，记为沿用。

## 3 使用方式

开发者：

1. 在工作区目录打开 Codex 或 Claude Code，说"按 https://github.com/AdolphKevin/sop-board 的安装说明，为这个工作区安装并搭建 sop-board"，回答代理的提问。
2. 代理报告自检通过后，核对它列出的服务、依赖和推断，确认后在工作区运行 `sop-board`，打开看板地址。
3. 需要同事参与时，加 `--lan` 重启，把内网地址发给测试同事。

测试同事：

1. 打开地址，填标记人。
2. 上传用例，等待看板合并并执行。
3. 在"SOP 场景"页复核：通过点一下，不通过填缺陷链接。

之后看板自动修复、复测、合入。需要开发者处理的事项显示在页面顶部，`sop-verify status` 也会列出。

## 5 分段与验收

沿主流程分三段，每段完成后，在真实工作区按[验收计划](../acceptance/2026-10-20-real-project-main-flow.md)验收：

| 段 | 接通的范围 | 验收 |
| --- | --- | --- |
| 1 | 免令牌、工作区、适配契约与自检、搭建指引；上传用例 → 合并 → 执行 → 复核 | 验收计划 E1–E4、N1 |
| 2 | 跨仓修复 → 用修复代码复测 → 全部可快进后合入 → 基线重启 | 验收计划 E5–E7、N2、N3 |
| 3 | 用例分层合并、报告；在结构不同的第二个项目上搭建 | 验收计划 E8、E9 |

本需求的场景文件只写业务流程，十几条，覆盖上面的主流程；页面文案等细节并入相关场景的预期。

## 6 后果与限制

- 看板对项目的了解只来自适配。适配写错时自检或执行会失败，由代理按指引修正，看板代码保持通用。
- 本机同一时间只运行一套环境。复测期间环境运行修复代码，页面显示"复测中"；开发者要手工使用环境时，先暂停自动任务。
- 修复只合入本机分支，不推送、不部署（同 v8）。
- 搭建在开发者自己打开的代理会话里进行，权限按该会话的设置；代理写的文件只在看板目录，开发者确认后启动看板。
- 开放内网后，内网的人可以查看、上传与复核；需要更严的访问控制时再加登录。
