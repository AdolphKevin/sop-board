# Web 验收脚本库：复用、保真检查与只读巡检（SOP-BOARD-23）

> 状态：方案 1，2026-11-04。第七节各项已由使用者选定（库放产品仓库且不计入快照；未参与该次改写者可审核；cw2 改写过的规范版本标未核实；三项一起做）。使用者决定：“把 cw2 自建的验收层（断言保真检查和审核账本、改 UI 后的只读巡检、spec 复用）收进 `sop-board playwright`。”
>
> 依据：Codex 只读调查（会话 01a1a610-28fe-72f1-a2e1-10a3099274f4，报告在仓库外 `~/sop-board-runs/sop-board-22/task-b-result.md`），Claude 抽查了其中的关键结论。
>
> 验收只以场景经真实入口执行为准，开发中不写单元、接口或集成测试（v9）。

## 一、现状

**本包**

- `sop-board playwright` 只有 guide、convert、tags、scope、submit 五个子命令（`playwright.py:170`）。
- 每轮由执行者在任务目录里写脚本，交互地图（atlas 或 `surface-map.md`）提供页面与定位。
- `docs/playwright-acceptance.md:60` 规定浏览器验收脚本和界面地图保留在仓库外的任务目录。

**cw2 自建层**

位置：Core 仓库 `.tw/local/sop-org-settings/accept-run`，Git 忽略。

| 组件 | 做什么 |
| --- | --- |
| 规范 spec 库 | 每个场景一份规范 spec，附来源快照、历史版本和索引 |
| 页面对象 | 规范 spec 不直接写定位，统一调用页面对象 |
| `check-specs.py` | 断言与 SQL 保真检查，配合文字账本和结构改写账本 |
| `seed.py` | 把范围内的 spec 预置进任务目录 |
| `promote.py` | 把审核过的 spec 收入规范库 |
| `patrol.mjs` | 只读巡检 |
| `drive*.py`、`sub-round.py` | 外围调度 |

这套东西在 front-b 改版时让 248 份来源脚本跟上了新界面，同时没有放宽断言。调查也发现以下不足：

- **规范库不能直接当作“通过”**：索引里有结果的场景 313 个，有来源脚本的 248 个，其中最近一次结果是通过的 234 个、受阻的 14 个（`INDEX.md:5`）。
- **断言签名不含被断言对象**：断言的对象或取值计算变了，只要匹配器和参数不变，检查仍会通过（`specs_common.py:96`）。
- **文字账本粗糙**：按整份 spec 做子串替换，同样的旧文字会被一起替换；没有审核署名。
- **promote 不推进基线**：收入新版本时不更新 `_source`，后来新增的断言在下一轮被删掉也查不出来（`promote.py:113`、`promote.py:153`）。
- **巡检的只读全靠约定**：只读性质只来自条目作者的约定；失败也不设非零退出码（`patrol.mjs` 末尾）。
- **预置不核对内容**：`seed.py` 只按场景编号选 spec，不核对场景内容指纹；`library.mjs` 会加载共享目录里随时可能被改动的代码。

## 二、目标

- 已审核、已核实通过的 Web 脚本按场景版本复用，下一轮直接预置，不再重写。
- 改脚本时，静态检查能找出删掉的断言和放宽的预期；每一处改写或撤销都有绑定具体版本的审核记录。
- 改界面后，可以在不改变业务数据的前提下，先检查定位器还能不能用。
- 复用不改变执行规则：仍须实际运行、留下新证据；执行者身份就是本轮实际运行的人；能否沿用仍按影响判定。

## 三、决定

### D114 规范脚本库与复用

- **位置**：工具随包发行；规范资产放在产品仓库受版本管理的目录，由 Web 入口在 `config.yaml` 中声明（如 `spec_library: <仓库别名>:<目录>`）；任务内的副本和证据放在看板数据目录的任务目录。
- **目录结构**：

  ```text
  specs/<批次>/<场景>.spec.mjs
  pages/
  INDEX.json
  baseline/
  _history/
  text-ledger.json
  assertion-ledger.json
  patrol.json
  support/<标识>/manifest.json
  ```

- **索引条目**记录：
  - 场景编号与内容指纹、引用用例的指纹；
  - 脚本及全部执行依赖的摘要；
  - 基线版本、审核记录；
  - 通过依据（批次、轮次、结果编号、产品快照）；
  - 状态，三选一：已核实通过 / 已审核未通过 / 历史导入未核实。
- **预置**：执行准备和修复复验准备在范围冻结之后，对本轮 Web 范围内的场景预置脚本和依赖，作为冻结副本放进任务目录，不再从共享目录加载。规则：
  - 只预置编号和内容指纹都一致、且状态为“已核实通过”的场景；
  - 指纹不一致的只列为参考；
  - 不覆盖任务目录里已有的文件；
  - 辅助脚本默认停用；
  - 结果写进 `specs-manifest.json`，分为预置、缺失、仅参考、冲突四类。
- **复用不改变执行规则**：仍须实际运行、留下新证据，不沿用旧结果。执行记录写入本次使用的库版本摘要。
- **库目录不计入产品快照**：声明后的库目录自动视为验收资产，效果同 `snapshot_exclude`；产品运行代码与配置照常计入。
- **收入：`playwright specs promote`**
  - 执行者提交候选，工具生成审核材料：差异、每条断言的去向、运行依据。候选文件的摘要必须与该次通过运行时的摘要一致。
  - 审核人须未参与该次改写：另一个会话、测试同事或使用者均可，但不能是写这次改动的会话（按会话标识比对）。审核绑定候选摘要与时间。审核人确认后收入，旧版本移入 `_history/`。撤销预期另须看板上的业务确认记录。
  - 收入的版本成为下一版的保真基线；首次新写的脚本同样建立基线。

### D115 断言保真检查与审核账本

- **`playwright specs check`**：比较候选与基线。断言条目包括稳定标识、匹配器与参数、被断言对象、所在步骤；SQL 和数据核对同样处理。输出分四类：
  - 相同：静态可证明没变；
  - 待审核：对象变了、断言移动了、条件变了；
  - 违规：断言缺失且没有账本记录；
  - 无基线。
- **账本**：
  - 文字替换绑定到具体的断言和文字节点，不再按整份 spec 替换；
  - 结构改写记录 old 和 new；
  - 预期撤销必须绑定用例变更前后的指纹，以及看板上对应的确认记录（`cases put` 的决定记录）；
  - 每条都记录改写者、审核者、时间和候选摘要；
  - 正向断言扩大可接受的文字，视为放宽预期，必须写明审核理由。
- **promote 的前提**：check 没有违规，且待审核项都已审核。静态检查不代替真实执行。

### D116 只读巡检

- **声明文件 `patrol.json`**，每个条目包括：
  - 入口与身份引用；
  - 页面和控件引用（来自 atlas 或 `surface-map.md`）；
  - 到达步骤；
  - 检查目标及数量要求；
  - 允许的请求（按业务用途声明，不能用“只放行 GET”代替，因为 GET 也可能写入）；
  - 禁止的动作；
  - 审核人与时间；
  - 已知未覆盖的范围。
- **`playwright patrol plan`**：根据地图生成候选条目，未审核的条目不执行。
- **`playwright patrol run`**：
  - 只执行已审核的条目，连接已有的登录态；
  - 遇到未声明的请求或对象，立即停止该条目；
  - 任一条目失败时退出码非 0；
  - 定位缺口写入 `atlas-feedback.jsonl`。
- **巡检结果的用途有限**：不登记为场景结论，也不能作为沿用旧结果的理由。

### D117 cw2 迁移

- 提供 `playwright specs import`，一次性导入外部目录（使用者 2026-11-04 复核后选定“改写过的标未核实”）：
  - 来源索引中最近结果为通过、且规范版本与来源脚本相同（摘要一致，没有改写）的，导入为“已核实通过（历史导入）”。
  - 规范版本相对来源脚本改写过的，以及其余（如受阻）的，都导入为“历史导入、未核实”。改写过的版本在新界面上真实运行通过、并经审核 promote 后，才升级为已核实。
  - 每条记录来源依据：来源任务、运行编号、来源脚本摘要，以及“规范版本相对来源脚本是否改写过”。cw2 的 248 份规范 spec 在 2026-11-03/04 改版时都已改写，改为通过页面对象定位、跟进新界面，只经过静态检查，没有在新界面上真实运行过（`drive.pause` 自 11-03 18:26 起生效）。
  - 命令为 `playwright specs import --from <目录> --batch <批次> [--data <目录>]`，首版只支持 cw2 accept-run 的目录结构：`lib/specs/INDEX.json`、`_source/`、规范脚本、`lib/pages/`、两份账本。导入的账本条目标为“历史导入，未经本包审核”。
  - 场景指纹取看板上该批次、该场景在来源运行中登记的结果所对应的指纹；查不到的记为未知，只列为参考。
  - 预置仍要求场景指纹一致（D114）：来源运行之后场景内容有变化的，即使状态为已核实，也只列为参考。
  - 导入不产生看板上的通过结果，也不改变任何已登记结论。
- 页面对象等产品资产由 cw2 迁入产品仓库的库目录。
- cw2 的外围调度（`drive*.py`、`sub-round.py`、服务恢复、Chrome 重启、邮箱、Redis 操作）不收编，由本包现有的任务内核负责调度。

### D118 文档、内网与存储

- 修改 `docs/playwright-acceptance.md:60` 与 `references/workflow.md:29` 的存放约定：经审核、受版本管理的执行资产库可以放进产品仓库；任务副本和过程证据仍放在仓库外。
- 库原文、账本、巡检材料仅本机可见。内网只显示业务摘要：复用数量、审核结论、审核人姓名。
- 数据库格式保持 5，资产以文件存储；确需跨任务查询时另加侧表。
- 录屏与 trace 继续服从冻结的 `web_evidence`，不照搬 cw2 关闭录制的做法。

### 补充契约（Claude，2026-11-04，回应场景编写者的 Q1～Q5）

**库结构与寻址**

- 库内脚本按批次分目录：`specs/<批次>/<场景>.spec.mjs`。同一批次、同一场景只有一个当前版本；不同批次的同编号场景互不影响。历史版本放在 `_history/<批次>/<场景>/<版本号>/`，基线放在 `baseline/<批次>/<场景>/<版本号>/`。
- 脚本只经同目录的 `./fixtures.mjs` 和 `./library.mjs` 导入；页面对象与辅助代码放在库根的 `pages/`、`support/`，由 `library.mjs` 重新导出。

**`INDEX.json`**

格式为 `{"version": 1, "entries": [...]}`，每个条目包含：

| 字段 | 内容 |
| --- | --- |
| `batch`、`scenario` | 批次与场景编号 |
| `scenario_fingerprint` | 场景内容指纹 |
| `case_fingerprints` | `{用例编号: 指纹}` |
| `spec`、`spec_sha256` | 脚本路径与摘要 |
| `deps` | 依赖文件的 `{相对路径: sha256}` |
| `version`、`baseline` | 版本号与基线路径 |
| `state` | `verified`、`reviewed-failing`、`unverified` 三选一 |
| `origin` | `promote` 或 `import` |
| `provenance` | 来源依据（导入时见 D117） |
| `review` | `{by, kind: person\|session, session, at, candidate_sha256}` |
| `run` | `{batch, round, result_id, status, product_digest}`，没有则为 null |
| `support` | `[{id, path, enabled: false}]` |

方案中的两种导入称谓与状态的对应：“已核实通过（历史导入）”= `state: verified` 且 `origin: import`；“历史导入、未核实”= `state: unverified` 且 `origin: import`。

**预置**

- 预置目标：脚本放在任务目录 `scenarios/<场景>.spec.mjs`；库依赖完整复制到 `scenarios/library/`，并生成 `scenarios/library.mjs` 重新导出这份冻结副本；辅助脚本以 `.off` 后缀复制，默认停用。执行者启用辅助脚本时去掉后缀，并在结果备注中说明。
- 预置条件：批次、场景编号与场景内容指纹都一致，且 `state` 为 `verified`。引用用例的指纹不同、但场景指纹相同时，照常预置，并在清单中注明。
- `specs-manifest.json` 分四类，每项都写明原因：
  - `seeded`：已预置；
  - `missing`：库中没有该批次与场景；
  - `reference`：有条目，但指纹不同或状态不是 `verified`；
  - `conflict`：目标文件已存在，或依赖路径冲突。依赖冲突时，受影响的每个场景都单独列出。

**运行与审核材料**

- 运行摘要：模板中的 `global-setup.mjs` 在每次运行开始时，把本次脚本与依赖的摘要写入任务目录 `spec-runs/<运行编号>.json`；`convert` 把对应摘要关联到结果行。
- 账本：
  - 执行者把本轮的文字替换与结构改写写进任务目录的 `spec-ledger.json`。
  - 文字替换条目：`{id, batch, scenario, assertion_id, node_path, old, new, reason, ref}`。
  - 结构改写条目：`{id, batch, scenario, assertion_id, kind: rewrite|withdraw, old, new, reason, ref, sop_change}`。其中 `sop_change` 为 `{case, before_fingerprint, after_fingerprint, decision_id}`，`decision_id` 指看板上 `cases put` 的决定记录。
  - `promote` 时把条目连同审核信息并入库内账本。

**命令**

| 命令 | 作用 |
| --- | --- |
| `playwright specs check [--library <目录>] [--task <编号>] [--scenario <批次>#<场景> ...]` | 只读。对照库或任务候选输出四类结果，有违规时退出码非 0。 |
| `playwright specs review --task <编号> --scenario <批次>#<场景> --out <文件>` | 生成审核材料：候选摘要、基线版本、check 结果、待审核项与对应账本条目、运行依据。 |
| `playwright specs promote --task <编号> --scenario <批次>#<场景> --reviewed-by <姓名> [--reviewer-session <标识>] [--state verified\|reviewed-failing]` | 收入候选版本，规则见下。 |

promote 的拒收条件：

- 候选摘要与该场景最近一次运行摘要不一致；
- check 有违规，或待审核项没有对应的账本条目；
- 给出的审核会话等于该任务的执行会话或实现会话；
- `verified` 状态要求该场景在已登记轮次中的结果为通过；`reviewed-failing` 状态要求结果为失败且有发现说明。

审核人是人时只需 `--reviewed-by` 填写姓名。首次收入（没有基线）时，check 对全部断言报“无基线”，审核材料逐条列出，收入后成为基线。

**标识与导入样例**

- 断言标识和文字节点标识的写法，由实现方在 `docs/reference.md` 中定义，并由 `specs check --format json` 输出。账本条目引用的标识以 check 输出为准；执行者从 check 输出读取标识，不手写推导。
- 导入的输入格式，以 cw2 现有 `lib/specs/INDEX.json`、`text-ledger.json`、`assertion-ledger.json` 的实际字段为准（实现方只读参照 cw2 目录）。演示用的导入目录照这些字段构造最小样例，不使用真实 cw2 内容。

**库绑定**

- Web 入口的 `spec_library` 归为“业务配置”，与 `snapshot_exclude` 相同：新增或更换绑定须重新自检，准备后的任务按现行规则作废。由于产品指纹的排除范围随之变化，已有通过可能一次性进入产品变化待判定，所以绑定应选在没有执行进行时设置。
- 库内容的变化不是配置变化：本轮使用冻结副本，下一轮采用新内容。

**巡检的请求与对象识别**

- 条目声明以下内容：
  - `pages`：允许到达的 URL 路径模式；
  - `allow_requests`：允许的请求，格式为 `[{method, path, purpose}]`，`path` 按路径模式匹配；
  - 到达步骤与检查目标。
- 运行时由 Playwright 拦截全部请求：
  - document、script、stylesheet、image、font、media 类静态资源直接放行；
  - xhr、fetch、websocket 等其他请求，与 `allow_requests` 匹配才放行；
  - 未声明的请求在发出前中止（不到达服务端），该条目停止并记录原因；
  - 导航到不在 `pages` 中的地址，同样停止。
- “对象”的识别粒度是页面地址与请求，不识别业务对象实例。

**巡检证据**

`patrol run` 不是看板任务。开跑时读取该入口当前的 `web_evidence`，写进巡检报告，本次运行按它决定是否录屏、是否保存 trace；失败截图始终保存。

## 四、不改的

- 任务调度、独立性规则、影响判定（D96、D107）与 `web_evidence` 的规则都不变。
- 产品回归测试仍由 regression-distill 负责建设。
- 外围驱动不收编。
