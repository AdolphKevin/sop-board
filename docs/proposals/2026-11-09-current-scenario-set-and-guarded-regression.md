**A2 新需求的流程。** 新需求照旧写 `docs/sop/sop-board-<N>.yaml`，验收范围清楚，实现与返工会话只读。交付后由审核方把它归入能力文件，同时退役被取代的旧场景。能力文件的版本说明记录每次归并来自哪个需求。

**A3 编号与内容。** 保留的场景编号和原文都不变，原通过证据继续有效。改写或合并的场景尽量沿用主场景编号，内容变化后须独立经真实入口重跑。退役的场景记入 `docs/sop/retired.yaml`（编号、原文件、退役类别、取代者、依据的决定），原文从 Git 历史可查。

**A4 退役与改写规则。** 每条都要有依据：

| 类别 | 处理 | 依据 |
| --- | --- | --- |
| 功能已删除 | 退役 | 已确认的决定原文，如 v9 修订 2 |
| 被后来的需求改写 | 旧条退役，列出取代者 | 逐条核对旧条的 expected 与 forbidden_effects 在现行场景里都有对应；没有对应的保留或补进取代者 |
| 重复覆盖同一行为 | 合并为一条，预期取并集 | 合并前后的断言对照表 |
| 写法过时但行为仍在（令牌、`/projects/`） | 按现行入口改写 | 内容变化，须重跑 |
| 一次性已完成（已完成的迁移、真实批次试点） | 退役 | 事件已完成的记录；场景里仍现行的行为先由其他场景覆盖，例如 SOP-135 退役前先补一条覆盖 D71 自动执行开关的演示场景 |
| 依赖尚未接入的外部系统（目前为 Jira） | 暂时退役，接入时从 `retired.yaml` 恢复并重新验收 | 使用者 2026-11-09 的说明；只退役依赖真实外部系统的场景或预期，其余预期须有现行场景对应 |

不因“难跑、常失败、受阻久”而退役，也不借合并放宽预期。

**A5 审核。** 审核方逐个能力文件给出新旧对照表：每条旧断言对应到哪条现行场景，或者退役理由。每个文件由未参与归并的新会话独立核对这张对照表。核对通过后，只对改写或合并的场景安排真实入口重跑。

## 三、方案 B：经场景验证后沉淀，测试守护的场景不必每轮重跑

**B1 守护资格。** 以下条件同时满足的场景才算“回归守护”：

- 已经由独立验收者经真实入口通过（实现者自检通过的不算）；
- 有已提交、未过期的回归关联；
- 报告中该场景的每条 expected 与 forbidden_effects 都已覆盖，没有“仍需真实入口”的部分；
- 检出能力核对已实际运行，并且确认失败的是对应业务断言。

部分覆盖的场景不算守护，照旧重跑。

**B2 产品变化后的判定（修订第 5 节）。** 原通过的守护场景在产品变化后，由执行会话在同一产品快照上运行关联测试。报告声明的测试都出现在实际执行清单中且全部通过时，记为“回归守护通过”，与重跑、沿用分开计数，测试的原始输出作为证据。测试失败、未发现、被跳过或缺环境时，该场景改为经真实入口重跑。第 6 节的整体完成条件相应改为“产品变化已逐项重跑、有效沿用或回归守护通过”。

**B3 仍须真实入口的情况。** 首次验收、场景内容变化（关联随之过期，重跑通过后重新沉淀）、缺陷复验、人工复核不通过。守护场景出现一次漏检（测试通过但人工复核或真实入口发现问题），就退出守护，直到测试补强并重新核对检出能力；漏检按第 9 节复盘。

**B4 先沉淀哪些。** 优先选 verify 为 cli 或 api 的反向场景（255 条），也就是拒绝分支、格式校验、版本拒绝、内网 403 这类确定性输出。Web 外观、模型与智能体语义、真实客户端会话不进入首批。

**B5 产品改动。** 这部分作为一个新需求（暂称 SOP-BOARD-24）走正常流程，由审核方写场景，独立验收：

- 执行任务的 `impact.json` 增加守护判定与测试运行证据；准备材料列出守护场景及其关联测试的命令。
- 看板统计、批次页与报告单列“回归守护通过”。
- 漏检时让场景退出守护并提示。
- 同步改写 regression-distill 技能、参考手册与标准第 1、5、6 节。

## 四、用在 sop-board 本仓

- **测试位置与框架**：恢复根目录 `tests/`，使用 pytest，在 `pyproject.toml` 加开发依赖组；运行命令为 `uv run --group dev pytest tests`。场景用 marker 标注，如 `@pytest.mark.scenario("SOP-132-N01")`，因为测试函数名不能含 `#`。
- **AGENTS.md** 的“本机验证”改为：实现、返工与修复会话不写测试；经独立真实入口验收通过的场景，在使用者授权的沉淀任务中按 regression-distill 沉淀到 `tests/`。不在开发中顺手补测试。
- **关联索引**：放在 `tests/regression-index.yaml`，按场景编号登记（各文件的场景编号全局唯一，所以按能力文件迁移不影响索引）。每项包括：场景编号、场景内容指纹、关联测试、覆盖是否完整、真实入口通过记录（执行者、快照、证据位置）、检出能力证据位置。场景内容指纹与索引不一致时，该项过期。本仓验收的影响判定由执行者读这份索引，在同一快照上运行守护场景的测试（B2）。
- **顺序**：先完成 SOP-BOARD-22/23 的验收与合入，再做方案 A（场景文件会改到 sop-board-3、-14、-20），然后沉淀测试。沉淀要求通过证据对应当前产品内容，22/23 合入并完成回归之前不能开始。方案 B 的产品改动（SOP-BOARD-24）可以和 A 并行。
