## 0 摘要

- **S1 本仓是 SOP 验收的唯一产品。** team-workflow 业务验收标准中仍适用的要求迁入 `docs/standard.md`；场景格式、结果契约、入口声明以本仓为准。
- **S2 回归沉淀由本地 agent 按随包技能完成。** 新技能 `regression-distill` 把已确认的场景写成产品仓库中按成本分层的回归测试；数据库接口测试的做法与 PostgreSQL 运行器一并收入。`sop-board skills install` 把随包技能链接进 Codex 与 Claude Code 的技能目录，agent 按名称发现。
- **两个入口，同一技能。** 开发会话中对 agent 说“把这些场景沉淀为测试”；或在看板场景页点“沉淀”，看板调度本机 Codex 在独立 worktree 中按同一技能沉淀。两种入口的测试都留给开发者审核提交，结果登记为场景与测试的关联，显示在场景详情与报告中。
- **场景仍是唯一的验收单位。** 回归测试不改变场景的验收结论，也不作为交付条件；执行会话与修复会话照旧不写测试。

## 1 问题

- 同时安装 team-workflow 与本仓时两套场景验收重复；旧方案仍以 tw 格式为准，现行契约来源不清。
- 回归只能靠看板重跑场景。看板在开发者本机启动整套服务，适合验收；两次验收之间的改动缺少低成本的持续保护，产品仓库 CI 发现不了业务回归。
- 真实对话表明，沉淀最有效的位置是开发会话：那里有已确认的规则、代码上下文和项目已有的测试设施。用户在自检通过后发起，Codex 按成本分层写出接口测试、单元测试和前端测试，在隔离数据库上跑通，约 20 分钟完成。

### D61 回归沉淀技能（S2）

技能位于 `src/sop_board/skills/regression-distill/`，由本地 agent（Codex 或 Claude Code）执行。

**安装与发现。** 新增 `sop-board skills install`：把随包技能（`regression-distill`、`playwright-acceptance`）链接到 `~/.agents/skills/` 与 `~/.claude/skills/`，agent 按技能名称与描述自动发现。目标位置已是指向本包的链接时更新链接；已有同名、不同来源的技能（包括目录、指向别处的链接）时，列出来源并跳过，由使用者处理。命令输出每个客户端实际解析到的技能路径与版本。

**数据库接口测试部分**取自 praxis-skills 的 `verify-backend-sop-db`。praxis-skills 中的原技能保留，供不使用看板、只想做轻量 SOP 业务验证的成员单独安装；本仓收入的副本记录来源提交，更新时从 praxis-skills 同步。

**发起条件。** 场景的预期已确认（`metadata.sources` 有确认人，或看板草稿已确认且该场景对应的问题已回答），并且实现经真实入口通过过一次（开发者自检或独立验收均可），留有证据。通过证据须对应当前的场景内容指纹与产品内容；不一致时先重新经真实入口执行。独立验收照常进行；尚未完成时，沉淀报告与交付记录如实写“独立验收未完成”。

**做法。**

- 断言取自已确认的场景原文与规则，测试名或标签含 `<批次>#<场景编号>`。
- 按成本选层：纯规则与计算用单元测试；接口与数据库共同产生的结果用经真实入口的接口测试；前端交互用组件测试；只有仓库已有端到端框架时才写浏览器测试。同一断言只覆盖一次。数据库接口测试按收入的做法执行：调用真实后端入口、使用生产同类数据库、确定性夹具、精确核对响应与数据变化，可用随附的 PostgreSQL 运行器。
- 沿用仓库已有的测试框架、目录、夹具与命令。允许修改测试、夹具、测试启动脚本、最小 CI 配置，以及项目知识的测试引用；产品代码保持不变。
- 测试与已确认预期不符时保留失败用例，停止扩写该场景并报告现象、预期依据与疑似原因，由调用方决定是否修改实现。
- **检出能力**按风险选择方式：复现已知缺陷，或在临时副本中做受控改错；判定依据是对应业务断言失败，编译失败、依赖失败或任意非零退出不算。改错只在副本中进行，完成后核对工作区只含沉淀改动。
- **运行证据**：本机实际执行测试，报告列出声明的每个测试名，并核对它们都出现在实际执行清单中且通过；零用例、跳过、环境缺失、声明的测试未被发现都算未运行。
- **CI**：说明产品仓库 CI 由哪个任务、哪条命令运行这些测试；“已运行”须给出 CI 运行编号或链接、对应提交、实际执行的测试清单与结果，缺少时记为“已接入，未验证”或“未接入”。
- **提交**：改动留在工作区，由调用方审核后提交。

**沉淀报告**（`regression.json`）逐条场景记录：场景文件、编号、内容指纹；通过证据（轮次或自检记录、产品提交与内容摘要、执行者）；每条 `expected` 与 `forbidden_effects` 是否被测试覆盖、由哪个测试覆盖、仍需真实入口验收的部分；仓库、测试文件、内容摘要与测试名、层级、运行命令；本机运行结果与原始输出位置；CI 状态与证据。

**与修复规则的关系。** v9 D34“修复会话只改产品代码、不写测试”继续有效；看板流程中的测试只由本技能产生。

### D62 两个入口

**入口一：开发会话。** 开发者在自己的会话里说“把这些场景沉淀为测试”，agent 按 `regression-distill` 在当前工作区完成，改动留在工作区。产品对应的看板工作区存在时，技能最后一步运行 `sop-board distill submit <工作区> --report <regression.json>` 登记关联；没有看板时只留下报告。

**入口二：看板调度。** 场景页（仅本机）勾选满足发起条件的场景，点“沉淀为回归测试”。看板建立沉淀任务：

- **输入快照**：入队时固定场景原文与内容指纹、场景来源与确认人、通过证据、各仓库提交与产品内容摘要、`config.yaml` 与适配脚本摘要、项目验证技能与 `regression-distill` 的版本。产品有未提交改动时任务显示“待提交”，提交后再开始，与执行任务的规则一致。
- **worktree**：用 `adapter.worktree` 从快照中的提交为涉及的仓库建立 `sop-board/distill/<编号>` 分支的 worktree，核对后持久记录仓库、路径与分支。调度本机 Codex 新会话，提示词指定按 `regression-distill` 执行。
- **环境**：测试默认使用项目自己的测试设施（如隔离数据库）。需要看板环境时，与修复复测相同：停止基线环境，用 worktree 运行 `adapter.env`，结束、失败或取消后恢复基线环境。
- **互斥**：沉淀任务与执行、修复任务双向互斥：任一运行时其他排队；排队时修复优先，其次执行，再次沉淀。浏览器沿用现有占用规则。
- **登记**：会话结束时重新核对输入快照；全部一致才校验 `regression.json` 并按 D63 登记，任一项变化则记为已作废、不登记，原因显示在任务中。改动留在 worktree 中不提交。

**状态与恢复**：

| 状态 | 进入条件 | 看板重启后 | 后续操作 |
| --- | --- | --- | --- |
| 排队、待提交 | 发起；产品有未提交改动 | 保持 | 自动开始 |
| 沉淀中 | 会话运行 | 记为已中断 | 重试 |
| 已中断、失败、已作废 | 重启时运行中；会话失败或输出无效；快照变化 | 保持 | 重试或放弃 |
| 待开发者审核 | 登记成功 | 保持，按持久记录找回 worktree | 标记已处理或放弃 |
| 清理失败 | 清理 worktree 出错 | 保持，现场保留 | 重试清理 |
| 已处理、已放弃 | 开发者标记且清理成功 | 保持 | — |

- 重试复用同一 worktree 与分支，先把上一次的报告与会话记录归档到 `attempts/<序号>/`，重新固定输入快照后新建会话。
- 登记按“任务、尝试序号”幂等：登记成功后、状态更新前中断，重启后识别已登记记录，直接进入待开发者审核。
- 清理前列出 worktree 中尚未提交的改动并请开发者确认；清理沿用适配的 `adapter.cleanup`，失败时保留现场。

**访问边界**：发起、重试、标记处理与放弃、清理的接口加入本机操作清单，内网直接请求返回拒绝。内网的任务列表与详情只显示状态、场景与时间；`regression.json`、提示词、会话记录、测试命令、本机路径与 worktree 文件只在本机可读、可下载。

### D63 看板记录场景与测试的关联

- `sop-board distill submit`（入口一）与沉淀任务登记（入口二）使用同一登记逻辑：核对场景存在且内容指纹与当前一致；核对报告声明的仓库身份、文件路径与内容摘要和实际文件一致（已提交的按提交读取，工作区或 worktree 中的按文件读取）。
- 关联分两种状态：**待提交**（测试仅在工作区或 worktree 中，记录任务或会话身份、仓库、路径与内容摘要）与**已提交**（记录提交、路径与内容摘要）。开发者提交后，在任务页标记“已处理”并给出提交（入口二），或再次运行 `distill submit`（入口一）；看板按提交复核文件与摘要后改为已提交。任务放弃时关联标为“已放弃”，作为历史保留。
- 新增表 `regression_links` 保存以上字段及逐项覆盖、本机运行结果、CI 状态与证据、登记时间与登记人。按现有方式在 `SCHEMA` 中以 `CREATE TABLE IF NOT EXISTS` 新增，数据库格式保持 5，不涉及旧数据迁移。
- 场景详情与批次页显示关联：状态、覆盖的预期、仍需真实入口的预期、运行与 CI 状态。场景内容指纹变化后显示“已过期，需重新沉淀”。
- D27 报告中的“回归覆盖”段列出每条场景的关联、部分覆盖的范围与 CI 状态。
- 内网页面可以查看关联的场景、覆盖与状态；测试命令与本机路径只在本机显示。

### D64 回归测试与场景验收的关系

- 场景的通过、失败只来自经真实入口的执行与人工复核。回归测试的结果不写入场景轮次，也不进入交付判定。
- 产品变化后的影响判定先依据改动范围与依赖关系；关联测试的通过结果可作为补充依据写进沿用理由。已知受影响或无法证明不受影响的场景，经真实入口重跑。
- 人工把场景标为不通过、而它有关联测试时，场景详情提示“关联测试待核查”。是否属于测试漏检，由开发者核对失败行为是否在测试覆盖的预期之内后在后续阶段记录。
- 沉淀提交改变产品摘要后，已通过场景照常进入待判定，执行会话按完整改动范围判定。

## 4 验收

场景文件 `docs/sop/sop-board-12.yaml`。执行者未参与实现。S2 的演示产品仓库带一套已有的接口测试与可运行的 CI 配置，并预置一个已知缺陷的提交，用于核对检出能力。预期依据为本方案第 2 节与 `docs/standard.md`。

**S1**

- **SOP-121 标准完整承接**：P01 对照 D60 去向表，`docs/standard.md`、`docs/sop-guide.md`、`docs/templates/` 覆盖每一项；README 与 `sop-board guide` 指向它们。P02 按新标准为演示产品写真实验证手册，工作区 `entries` 引用手册章节且 `sop-board check` 通过；开发会话与看板执行会话都按同一份手册操作，并沿用任务开始时记录的账号授权。N01 仓库现行文档中以 team-workflow 为契约来源的段落都带取代说明。

**S2 第一段**

- **SOP-122 开发会话中沉淀**：P01 只装 sop-board 并运行 `sop-board skills install` 后，分别在 Codex 与 Claude Code 会话中说“把这两条场景沉淀为测试”，agent 使用 `regression-distill`：仓库新增分层测试，测试名含场景编号；本机运行的执行清单包含声明的每个测试且全部通过；改动留在工作区未提交；报告逐项列出覆盖与仍需真实入口的预期。P02 用预置缺陷提交运行，对应业务断言失败。P03 开发者提交并推送后，CI 实际运行这些测试，报告记录运行编号、提交与执行清单，CI 状态为已运行。N01 场景预期与实现不符时，失败用例保留，报告列出依据，产品代码无改动。N02 测试数据库变量缺失导致用例被跳过、或声明的某个测试未被执行时，报告记为未运行。N03 没有 CI 证据时 CI 状态为“已接入，未验证”。

- **SOP-123 资格**：N01 场景预期没有确认人，技能停止并说明原因。N02 实现从未经真实入口通过、或通过证据对应的场景指纹与当前不同，技能停止并说明原因。P01 独立验收未完成时可以沉淀，报告写明“独立验收未完成”。
- **SOP-124 看板登记关联**：P01 入口一的 agent 运行 `distill submit` 后场景详情显示待提交关联、覆盖项、部分覆盖范围与 CI 状态，报告“回归覆盖”段一致；开发者提交后再次登记，关联变为已提交。P02 修改场景内容后关联显示已过期。N01 报告中的场景指纹或测试文件摘要与实际不一致，登记被拒并说明原因。N02 内网页面看不到测试命令与本机路径。
- **SOP-125 与验收的关系**：P01 一个批次没有任何沉淀，照常完成验收与报告。P02 沉淀提交后执行增量验证，已通过场景按完整改动范围判定：只有测试改动时沿用并写理由，统计中沿用与重跑分开计数。P03 人工把有关联测试的场景标为不通过，详情显示“关联测试待核查”，场景结论为不通过。P04 沉淀失败的场景，其验收结论保持原样。
- **SOP-126 数据目录兼容**：P01 用现有格式 5 的数据目录启动新版本，批次、轮次、证据、修复、草稿、批注、确认与配对记录完整可见，关联表已建立。

**S2 第二段**

- **SOP-127 看板调度沉淀**：P01 本机场景页勾选两条可沉淀场景并发起，任务依次显示排队、沉淀中、待开发者审核；worktree 中有分层测试且未提交，关联为待提交；开发者在 worktree 提交并标记已处理、给出提交后，关联变为已提交，清理前列出的未提交改动为空，worktree 被清理。P02 沉淀中重启看板，任务显示已中断；重试复用原 worktree，上一次记录在 `attempts/` 中。P03 需要看板环境时，任务期间基线环境停止，结束后恢复，执行任务在此期间排队。N01 内网直接请求发起、重试、任务附件接口均被拒绝，内网任务详情不含路径与命令。N02 会话运行期间修改其中一条场景或项目验证技能，任务显示已作废及原因，关联未登记。N03 产品有未提交改动时任务显示待提交。N04 放弃任务后关联显示已放弃，清理失败时任务显示清理失败并保留现场。
