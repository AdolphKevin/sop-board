# 待执行与产品变化待判定分开显示（SOP-BOARD-21）

> 状态：方案 1，2026-11-03。cw2 会话里使用者看到组织-品牌-店铺批次“待执行 351”后问：“当前 sop-board 里的待执行的场景数也不对，现在不是已经有 200 多个场景已经验证通过了吗？”核对后选择“改看板展示”。
>
> 验收只以场景经真实入口执行为准，开发中不写单元、接口或集成测试（v9）。本仓 AGENTS.md 规定不运行 tw 命令，批准与验收记录写在本文状态栏。

## 现状

`statistics.calculate` 把场景放进四个队列：待执行、问题、复测、等待修改场景。进入“待执行”的有两种：

1. 当前内容没有任何结果（新增、内容变化、执行中途未执行）；
2. 最近一次 Agent 结果与最近结果都是通过，但通过时的产品摘要与批次当前摘要不同，或执行期间产品有变化（`stale`，即 source-changed）。

cw2 组织-品牌-店铺批次 2026-11-03 的实际数据：379 条场景，Agent 通过 283 条，待执行 351 条，其中 source-changed 283、new 65、changed 3。283 条通过分布在几十个产品摘要下，其中 71 条执行期间产品有变化，没有一条等于当前摘要，所以全部算作待执行。产品仓库每次提交或未提交修改都会让这类通过重新回到待执行。

按标准，这 283 条在下一轮按影响判定：不受影响的沿用，受影响的重跑（reference.md「用例、合并与执行」，D96 之后的影响判定段落）。但首页、概览、进度页与命令行只显示一个“待执行”数字，读起来像这些场景没有验证过。

## 决定

### D107 队列与计数把产品变化待判定单列

- 统计新增队列 `source-changed`，显示名“产品变化待判定”：最近一次 Agent 结果与最近结果都是通过，且通过记录已不能代表当前产品（产品摘要不同或执行期间产品有变化，判定与 `stale` 相同）。
- “待执行”（`pending`）只保留当前内容没有结果的场景。问题、复测、等待修改场景的口径不变；产品变化待判定的场景不进复测。
- `queue_counts` 与 `queues` 增加 `source-changed` 键；`pending` 的数值随之变小。状态接口、批次接口与 `sop-board status --json` 同步。
- 执行范围不变：`--scope pending`、“执行待执行场景（N 条）”按钮、执行计划的 pending 模式仍包含新增、内容变化、失败与产品变化待判定（`pending_scope` 不改）。按钮说明改为“与‘待执行’队列相比，还包含失败和产品变化待判定的场景”。
- 显示位置：
  - 首页批次条目与批次概览的状态行：待执行 A > 0 时显示“有待执行 A 条”，产品变化待判定 B > 0 时追加“，产品变化待判定 B 条”；A 为 0、B > 0 时只显示“产品变化待判定 B 条”；两者都为 0 时沿用现有的“Agent 已测完……”。
  - 批次概览的队列面板：在“待执行”与“问题”之间增加“产品变化待判定”面板，说明文字为“Agent 已通过，之后产品有变化；下次执行逐条判定影响，不受影响的沿用，受影响的重跑”。默认展开顺序为问题 → 待执行 → 产品变化待判定 → 复测。
  - 进度页开发侧：“待执行”之后增加“产品变化待判定”指标。
  - 命令行 `sop-board status`：每个批次一行“N 条场景；待执行 A；产品变化待判定 B”。
  - 内网页面同样显示新队列与计数（只读）。

### 不改的

- 影响判定、沿用规则、`impact.json` 与 pending.json 的 reason 不变（SOP-151、SOP-153）。
- 统计比率（已执行进度、Agent 验收通过率、一次通过率等）不变。
- 不新增“已通过”队列；通过数继续看 Agent 验收通过率与筛选。

## 备选

- 只改“待执行”的说明文字，不拆计数：数字仍是 351，问题不解决。
- 让产品变化后的通过直接算复测或通过：违背 SOP-151-P04 与影响判定，产品变化后的通过不能直接代表当前产品。
- 把“待执行”的执行范围也拆开（只执行新增与变化）：改变已验收的执行语义，不在本次范围。
