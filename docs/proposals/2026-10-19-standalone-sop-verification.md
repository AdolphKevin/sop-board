## 0 摘要

场景验收今天只在 team-workflow 的团队任务里可用：命令以任务为身份，产品指纹由方案推导，独立性读方案角色，场景核对要团队配置。
一个成员想"验一个 SOP"，先要接受整套团队流程；用其他开发流程的成员拿不出统一报告；测试岗看不到 Agent 验过什么；Agent 的场景与测试岗的用例各成一套，判不通过的缺陷全部回到开发者手里排查。

v8 的决定：

- **测试岗的用例是验收标准。** 测试同事把用例 YAML 上传到看板，看板调用 Codex 把用例与本地 SOP 场景合并成一份场景文件：每条用例生成一条同编号的场景，与用例重复或冲突的 SOP 场景移除，其余作为补充保留。没有 SOP 场景时同样以用例为准。
- **看板在开发者本机运行，与 Codex 同机，默认对项目仓库只读，开发者授权后可写。** 授权的仓库里，看板写入合并后的场景、对已提交的代码执行黑盒验收；出现不通过（测试岗标记并贴 Jira 单号，或 Agent 判失败）后，看板把仓库中全部未解决的问题放进一个方案，由 Codex 做根因分析，在 worktree 中按仓库自己的开发流程从根因修复；新会话复测问题场景、看板运行回归检查，都通过后合入本机基线分支，并在 Jira 写评论、更新状态。只能在固定地址运行的被测系统，修复后直接替换再复测。连续三次未通过转给开发者。
- **通过的场景沉淀为低成本测试。** 浏览器场景通过后，看板让 Codex 把它沉淀为集成、接口或单元测试，另一个会话一次复核本轮全部沉淀的测试，再在场景上写回归声明；之后代码变化时由这些测试守护该场景，测试通过即视为场景通过，不再经浏览器回归。
- **测试岗在 SOP 场景页上就地复核。** 看板除了总览，还有一页 SOP 场景说明，列出批次的全部场景；测试同事任选一条复核，"通过"一键提交，"失败""受阻"只填缺陷链接，可选填备注，页面不跳转。
- **独立验证在 praxis-skills。** `sop-verify` 技能加标准库脚本：没有看板时在本机登记与报告；有看板时推送场景与结果、取回合并后的场景，开发者下次使用时列出待处理的事项。
- **项目仓只放场景与入口声明。** 用例、轮次、证据与修复记录在看板；看板导出 Markdown 报告，贴到 Notion 或其他地方由开发者决定。
- **team-workflow 保持独立。** 不新增命令；看板导出的结果 JSONL 直接用 `tw team scenarios submit` 登记；浏览器执行使用其试点技能 `playwright-acceptance`。

不做：主动通知；反馈线程；看板写 Notion；推送远端或部署；源码复用或锁定；契约版本协商；证据入库；在 team-workflow 内提供看板。

## 2 目标与非目标

目标：

- **G1 无需接入团队流程**。装 praxis 的一个技能，一个 Git 仓库加一份 SOP 原文或一份测试用例，一句话触发，结果进看板。
- **G2 统一数据**。任何开发流程的轮次都进同一个看板，口径一致：每轮通过率、一次通过率、复测通过率、误判明细。
- **G3 两岗一个页面**。测试岗上传用例，在 SOP 场景页上任选场景就地复核，不通过时贴缺陷链接；开发岗看到合并结果、执行与修复进度；双方互见，刷新延迟在秒级。
- **G4 可迁移**。同一场景文件与看板导出的结果 JSONL 被 team-workflow 直接使用。
- **G5 项目仓轻**。仓内只有场景与入口声明，大小与轮次无关。
- **G6 事实替代门槛**。执行者与实现者关系、预期确认人、回归声明、合并时移除的场景、被测环境的版本依据如实标注。
- **G7 闭环**（v8）。授权的仓库里，从不通过到修复合入、场景回到复测队列、Jira 更新，全程由看板调度；需要开发者时，看板与 `sop-verify status` 给出原因、证据和下一步。
- **G8 可观察**（v8）。看板统计自动修复的触发、合入、转人工数与尝试次数，报告列出每个问题的根因与处理结果，用来观察修复准确率与成功率。
- **G9 回归成本低**（v8）。通过的场景沉淀为集成、接口或单元测试，回归由这些测试承担；浏览器只执行新增、变化与出问题的场景。

非目标：team-workflow 新命令；三个仓库之间的代码依赖；证据入库；自动写知识；登录体系（见第 6 节）；主动通知；反馈线程；看板写 Notion；推送远端或部署。

## 3 决定

- **D1 归属**（已确认）。`sop-verify` 技能与脚本在 praxis-skills；看板服务在独立仓库 `sop-board`，与 praxis 同一维护者；team-workflow 保留团队流程中的场景验收。
- **D2 握手文件**。场景文件字段与 team-workflow 现行格式相同，见[场景指南第 1 节](https://github.com/AdolphKevin/team-workflow/blob/main/skills/team-workflow/references/scenarios.md#1-场景文件)；结果 JSONL 字段与[第 5 节](https://github.com/AdolphKevin/team-workflow/blob/main/skills/team-workflow/references/scenarios.md#5-执行与提交)相同。入口声明放 `docs/sop/entries.yaml`，字段同 `acceptance_entries`，另有可选字段 `candidate`、`start`、`reload`（v8，见 D23）；项目已有 `.tw/config.json` 时读其 `acceptance_entries`。回归声明 `regression.check` 引用的检查，在 `entries.yaml` 的顶层 `checks` 中声明，字段同 tw 的 `checks`（`argv`、`cwd`、`timeout`、`format`、`report`、`required_env`）；项目已有 `.tw/config.json` 时读其 `checks`（v8，见 D29）。
- **D3 轮次与证据的位置**。配置了看板时，`submit` 把结果 JSONL 与证据推送到看板，本机不留副本；没有看板时写到项目仓外的本机目录，`report` 按需生成 Markdown 供成员贴进 PR 或 Issue。项目仓没有报告文件。
- **D4 独立性事实**。`submit --implementer <姓名>` 可选；执行者与实现者相同标 `self-check`，缺实现者标 `undeclared`，不同标 `independent`。看板发起的执行（D22）以仓库的 `git config user.name` 为实现者，修复后的复测（D25）以修复会话编号为实现者。
- **D5 看板的三个队列**。按 SOP-BOARD-1 方案 D2：待执行队列为没有结果，或 Agent 最新通过之后产品已变化且未声明 `regression.check` 的场景；问题队列为最新结果是 `fail`、`blocked`、`skip` 的场景；复测队列为最新结果是 Agent 的 `pass` 且不在待执行的场景，人工判失败后经修复再由 Agent 判通过的场景也回到这里。声明了 `regression.check` 的场景显示其检查在当前产品上的结果，检查失败的进入问题队列（D29）。统计沿用 2026-10-14 稿第 4 节：复测通过率、复测覆盖率、误判明细，同时显示样本量。批次另显示执行与修复状态（D26）。

- **D16 以用例为准的场景合并**（v8 改）。
  - 触发：上传用例；场景文件变化（sop-verify 推送，或授权仓库中看板读到外部修改）；开发者发起"重新合并"。看板以"用例并集版本、场景文件、SOP 原文、入口声明"的摘要组合识别同一次合并：组合已合并过，或文件变化来自看板自己的写入时，不再建任务。
  - 输入：用例并集、当前场景文件（没有时为空）、SOP 原文（有则带上）、入口声明，均以快照放入任务目录。
  - 运行：看板在任务目录中以只读沙箱调用本机 Codex，用 `--output-schema` 约束最终输出，提示词模板随看板发行。输出合并后的场景文件、对应关系，以及每条原有场景的去向和理由。结构化输出只约束格式，业务内容由下面的核对与人工复核把关。
  - 规则：每条用例生成一条场景，编号就是用例编号，字段按 S7 映射；用例的前置条件、步骤与预期按解析后的字符串内容保留，允许 YAML 转义与排版不同。原有 SOP 场景只有在角色、初始状态、入口与全部结果保证（`expected` 与 `forbidden_effects`）都被某条用例场景覆盖时才移除，记为"与 <编号> 重复"，它独有的 `forbidden_effects` 与回归声明并入该用例场景；上下文相同而预期相反时以用例为准移除，记为"与 <编号> 冲突"；其余保留为补充场景，编号不变。原有场景使用 `TC_` 形式的编号时报错。用例之间疑似重复的只列出。重新合并时按场景编号保留已有的回归声明。
  - 缺口：节点按用例的 `section:` 标签分组。某组没有正向场景时并入对应正向场景所在的节点；仍没有正向依据的，任务停在"待补充"并列出缺口，由测试岗补用例或开发者补 SOP 场景。没有反向场景的节点写 `negative_exempt`，理由须有依据；依据出自推断时同时写 `# 待确认` 注释，报告列为待确认预期。
  - 核对：看板核对场景文件格式（sop-verify 规则）、每条用例都有同编号的场景且前置条件（用例有时）、步骤与预期与原文一致、每条原有场景都有去向、引用的编号都存在。核对不通过时任务为"失败"，保留 Codex 原始输出，可重新运行。
  - 落地：只读模式下合并结果是草稿，开发者用 `sop-verify pull` 写入仓库并推送后成为当前版本。授权仓库中，看板把结果写入工作区的 `docs/sop/<批次>.yaml`（入口声明缺失时一并写 `entries.yaml`）并记为当前版本，前提是磁盘上的文件与合并依据的版本相同；不同则任务停在"待同步"，开发者推送本地修改后重新合并。这次写入不提交，由开发者随自己的改动提交。
  - 对应关系可直接作为 `sop-verify coverage --pairs` 的配对文件，全部归入 `covered`。

- **D22 看板发起的执行**（v8 新增）。
  - 原则：看板的自动执行、修复、复测与合入都针对已提交的代码。授权仓库的工作区有未提交的产品改动（工作区产品指纹不等于 HEAD 的产品指纹）时，自动任务停在"待提交"，开发者提交后开始；只改了 `docs/sop/` 不算产品改动。
  - 触发与范围：合并结果写入后，自动执行新增与内容变化的场景；开发者发起"执行待执行场景"时，执行 S2 列出的全部待执行场景。看板不自动做全量回归。每轮执行时，看板在同一快照上运行由回归守护的场景的检查（D29）。
  - 快照：执行开始时固定场景、入口、用例并集与产品版本，执行结束与登记时各核对一次；产品指纹按 SOP-VERIFY-1 方案 D2 的现行算法计算，任何一次不一致则本轮作废，页面写明原因。
  - 被测对象：按入口的 `candidate`（D23）。`checkout` 与 `start` 入口在基线分支最新提交的 worktree 上执行；`in-place` 入口测开发者正在运行的环境，轮次记"运行环境按 HEAD 记录，未经核实"。
  - 执行会话：每轮一个新会话，工作目录为任务目录，可写任务目录、可联网；输入快照、入口与证据目录，按入口选驱动（D9），在任务目录写结果文件与证据。看板按结果契约核对后登记为 Agent 轮次，执行者为会话编号。
- **D23 候选版本的验证方式**（v8 新增）。入口的可选字段 `candidate` 说明怎样验证一个候选版本：
  - `checkout`：执行者直接在检出目录中操作，适用于命令行、带自备数据库的接口测试等不需要常驻服务的入口。
  - `start`：看板以检出目录为工作目录运行入口的 `start` 命令启动服务，经环境变量 `SOP_PORT` 给出端口，并把同一地址写入服务与执行者环境中 `address_env` 指定的变量；120 秒内地址有响应视为就绪；结束后终止其进程组。数据隔离按入口的 `isolation` 由项目负责。端口被占、启动失败或就绪超时按一次未通过处理，日志交给修复会话。
  - `in-place`（缺省）：只能测开发者正在运行的环境，例如只能挂在一个隧道地址上的 Shopify 内嵌应用。修复后直接替换（D25），替换后运行入口的 `reload`；未声明 `reload` 时依赖被测系统自身的热更新。
- **D24 修复任务**（v8 新增）。
  - 触发：授权仓库中出现未解决的问题：测试岗标"不通过"（失败或受阻，带缺陷链接）、Agent 结果为 `fail`，或由回归守护的场景其检查失败。Agent 的 `blocked` 与 `skip` 留在问题队列。未授权时问题留在问题队列，由开发者按自己的流程处理。
  - 范围：所有项目都按整体修复执行：每个授权仓库同一时间只有一个修复任务，纳入该仓库各批次全部未解决的问题，放进同一个方案。任务进行中出现的新问题，在下一次尝试时纳入。
  - 准备：按 D22 的原则，工作区有未提交的产品改动时任务停在"待提交"，开发者提交后以最新提交开始。看板读取各问题的 Jira 单，读取失败时记下原因，以标记内容继续；以基线分支（任务开始时仓库主工作区所在的分支）的最新提交建 worktree 与分支 `sop-board/fix/<序号>`，固定场景、入口与用例并集的快照。
  - 修复会话：同一任务的各次尝试用同一个会话，可写 worktree、可联网。输入全部问题（场景快照、实际结果与证据、Jira 单内容、此前 Agent 结果）与入口声明。要求：
    1. 先对全部问题做一份根因分析，判定每个问题属于产品缺陷、执行或环境问题、场景或需求问题；
    2. 只修产品缺陷，并从根因修复：直接替换错误的逻辑，不加兼容层，不保留新旧两套实现，不做只让个别场景通过的局部修补，修改时顾及其他场景与已有行为；
    3. 按仓库自己的开发规则（AGENTS.md、CLAUDE.md 与已装技能）修复，走 TDD 的仓库先写能复现缺陷的失败测试；
    4. 场景文件与入口声明保持原样，改动留在 worktree，由看板提交；
    5. 按输出模式交回根因分析、每个问题的判定与处理、改动文件、运行过的测试与结果。
  - 转开发者：判定为执行、环境、场景或需求问题的，以及会话判定无法修复的，写明理由与方案，转"待开发者处理"，不改代码；同一任务中的其余产品缺陷照常修复。开发者批准方案时，看板用同一会话继续，附上开发者说明。
  - 提交：看板核对改动只涉及场景文件与入口声明以外的文件，在修复分支提交，提交信息列出 Jira 单号与场景编号。
  - 计数：一次修复加一次验证为一次尝试。验证未通过时（含候选启动失败、回归检查失败，以及合入前基线前进后的追加验证失败），看板把证据与新出现的问题交回同一会话继续；连续三次未通过，任务转"待开发者处理"，附每次的根因、改动与复测证据，并记录会话编号。会话异常中断不计次数，看板重试一次，仍中断则转开发者。
- **D25 复测、合入与 Jira 回写**（v8 新增）。
  - 验证：每次复测是一个新会话，与修复会话不同，也不复用之前的复测会话；范围是任务中的全部问题场景。看板同时在候选版本上运行全部由回归守护的场景的检查（D29）；其余场景不自动重跑，合入后因产品变化需要执行的，列入待执行队列。问题场景全部通过且这些检查全部通过，才算验证通过。
  - `checkout` 与 `start` 入口：在 worktree 上复测并运行检查，验证通过后合入。合入前重新核对基线分支所在的工作目录、该目录当前所在分支、基线提交与候选提交。基线已前进时在 worktree 中合入基线：有冲突转"待开发者合入"；无冲突则对合并提交再验证一次。基线分支检出在开发者工作区时，在该目录运行 `git merge --ff-only`；Git 因未提交修改拒绝时转"待开发者合入"，工作区保持原样；合入成功而工作区另有未提交修改时，记录"工作区含未经验收的修改"。看板不暂存、不还原、不强制移动分支。
  - `in-place` 入口：修复提交后，看板先在 worktree 上运行回归检查；检查通过后直接替换：按上面的核对把修复快进合入基线分支，运行 `reload`，再由新会话在开发者的运行环境中复测问题场景；未全部通过时，在已替换的代码上继续下一次尝试。三次未通过时保留已替换的代码，转"待开发者处理"，看板列出本任务合入的提交与每次的证据。
  - 登记：worktree 上的复测结果先存为候选记录，合入后由看板提升为批次的 Agent 轮次：保留原执行时间，更新批次产品指纹；提升可以重复执行而结果不变；看板重启时发现候选提交已在基线中而未提升的，补做提升。`in-place` 的复测直接登记为 Agent 轮次。候选失败只计入修复统计。
  - 通过后：场景回到复测队列等测试岗复核，删除 worktree 与已合入的分支。对任务中带 Jira 单号的问题，看板写一条评论（根因、改动摘要、修复提交与所在本机分支、复测场景与结果，并注明尚未部署），并流转到 `JIRA_FIXED_STATUS` 指定的状态，取团队流程中表示修复待部署到测试环境的状态：修复只在开发者本机分支，测试岗的缺陷流程会对"已修复"的单立即复测，开发者部署后再按现有流程改为"已修复"。该状态从当前状态不可达时不流转，记为"Jira 状态待人工更新"，在 `status` 中列出。部署到测试环境仍按现有流程由人完成。
- **D26 执行与修复状态**（v8 新增）。不做主动通知。批次总览与项目列表显示 Agent 执行状态：执行中（会话数与开始时间）、已测完（完成时间与通过、不通过、受阻、跳过数）、有待执行（数量与原因）、待提交、已暂停。合并任务显示：运行中、草稿、已写入、待同步、待补充、失败。修复任务显示：分析中、修复中、复测中、待合入、已合入、待开发者处理、待开发者合入、已中断，均附原因。沉淀任务显示：沉淀中、复核中、已合入、无法沉淀（附理由）。由回归守护的场景显示：检查通过、检查失败、检查待运行。任何任务在同机 Codex 不可用时显示"Codex 不可用"。
- **D27 报告导出**（v8 新增）。看板按批次导出 Markdown 报告，区块为：头部（项目、批次、场景版本与提交号、用例并集版本、产品提交号与指纹、生成时间）；用例覆盖（每条用例的场景及最新 Agent 与人工结果）；Agent 统计（通过率、一次通过率、每轮通过率）；人工复测（通过率、覆盖率、误判明细与 Jira 链接）；修复记录（问题、根因摘要、尝试次数、结果、合入提交与 Jira 回写结果）与自动修复统计；回归覆盖（每条场景的回归声明、检查在当前产品上的结果、无法沉淀的理由、漏检次数）；合并记录（移除的场景及理由、待确认的推断）；未验证范围（受阻、跳过）。贴到哪里由开发者决定，看板不上传；有看板时 `sop-verify report` 取同一份报告。
- **D28 会话里的提示**（v8 新增）。sop-verify 增加 `status`：有看板时列出当前仓库待开发者处理的事项（待开发者处理、待开发者合入、待提交、待补充、待同步、Jira 状态待人工更新、已中断），每项附看板链接、原因与接续会话的命令。开发者下次使用 sop-verify 时，代理先报告这些事项；看板不向任何会话推送消息。
- **D29 场景沉淀为低成本测试**（v8 新增）。
  - 触发：授权仓库中，场景经 Agent 执行通过且没有回归声明时，看板建沉淀任务。每个仓库同一时间只有一个沉淀任务，纳入全部待沉淀的场景；与修复任务不同时运行，修复优先（D21）。
  - 沉淀会话：可写 worktree（基线分支最新提交）、可联网。按仓库已有的测试体系，为每条场景写能覆盖其业务结果的最低成本自动化测试，按单元、接口、集成的顺序选层级；断言来自场景的 `expected` 与 `forbidden_effects`，不照抄当前输出；测试登记为一项检查（已有的检查优先，新检查写入 D2 所述的 `checks`），交回每条场景的 `regression: {check, cases}`。只能靠浏览器验证的场景写明理由，保持由浏览器执行。
  - 复核：另开一个新会话，一次复核本轮沉淀的全部测试。复核会话在同一 worktree 中可写、可运行：逐条核对断言是否覆盖场景的 `expected` 与 `forbidden_effects`，可以临时改动被测代码，确认相应测试会失败；再把本轮全部测试与项目已有的测试放在一起运行，检查重复、互相干扰、结果不稳定与耗时，避免单条可用、整体不可用。复核会话的改动只用于验证，复核结束后看板把 worktree 恢复到沉淀提交，这些改动全部丢弃。有意见时交回同一沉淀会话统一修改，再由新的复核会话复核全部测试；最多三轮，三轮仍未通过的场景不写回归声明，继续由浏览器执行，理由记入任务。
  - 落地：看板在修复分支之外的 `sop-board/distill/<序号>` 上提交测试，运行对应检查，确认声明的用例全部出现且通过后，按 D25 的保护快进合入；回归声明与新检查按 D16 的写入规则写入工作区的场景文件与入口声明。
  - 守护：之后产品变化时，由回归守护的场景不再经浏览器执行，看板在当前产品或候选版本上运行其检查：声明的用例全部出现且通过，即视为该场景在这一版本通过；失败则场景进入问题队列并触发修复（D24）。检查命令须能在全新的检出目录中运行，依赖准备由命令负责。
  - 漏检：测试岗把一条由回归守护的场景标为不通过，而其检查在同一版本上通过时，看板记一次"回归检查漏检"，撤下该场景的回归声明，场景回到浏览器执行，并重新沉淀。漏检次数计入统计与报告。

## 4 设计

### S1 praxis 的命令面

```bash
python3 <sop-verify 目录>/scripts/sop.py check <场景文件>
python3 <sop-verify 目录>/scripts/sop.py pending <场景文件> [--format json]
python3 <sop-verify 目录>/scripts/sop.py submit <场景文件> --results <结果.jsonl> [--implementer <姓名>]
python3 <sop-verify 目录>/scripts/sop.py import-cases <场景文件> <用例文件>
python3 <sop-verify 目录>/scripts/sop.py coverage <场景文件> --pairs <配对.json>
python3 <sop-verify 目录>/scripts/sop.py report <场景文件>
python3 <sop-verify 目录>/scripts/sop.py pull <场景文件>     # v8：取回看板上的合并结果
python3 <sop-verify 目录>/scripts/sop.py status              # v8：列出待开发者处理的事项
```

看板地址因启动者而异，由环境变量 `SOP_BOARD_URL` 提供，写入令牌为 `SOP_BOARD_TOKEN`；`entries.yaml` 只写入口。`pending`、`report` 与 `status` 在有看板时读看板，
没有看板时 `pending` 与 `report` 读本机目录。Python 3.10 以上标准库，与 team-workflow 同名子命令同义、独立实现。

### S2 产品指纹与执行选择

场景内容指纹覆盖 `initial_state`、`steps`、`expected`、`forbidden_effects`。产品指纹按 SOP-VERIFY-1 方案 D2：`git ls-files` 列出的已跟踪与未忽略的文件，排除 `docs/sop/`、当前场景文件与所用入口文件，取工作区中的内容。

看板页面的队列按 D5。待执行场景是：新增、内容变化、最新结果为 `fail`、Agent 通过之后产品已变化且未声明 `regression.check`。
看板自动执行时只选新增与内容变化的场景（D22），修复后的复测只选问题场景（D25）；开发者发起时执行全部待执行场景。声明了 `regression.check` 的场景不经浏览器执行：授权仓库中由看板运行其检查（D29）；没有看板时 `sop-verify pending` 照旧单列为"由回归守护，需确认检查通过"，检查由项目自己运行。

### S3 看板

独立仓库 `sop-board`，uv 管理的 Python 项目，SQLite 存储，数据目录由启动参数指定；成员 clone 后在本机启动，默认监听本机，内网访问显式开启，可写授权按仓库显式开启。
接口接收场景文件、SOP 原文、用例、结果 JSONL 与证据文件；页面即在线 HTML，按项目、批次组织：

| 页面 | 内容 |
| --- | --- |
| 批次总览（看板） | 面向全员的在线页：Agent 执行状态、Agent 验收通过率、人工复测通过率与覆盖率、一次通过率、三个队列的数量、测试进度、误判数、自动修复统计，均带样本量；导出 Markdown 报告 |
| SOP 场景 | 按节点列出批次的全部场景说明：编号、标题、极性、优先级、角色、入口、初始状态、步骤、预期、禁止副作用、对应用例；每条附最新 Agent 结果、最新人工结果与回归状态。可按全部、未人工复核、Agent 已通过、不通过、受阻筛选。测试岗在每条场景上就地复核（D6），提交后不跳转，状态在原处更新 |
| 场景详情 | 单条场景的完整历史：各轮结果、执行者与独立性标注、被测环境的版本依据、证据预览、缺陷链接、所属修复任务、回归声明与检查结果；同样可以就地复核 |
| SOP | SOP 原文渲染，含 mermaid；版本列表、两版差异、确认人；每个场景节点链接到原文段落 |
| 用例 | 测试岗选择项目与批次上传用例 YAML，按 Schema 校验；列出历次上传与并集，下载当前并集 |
| 合并 | 合并任务与状态；用例到场景的对应关系、移除的场景与理由、待确认的推断与缺口；失败时保留 Codex 原始输出 |
| 修复 | 修复任务与状态、尝试次数、根因分析、每个问题的判定、改动摘要、复测证据、合入提交、Jira 回写结果；开发者操作凭开发者令牌 |
| 回归 | 沉淀任务与状态；已沉淀与无法沉淀的场景及理由；检查运行记录与输出；漏检记录 |
| 进度 | 开发侧：待执行、已执行、通过率、已沉淀；测试侧：待复核、已复核、复测通过率；两列并排，带样本量 |
| 趋势 | 跨批次的上述指标，含自动修复统计 |
| 导出 | 按轮次导出结果 JSONL 与证据、测试岗结果 Schema 的 `results.yaml`；场景、用例、对应关系的 YAML 与 JSON；Markdown 报告 |

标记人在页面声明一次保存在浏览器；写入接口凭令牌。场景文件重新推送后，内容变化的场景的旧结果与标记标为"场景已变更"。
用例页沿用测试岗 HTML 导出的字段映射与 `section:` 分组，保留原用例编号；执行记录以看板为准。

### S4 sop-verify 的对话流程

用户说"验证 <SOP 位置>"或 `/sop-verify <路径>`。代理：

1. 有看板时先运行 `status`，报告待开发者处理的事项；再读 SOP 原文与项目事实：入口、认证、存储、已有测试与运行方式。
2. 看板上该批次已有用例时，以合并后的场景为准：推送自己写的补充场景，等看板合并后 `pull` 取回。没有用例时写 `docs/sop/<批次>.yaml` 与 `docs/sop/entries.yaml`：节点正反向场景、来源与版本；推断出的预期进入"待确认"；按项目类型选入口，并按 D23 写明 `candidate`。
3. 请负责人确认补充场景中的推断预期与合并时写下的待确认内容，这是唯一必停点；由用例生成的场景以用例为准。
4. `check` 后推送场景文件与 SOP 原文。
5. 授权仓库由看板发起执行（D22）；否则按 D10 派执行者，经驱动执行，收结果 JSONL，`submit` 推送看板。
6. 不通过的场景：授权仓库由看板按 D24 处理；否则交回成员自己的流程，之后执行选择只列该测的，再派执行者。
7. 报告看板地址与本轮统计；需要报告时用 `report` 取 Markdown。

### S5 与 team-workflow 的关系

零代码依赖，三个接点都是文件：入口声明复制进 `acceptance_entries`；方案验收节引用同一个场景文件；看板导出的结果 JSONL 直接
`tw team scenarios submit`。team-workflow 不读看板。浏览器执行会话调用 team-workflow 的 `playwright-acceptance`，经文件交接待执行清单与结果。

```bash
cd <sop-board 检出目录> && SOP_BOARD_TOKEN=… SOP_BOARD_ADMIN_TOKEN=… \
  JIRA_URL=https://<站点>.atlassian.net JIRA_EMAIL=… JIRA_API_TOKEN=… JIRA_FIXED_STATUS=<状态名> \

```

项目仓：`docs/sop/<批次>.yaml`、`docs/sop/entries.yaml`；AGENTS.md 一句约定："交付前对改动涉及的 SOP 节点运行 sop-verify"。

### S7 用例到场景的字段映射

| 场景字段 | 来源 |
| --- | --- |
| `metadata.requirement` | 批次的需求名，新建批次时填写，缺省取用例文件的 `metadata.feature` |
| `metadata.batch`、`metadata.version` | 看板批次名；用例并集版本 |
| `metadata.owner` | 用例文件的 `metadata.owner` |
| `metadata.sources` | 一项指向用例批次与上传版本，`confirmed_by` 为用例文件的 `metadata.owner`；补充场景原有的 SOP 来源保留 |
| 节点 `id`、`title` | 按用例的 `section:` 标签分组，编号由看板按标签生成，重新合并时不变 |
| 节点 `actor`、`entry` | Codex 依据用例与入口声明填写 |
| 场景 `id`、`title`、`priority`、`tags` | 用例的 `id`、`title`、`priority`、`tags` |
| `polarity` | 用例 `tags` 含 `negative` 为 `negative`，否则为 `positive` |
| `negative_type` | Codex 从枚举中选择，没有合适的取 `other` |
| `actor`、`verify` | Codex 依据用例填写业务角色，从入口声明中选择入口 |
| `initial_state` | 用例的 `preconditions`；用例没有时由 Codex 补写，在对应关系中标明并写 `# 待确认` 注释 |
| `steps`、`expected` | 用例的 `steps`、`expected_results` |
| `forbidden_effects` | 空数组，或并入的重复 SOP 场景的禁止副作用 |
| `refs` | 用例编号 |
| `regression` | 重新合并时按场景编号保留；首次由沉淀任务写入（D29） |

## 5 备选与不采用

- **按轮入库报告**（v2）：仓库随轮次变重，多人并行在同一目录冲突，测试岗仍无交互。
- **每批一份覆盖式状态文件入库**：仓库大小可控，但分支并行时同一文件冲突，且仍无交互。
- **看板放进 praxis-skills**：技能安装工具按 `SKILL.md` 目录安装，服务放在里面语义混乱。
- **看板放进 team-workflow**：team-workflow 2026-10-16 方案的 D6 已定 team-workflow 只给契约与指南。
- **用 Issue 评论当看板**：能提 BUG，看不到队列与趋势，人工标记无法回到数据。
- **team-workflow 锁定复用 praxis 源码**：用户决定各自独立维护。
- **看板以 Docker 部署**（v3 到 v5）：容器内拿不到本机已登录的 Codex，用户决定以 uv 在本机启动。
- **固定一台主机部署看板**（v6）：用户决定暂不考虑服务器部署，谁 clone 谁启动。
- **离线 HTML 导出**（v4、v5）：看板本身就是在线页面，执行记录以看板为准，用户决定去掉。
- **看板只读，修复全部由成员完成**（v6、v7）：失败与修复之间要人工搬运，团队诉求要求闭环；v8 保留为未授权时的模式。
- **以 SOP 场景为准，用例只核对覆盖**（v3 到 v7）：测试岗用例才是交付验收的依据，用户决定以用例为准。
- **测试岗把用例标为"本批次不验"**（v8 初稿）：会缩小验收标准，违背全面覆盖；无法执行的用例改记受阻或跳过。
- **每个问题一个修复任务、并行修复**：各修一处是局部最优，并行的修复还会互相冲突；用户决定所有项目都把全部问题放进一个方案。
- **合入前自动全量回归**（v8 第二轮草稿）：浏览器场景串行执行，场景越多每次修复尝试越久；用户决定改由沉淀的低成本测试守护已通过的场景。
- **只能直接替换的项目三次未通过后自动撤回**（v8 第二轮草稿）：用户决定保留已替换的代码，交人工处理。
- **Codex 在开发者工作区修复**：会与开发者未提交的改动混在一起；改在 worktree。
- **以工作区快照为修复基线**：开发者未提交的改动会随修复一起进入分支，快进时又与工作区的同一改动冲突；改为只针对已提交的代码。
- **修复会话自己复测**：执行者与实现者相同，只算自检；复测改由新会话执行。
- **以本机请求代替开发者身份**：本机的反向代理与端口转发会让远端请求显示为本机来源；改为开发者令牌。
- **主动通知与反馈线程**：用户决定暂不做，看板展示执行与修复状态，`status` 在会话里列出待办。
- **GitHub Issues 一键建单**（v4 到 v7）：团队缺陷流程在 Jira，改接 Jira。
- **看板写 Notion**：Notion 开放的编辑能力不全；报告由开发者自行贴入。
- **没有 Codex 时由开发机 sop-verify 完成分析**（v5 到 v7）：看板与 Codex 同机，这条退路不再需要。

## 6 后果与限制

- 三个仓库、三套测试；格式变更靠人同步。
- 看板由启动它的成员在本机运行并备份数据目录；Codex 对话消耗该成员的订阅，并发不超过三个。每次修复尝试含一次修复会话与一次复测会话，三次封顶；复测只执行问题场景，其余已通过的场景由沉淀的测试守护。不同成员各自启动时数据彼此独立；团队共用一份数据时约定一位启动者，可写授权只覆盖启动者本机的仓库。没有看板时退化为本机轮次加按需报告。
- 自动任务只针对已提交的代码：开发者有未提交的产品改动时，执行与修复停在"待提交"；习惯长时间不提交的成员需要先提交才能用上自动修复。
- Agent 判失败也会自动修复：功能尚在开发、本就未完成时，修复会话可能去补功能；根因分析把这类问题判为场景或需求问题时转开发者；与开发者改动冲突的合入转"待开发者合入"。
- 内网中持有写入令牌的人上传的用例与 Jira 单内容会进入 Codex 提示词；授权仓库中，执行与修复会话可写任务目录与 worktree、可联网、可读本机文件。对应措施：合并会话只读；修复只在 worktree，合入前须通过新会话的复测；修复改动只涉及场景文件与入口声明以外的文件；看板从不推送；开发者操作凭单独的令牌；所有子进程的环境中没有看板与 Jira 令牌，Codex 显式指定沙箱。剩余风险是提示词注入可借会话读取本机文件并向外发送，内网访问只在可信网络开启。
- 自动合入会更新开发者工作区中被修复改动的文件，编辑器里未保存的同名文件需要开发者留意；工作区另有未提交修改时，合入后的工作区与已验收的提交并不相同，看板如实记录。合入只到本机分支，部署由人完成，测试岗复核要等修复部署到其测试环境。
- `in-place` 入口在复测前就替换了代码，复测针对开发者正在运行的环境，看板无法证明该环境已加载新代码，只记录 HEAD 与 `reload` 的结果；替换前的回归检查能拦下沉淀过的场景的回归。三次未通过时，已替换的代码留在开发者分支，由开发者处理。
- 回归改由沉淀的测试承担后，场景在新版本上是否通过取决于这些测试是否真正覆盖了场景的业务结果。复核会话与漏检记录用来发现覆盖不足；尚未沉淀或无法沉淀的场景在代码变化后进入待执行队列，等开发者发起执行，期间可能漏掉它们的回归。
- 沉淀的测试是项目自己的测试代码，随合入进入开发者分支，由项目按自己的规则维护；检查命令要能在全新的检出目录中准备依赖并运行。
- `start` 入口的数据隔离由项目负责；两个检出同时运行时共用一份数据会互相干扰。
- 浏览器执行依赖开发者本机打开的测试专用 Chrome 与已登录的测试账号；未就绪时执行结果为受阻。
- Jira 的评论与状态以启动者的 Jira 账号写入。
- 标记人身份自行声明，防误操作，防不了冒充；推广到更大范围前接入登录。
- 证据上传到看板，容量与保留期由启动者设置；项目仓始终只有场景与入口声明。
- praxis 与 sop-board 为公开仓库，只承载契约与实现；业务 SOP、场景、用例、结果与证据只在项目仓和本机看板。
- 修复准确率与成功率靠试用观察（G8）；首批真实项目的数据决定是否调整自动修复的范围。
