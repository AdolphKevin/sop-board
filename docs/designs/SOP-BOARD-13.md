## 目标与非目标

目标：

```
上传用例 ──▶ 合并 ──▶ 可确定的用例落地为场景并照常执行
                 └──▶ 缺口（业务场景语言）──▶ 合并对话：人回复 ⇄ Codex 采纳或追问
                                               └──▶ 看板按采纳的回复更新用例 ──▶ 同一轮落地补齐的场景
                                               └──▶ 本批不纳入（人工完成）
```

非目标（后续需求）：
- 不经用例、直接通过对话修改已落地场景的字段。本需求中场景始终由用例生成，对话通过更新用例影响场景；
- 修改测试同事本机的用例文件或场景目录之外的文件。更新后的用例登记在看板中，从用例页下载；
- 删除或撤回已登记的用例；
- 改变现有执行、复核、修复流程和「来自草稿确认的合并不自动执行」（D58）。

## D66 缺口结构化，用业务场景语言表达

缺口是给测试同事和业务确认人读的问题单，写法沿用 cw2-live-chat 测试问题单（场景 → 用例目前的写法 → 缺什么 → 请确认 → 涉及用例），2026-10-22 经 AdolphKevin 确认。

- 合并输出的 `gaps` 由字符串数组改为对象数组，每项：
  - `id`：本轮内唯一，`G1…`；
  - `kind`：`business`（缺业务规则，由业务确认人或测试同事回答）或 `entry`（验收需要的操作看板做不到，由开发者处理）；
  - `title`：一句话说清问题，例如「额度周期多长、按哪个时区算、几点切换」；
  - `scenario`：谁、在哪里、做什么，用用例中的具体数值举例，例如「店铺 10 月 15 日安装，本期额度 100，用了 60；到下个周期剩下的 40 应该清零」；
  - `current`：用例目前的写法（摘录要点）；`entry` 类写「现状」：看板目前能操作什么、做不到什么；
  - `missing`：缺什么、为什么测试时无法判断通过与否，例如「判断不了 11 月 14 日 23:30 用掉的额度算本期还是下期」；
  - `question`：请确认的内容，只问一件事，能直接回答；`entry` 类写需要开发者做什么，或可决定本批不纳入；
  - `known`：已知口径，可为 null，引用已有澄清回复或已定结论；
  - `options`：可选回答，0–3 项，只为方便回答，不作为推断出的预期；
  - `cases`：受影响的用例编号，非空，均在用例并集中。
- **语言要求**（写入 `prompts/merge.md`）：面向测试同事和业务方，不出现快照、SOP 原文、入口声明、flow/detail、节点、section、schema、合并等内部术语；不用产品当前实现补齐答案；缺口只列确实无法从用例、SOP 原文、已有场景与澄清记录得出的内容。
- **看板核对**：`id` 本轮唯一，`title`、`scenario`、`current`、`missing`、`question` 非空，`options` 不超过 3 项，`cases` 非空且都在用例并集中；不合格时任务「失败」并列出问题。
- **展示**：合并页、合并对话与用例页按「标题 / 场景 / 用例目前的写法（或现状）/ 缺什么 / 已知口径 / 请确认 / 涉及用例」排版；涉及用例显示编号加标题并链接到用例页；`entry` 类标「由开发者处理」。
- 看板自补的「节点没有正向依据」按同一结构生成：标题「“<分组名>”这组用例只有失败或异常情况，没有一条正常完成的流程」，请确认「补一条正常完成的用例，或说明这组并入哪个分组」，`cases` 为该组全部用例。
- 旧任务 `result.gaps` 中的字符串照旧显示，视为不关联用例的缺口，不迁移。

## D67 部分落地

- **暂缓集合**：本轮缺口 `cases` 的并集为初始暂缓用例；所属流程被暂缓的细节用例一并暂缓；节点内正向流程用例全部被暂缓时，该节点全部用例暂缓。
- **组装**：只为未暂缓的用例生成场景，按现有规则核对（确定字段、正反向覆盖、去向、入口、`relocate` 等）。暂缓的细节用例所在流程照常落地：该细节此前从未并入过这条流程时，不含它的预期；此前已并入过、而该流程本轮有更新时，按新内容重建流程，同时原样保留上一版中该细节的 `[用例 <编号>]` 预期条目、`refs` 与配对，并对该用例标「用例已更新，新内容待补充」（2026-10-22 经 AdolphKevin 确认）。补齐后按新内容重建，该流程场景变化，按现有规则转为待执行。
- **暂缓用例已有场景**（例如测试同事修改了已落地的用例，新内容产生缺口）：沿用当前版本中的该场景原文，连同其执行历史、复核与回归声明；用例页与场景页标「用例已更新，新内容待补充」，该场景不因本次合并转为待执行。补齐后按新内容重建，场景变化按现有规则转为待执行。
- **结果**：
  - 有可落地的场景时，按现有 `land` 写入场景目录并登记场景版本，任务为「已完成」；`result` 同时保留 `gaps` 与 `held`（暂缓用例及原因）。新增与变化的场景照常自动入队执行（草稿确认来源除外，D58）。
  - 没有任何可落地的场景时，任务为「待补充」，不写文件（与现在相同）。
- **展示**：
  - 用例页每条暂缓用例标「待补充」，显示对应问题并链接到合并对话；
  - 批次概览页与场景页显示「待补充 N 项 · 暂缓 M 条用例 → 去补充」；
  - 批次报告的「尚无对应场景」写明暂缓原因。
- 暂缓用例不进入执行范围与通过率分母，只在上述位置单独计数。

## D68 合并对话

- **页面**：批次「合并」页顶部新增「合并对话」区，内网可访问：
  - 当前未解决的缺口卡片：问题、类型、说明、受影响用例（链接到用例页），各带一个回复框；
  - 一个通用输入框，用于不针对单个缺口的补充说明；
  - 对话记录：按时间列出人的回复（回复人、时间、对应缺口、原文、处理状态）与每轮 Codex 的答复（`reply`、各条回复的处理结论、新缺口或追问）；
  - 缺口卡片按 D66 的业务场景格式排版；`entry` 类缺口标「由开发者处理」，可由开发者补入口声明后重新合并，或由任何人点「本批不纳入」；仅凭文字回复不能消除该缺口。
- **接口**（普通写入，内网可调用，不加 `developer` 限制）：
  - `GET /api/v1/workspaces/<k>/batches/<b>/merge-conversation`：未解决缺口、暂缓用例、对话记录、当前合并状态；
  - `POST /api/v1/workspaces/<k>/batches/<b>/merge-conversation/messages`，正文 `{author, messages: [{gap, text}]}`。`author` 取身份栏的标记人，不能为空；`gap` 为 `<任务编号>:<缺口编号>` 或 `null`（通用说明）；`text` 非空，单条不超过 4000 字。不合格返回 422 并列出字段与原因，不保存。
- **记录**：每条回复保存回复人、时间、对应缺口及缺口问题的快照、原文、状态（待处理、已采纳、已追问、不适用）与处理该条的合并任务编号。新增表以 `CREATE TABLE IF NOT EXISTS` 加入 `SCHEMA`，数据库格式保持 5。
- **触发下一轮**：提交后，批次没有排队中或运行中的合并任务时，立即入队合并任务，触发原因为「补充澄清」；否则回复保持待处理，当前合并结束后由看板自动入队下一轮。批次没有用例时拒绝提交（409）。
- **续接会话**：批次已有带 `session_id` 的合并任务时，用 `resume_codex` 续接最近一个，提示词写明本轮任务目录的绝对位置与新增材料。续接失败时改为新会话，快照中带全部澄清记录，任务记录写明「会话续接失败，已用完整历史新开会话」（沿用 D56 的回退方式）。上传用例、场景文件变化与重新合并触发的合并同样优先续接，保证一个批次只有一条对话主线。
- **快照**：合并任务目录新增 `clarifications.json`，含该批次全部回复（按时间排序，标明本轮待处理的条目）及其对应缺口。澄清记录计入输入摘要，相同输入去重规则不变。
- **Codex 输出新增**：
  - `reply`：给回复人看的本轮答复，业务语言，可为空字符串；
  - `responses[]`：对本轮每条待处理回复恰好一次，`action` 为 `adopted`、`question` 或 `not_applicable`，`note` 非空；
  - `case_updates[]`：`{case, changes, messages, reason}`，把被采纳回复确定的内容写进用例。`changes` 只能含 `title`、`preconditions`、`steps`、`expected_results`、`tags` 中需要修改的字段，取值为修改后的完整字段；`messages` 为依据的回复编号；`reason` 用业务语言说明改了什么。回复与用例原文冲突时（例如已定“断开店铺不需要指定会话去向”，而用例要求必须指定），按回复改写对应条目。
- **看板核对**（不合格时任务「失败」并列出问题，回复状态与用例都不变）：
  - `responses` 覆盖且只覆盖本轮待处理回复；
  - `case_updates` 引用的回复在本轮或此前已被采纳；用例存在且未被标为本批不纳入；`changes` 只含允许的字段、与当前内容确有不同；更新后的用例仍符合用例格式（`load_cases` 规则），编号不变；
  - 同一用例本轮最多一项更新。
- **更新用例**：核对通过后，看板在落地前把本轮全部 `case_updates` 登记为一次用例上传：`filename` 为「合并澄清 第 k 轮（任务 #<编号>）」，`uploaded_by` 为所依据回复的回复人（多人以「、」连接），`metadata` 沿用最近一次上传；每条更新的用例在 `description` 末尾追加一行「澄清依据：#n（回复人，日期）」。本轮组装与核对使用更新后的用例，不因用例变化把本轮转为「待同步」。用例页显示该次上传、每条用例的「已按澄清 #n 更新」标记及与上一版本的对比；「下载用例并集」得到更新后的用例。
- **场景来源**：`metadata.sources` 为每条被采纳并用于更新用例的回复增加一项：`ref` 为 `看板合并澄清 #n`，`version` 为回复时间，`confirmed_by` 为回复人。
- **后续上传覆盖**：测试同事之后上传的同编号用例按现有规则覆盖看板中的版本；已采纳的澄清仍在快照中，Codex 发现新上传内容与已采纳澄清不一致时，再次按澄清更新用例并在 `reply` 中说明，或在内容确有新含义时列为缺口追问。
- **本批不纳入**：缺口卡片提供「本批不纳入」操作（填写理由，例如「本批由人工完成」，回复人取标记人），等同一条 `action` 固定为采纳的回复，不需要 Codex 判断。对应用例标「本批不纳入：<理由>（回复人，日期）」，不生成场景、不计入缺口与暂缓数，也不进入合并快照中需要判断的用例；用例页可「重新纳入」，下一轮合并照常处理。
- 回复与 Codex 答复中的文字原样显示；内网响应沿用现有本机路径与凭据名遮蔽。

## D69 合并进度可见

- **自动刷新**：批次变化标记（`batch_etag`）计入合并任务的编号、状态、开始与结束时间、错误；合并页改为与其他批次页相同的 3 秒轮询。状态变化后，合并页、批次概览页、场景页、用例页无需手动刷新即可更新。
- **状态条**：批次概览页、场景页、用例页与合并页显示最近一个合并任务的状态：
  - 排队中：前面还有几个任务、同时运行上限 3；
  - 运行中：开始时间、已用时长、超时上限（`SOP_BOARD_CODEX_TIMEOUT`，默认 30 分钟）、最近活动时间（`events.jsonl` 的修改时间）；
  - 已完成（含部分落地时的「待补充 N 项 · 暂缓 M 条」）、待补充、失败（原因）、待同步（原因）、Codex 不可用。
  每种状态都链接到合并页对应任务。
- **本机活动摘要**：仅本机在合并页运行中任务下显示最近 20 条事件摘要（读取的文件、执行的命令、推理摘要的首行），以及 `codex resume <session_id>`。内网只显示时长与最近活动时间，不显示事件内容，保持代理材料仅限本机（D45、D62）。

## D71 合并后自动执行开关

- **设置**：工作区级设置「场景写入后自动执行」，存于 `settings` 表（键 `auto_execute`），缺省开启，保持现有行为。
- **作用范围**：关闭时，任何自动触发都不入队执行任务，包括合并写入（「合并写入」）与场景文件推送或发现（「场景版本」）。新增与变化的场景保持待执行；开发者在批次概览页点「执行待执行场景」的手动执行不受影响。开启后不补发关闭期间错过的自动执行。
- **入口**：本机首页工作区卡片显示当前状态与切换按钮；接口 `POST /api/v1/automation/auto-execute`，正文 `{enabled: true|false}`，仅本机（与「暂停自动任务」同属开发者操作）。内网只显示状态，不能切换。
- **展示**：关闭时，批次概览页与合并状态条写明「自动执行已关闭，场景保持待执行」。
- 与「暂停自动任务」的区别：暂停会停住合并、草稿生成与执行的全部排队；本开关只阻止自动入队执行，合并照常进行。
