# 场景验收操作手册：Flow Board

验收以 `docs/sop/` 的场景经最终交付产物的真实入口执行为准，不写单元、接口或集成测试。预期来自已确认的方案和 SOP；实现者自检与独立业务验收分别留证。

工作区、适配与一键验证依据 SOP-BOARD-7 修订 3 的 I2–I4，以及 SOP-BOARD-8 修订 2 的 D37–D39（修订 v9 D30、D33），对应 SOP-71、SOP-72、SOP-81、SOP-82、SOP-83；跨仓修复依据 I5、D34，对应 SOP-74-P01、N01、N02。

## 准备与真实入口

需要 Python 3.10 以上、uv、Git、POSIX 进程组，以及用于列出占用进程的 lsof。本机 Codex 的实际合并和执行调用使用开发者已有登录状态；不可调用时保存真实错误，不修改凭据或替换为假输出。

先用 `uv tool install <本地检出>` 安装，再运行 `sop-board guide`。询问名称与全部仓库目录后运行 `sop-board init demo <app> <lib> [--data <数据目录>]`；验收使用独立名称、临时数据目录和空闲端口。按 init 的命令进入数据目录会话继续，配置、适配、验证技能只写数据目录。旧格式用 init 新建；旧适配可经确认重写，用例与轮次不迁移。

| 入口 | 执行方式 | 核对位置 |
| --- | --- | --- |
| 安装与命令行 | uv tool install、sop-board guide/check/启动 | 安装输出、指引原文、退出码、监听地址、checks 报告 |
| HTTP | curl 调用实际看板与演示服务 | 状态码、JSON、SQLite、场景文件、环境目录及提交记录 |
| 页面 | 真实浏览器按场景操作；HTML 检查单独注明 | 页面变化、请求记录、截图、环境日志的访问范围 |
| Codex 任务 | 上传用例并观察真实任务 | 会话编号、原始输出、生成文件、执行结果与证据 |

## SOP-71：搭建与自检

1. 在临时工作区准备有已提交基线的演示仓库和真实 HTTP 服务，origin 使用明确标注的演示地址。
2. 读取已安装命令的 `sop-board guide`，与开发者确认工作树建法、清理方式及外部工具依赖；先用 `sop-board init demo <仓库目录> --data <数据目录>` 登记，据此只在数据目录写 config.yaml、项目验证技能、env 和可选 worktree/cleanup 命令，仓库仍应干净。
3. 运行 `sop-board check demo --data <数据目录>`，核对五步均通过、退出码 0、基线与临时工作树的就绪日志，以及建立/清理脚本的调用记录；确认路径、共同 Git 仓库和分支均已核对，临时工作树和分支已清理。
4. 用本轮进程占用声明端口，再运行同一命令；端口一步应失败、列出占用进程并退出 1，不能终止占用者。停止本轮占用进程后重新自检。
5. 启动 `sop-board demo --data <数据目录> --port <空闲端口> --lan`。自检通过且配置未变时环境自动就绪；本机页面显示最近自检、环境状态与最近 50 行日志，内网页面无日志及开发者按钮。
6. 运行中的看板通过本机页面“自检”按钮发起自检；对应真实接口为 `POST /api/v1/environment/check`。重启使用 `/api/v1/environment/restart`，均仅限回环来源。

配置或数据目录中的适配脚本变化后须重新自检。删除配置再启动时，应正常提供页面，显示“尚未搭建”；`POST /api/v1/workspaces/<工作区名>/batches/<批次>/executions` 返回 409 `workspace-not-ready`。

### 修订 3 的工作树适配核对

在临时双仓工作区，用 worktree 命令建立指定分支，复制一个被 Git 忽略的 marker，输出 repos/env；cleanup 读取 SOP_WORKTREES 删除工作树，记录调用时修复分支仍存在。运行 check 核对第 4 步实际调用了两个脚本、env 使用返回目录与变量，结束后目录、Git 登记及临时分支均消失。

分别让输出指向错误分支、另一仓库或工作树内部子目录，再运行 check；必须在第 4 步失败并指出原因，不能启动这些目录的环境。未核对的路径不交给自动删除；记录残留位置后仅清理本轮人为构造的目录。去掉两个可选命令再运行，核对默认 git worktree add/remove 生效且自定义脚本没有被调用。

配置不接受已删除的 prepare 字段。修复、重试、复测及合入后清理的真实 Codex 链路由独立验收者复核；通用指引必须写明先确认建法，并报告外部工具在仓库内还是仅本机、团队共用的前提。验证不会以手写适配冒充 SOP-71-P01 的独立代理搭建完成。

## SOP-72：合并、执行与提交等待

1. 通过首页或 `POST /api/v1/workspaces/<工作区名>/batches/<批次>/cases` 上传至少两条有独立预期的用例；正文为 filename、content、uploaded_by。
2. 观察真实 Codex 合并任务，核对场景生成在配置的 `<批次>.yaml`，字段与用例对应。不能把手工推送的场景记为 Codex 合并成功。
3. 发起执行并核对实际环境、结果和证据。场景文件中的 metadata.repos 决定涉及仓库，缺省全部仓库。
4. 在涉及仓库留一处未提交产品改动后发起执行，应为“待提交”并列路径。经授权提交演示改动后，核对环境日志和 environment.json 中的提交号已更新，再核对执行会话。
5. 产品变化后，由实际执行会话判定受影响范围；沿用只保留原通过状态，note 必须写“沿用：<理由>”，任务、批次与报告单独计数。没有实际会话及证据时，不判该环节通过。

Codex 无法启动时，记录任务停止在哪一步、退出码与原始错误。可用真实场景推送入口准备数据，单独验证队列和环境切换，但必须说明这没有覆盖合并、实际执行、沿用判断或修复复测。

T2 返工时，Claude 在沙箱外经真实上传入口发现合并模式被拒绝：`cases.items.required` 缺少 `initial_state`。修改随包输出模式时，用一次性脚本遍历全部对象，核对 `required` 包含全部 `properties`、`additionalProperties` 为 false；可选字段须允许 null，枚举也要包含 null。任意键映射应改为固定字段数组，读取入口先校验再转换为业务所需形式。静态核对不替代真实 Codex 合并复验。

核对搭建提示时，分别获取首页和批次页：配置有效且当前自检通过时，不应输出“尚未搭建”和执行停用提示；移走配置后，等待配置发现与页面轮询更新，再核对提示出现、环境接口 enabled/check_passed 为 false。失败摘要可用明确标记为人工构造的事件文件检查解析和页面展示；摘要不超过 300 字，不把这种核对记成真实模型执行。

## SOP-74：跨仓修复

用 `sop-board init demo <app> <lib> --data <数据目录>` 登记分散在不同目录的 app 和 lib 两仓：app 经真实 HTTP 入口调用 lib；lib 含明确植入的缺陷，两仓都有干净 main 和标明虚构的 origin。按 guide 编写适配，用 worktree 返回的 env 指向本次 lib 工作树目录；自检五步通过后，通过真实标记入口提交失败场景与演示缺陷链接，再由测试同事点击“复核完成，开始修复”。P01 等整个工作区的执行任务全部结束后才应建立修复任务；新任务汇总当时全部可修复问题。

1. 核对适配返回的 app/lib 路径是各自修复分支的工作树，修复会话工作目录是任务目录并能写入这些路径。缺省建立方式才固定为 repos/<别名>。提示词应列出全部仓库身份及实际路径。
2. P01 使用真实 Codex 分析根因并修复；只有 lib 改动时只能产生 lib 提交。若两仓都有改动，逐仓提交信息应一致。任何 docs/sop/ 或场景文件改动均不得进入成功尝试。
3. 新会话经修复环境执行问题场景及可能受影响场景，结束后恢复基线。连续三次失败时核对各仓 main 未被看板改变，修复分支仍在。
4. P01 全部条件满足后核对 lib 快进、app 无新提交、基线环境重启、场景进入人工复测队列，先按 cleanup 删除工作树，再由看板删除已合入分支。
5. N01 在 app 基线留下未提交产品改动，核对整组停止在“待开发者合入”，app/lib main 都没有变化，页面、接口与报告逐仓显示原因。
6. 基线已前进时，须在修复工作树合入新基线并重新复测；冲突或任一仓条件失败时不开始基线合入。Git 落地中遇到外部竞争或故障时，核对停止原因和逐仓真实状态，不要求强制回退。
7. N02 的根因放在被忽略的本机配置；真实会话应判为 environment、转开发者，没有代码提交，页面与报告没有凭据值。
8. 任务附件不列出 repos/ 文件，直接请求其中的本机配置返回 404。停止看板后保存证据并清理演示工作区。

若当前环境无法调用 Codex，可在明确标记为模拟的范围内手写工作树改动和修复输出，调用产品的准备、逐仓提交、适配切换和合入前置核对阶段。通过真实 HTTP 响应核对基线→修复→基线的差异。不得伪造独立会话编号或复测通过记录；这些阶段验证不能代替 P01、N02 的真实模型验收。使用新数据目录，不迁移旧修复记录。

## SOP-75：用例分层与沿用报告

1. 用 `sop-board init demo <演示仓库> --data <新临时数据目录>` 登记，再按 guide 搭建，自检五步通过；上传 3 条流程和 2 条字段格式用例。
2. 真实 Codex 的每条输出都须包含 kind、kind_reason、merged_into；流程的 merged_into 为 null。核对最终只生成 3 条流程场景，2 条细节的每项原预期都带来源编号写入目标 expected，配对文件覆盖全部 5 条用例。
3. 通过合并页把一条 detail 改为单独成场景。核对本机接口成功、非回环请求为 403 local-only；重新合并的输入含 forced_flow，生成第 4 条同编号场景，另一细节仍并入原流程。重启后再次合并仍保留选择。
4. 用例内容、场景或选择变化后，旧合并输出不得覆盖新输入。覆盖率根据当前有效配对计算，不以用例编号是否有同编号场景判断。
5. 导出报告，核对每条细节的归属与理由、逐轮沿用数量和逐条理由。产品改变后的真实执行仍需由会话判断影响并保留证据，不能只凭报表展示认定 P02 通过。

模型不可调用时，可以把明确标记的模拟最终输出文件交给产品的 prepare_merge、consume_merge_output 核对和写入阶段；不伪造模型会话编号。报表展示可使用标为人工自检的记录，附真实入口响应并让 implementer 与 executor 相同；人工构造的沿用说明不能冒充模型判断或独立验收。记录操作前后的配对表、持久选择、场景数量及导出原文，最后停止服务并清理演示目录。

随包模式须用一次性脚本递归核对：每个对象 additionalProperties 为 false，required 与 properties 的键一致，允许 null 的枚举也包含 null。不提交该脚本，不新增测试。真实分类、页面点击、改类后模型输出以及产品变化后的影响判断由独立验收者复核。

## SOP-81：分散仓库登记与查找

1. 在临时根的 a/app 和 b/lib 建两仓，app 提供调用 lib 的真实 HTTP 服务；两仓 main 干净，origin 明确标注演示地址。P01 从 app 中新开的代理会话开始，由代理询问名称 demo、完整仓库路径，运行 `sop-board init demo <app> <lib>`；执行者在搭建完成前不手写配置或技能。
2. 核对输出的数据目录、别名、origin 身份及 `codex -C <数据目录>` 继续命令（Claude Code 使用 `/add-dir`）。新会话只写数据目录，config 的 repos 为绝对路径，scenarios 为 {repo, path}，workspace.json 为 v10 与名称。运行 `sop-board check demo`，五步通过后运行 `sop-board demo --port <空闲端口>`，核对页面身份和环境就绪。
3. P02 在 lib 子目录运行 `sop-board check`，在其根目录运行 `sop-board --port <空闲端口>`；应找到 demo，报告仍在同一数据目录，不能新建另一份。
4. N01 用 `sop-board init bad <app/src> <无 origin 仓库>`，核对退出 1、逐目录原因且没有 bad 数据目录。补核对重复仓库、不能规范化的 origin、已存在数据目录及相对 repos 路径的拒绝原因。
5. N02 在未登记仓库或非 Git 目录运行 `sop-board`，退出 1 且提示 init 与指定名称。N03 用 `sop-board init demo2 <lib>` 登记后在 lib 运行 `sop-board check`，应列 demo、demo2，退出 1 且不启动环境。
6. 核对发现与合并生成的批次、版本、问题 path 为 `<别名>:<仓内路径>`；来源分别用场景仓内路径和其他仓库别名引用，越界或不存在的来源应忽略。SQLite workspaces.root 保存数据目录。v9 登记或旧数据库不得读取、迁移。

## SOP-82：项目验证技能

1. P01 沿用 SOP-81-P01 的独立代理搭建；用空目录作为 SOP_BOARD_SKILLS_DIR，确认不依赖个人缺省技能。代理技能须有 name、description 文件头，每个入口对应二级标题，写明工具、地址变量、登录责任、数据观察、证据、隔离、清理及前置条件。报告单列技能摘要请开发者确认，只写凭据位置与变量名。
2. `sop-board check demo` 的第 5 步名为“验证技能”，输出项目技能路径、各入口及声明的辅助技能。driver 声明时先找数据目录 skills，再找外部技能目录；都没有则失败。Web 入口未声明 driver 时应列出随包 `playwright-acceptance/SKILL.md`，其他未声明的入口为“辅助技能：无”。逐项制造缺失/非法 skill、缺失文件、目录内符号链接、缺少文件头、空或非文字 name/description、缺入口标题、缺失辅助技能。核对页面“尚未搭建”、执行接口 409 workspace-not-ready，以及没有新增任务。
3. 启动看板，P01 经上传用例、真实合并，再点“执行待执行场景”。查看任务 prompt.md 的项目技能绝对路径、entries.json 的辅助技能绝对路径、snapshot.json 的 skill_digest；真实会话须有读取技能的事件、每条场景结果与证据。报告轮次的摘要为该轮前 12 位。N01 删除入口二级标题或技能文件后，核对首页批次条目、批次概览页及 SOP 场景页的两个验证按钮都停用，旁边显示“尚未搭建：<首个配置问题>”；缺标题的问题须指出入口，缺文件时须写明“验证技能不存在”。
4. N02 在会话运行期间修改技能普通文件（包括引用脚本、参考文件），结束后核对任务“已作废”、原因含“验证技能变化”，SQLite 没有新轮次或结果。恢复合格技能内容后不重新自检，已有结果仍有效。修复复测同样保存技能摘要，变化时复测轮次作废且不登记结果。
5. 实现者可以手写配置、适配和技能做自检，但必须标为“实现者手写，不代替 SOP-81-P01/SOP-82-P01 的独立代理搭建”。Codex 不能运行时保存真实错误；用人工手段停留会话须注明，不伪造会话编号或结果。

## SOP-83：一键增量与全量验证

使用 SOP-81、SOP-82 已搭建的隔离双仓与数据目录，以 `sop-board demo --lan --port <空闲端口>` 启动，记录启动输出的本机和内网地址。真实浏览器操作是首次验收入口；实现者用 curl 留存 HTML 与接口响应时须注明未完成浏览器点击。

1. P01：全部场景已有通过结果后，修改其中一条场景的预期并在演示仓库提交。首页 `/`、概览 `/w/demo/b/<批次>`、场景 `/w/demo/b/<批次>/scenarios` 都应显示待执行 1 条与当前版本总条数。点击首页“执行待执行场景（1 条）”，核对页面没有跳转、按钮旁出现任务编号及状态；任务范围、结果和新证据仅含该场景。按钮 N 按入队范围计算，失败也在范围内；原 `queue_counts.pending` 不含失败，不可用它代替按钮 N。
2. P02：没有待执行时，增量按钮停用并显示“没有待执行场景”，全量按钮可用。点击首页“重新验证全部场景”，查看 `GET /api/v1/tasks/<编号>` 的 scope，以及数据目录 `tasks/<编号>/pending.json`：当前版本全部场景的 reason 均为 `rerun`。等待真实 Codex 完成，逐条核对新轮次结果与新证据，沿用为 0，`report.md` 中该轮记录的技能摘要等于 snapshot.json 中 skill_digest 前 12 位。`rerun` 返回“沿用：”说明或无新证据时应整轮失败且不登记轮次。
3. 合并范围：暂停自动任务或制造未提交产品改动，使同批次执行任务处于排队、待提交或等待浏览器状态；先增量再全量、再增量，检查 tasks 数量不增加，scope 合并且同一场景的 `rerun` 不被覆盖。恢复后核对实际执行范围。前置条件的人工操作单独记录。
4. N01：用真实内网地址取上述三个页面，两个按钮及原因均不出现。用 `curl -i -H 'Content-Type: application/json' --data '{"scope":"all"}' http://<内网地址>:<端口>/api/v1/workspaces/demo/batches/<批次>/executions` 应为 403 `local-only`；改用本机地址并加 `-H 'Origin: http://other.invalid'` 应为 403 `cross-origin`。不能只伪造 Host 或转发头代替真实内网连接。
5. N02：在同一本机执行接口依次发送 `{"scope":"some"}`、`{"scope":1}`、`{"scope":null}`、`{"scope":"all","extra":true}` 与非对象正文，均为 422 `invalid-scope`。`{}` 和 `{"scope":"pending"}` 行为一致；没有待执行时为 409 `nothing-to-execute`，页面错误应提示可改用“重新验证全部场景”。每次请求前后用只读 SQLite 查询保存 tasks、rounds 的数量及 scope_json，拒绝请求不得新增任务或轮次。
6. 分别制造缺技能、配置合格但没有成功自检、没有场景、没有待执行四种状态，在三个本机页面逐一核对按钮与原因。前两种分别为“尚未搭建：<首个配置问题>”“自检未通过”，两个按钮均停用；就绪但无场景时均为“尚无场景”；待执行 0 且有场景时仅增量停用。等待至少一次页面轮询，确认停用状态不会被错误恢复。未就绪请求返回 409 `workspace-not-ready`；就绪但无场景时全量请求返回 409 `nothing-to-execute`。

按钮的待执行条数使用发现线程每 5 秒更新的批次产品摘要，最多滞后 5 秒；页面读取和轮询不重新扫描仓库。点击入队时才按当时的产品内容精确计算。核对时保存产品变化、发现更新和点击入队的时间与范围，不能把轮询期间的旧计数当成点击后的实际范围。无真实模型成功结果时保留原始错误，不能人工补写执行结果冒充 P02 完成。

SOP-BOARD-11 的合并缺陷复验：确认含“代码推理”和“批注确认”预期的草稿后，核对合并任务的 `case_confirmations.json` 按当前用例列出草稿确认人，`cases.yaml` 保留预期及依据说明。混合普通上传时，确认信息只跟随该用例当前版本的来源，不由最后一次上传的 `metadata.tags` 代表整个并集；普通上传覆盖同编号用例后，不沿用旧草稿确认。真实 Codex 不得仅因代码推理或批注来源产生缺口；确实无法从用例、SOP 原文与已有场景确定的业务缺口仍应停在“待补充”。此前已排队或失败任务的快照不追写，复验时使用“重新合并”生成新快照。假 codex 仅能核对快照和提示词传递，不能证明模型判断已修复。浏览器对超过 1 MiB 或非 UTF-8 的 SOP 原文拒绝时，应显示“上传失败：<原因>”。

修订 2 的首版差异与执行时机：确认后上传新版 SOP，让新草稿首版含两条已有编号（一条修改、一条内容相同）和一条新编号，核对“对比已登记用例”下分别为修改、未变、新增；基准取该首版生成任务保存的用例并集，确认草稿后再查看也不能变化。未在新草稿中输出的已登记用例不代表删除；之后各版仍对比上一版。确认草稿并完成合并后，核对场景文件、概览页待执行数和执行任务记录：不能自动新增执行任务，本机开发者仍可手动执行。随后在同批次直接上传普通用例并合并，应照常自动入队执行；判断绑定合并快照中的上传序号，不能因为批次曾有草稿确认而禁止自动执行。场景文件推送、工作区发现也应保持原有行为。假 codex 可核对渲染及任务流转，真实模型、浏览器交互和独立验收须分别记录执行情况。

生成阶段的节点覆盖核对：本次输出中每条用例须恰好有一个非空 `section:` 标签。每条规则的正向覆盖至少有一条同节点用例，负向覆盖非空时也至少有一条同节点用例；已有用例可以参与覆盖，但同编号采用本次输出的新内容，节点取值与合并保持一致。用假 codex 分别返回双标签、跨节点正向／负向覆盖及合格输出，核对不合格任务逐项列出用例或规则问题、状态为“失败”、不新增草稿版本；合格输出正常成为待确认草稿。真实模型生成及后续合并效果另经真实入口复验。

## 访问边界与数据

- 看板不需要令牌，页面只保存标记人。内网同事可以上传、查看和复核；开发者操作只接受实际连接来自回环地址，其他来源为 403 `local-only`。
- POST、PUT 带不同源 Origin 时为 403 `cross-origin`。JSON 接口须声明 application/json，否则为 415 `json-required`；二进制证据上传仅免 JSON 类型要求。
- 当前页面为 `/w/<工作区名>/…`，接口为 `/api/v1/workspaces/<工作区名>/…`。工作区名称、仓库 origin 身份和批次不得混用。
- 环境日志、适配和完整自检报告只在本机展示。负向请求要核对没有新增任务、轮次、文件或禁止的副作用。
