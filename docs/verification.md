# 场景验收操作手册：Flow Board

验收以 `docs/sop/` 的场景经最终交付产物的真实入口执行为准，不写单元、接口或集成测试。业务验收标准以 [docs/standard.md](standard.md) 为统一正文；本页记录 Flow Board 的实际操作。预期来自已确认的方案和 SOP，实现者自检与独立业务验收分别留证。

工作区、适配与一键验证依据 SOP-BOARD-7 修订 3 的 I2–I4，以及 SOP-BOARD-8 修订 2 的 D37–D39（修订 v9 D30、D33），对应 SOP-71、SOP-72、SOP-81、SOP-82、SOP-83；跨仓修复依据 I5、D34，对应 SOP-74-P01、N01、N02。

## SOP-BOARD-14 统一验收

依据[整体方案](proposals/2026-10-22-integrated-rework.md) D72～D83、第 5 节及其保留的原方案执行。各段代码审核和真实模型冒烟是交验收准备，不能直接合并成整批独立验收结论。使用最终冻结版本，未参与实现的执行者串行操作；实际参与实现或收到实现推断的会话只登记自检。

### 冻结、环境与顺序

1. 固定最终源码（包含未提交改动）、提示词、技能、全部验收 YAML 的版本及 SHA-256，记录安装包来源。为各执行轮次分配仓库外证据目录；源码、提示或场景在运行中变化时作废本轮，按新快照重跑。实现会话不修改 docs/sop/*.yaml；发现预期冲突先报告，由审核方确认和修订后再冻结。
2. 从集成版本重新安装 sop-board，在隔离双仓 app/lib 中完成真实搭建与自检。账号按标准授权；原生 Codex、Claude Code 和浏览器需要可用的本机环境。Codex 沙箱内不能运行的模型、浏览器或工作树链路由审核方在本机执行，不能用假编号或模拟输出顶替。
3. 看板以 --lan 启动。本机回环浏览器扮演开发者，第二个浏览器经启动输出中的实际非回环地址扮演测试同事；保留实际地址、请求响应和截图，不以 Host、转发头或 local 参数代替内网来源。
4. 先走安装、SOP/草稿/合并和公共内核，再走真实执行、修复与复验，最后走经授权的沉淀。对话与会话入口分别在 Codex、Claude Code 的新会话中只用自然语言触发，不预先点名技能或给出实现答案。需要复验时派未参与修复的新会话，只交任务材料、手册、环境与授权记录位置。
5. SOP-135 最后进入已授权的 cw2-live-chat 真实批次：重启为冻结版本、关闭自动执行，只上传/合并/澄清，不执行该工作区的场景。业务问题由用户或指定确认人原话答复。SOP-148 的外部仓库退役按 D82 在发布后另行完成；未就绪时单独记未执行，不能据此删掉场景或宣称整体完成。

### 逐条留证与交付判断

每条保存场景编号/指纹、前置状态、实际命令或浏览器步骤、模型原生回执、HTTP 请求响应、关键数据库与文件前后值、结果证据及清理情况。轮次登记回原工作区与批次，明确入口、执行者、实现者和独立性；重复提交应复用原轮次，不能把子集登记当整批完成。

按[交付记录模板](templates/business-delivery.md)分别填写实现者自检、独立业务验收、人工复核、缺陷复验、回归建设与整体状态。A 合并、B 沉淀、C 会话入口各自报告通过/失败/受阻/未执行范围，再判断整体；真实模型、浏览器、外部退役、试点或凭据相关场景缺证据时如实保留，不能用编译、命令帮助或模拟登记替代。

## 准备与真实入口

需要 Python 3.10 以上、uv、Git、POSIX 进程组，以及用于列出占用进程的 lsof。本机 Codex 的实际合并和执行调用使用开发者已有登录状态；不可调用时保存真实错误，不修改凭据或替换为假输出。

先用 `uv tool install <本地检出>` 安装，再运行 `sop-board guide`。询问名称与全部仓库目录后运行 `sop-board init demo <app> <lib> [--data <数据目录>]`；验收使用独立名称、临时数据目录和空闲端口。按 init 的命令进入数据目录会话继续，配置、适配、验证技能只写数据目录。旧格式用 init 新建；旧适配可经确认重写，用例与轮次不迁移。

| 入口 | 执行方式 | 核对位置 |
| --- | --- | --- |
| 安装与命令行 | uv tool install、sop-board guide/check/启动 | 安装输出、指引原文、退出码、监听地址、checks 报告 |
| HTTP | curl 调用实际看板与演示服务 | 状态码、JSON、SQLite、场景文件、环境目录及提交记录 |
| 页面 | 真实浏览器按场景操作；HTML 检查单独注明 | 页面变化、请求记录、截图、环境日志的访问范围 |
| Codex 任务 | 上传用例并观察真实任务 | 会话编号、原始输出、生成文件、执行结果与证据 |

## SOP-71：搭建与自检

1. 在临时工作区准备有已提交基线的演示仓库和真实 HTTP 服务，origin 使用明确标注的演示地址。
2. 读取已安装命令的 `sop-board guide`，与开发者确认工作树建法、清理方式及外部工具依赖；先用 `sop-board init demo <仓库目录> --data <数据目录>` 登记，据此只在数据目录写 config.yaml、项目验证技能、env 和可选 worktree/cleanup 命令，仓库仍应干净。
3. 运行 `sop-board check demo --data <数据目录>`，核对五步均通过、退出码 0、基线与临时工作树的就绪日志，以及建立/清理脚本的调用记录；确认路径、共同 Git 仓库和分支均已核对，临时工作树和分支已清理。
4. 用本轮进程占用声明端口，再运行同一命令；端口一步应失败、列出占用进程并退出 1，不能终止占用者。停止本轮占用进程后重新自检。
5. 启动 `sop-board demo --data <数据目录> --port <空闲端口> --lan`。自检通过且配置未变时环境自动就绪；本机页面显示最近自检、环境状态与最近 50 行日志，内网页面无日志及开发者按钮。
6. 运行中的看板通过本机页面“自检”按钮发起自检；对应真实接口为 `POST /api/v1/environment/check`。重启使用 `/api/v1/environment/restart`，均仅限回环来源。

配置或数据目录中的适配脚本变化后须重新自检。删除配置再启动时，应正常提供页面，显示“尚未搭建”；`POST /api/v1/workspaces/<工作区名>/batches/<批次>/executions` 返回 409 `workspace-not-ready`。

### 修订 3 的工作树适配核对

在临时双仓工作区，用 worktree 命令建立指定分支，复制一个被 Git 忽略的 marker，输出 repos/env；cleanup 读取 SOP_WORKTREES 删除工作树，记录调用时修复分支仍存在。运行 check 核对第 4 步实际调用了两个脚本、env 使用返回目录与变量，结束后目录、Git 登记及临时分支均消失。

分别让输出指向错误分支、另一仓库或工作树内部子目录，再运行 check；必须在第 4 步失败并指出原因，不能启动这些目录的环境。未核对的路径不交给自动删除；记录残留位置后仅清理本轮人为构造的目录。去掉两个可选命令再运行，核对默认 git worktree add/remove 生效且自定义脚本没有被调用。

配置不接受已删除的 prepare 字段。修复、重试、复测及合入后清理的真实 Codex 链路由独立验收者复核；通用指引必须写明先确认建法，并报告外部工具在仓库内还是仅本机、团队共用的前提。验证不会以手写适配冒充 SOP-71-P01 的独立代理搭建完成。

## SOP-72：合并、执行与提交等待

1. 通过首页或 `POST /api/v1/workspaces/<工作区名>/batches/<批次>/cases` 上传至少两条有独立预期的用例；正文为 filename、content、uploaded_by。
2. 观察真实 Codex 合并任务，核对场景生成在配置的 `<批次>.yaml`，字段与用例对应。不能把手工推送的场景记为 Codex 合并成功。
3. 发起执行并核对实际环境、结果和证据。场景文件中的 metadata.repos 决定涉及仓库，缺省全部仓库。
4. 在涉及仓库留一处未提交产品改动后发起执行，应为“待提交”并列路径。经授权提交演示改动后，核对环境日志和 environment.json 中的提交号已更新，再核对执行会话。
5. 产品变化后，由实际执行会话判定受影响范围；沿用只保留原通过状态，note 必须写“沿用：<理由>”，任务、批次与报告单独计数。没有实际会话及证据时，不判该环节通过。

Codex 无法启动时，记录任务停止在哪一步、退出码与原始错误。可用真实场景推送入口准备数据，单独验证队列和环境切换，但必须说明这没有覆盖合并、实际执行、沿用判断或修复复测。

T2 返工时，Claude 在沙箱外经真实上传入口发现合并模式被拒绝：`cases.items.required` 缺少 `initial_state`。修改随包输出模式时，用一次性脚本遍历全部对象，核对 `required` 包含全部 `properties`、`additionalProperties` 为 false；可选字段须允许 null，枚举也要包含 null。任意键映射应改为固定字段数组，读取入口先校验再转换为业务所需形式。静态核对不替代真实 Codex 合并复验。

核对搭建提示时，分别获取首页和批次页：配置有效且当前自检通过时，不应输出“尚未搭建”和执行停用提示；移走配置后，等待配置发现与页面轮询更新，再核对提示出现、环境接口 enabled/check_passed 为 false。失败摘要可用明确标记为人工构造的事件文件检查解析和页面展示；摘要不超过 300 字，不把这种核对记成真实模型执行。

## SOP-74：跨仓修复

用 `sop-board init demo <app> <lib> --data <数据目录>` 登记分散在不同目录的 app 和 lib 两仓：app 经真实 HTTP 入口调用 lib；lib 含明确植入的缺陷，两仓都有干净 main 和标明虚构的 origin。按 guide 编写适配，用 worktree 返回的 env 指向本次 lib 工作树目录；自检五步通过后，通过真实标记入口提交失败场景与演示缺陷链接，再由测试同事点击“复核完成，开始修复”。P01 等整个工作区的执行任务全部结束后才应建立修复任务；新任务汇总当时全部可修复问题。

1. 核对适配返回的 app/lib 路径是各自修复分支的工作树，修复会话工作目录是任务目录并能写入这些路径。缺省建立方式才固定为 repos/<别名>。提示词应列出全部仓库身份及实际路径。
2. P01 使用真实 Codex 分析根因并修复；只有 lib 改动时只能产生 lib 提交。若两仓都有改动，逐仓提交信息应一致。任何 docs/sop/ 或场景文件改动均不得进入成功尝试。
3. 新会话经修复环境执行问题场景及可能受影响场景，结束后恢复基线。连续三次失败时核对各仓 main 未被看板改变，修复分支仍在。
4. P01 全部条件满足后核对 lib 快进、app 无新提交、基线环境重启、场景进入人工复测队列，先按 cleanup 删除工作树，再由看板删除已合入分支。
5. N01 在 app 基线留下未提交产品改动，核对整组停止在“待开发者合入”，app/lib main 都没有变化，页面、接口与报告逐仓显示原因。
6. 基线已前进时，须在修复工作树合入新基线并重新复测；冲突或任一仓条件失败时不开始基线合入。Git 落地中遇到外部竞争或故障时，核对停止原因和逐仓真实状态，不要求强制回退。
7. N02 的根因放在被忽略的本机配置；真实会话应判为 environment、转开发者，没有代码提交，页面与报告没有凭据值。
8. 任务附件不列出 repos/ 文件，直接请求其中的本机配置返回 404。停止看板后保存证据并清理演示工作区。

若当前环境无法调用 Codex，可在明确标记为模拟的范围内手写工作树改动和修复输出，调用产品的准备、逐仓提交、适配切换和合入前置核对阶段。通过真实 HTTP 响应核对基线→修复→基线的差异。不得伪造独立会话编号或复测通过记录；这些阶段验证不能代替 P01、N02 的真实模型验收。使用新数据目录，不迁移旧修复记录。

### 修复复验中断后的重试

在隔离双仓演示中保存修复任务的尝试序号、逐仓提交和修复会话编号。待修复提交完成、任务进入“复测中”后停止看板并重新启动，经本机任务页重试：只应启动新的复验会话，不重新修复、不增加尝试、不重复提交；原未完成的复验目录仍在，新复验使用新目录。复验结束后，原尝试必须记录结果和结束时间；真实通过时核对同一提交合入，页面尝试号与提交信息一致。另在“分析中／修复中”重启，确认仍按原路径续接修复。

分别保存新建与续接的实际启动参数，带输出模式的任务两者都包含同一 `--output-schema`。本机继续会话命令指向修复会话，复验记录单独显示其编号；内网逐状态读取任务接口和页面，运行中说明正在做什么，已合入说明修复完成，不能误报待开发者处理。轮次的 executor、implementer、submitted_by 仍按 D79 展示，不以任务级会话隐私规则隐藏。

禁止提交或原生模型不可用的实现者自检，可引用独立 clone 中已有提交，并明确标记模拟修复输出、提交登记边界与进程；不得实际执行提交、合入、工作树建立或凭据操作。通过真实 HTTP 重试和产品恢复流程核对阶段、尝试、提交与目录。无新的独立会话编号时保留真实拒绝原因，不制造通过记录；真实 Codex 复验成功及合入交审核方完成。

P02、P03、N02、N04 由独立验收者按场景原文执行：中断重试须复用工作树并保留 attempts/<序号>/；切换环境后各任务互斥且结束恢复基线；输入变化作废且不登记；放弃保留关联历史，清理失败保留现场并可再次清理。

沉淀返工的定点核对：运行时任务页身份与进度区一致；停止并重启后，本次尝试的会话编号写入任务记录，已经保存的结束时间不变。记录审核前的结束时间与已用时长，再确认清理，二者应保持，不把审核等待计入运行时间。失败清理脚本退出后保留现场，错误提示仅有一处“日志：<路径>”。没有原生模型时，可以明确重放已保存的真实回执核对身份恢复，注明回执来源和替代环节，不能称作新模型会话。

真实 Codex 无法启动时保存实际错误，不能用合成输出声称 P01 成功。为核对登记、幂等、恢复或处理，可以使用明确标注的合成报告及已有测试文件，运行结果记未运行，报告单列这种局部自检。浏览器受限时保留 HTTP 原文，点击和截图写未执行。结束停止本轮服务、核对端口并清理本轮演示工作树；禁止提交、推送或凭据操作的任务继续遵守该边界。

### K4 会话入口返工 1 定点复核

2. 所有问题呈报后，先尝试 submit：未答问题应拒绝，无新 SOP 版本和草稿。使用者按场景规定给出真实业务答复及姓名，经 sop answer 登记；原话、作者、问题归属和历史均保持。尚未按新答复修订输出再次 submit 仍拒绝。
3. 更新正文后不提供确认人，命令和技能均应停止确认，SOP 未登记；使用者在本次请求中指定确认人后再 submit。SOP 页显示来源资料名、摘要、答复和确认人，后续草稿由原会话认领；再 draft prepare 核对使用该 SOP。重复提交不增加版本或重复草稿。
4. 补充核对：他人认领、同批次排队替换、取消后重建、仅排队修复不阻挡；问题删改、借用其他任务答复、来源摘录不存在、资料副本或目标原文变化均不得静默登记。输出错误仍可修正重交，输入变化须作废。
5. 启动真实 `--lan` 看板，本机和实际非回环地址查看 SOP 页与任务，保存响应原文；内网只见明确业务记录，编写附件 403，没有新增 HTTP 编写命令。浏览器截图、流程图渲染与自然语言的等待确认行为分别留证。

禁止启动模型或沙箱受限的实现者自检，可把明确标为“模拟最终输出”的 final.json 交给真实 CLI 消费，直接核对拒收、答复、登记与页面 HTTP。业务答复也须标为演示资料给定的模拟角色，不冒充真实业务确认。代码编译、导入、guide 与 diff 核对单独记录；不新增测试。真实模型规则质量、两个客户端触发效果、浏览器及独立验收交审核方完成。

### 编写 SOP 的发行包与提示复核

- 使用 `uv build --wheel --out-dir <仓库外目录>`，将产出的 wheel 非 editable 安装到临时环境，从产品演示仓库运行安装后的 `sop prepare`。确认导入位置位于临时环境，任务提示词指向实际可读的 sop-guide.md；其内容与安装包 `prompts/author-sop-guide.md`、人工指南 `docs/sop-guide.md` 的 `author-sop-rules` 标记区一致。不能用源码目录中的 docs 补齐缺失资源。
- 缺工作区时保留 guide/init 指引；确认人被拒、缺批次或资料、名称与数据目录不匹配、登记格式错误分别显示具体原因，不误导重新初始化。缺确认人及未答问题仍拒绝，拒绝后无新 SOP 版本。
- 用明确标记的跨日模拟答复时间核对新生成预览、登记原文和 SOP 页显示一致，包含时区偏移；数据库及 answers.json 仍保留原始时间。旧版本原文不批量重写。
- 真实会话中直接询问需要的业务决定，不暗示待定或排除；最终标题与正文不保留“待业务确认”“确认稿”等过程状态，确认信息由命令附加，问题与答复原文仍保留。未覆盖范围只写业务范围，不夹入是否生成场景等过程说明。询问确认人不提供示例姓名；看板未运行时报告 CLI 给出的位置或说明未运行，不为找链接加跑命令。
- wheel 启动真实 `--lan` 看板，分别经回环和实际非回环地址读取 SOP、任务及编写规则附件：SOP 业务内容可见，编写材料仅本机。保存 HTTP 原文后停止本轮看板并核对端口关闭；页面响应不代替浏览器及模型行为证据。

## 最终返工的定点复核

1. 普通会话执行与 `execute prepare --fix` 的目录均有 repos.json；提示词要求按别名从清单读路径。逐条核对清单为实际当前目录，复验 snapshot.json 的 session_files 与准备时修复后的文件一致，session_files_stage 说明含义；原修复任务保留修复前清单。相同材料参数下，看板入口的两份提示词渲染原文不变。
2. Codex 与 Claude Code 实际呈报合并缺口、写 SOP 的问题时，每个问题按标题、场景、目前的写法、缺什么、请确认、涉及用例六段完整呈报，不能改成表格或一行摘要。阶段 1 尚无用例时明确列涉及规则或资料章节，不编造编号。静态全文差异不能证明真实模型的呈报行为。
3. 在隔离演示目录中保留有效自检记录和正在进行的会话修复，明确使自检工作树命令因权限拒绝而无法运行。CLI 应退出 1，给出“自检未能在当前环境运行”、原因和沙箱外提示；原正式报告不变，新尝试位于 checks/unavailable/，completed=false。setup_check.ok 仍按原已完成结果与当前配置判断，修复正常提交而非作废。再给出确实不合格的适配返回或配置，须保存正式未通过结果；此后再遇不可完成也不能恢复更早的通过，没有既有通过记录也不放行。
4. 同一修复身份（含大小写、前后空白变体）在 prepare 即拒绝，复验任务和认领数量不变；新会话仍可准备。提交端拒收保留，历史错误认领不能绕过。取消复验分别经 CLI 和本机 HTTP，父修复不再等待已取消编号；随后新复验的说明不能被旧取消覆盖。放弃会话修复只提当前工作区，待处理事项无可用续接时不含空 resume。
5. 执行者按手册启动本轮服务，结束前逐个停止并核对退出；结果 note 列已停止的名称、PID 或进程组及结果。无启动、停止失败均如实说明，保留原有服务与浏览器。普通执行与复验都核对，实际停进程行为由真实会话留证；不能只凭提示词文字判为完成。
6. 使用真正 --lan CLI 服务保存本机/非回环环境、任务及页面响应。本机可见最近尝试的详细原因，内网仅通用提示；有效 check_passed 不被不可完成的尝试替换。浏览器刷新与模型行为另行核对。

禁止工作树写入的实现者自检可使用明确模拟的权限拒绝适配、已有通过前置和根因输出，真实 CLI/HTTP、任务消费与数据库仍走产品路径；不执行 Git worktree add，不创建测试、不使用凭据。默认 Git 路径只能在写命令边界明确截住并记录未实际执行，不能冒充真实工作树验证。旧失败报告与已作废任务不追溯恢复，审核方冻结资料只读。

## 访问边界与数据

- 看板不需要令牌，页面只保存标记人。内网同事可以上传、查看和复核；开发者操作只接受实际连接来自回环地址，其他来源为 403 `local-only`。
- POST、PUT 带不同源 Origin 时为 403 `cross-origin`。JSON 接口须声明 application/json，否则为 415 `json-required`；二进制证据上传仅免 JSON 类型要求。
- 当前页面为 `/w/<工作区名>/…`，接口为 `/api/v1/workspaces/<工作区名>/…`。工作区名称、仓库 origin 身份和批次不得混用。
- 环境日志、适配和完整自检报告只在本机展示。负向请求要核对没有新增任务、轮次、文件或禁止的副作用。
