# 业务验收与质量改进标准

开发、测试、用户和 AI 在设计验收方式、执行场景、交付、修复缺陷与每周复盘时共同使用本页。产品仓库的真实验证手册补充本项目的操作方法；场景写法见 [SOP 业务场景编写指南](sop-guide.md)，字段与工具行为见[参考手册](reference.md)及本仓的[场景校验器](../src/sop_board/scenario_file.py)。

## 1. 原则与术语

- **真实入口**是用户实际使用的页面、运行中的服务接口或安装后的命令。**独立验收者**是未参与该功能实现、亲自操作这些入口并留证的测试同事、用户或 AI；实现者自检属于交付准备。
- **正确性依据**是已经确认、独立于当前实现的业务要求、SOP、接口约定或外部事实。预期保留来源、版本与实际确认人；发现冲突先保留原预期及证据，再确认要求或修复实现。保持断言和场景完整，不以删断言、放宽预期、跳过场景或改成当前输出来取得通过。
- 完成需求须由独立验收者在最终交付产物上走完约定场景并核对数据结果：写入、状态、数量、重复写入、权限与租户边界，以及通知的实际接收方。首次业务验收和缺陷复验都须独立执行；重构或拆分也须逐项核对承诺保留的行为。
- **执行证据**是实际运行产生的原始输出，或核对过来源的导入材料；**场景证据**把实际结果和文件绑定到具体场景、轮次、场景内容指纹与产品快照。源码、测试文件和说明链接是辅助资料，结论引用原始证据；引用平台评审时保留实际作者与原文。
- **对抗性验收**是主动构造可能使实现出错的操作，记录每项尝试与实际结果。**场景回归**是产品变化后判定影响、重跑受影响场景并核对未受影响场景的沿用理由，见第 5 节。
- 已有自动测试可以照常运行，供开发者自检参考；业务验收与交付判定来自真实入口的场景执行与人工复核。场景执行会话只做验证，修复会话只改产品代码；回归测试的建设按授权任务另行进行，并记录建设与实际运行情况。
- 如实区分通过、失败、受阻、跳过、未执行和回归未建设。质量结论限于有证据的版本、环境与业务范围；整体交付按第 6 节判断。

## 2. 为项目设计验收方式

首次接入、新增一类入口或服务装配明显变化时，指定成员或 AI 按下表写出或补齐产品仓库的真实验证手册。使用[项目验收方案模板](templates/project-verification.md)；已有手册在原文件补齐，多仓项目在负责联合验证的仓库保存一份，其余仓库的指引链接到它，各入口注明所属仓库。

| 步骤 | 可核对的产出 |
| --- | --- |
| 调查项目事实 | 从本项目现行代码、配置、部署和文档列出页面、接口、命令、定时任务、消息消费、回调、认证、存储、通知接收端、外部依赖、配置来源、可用环境和已有工具。逐项附来源路径；未知照实填写，过时材料注明。使用工具前查清它连接隔离、共享还是生产系统，以及真实写入、推送和邮件等副作用，先隔离共享与外部系统。 |
| 列出关键业务保证 | 从已确认要求和缺陷列出必须长期成立的业务结果、来源及风险，如鉴权、持久化、消息、并发、跨服务。代码或使用方式推导的内容标为待确认，由业务负责人确认后用于验收。测试同事评审过的用例集保留其原文与确认人，有歧义时请该测试同事确认解释；其他线索追溯到需求方认可的原文。 |
| 选入口与观察点 | 每项保证对应真实发起入口和最终观察位置，如页面、数据记录、成员连接或下游收到的请求；在工作区 `config.yaml` 的 `entries` 绑定入口名，场景的 `verify` 引用它。 |
| 设计执行方式 | 按第 3、4 节确定依赖就绪、身份、隔离数据、执行与指定场景重跑、证据、清理、替代依赖和维护人。未列出的入口从最终可观察结果反推需要走过的真实环节。工具、编排与隔离方式按项目事实选择，并说明理由。 |
| 标出入口缺口 | 按第 7 节列受阻场景及建设任务；仅能人工观察的外部通道列责任人、触发时机、步骤与证据位置。 |
| 开发与测试独立确认 | 分别记录确认人、时间与分歧。待确认手册为草稿；实际跑过的启动和执行方法可用于操作，业务预期与人工范围经独立确认后用于验收。 |
| 维护 | 项目指引和验证技能引用该手册。业务、入口、依赖、路由、认证、连接协议或服务装配变化时，同步更新方法、按[链路边界](sop-guide.md#端到端场景的边界)复核覆盖范围，重新确认受影响部分。 |

## 3. 真实验证手册的最低内容

手册保存在产品仓库，例如 `docs/operations/verification.md`。项目业务脚本随产品维护；本机适配与绑定按[搭建指引](../src/sop_board/guide.md)放在看板数据目录。手册至少能让另一位执行者完成以下操作：

1. **准备并确认就绪**：列出链路所需服务、依赖、版本、配置与地址来源、启动顺序、命令和账号来源；实际核对服务及数据库就绪，失败时记录原因与受阻范围。
2. **准备可重复数据**：自动建立隔离数据，说明数据库引擎、真实迁移、数据版本和并发隔离方式。身份、依赖与数据准备可重复，从干净环境和连续再次运行均能核对结果。
3. **执行与观察**：逐入口说明用户身份、工具、操作、参数来源、结果位置、全量及指定场景的执行方法、关键反向场景。链路记录遵循[端到端场景的边界](sop-guide.md#端到端场景的边界)。列出仅能人工执行的场景及责任人、时机、步骤、证据位置。
4. **保存证据**：失败时自动保存执行版本、场景输入、日志、请求响应、数据变化和实际接收端输出，按需补截图、录像。注明冻结方式、位置与保留期限；重试保留首次失败和每次重试结果，构建产物注明构建提交与命令。
5. **清理与恢复**：成功、失败、中断后均先留证，再清理本次创建的数据、账号、连接、进程和依赖。列清资源边界、并发隔离标识与清理失败的接手方法；清理仅限获授权的本次隔离资源。
6. **本机与持续集成**：持续集成（CI）指代码变化后自动运行检查的流水线。分别给出本机命令、CI 任务位置与实际执行范围；CI 留运行编号或链接、提交、场景清单、结果与原始输出。只有本机记录时写“CI 未验证”，缺密钥或环境而跳过的部分保留为未验证。
7. **维护**：注明维护人、最近确认时间及更新触发条件。业务、服务装配变化时同改依赖准备、操作、观察与清理；当轮发现的问题补入手册，稳定结论按产品仓库的知识约定记录。大规模删除已有测试须有用户明确要求。

### 测试账号与授权

手册逐项声明账号类别、用途、环境、隔离方法和凭据环境变量名；**账号声明本身不是授权**。

| 账号类别 | 登录责任与授权 |
| --- | --- |
| 真实或生产账号，包括第三方账号 | 用户在真实浏览器完成登录、人机验证与二次验证，之后恢复已授权操作。未声明类别的账号按此类处理。遇到 `browser may not be secure` 立即停止并报告；授权链接取当前真实浏览器生成的链接，服务续期使用服务端刷新机制。 |
| 已声明的本地隔离测试账号 | 任务开始时向用户取得一次授权，之后 AI 可在该范围内登录和操作。验证码的申请与读取也须在授权范围内。 |

将授权记录保存在本机任务材料中：任务标识、授权人、时间、环境、账号标识及类别、允许的操作与资源范围。开发会话与看板执行会话在同一任务中读取并沿用该记录；接手者无法取得记录或范围变化时先取得相应授权。手册写授权记录的存放方式，项目验证技能说明怎样找到本任务记录。看板的入口声明和自检通过均不代替用户授权。

凭据仅经环境变量传递，手册、配置、会话记录与证据只写变量名和获取方式。看板的执行会话只继承基础环境（`PATH`、`HOME`、`USER`、`LANG`、`TMPDIR`、`CODEX_HOME`、`SHELL`、`LC_*`）、仓库路径变量与入口的 `address_env`；修复与修复复测会话另外继承 `adapter.worktree` 返回的环境变量。需要凭据变量的入口在执行会话中记为受阻，由持有授权的开发会话执行。需要用户交互的部分列为人工范围，CI 按真实执行范围报告。

### 手册、配置与验证技能的分工

入口的操作、账号、观察、证据、隔离与清理只有手册这一份正文。`config.yaml` 保存仓库路径、地址变量、驱动和适配等本机绑定；`entries` 中的必填说明用简短引用指向手册章节。项目验证技能执行前先读取手册和本任务授权记录，按章节操作，补充本机参数的取得方法。

以下是 `config.yaml` 的入口片段；`app` 指已登记仓库别名，手册章节采用[模板](templates/project-verification.md)的安排：

```yaml
entries:
  api:
    surface: http
    address_env: APP_URL
    operate: "按 app 仓库 docs/operations/verification.md 第 2 节 api 入口操作"
    observe: ["按同手册第 3 节核对响应、数据和禁止副作用"]
    evidence: ["按同手册第 3 节保存原始输出和数据查询"]
    isolation: "按同手册第 4 节准备隔离数据、留证后清理"
```

字段类型以[入口校验器](../src/sop_board/entries.py)为准：`surface`、`operate`、`isolation` 为非空文字，`observe`、`evidence` 为非空文字数组；可选 `address_env` 为环境变量名，`driver` 为技能目录名。引用手册也须填齐这些字段；账号与授权记录的位置由手册和技能说明。

## 4. 按真实入口选择核对方式

下表补充项目设计时的核对点，操作命令写入项目手册；其他入口按第 2 节推导。

| 入口 | 执行与核对 |
| --- | --- |
| 浏览器 | 先核对服务就绪，使用隔离账号或租户，驱动真实浏览器；按角色、标签或测试标识定位，等待元素状态、文字或请求完成等可观察条件。失败保留截图、控制台与页面日志，工具支持时保存轨迹或录像。Web 驱动见[随包指引](playwright-acceptance.md)。 |
| 命令行 | 安装交付物后运行用户会使用的命令，隔离用户数据与工作目录，保留完整命令、标准输出、错误输出、退出码及文件清单和摘要；覆盖错误参数、缺文件、权限不足、重复、中断续接与并发。 |
| 接口与数据库 | 调用真实 HTTP、gRPC 或服务命令，经过与生产相同的中间件、鉴权与业务层；使用生产同类数据库、兼容字段约束及真实迁移，在临时库或模式中准备确定性数据。事先写明身份与租户、应选记录、响应原因、增改和应保持不变的行、计数、消息与审计状态；按确切值核对并保存前后查询。按业务覆盖较新但不合条件、无匹配、租户或对象不符、已处理与可重试、先读后写的最终状态复核。边界外依赖可替代并记入未覆盖范围；目标入口和数据库走真实实现。失败保留证据，从字段映射、查询、业务选择、响应转换到持久化找最早偏差；数据库不可用时记受阻。 |
| 消息接收端 | 使用真实订阅者、消费者或连接客户端，核对内容、次数、应收到和不应收到的接收方；设有明确上限的等待，超时失败并保存实际原始消息；业务要求幂等时核对重复投递。 |
| 消费者与定时任务 | 经真实消息中间件投递或调度器触发，核对最终数据和下游结果；覆盖重复投递、失败重试、多实例、锁与幂等、补偿或可追踪记录。直接调用替代触发时，在链路记录中列出被截断部分。 |
| 部署与外部通道 | 部署状态与访问地址须指向预期版本，视觉结果写“等待用户验收”。无法自动捕获的邮件、推送等由用户或独立验收者观察，按手册的人工场景留证。 |

### 模型与智能体

模型输出有随机性，确定性结果与语义判断分开核对：

1. 业务动作、权限与身份、数据写入、外部能力调用、状态提交按接口与数据库的确切值核对。
2. 用场景文件驱动真实对话，经过与生产相同的模型、提示与能力边界；预期描述用户可观察的结果，供独立复核。每次运行有唯一标识，会话按运行隔离，固定会话执行前清理、动态会话执行后清理。敏感信息脱敏后，冻结完整输入、回复、调用轨迹、业务动作、调用次数与 token 用量、运行清单及文件摘要；执行、清理和结果核对状态分别记录。运行中源码、提示或场景变化则整次作废。
3. 扮演用户的执行者与语义复核者分开。未参与实现的人或 AI 使用独立于被测智能体的会话，逐场景、逐轮读完全部证据；复核文件绑定证据摘要。各项业务要求成立为通过，可附符合业务边界的一般观察；执行失败、确定性结果错误、虚构已办理或已发送等承诺、回复与动作轨迹不一致为失败；运行作废、证据或环境缺失为受阻。每项问题记录场景、轮次、最早偏差环节、根因、证据与建议修复范围。复核文件齐全后记复核完成，运行状态与复核结论分别保存。

稳定性验收分别统计机械失败率和关键语义偏差率；连续通过须来自同一源码、配置和场景快照。修复后从首次重新计数，运行完整集合；模型、提示、知识库或能力边界变化后重新运行并复核。缺密钥而无法执行的场景记受阻。

## 5. 场景执行、人工复核与产品变化

场景的四要素、来源确认、正反向写法、粒度和端到端范围统一按[场景编写指南](sop-guide.md)编写。

### 首次执行与人工复核

独立验收者按项目技能和手册准备环境。可准备无关前置数据，被验收流程应生成的对象由该流程实际生成。固定场景与产品快照，记录时间、实际应用和依赖版本、环境、执行者及独立性，然后经声明入口逐项核对：

- 保存脱敏请求响应、操作前后数据查询，以及实际接收端的通知、事件或实时消息，包含应接收与不应接收的对象。
- 对抗性尝试逐项留证；问题保留前置条件、输入、原预期及依据、实际结果和首次失败输出，区分实现缺陷、环境问题、场景写法问题和业务变化。
- 结果返回原工作区、原批次，保持编号、内容指纹、产品快照和证据关联。执行中输入变化按工具规则作废并重取范围；结果与过程证据放产品仓库外，避免改变被测快照。手工 Web 结果登记见[Web 验收集成](playwright-acceptance.md#手工登记)。
- 测试同事在看板按场景人工复核，通过或不通过都登记标记人；不通过附缺陷链接或编号。人工标记保留独立的执行结果。复核完成后点击“复核完成，开始修复”，修复按第 8 节进行。

### 影响判定、重跑与沿用

按现有 D39、D46 的[执行契约](reference.md#用例合并与执行)，新增、内容变化、失败场景须执行；产品变化后，原已通过场景进入待判定。执行者按完整改动范围与依赖关系判断每条场景：已知受影响或无法证明不受影响的经真实入口重跑；同一场景内容此前通过且能证明不受影响的必须沿用，写清改动范围、依赖与理由，保留原证据。

执行会话在 `impact.json` 中逐条记录产品变化待判定项（`source-changed`）的 `scenario`、`affected` 布尔值及 `reason`。`affected: false` 对应 `status: pass`、`note: 沿用：<理由>` 的沿用结果；`affected: true` 对应实际执行结果。缺项或判定与结果不一致时整轮不合格。全量重跑和修复复测均须实际执行并留新证据。沿用与重跑分开计数，判定材料随交付记录保留。

业务要求变化先确认新依据并更新场景，再由独立验收者验证新行为；记录实际运行依赖、环境、场景数和逐项未验证范围。仅能人工执行的场景写在产品仓库手册的人工范围一节：原因、负责人、触发时机、步骤与证据位置；场景本身照常写四要素。

## 6. 交付记录与报告导出

从批次导出 Markdown 报告、用例与结果 YAML、按轮次的证据 ZIP（D27，见[报告入口](reference.md#接口与页面)）。导出内容包括批次与版本、用例覆盖、执行及人工复测统计、沿用明细、缺陷与跨仓修复、合并记录和未验证范围。用[交付验收记录](templates/business-delivery.md)补充环境、独立性和报告未列出的事实，并逐项引用原始材料。

记录至少包含：已确认要求及版本、任务链接、场景文件与指纹、实际源码提交及未提交变化、依赖和配置版本、环境与数据初态、执行时间和执行者、原始证据、缺陷及复验、重跑与沿用理由、替代依赖、人工范围、回归建设及本机和 CI 实际运行情况。报告与证据保存在仓库外；稳定项目知识按项目约定更新。

分别报告开发者自检、独立业务验收、人工复核、缺陷复验和整体交付状态。整体完成须同时具备：依据已确认，约定范围内场景经独立真实入口验收全部通过且核对数据，产品变化已逐项重跑或有有效沿用，缺陷均独立复验通过，所需人工复核已完成。受阻、延期、未执行、缺证据、回归未建设或未实际运行逐项列出负责人和后续安排；子集通过仅证明该子集，延期保留未验证事实。

## 7. 入口缺口与过渡

缺服务、测试账号或接收端观察能力等导致入口不可用时，场景记受阻，结果的 `finding` 写清缺口。开发与测试确认延期处置，记录确认人、原因、建设任务、负责人、期限和最小入口内容；交付保留未验证范围。

第一个需要该入口的需求负责建设：启动真实依赖并核对就绪，自动准备隔离数据，失败留证，结束清理；由独立执行者从干净环境和连续再次执行各验证可核对的结果，写入项目手册并在 `entries` 绑定。当周无法完成时记录一次过渡，由建设任务承接；下一个同类需求完成建设，该区域出现缺陷时优先建设能复现它的入口。

多处缺口按已记录缺陷和业务风险排序，优先鉴权、持久化、消息、并发与跨服务。每周跟踪场景、关键保证、风险、受阻开始时间、任务、负责人和期限；到期未完成写原因，由原延期确认人重新确认。入口建成且独立执行通过后移出缺口清单。手册尚缺时先建骨架、缺项标待填，实现可继续，验收状态按事实记录。

## 8. 缺陷关联、跨仓修复与复验

每个缺陷使用稳定编号，按[缺陷复验与保护记录](templates/defect-protection.md)保留发现时间线、严重程度、复现步骤和原始失败证据。开发与测试分别核对以下关联，每项选择“已确认、推测、待调查、历史缺陷或来源未知”，附证据、反证及待调查负责人：

| 关联 | 依据 |
| --- | --- |
| 违反的业务要求 | 当时有效的条目、版本和预期 |
| 影响的需求 | 实际使用场景和范围，可涉及多个需求 |
| 引入缺陷的改动 | 版本比较、复现或变更证据，与修复提交分开 |
| 当时应能发现的场景 | 当时需求范围、执行版本、场景原文与验收证据 |

解释此前未发现的原因时，按事实区分当时范围外、缺场景、环境或版本差异、断言缺漏、替代依赖截断、未重跑、沿用理由不成立或待调查。缺陷保护是能暴露它的场景，缺失时先确认业务依据并补场景。

修复经[跨仓修复流程](reference.md#跨仓修复)处理，按仓库记录根因、改动与提交；环境或配置问题交开发者处理。由未参与修复的独立执行者在真实修复环境重跑问题场景及受影响场景，保留修复前后证据；合入后在看板继续人工复核。记录新增或修改的保护场景、沿用判定、替代依赖、未覆盖及仍需人工范围，持续观察同类缺陷是否再现。

## 9. 开发与测试每周共同复盘

共同填写[每周质量复盘记录](templates/weekly-quality-review.md)。先核对交付证据，再确认缺陷关联和重跑、沿用的有效性，使用实际案例与严重程度依据观察：验收后新增缺陷、漏场景导致的返工、已通过或沿用场景的漏检、同类缺陷再现、独立复验及保护场景情况。

指标取看板统计与导出报告：执行进度、Agent 通过率、一次通过率、人工复测通过率与覆盖率、误判明细、场景数、重跑与沿用数、修复结果。保留分子、分母、轮次、执行者、场景版本与样本量，按[统计实现](../src/sop_board/statistics.py)的实际口径解释；一次通过率用于观察提测质量，运行数量用于解释过程。比较时注明周期、版本、业务范围和记录缺口，缺材料写“未知”。

复盘同时跟踪第 7 节入口缺口，回看上次行动的实际证据。每项改进写清问题、负责人、期限、跟进任务、预期改善和下次核对方法；以同类问题是否减少、场景是否在真实改动中发现问题评价效果，观察不足则继续跟踪。

## 推荐放进全局指引的文字

> 需求完成须由未参与实现的测试同事、用户或 AI 经用户实际使用的入口执行已确认的 SOP 场景、核对数据结果并留证。预期来自已确认的业务要求、SOP、接口约定或独立事实；实现者自检用于交付准备。真实账号由用户在真实浏览器登录；已声明的本地隔离测试账号在任务开始时向用户取得一次授权，记录任务、环境、账号与操作范围，同一任务沿用该记录，账号声明本身不是授权。保持场景与断言完整，不删断言、不放宽预期、不跳过场景或改成当前输出来通过。缺真实入口证据或缺独立验收时如实报告未完成范围；回归测试的建设与实际运行情况单独如实报告，不作为交付条件。验收、缺陷复验与每周复盘读取并遵循 [Flow Board 业务验收与质量改进标准](https://github.com/AdolphKevin/sop-board/blob/main/docs/standard.md)，项目操作方法统一维护在产品仓库的真实验证手册。
