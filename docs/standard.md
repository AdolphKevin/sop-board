# 业务验收与质量改进标准

开发、测试、用户和 AI 在设计验收方式、执行场景、交付、修复缺陷与每周复盘时共同使用本页。产品仓库的真实验证手册补充本项目的操作方法；场景写法见 [SOP 业务场景编写指南](sop-guide.md)，字段与工具行为见[参考手册](reference.md)及本仓的[场景校验器](../src/sop_board/scenario_file.py)。

## 1. 原则与术语

- **真实入口**是用户实际使用的页面、运行中的服务接口或安装后的命令。**独立验收者**是未参与该功能实现、亲自操作这些入口并留证的测试同事、用户或 AI；实现者自检属于交付准备。
- **正确性依据**是已经确认、独立于当前实现的业务要求、SOP、接口约定或外部事实。预期保留来源、版本与实际确认人；发现冲突先保留原预期及证据，再确认要求或修复实现。保持断言和场景完整，不以删断言、放宽预期、跳过场景或改成当前输出来取得通过。
- 完成需求须由独立验收者在最终交付产物上走完约定场景并核对数据结果：写入、状态、数量、重复写入、权限与租户边界，以及通知的实际接收方。首次业务验收和缺陷复验都须独立执行；重构或拆分也须逐项核对承诺保留的行为。
- **执行证据**是实际运行产生的原始输出，或核对过来源的导入材料；**场景证据**把实际结果和文件绑定到具体场景、运行、场景内容指纹与产品快照；产品快照记录取证时的代码版本，不决定场景是否需要重新验收。源码、测试文件和说明链接是辅助资料，结论引用原始证据；引用平台评审时保留实际作者与原文。
- **对抗性验收**是主动构造可能使实现出错的操作，记录每项尝试与实际结果。**业务交叉**是新需求的业务规则与已有 SOP 或场景作用于同一业务对象、状态或结果。**场景回归**有两条来源：业务变化时按业务交叉更新受影响的已有场景并重新执行；代码改动带来的回归由守护测试发现，见第 5 节。
- 首次业务验收、场景内容变化后的验收与缺陷复验都来自真实入口的场景执行与人工复核。场景执行会话只做验证，修复会话只改产品代码。经独立真实入口通过的场景进入“待沉淀”，由人触发后按随包 [regression-distill](../src/sop_board/skills/regression-distill/SKILL.md) 写成守护测试并登记在产品仓库的 `regression.yaml`；改动留给开发者审核提交。`sop-board retest` 运行守护测试，守护未通过的场景转为待复测，见第 5 节。
- 如实区分通过、待复测、失败、受阻、需求变更、跳过、未执行和待沉淀。质量结论限于有证据的版本、环境与业务范围；整体交付按第 6 节判断。
- **未执行与受阻按性质划分**，不看发生在执行开始前还是执行中。**未执行**是本机暂时不具备、补齐或换一台机器就能执行的情况：场景用到的服务本机没有搭建或被人为停着；缺少入口声明的凭据变量；等人处理的事，即真实账号登录、人机验证（包括执行中途出现的）、只发到本人设备的验证码、身份使用次数到上限，同时登记待人处理。未执行不形成结论，不改变任何场景状态，只记录谁、什么时候、缺什么。**受阻**是意外故障或全队都不具备的能力：服务或浏览器异常退出（附日志末尾并登记待人处理）；前置数据准备失败、证据丢失、运行作废；出现 `browser may not be secure`；入口或观察能力还没建设（第 7 节）；需要停外部共享中间件的故障场景。独立复验须完整执行，不接受未执行。

### 独立性登记

所有 AI 工作都经 `sop-board` 命令登记到同一项目与检出。每次运行记录执行者、实现者与独立性：声明实现者且与执行者相同为“实现者自检”，不同为“独立验收”，未声明实现者为“独立性未声明”；修复的复验自动以修复会话为实现者。同一台机器上用实现者的会话编号声明（`--implementer`）；多人共享验收记录时，在另一台机器上验收别人实现的功能，执行会话拿不到实现者的会话编号，用 `--implemented-by <实现者的操作者>` 声明，与本机操作者不同记为独立验收，相同则被拒绝、须改填会话编号。实现者由使用者在任务里说明，没说明的如实记为未声明，会话不追问。三类结果分别展示与计数，导出时保留声明与未执行范围。

这些字段是身份声明，不是独立验收已完成的证明。真正的独立执行者须未参与实现，并实际经入口核对；替代标签或只改会话编号不能制造独立性。首选做法是由协调会话运行 `sop-board run launch`，由看板守护进程启动一个只拿到运行提示词的新会话执行，启动记录（进程、日志、会话编号）即独立执行的证据。使用者要求当前会话执行时如实记录；修复后的复验仍须独立执行。会话编号仅本机可见，执行者、实现者与独立性作为验收记录向测试同事展示。

## 2. 为项目设计验收方式

首次接入、新增一类入口或服务装配明显变化时，指定成员或 AI 按下表写出或补齐产品仓库的真实验证手册。使用[项目验收方案模板](templates/project-verification.md)；已有手册在原文件补齐，多仓项目在负责联合验证的仓库保存一份，其余仓库的指引链接到它，各入口注明所属仓库。

| 步骤 | 可核对的产出 |
| --- | --- |
| 调查项目事实 | 从本项目现行代码、配置、部署和文档列出页面、接口、命令、定时任务、消息消费、回调、认证、存储、通知接收端、外部依赖、配置来源、可用环境和已有工具。逐项附来源路径；未知照实填写，过时材料注明。使用工具前查清它连接隔离、共享还是生产系统，以及真实写入、推送和邮件等副作用，先隔离共享与外部系统。 |
| 列出关键业务保证 | 从已确认要求和缺陷列出必须长期成立的业务结果、来源及风险，如鉴权、持久化、消息、并发、跨服务。代码或使用方式推导的内容标为待确认，由业务负责人确认后用于验收。测试同事评审过的用例集保留其原文与确认人，有歧义时请该测试同事确认解释；其他线索追溯到需求方认可的原文。 |
| 选入口与观察点 | 每项保证对应真实发起入口和最终观察位置，如页面、数据记录、成员连接或下游收到的请求；在项目 `config.yaml` 的 `entries` 绑定入口名，场景的 `verify` 引用它。 |
| 设计执行方式 | 按第 3、4 节确定依赖就绪、身份、隔离数据、执行与指定场景重跑、证据、清理、替代依赖和维护人。未列出的入口从最终可观察结果反推需要走过的真实环节。工具、编排与隔离方式按项目事实选择，并说明理由。 |
| 标出入口缺口 | 按第 7 节列受阻场景及建设任务；仅能人工观察的外部通道列责任人、触发时机、步骤与证据位置。 |
| 开发与测试独立确认 | 分别记录确认人、时间与分歧。待确认手册为草稿；实际跑过的启动和执行方法可用于操作，业务预期与人工范围经独立确认后用于验收。 |
| 维护 | 项目指引和验证技能引用该手册。业务、入口、依赖、路由、认证、连接协议或服务装配变化时，同步更新方法、按[链路边界](sop-guide.md#端到端场景的边界)复核覆盖范围，重新确认受影响部分。 |

## 3. 真实验证手册的最低内容

手册保存在产品仓库，例如 `docs/operations/verification.md`。项目业务脚本随产品维护；本机适配与绑定按[搭建指引](../src/sop_board/guide.md)放在看板数据目录。手册至少能让另一位执行者完成以下操作：

1. **准备并确认就绪**：列出链路所需服务、依赖、版本、配置与地址来源、启动顺序、命令和账号来源，每个服务写一句业务说明并注明能否在运行中停启（供 `adapter.services` 声明与故障场景使用）；实际核对服务及数据库就绪。环境不要求所有服务都在运行：本机没有搭建的服务列为未执行范围，意外故障记录原因与受阻范围。
2. **准备可重复数据**：自动建立隔离数据，说明数据库引擎、真实迁移、数据版本和并发隔离方式。身份、依赖与数据准备可重复，从干净环境和连续再次运行均能核对结果。
3. **执行与观察**：逐入口说明用户身份、工具、操作、参数来源、结果位置、全量及指定场景的执行方法、关键反向场景。链路记录遵循[端到端场景的边界](sop-guide.md#端到端场景的边界)。列出仅能人工执行的场景及责任人、时机、步骤、证据位置。
4. **保存证据**：失败时自动保存执行版本、场景输入、日志、请求响应、数据变化和实际接收端输出，按需补截图、录像。注明冻结方式、位置与保留期限；重试保留首次失败和每次重试结果，构建产物注明构建提交与命令。
5. **清理与恢复**：成功、失败、中断后均先留证，再清理本次创建的数据、账号、连接、进程和依赖。列清资源边界、并发隔离标识与清理失败的接手方法；清理仅限声明范围内本次创建的资源。
6. **本机与持续集成**：持续集成（CI）指代码变化后自动运行检查的流水线。分别给出本机命令、CI 任务位置与实际执行范围；CI 留运行编号或链接、提交、场景清单、结果与原始输出。只有本机记录时写“CI 未验证”，缺密钥或环境而跳过的部分保留为未验证。
7. **维护**：注明维护人、最近确认时间及更新触发条件。业务、服务装配变化时同改依赖准备、操作、观察与清理；当轮发现的问题补入手册，稳定结论按产品仓库的知识约定记录。大规模删除已有测试须有用户明确要求。

### 测试账号

手册逐项声明账号类别、用途、环境、隔离方法和凭据环境变量名。**声明即授权**：AI 在声明的环境与用途内直接使用声明的测试账号，不逐任务向用户另取授权，也不写授权记录。

| 账号类别 | 由谁登录与验证 |
| --- | --- |
| 声明的测试账号，包括为验收注册的第三方账号与测试邮箱 | AI 用声明的凭据变量登录，申请验证码并从声明的测试邮箱读取。每次真实登录或请求验证码前按身份计数登记，达到上限时停下交给用户。 |
| 真实或生产账号，以及未声明的账号 | 用户在看板打开的有界面窗口（`sop-board browser open --headed`）中登录。 |

人机验证与只发到用户本人设备（手机、身份验证器）的验证码，不论账号类别都由用户在看板窗口完成。用户完成后用 `sop-board browser release` 交还：窗口保持打开，之后的运行直接沿用其中的登录、验证与浏览器权限。遇到 `browser may not be secure` 立即停止并报告。授权链接取当前真实浏览器生成的链接，服务续期使用服务端刷新机制。测试环境自身在看板浏览器中触发的提示（本地网络访问、localhost 自签名证书警告等）由 AI 处理，处理不了时登记待人处理。

凭据仅经环境变量传递，手册、配置、会话记录与证据只写变量名和获取方式。会话从自身环境取得入口 `credential_env` 声明的变量；看板启动的无头会话与产品环境继承启动守护进程时的环境。配置、运行材料、提示词、日志、报告与页面只记变量名，凭据取值在日志与留痕中遮蔽，内网页面与接口也不显示变量名。缺少某个声明变量时，涉及该入口的场景记为未执行，`finding` 只写缺少的变量名。需要用户交互的部分列为人工范围，CI 按真实执行范围报告。

### 手册、配置与验证技能的分工

入口的操作、账号、观察、证据、隔离与清理只有手册这一份正文。`config.yaml` 保存仓库路径、地址变量、驱动和适配等本机绑定；`entries` 中的必填说明用简短引用指向手册章节。项目验证技能执行前先读取手册，按章节操作，补充本机参数的取得方法。

以下是 `config.yaml` 的入口片段；`app` 指已登记仓库别名，手册章节采用[模板](templates/project-verification.md)的安排：

```yaml
entries:
  api:
    surface: http
    address_env: APP_URL
    operate: "按 app 仓库 docs/operations/verification.md 第 2 节 api 入口操作"
    observe: ["按同手册第 3 节核对响应、数据和禁止副作用"]
    evidence: ["按同手册第 3 节保存原始输出和数据查询"]
    isolation: "按同手册第 4 节准备隔离数据、留证后清理"
```

字段类型以[入口校验器](../src/sop_board/entries.py)为准：`surface`、`operate`、`isolation` 为非空文字，`observe`、`evidence` 为非空文字数组；可选 `address_env` 为环境变量名，`credential_env` 为不重复的环境变量名数组，`driver` 为技能目录名；Web 可选身份 `identities`、录制开关 `web_evidence`、规范库 `spec_library` 与交互地图 `atlas`，见[参考手册](reference.md)。引用手册也须填齐这些字段；账号由手册说明。

## 4. 按真实入口选择核对方式

下表补充项目设计时的核对点，操作命令写入项目手册；其他入口按第 2 节推导。

| 入口 | 执行与核对 |
| --- | --- |
| 浏览器 | 先核对服务就绪，使用隔离账号或租户，驱动看板启动的 Chrome for Testing（每个身份一份持久 profile，各检出共用）；真实账号由人在有界面的窗口登录一次，完成后交还，窗口保持打开供之后的运行沿用。项目可为 Web 入口梳理交互地图，记录页面、控件、各语言文案和定位方式，只说明怎么操作、不提供预期，执行仍以实际页面为准；按角色、标签或测试标识定位，等待元素状态、文字或请求完成等可观察条件。失败保留截图、控制台与页面日志，工具支持时保存轨迹或录像；浏览器崩溃记为受阻并写明信号与日志。Web 驱动见[随包指引](playwright-acceptance.md)。 |
| 命令行 | 安装交付物后运行用户会使用的命令，隔离用户数据与工作目录，保留完整命令、标准输出、错误输出、退出码及文件清单和摘要；覆盖错误参数、缺文件、权限不足、重复、中断续接与并发。 |
| 接口与数据库 | 调用真实 HTTP、gRPC 或服务命令，经过与生产相同的中间件、鉴权与业务层；使用生产同类数据库、兼容字段约束及真实迁移，在临时库或模式中准备确定性数据。事先写明身份与租户、应选记录、响应原因、增改和应保持不变的行、计数、消息与审计状态；按确切值核对并保存前后查询。按业务覆盖较新但不合条件、无匹配、租户或对象不符、已处理与可重试、先读后写的最终状态复核。边界外依赖可替代并记入未覆盖范围；目标入口和数据库走真实实现。失败保留证据，从字段映射、查询、业务选择、响应转换到持久化找最早偏差；数据库本机没有搭建或被人为停着时记未执行，意外不可用时记受阻。 |
| 消息接收端 | 使用真实订阅者、消费者或连接客户端，核对内容、次数、应收到和不应收到的接收方；设有明确上限的等待，超时失败并保存实际原始消息；业务要求幂等时核对重复投递。 |
| 消费者与定时任务 | 经真实消息中间件投递或调度器触发，核对最终数据和下游结果；覆盖重复投递、失败重试、多实例、锁与幂等、补偿或可追踪记录。直接调用替代触发时，在链路记录中列出被截断部分。 |
| 部署与外部通道 | 部署状态与访问地址须指向预期版本，视觉结果写“等待用户验收”。无法自动捕获的邮件、推送等由用户或独立验收者观察，按手册的人工场景留证。 |

### 模型与智能体

模型输出有随机性，确定性结果与语义判断分开核对：

1. 业务动作、权限与身份、数据写入、外部能力调用、状态提交按接口与数据库的确切值核对。
2. 用场景文件驱动真实对话，经过与生产相同的模型、提示与能力边界；预期描述用户可观察的结果，供独立复核。每次运行有唯一标识，会话按运行隔离，固定会话执行前清理、动态会话执行后清理。敏感信息脱敏后，冻结完整输入、回复、调用轨迹、业务动作、调用次数与 token 用量、运行清单及文件摘要；执行、清理和结果核对状态分别记录。运行中场景变化则整次作废；源码或提示变化按第 5 节登记并列出变化路径，这次运行不计入下文的稳定性连续通过。
3. 扮演用户的执行者与语义复核者分开。未参与实现的人或 AI 使用独立于被测智能体的会话，逐场景、逐轮读完全部证据；复核文件绑定证据摘要。各项业务要求成立为通过，可附符合业务边界的一般观察；执行失败、确定性结果错误、虚构已办理或已发送等承诺、回复与动作轨迹不一致为失败；运行作废、证据缺失或环境意外故障为受阻；本机暂时没有搭建的依赖记未执行。每项问题记录场景、轮次、最早偏差环节、根因、证据与建议修复范围。复核文件齐全后记复核完成，运行状态与复核结论分别保存。

稳定性验收分别统计机械失败率和关键语义偏差率；连续通过须来自同一源码、配置和场景快照。修复后从首次重新计数，运行完整集合；模型、提示、知识库或能力边界变化后重新运行并复核。本机缺密钥而无法执行的场景记未执行。

## 5. 场景执行、人工复核与产品变化

场景的四要素、来源确认、正反向写法、粒度和端到端范围统一按[场景编写指南](sop-guide.md)编写。

### 首次执行与人工复核

独立验收者按项目技能和手册准备环境。无关前置数据是场景 `initial_state` 中不由本场景步骤产生、也不是本场景要验证其产生过程的对象和状态，例如组织已有的成员或已归档时长。先使用项目声明的数据配方；没有合适配方且项目显式允许 `fixtures.adhoc: true` 时，才在声明环境与写入范围内临时写入。两者都用 `sop-board fixtures` 带运行与场景编号留痕，保存命令或参数、核对输出、退出码、时间与执行者，凭据打码。无法准备时记受阻，finding 写明缺少的配方、范围或真实流程。被验收流程应生成的对象及 `real_only` 对象只能经真实入口产生，不能写库代替；禁止声明环境外、范围外写入，以及 DROP、TRUNCATE、无条件 DELETE/UPDATE。建议使用只能写测试数据的受限账号。准备记录只留痕，不参与判定，预期只来自场景，结论只来自真实入口的观察。固定场景与产品快照，记录时间、实际应用和依赖版本、环境、执行者及独立性，然后经声明入口逐项核对：

- 保存脱敏请求响应、操作前后数据查询，以及实际接收端的通知、事件或实时消息，包含应接收与不应接收的对象。
- 对抗性尝试逐项留证；问题保留前置条件、输入、原预期及依据、实际结果和首次失败输出，区分实现缺陷、环境问题、场景写法问题和业务变化。
- 场景起点要求某个依赖故障时，执行者用 `sop-board env stop|start <服务>` 停启本机由 adapter 启动、声明为可停的服务，不直接结束进程或改动环境；停启记进本轮运行，结果注明“执行时 <服务> 已停止”，提交或放弃时还停着的服务自动恢复。外部共享的中间件不能停，需要这类故障的场景记受阻并写明原因。
- 结果返回原项目与原检出，保持场景编号、内容指纹、产品快照和证据关联。执行中途场景内容变化时，只作废这些场景，不登记它们的结果，本轮其他场景照常登记。产品代码可在执行期间继续修改和提交，本轮不作废，结果按开始时的产品快照登记并列出期间变化的路径，作为版本记录。另一会话的修复已经改动代码而还没提交时不开始新的一轮（`fix-in-progress`），等修复提交后再准备，避免环境按改到一半的代码启动。执行会话异常退出时由看板接续一次；最终失败的运行由看板放弃并登记待人处理，没提交的结果不登记。结果与过程证据放产品仓库外。
- 测试同事在看板工作台按场景人工复测，登记通过、不通过、阻塞或需求变更，可附复测人、缺陷链接或编号与说明。人工标注与执行结果分别保存。Agent 经真实入口独立通过、尚无人工标注的场景显示“待人工复核”。人工标注不通过时场景即显示为失败。不通过的场景按第 8 节修复；修复关闭后，人工标注过不通过的场景回到“待复测”，由测试同事再次复测。

### 业务变化与回归

哪些场景需要执行由业务变化决定：未执行（新增或内容变化）、待复测、失败、受阻和跳过的场景须经真实入口执行。场景内容没有变化，说明它验证的业务没有变化；代码改动，包括执行期间的改动，不使已有通过失效，场景状态保持不变。

1. **业务交叉在编写时识别**：编写或修改业务 SOP 时，逐份核对场景目录中已有的 SOP，交叉写进新 SOP；改变已有规则口径的，确认后同时改正已有 SOP。由 SOP 生成正向、反向场景或合并测试用例时，核对已有场景：交叉改变已有场景预期的，直接修改这些场景，场景内容一变即回到未执行；不改变预期的，写明理由。交叉的发现与处理随 SOP 或场景一起交确认人确认。
2. **守护发现代码回归**：`sop-board retest` 运行有效守护（见 regression-distill 的有效条件）。命令退出码为 0、声明的测试都在执行清单中且通过、运行前后快照不变，记一次守护运行通过，原始输出作为证据，场景状态不变；未通过的场景转为“待复测”，经真实入口复测，或修好后守护重新运行通过。retest 不判断失败原因，待复测的原因写明失败的测试、当时本机没在运行的服务与工作区是否有未提交改动；复测时因服务没有搭建或被停着而跑不通的记未执行，场景保持待复测。故障场景的守护写在不需要真实停服的层（单元、接口或组件层，用替身模拟依赖不可用），写不出时不沉淀并写明原因。某场景最近一次守护运行通过之后，真实入口或人工复测发现失败，记一次漏检，该守护失效，直到漏检之后取得新的独立通过并以变化后的测试重新沉淀。

守护运行不代替真实入口：首次验收、场景内容变化后的验收与缺陷复验都须实际执行并留新证据。任务本身承诺保留已有行为时（例如重构或拆分），由负责人选定要回归的场景，用 `sop-board run prepare --scope <场景>…` 或 `--scope all` 主动执行。

业务要求变化先确认新依据并更新场景，再由独立验收者验证新行为；记录实际运行依赖、环境、场景数和逐项未验证范围。仅能人工执行的场景写在产品仓库手册的人工范围一节：原因、负责人、触发时机、步骤与证据位置；场景本身照常写四要素。

### 分步实现时的验收时机

一项需求分几步实现，或几项需求接连实现时，每一步什么时候验收按事实判断并说明理由，不照搬“每一步都验”或“全部做完才验”这类固定节奏。底线不变：交付条件按第 6 节；分步验收只改变每条场景在哪一步执行，不减少要经独立真实入口执行的场景；先验的通过要到交付时仍然可信（第 3 条）。实现者自检每一步都做。

1. **开始实现前定安排**：负责实现的会话或开发者对每一步判断“做完就验”还是“并到后面一起验”，把安排和理由告诉使用者，由使用者确认或调整。判断看这些事实：这一步是否会先单独交付或装给别人用；后面的步骤是否会重做这一步验过的实现；后面的步骤是否以这一步正确为前提；各步改动的范围是否重叠（重叠多时，晚发现的缺陷难分清出自哪一步）；这一步是否涉及鉴权、持久化、金额、消息、并发这类高风险内容；验收一轮的成本（环境、真实账号、人工复核、时间）。
2. **如实标注每一步**：每一步标为已独立验收、只做了实现者自检、未验证三者之一。并到后面验收的步骤，在报告和提交说明里写明“未经独立验收”，不说成可以验收或可以交付。
3. **先验的结果怎样保持有效**：代码改动不改变场景状态（见上节），所以先验通过的场景在后面的步骤重做了它依赖的实现之后仍显示通过，`--scope pending` 不会再选中它。这样的通过要到交付时仍然可信，二选一：先验的那一步通过后沉淀守护，之后每一步用 `sop-board retest` 检查，交付时守护有效且最近一次运行通过；或者在统一验收时用 `sop-board run prepare --scope <场景>…` 或 `run launch --scope <场景>…` 把这些场景明确列入、重新执行。两样都没有的，这条通过不能算进交付。
4. **统一验收的范围**：全部推迟验收的步骤的场景，加上先前通过、被后续步骤重做了实现、又没有“守护有效且最近一次运行通过”的场景。

## 6. 交付记录与报告导出

用 `sop-board report [--file 场景文件] [--zip]` 按检出导出 Markdown 报告与证据 zip。导出内容包括当前产品快照、各场景状态、每条结果取证时的代码版本、执行与人工复测、守护运行、独立性和未执行范围（含各场景最近一次未执行的人、时间与原因）。多人共享验收记录时，报告与看板使用同一套状态推导（结论按分支归属、本分支优先，受阻、跳过与守护未通过只取本检出的），逐条写明结果的产出机器与分支，结论来自其他分支的标出来源；证据在别人机器上而取不到的，逐条写明“证据在 <机器> 的机器上，未包含”，不冒充齐全。用[交付验收记录](templates/business-delivery.md)补充环境、独立性和报告未列出的事实，并逐项引用原始材料。

记录至少包含：已确认要求及版本、任务链接、场景文件与指纹、实际源码提交及未提交变化、依赖和配置版本、环境与数据初态、执行时间和执行者、原始证据、缺陷及复验、业务交叉的识别与处理、守护运行结果、替代依赖、人工范围、回归建设及本机和 CI 实际运行情况。报告与证据保存在仓库外；稳定项目知识按项目约定更新。

分别报告开发者自检、独立业务验收、人工复核、缺陷复验和整体交付状态；分几步实现的，逐步写明验收安排与每一步的标注（第 5 节“分步实现时的验收时机”）。整体完成须同时具备：依据已确认，约定范围内场景（含因业务交叉而修改的已有场景）经独立真实入口验收全部通过且核对数据，没有守护未通过而待复测的场景，缺陷均独立复验通过，所需人工复核已完成。受阻、延期、未执行、缺证据逐项列出负责人和后续安排；待沉淀的场景单独列出；子集通过仅证明该子集，延期保留未验证事实。

## 7. 入口缺口与过渡

入口缺口是全队都不具备的能力：入口或观察能力还没建设，例如没有可用的测试账号、接收端观察能力，或服务还没有任何可用于验收的搭建方法。这时场景记受阻，结果的 `finding` 写清缺口。只是本机没有搭建的服务、没有设置的凭据变量不是入口缺口，记未执行（第 1 节），补齐后执行。开发与测试确认延期处置，记录确认人、原因、建设任务、负责人、期限和最小入口内容；交付保留未验证范围。

第一个需要该入口的需求负责建设：启动真实依赖并核对就绪，自动准备隔离数据，失败留证，结束清理；由独立执行者从干净环境和连续再次执行各验证可核对的结果，写入项目手册并在 `entries` 绑定。当周无法完成时记录一次过渡，由建设任务承接；下一个同类需求完成建设，该区域出现缺陷时优先建设能复现它的入口。

多处缺口按已记录缺陷和业务风险排序，优先鉴权、持久化、消息、并发与跨服务。每周跟踪场景、关键保证、风险、受阻开始时间、任务、负责人和期限；到期未完成写原因，由原延期确认人重新确认。入口建成且独立执行通过后移出缺口清单。手册尚缺时先建骨架、缺项标待填，实现可继续，验收状态按事实记录。

## 8. 缺陷关联、跨仓修复与复验

每个缺陷使用稳定编号，按[缺陷复验与保护记录](templates/defect-protection.md)保留发现时间线、严重程度、复现步骤和原始失败证据。开发与测试分别核对以下关联，每项选择“已确认、推测、待调查、历史缺陷或来源未知”，附证据、反证及待调查负责人：

| 关联 | 依据 |
| --- | --- |
| 违反的业务要求 | 当时有效的条目、版本和预期 |
| 影响的需求 | 实际使用场景和范围，可涉及多个需求 |
| 引入缺陷的改动 | 版本比较、复现或变更证据，与修复提交分开 |
| 当时应能发现的场景 | 当时需求范围、执行版本、场景原文与验收证据 |

解释此前未发现的原因时，按事实区分当时范围外、缺场景、环境或版本差异、断言缺漏、替代依赖截断、业务交叉漏识别、守护漏检或待调查。缺陷保护是能暴露它的场景，缺失时先确认业务依据并补场景。

修复由会话经 `sop-board fix prepare/submit` 认领并登记：在当前检出只改产品代码，保留原有改动，不修改 SOP 或场景、不写测试、不自行提交。环境、场景写法、需求变化或无法修复的问题登记到待人处理，交使用者处理，不用产品修改代替业务答复。

修复须另派未参与修复的新会话经 `sop-board run prepare --fix <编号>` 复验：复验逐条实际执行问题场景；实现者自动绑定修复会话，修复会话自己复验记为实现者自检，不能关闭修复。开发者审核并自行提交后，`sop-board fix close` 只在修复改动的文件已提交、且内容与独立复验通过时一致才关闭；未提交或内容不同时列出文件拒绝。人工标注过不通过的场景在修复关闭后回到待复测，由测试同事再次复测。记录新增或修改的保护场景、替代依赖、未覆盖及仍需人工范围，持续观察同类缺陷是否再现。

## 9. 开发与测试每周共同复盘

共同填写[每周质量复盘记录](templates/weekly-quality-review.md)。先核对交付证据，再确认缺陷关联、业务交叉识别与守护的有效性，使用实际案例与严重程度依据观察：验收后新增缺陷、漏场景导致的返工、业务交叉漏识别、已通过场景的回归与守护漏检、同类缺陷再现、独立复验及保护场景情况。

指标取看板统计与导出报告：执行进度、Agent 通过率、一次通过率、人工复测通过率与覆盖率、Agent 独立通过的人工确认率与复核覆盖、场景数、守护运行与未通过数、漏检、修复结果。保留分子、分母、执行者、场景指纹与样本量，按[参考手册的统计口径](reference.md#10-报告与看板页面)解释；一次通过率用于观察提测质量，运行数量用于解释过程。人工确认率只统计人工复核过的 Agent 独立通过，复核由测试同事自选场景，须与复核覆盖一起解读；误判明细逐条归因为 Agent 判断错误、场景缺漏、断言缺漏、环境或数据问题、人工标注有误等，只有归因为 Agent 判断错误的才说明执行者不可靠。比较时注明周期、版本、业务范围和记录缺口，缺材料写“未知”。

复盘同时跟踪第 7 节入口缺口，回看上次行动的实际证据。每项改进写清问题、负责人、期限、跟进任务、预期改善和下次核对方法；以同类问题是否减少、场景是否在真实改动中发现问题评价效果，观察不足则继续跟踪。

> 需求完成须由未参与实现的测试同事、用户或 AI 经用户实际使用的入口执行已确认的 SOP 场景、核对数据结果并留证。预期来自已确认的业务要求、SOP、接口约定或独立事实；实现者自检用于交付准备。项目声明的测试账号（含为验收注册的第三方账号与测试邮箱）声明即授权，AI 在声明的环境与用途内直接登录、读取测试邮箱验证码，不逐任务另取授权；真实或生产账号、未声明的账号、人机验证与只发到用户本人设备的验证码由用户在看板打开的浏览器窗口完成，完成后交还给会话继续使用，不关闭窗口。保持场景与断言完整，不删断言、不放宽预期、不跳过场景或改成当前输出来通过。缺真实入口证据或缺独立验收时如实报告未完成范围。分几步实现时，开工前按事实定下每一步做完就验还是并到后面一起验，告诉用户并由用户确认；推迟验收的步骤报告为未经独立验收；先前通过、但被后续步骤重做了实现的场景，交付时要么守护有效且最近一次运行通过，要么在统一验收时列入范围重新执行。哪些场景需要验收由业务变化决定：编写 SOP 与场景时核对已有 SOP 和场景的业务交叉；场景内容未变的通过不因代码改动失效，代码回归由守护测试发现。验收、缺陷复验与每周复盘读取并遵循 [Flow Board 业务验收与质量改进标准](https://github.com/AdolphKevin/sop-board/blob/main/docs/standard.md)，项目操作方法统一维护在产品仓库的真实验证手册。
